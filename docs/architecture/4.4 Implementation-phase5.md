# cockpit-slurm Implementation Phase 5 — Node Commands and Authorization

## 1. Purpose

Phase 5 extends the completed Phase 4 Node live-stream vertical slice with controlled Node mutation.

Phase 3 established:

```text
Slurm
  ↓
Node Adapter
  ↓
Node Cache
  ↓
Node Query Service
  ↓
IPC
  ↓
NodeProvider
  ↓
NodeTable
```

Phase 4 established:

```text
Slurm
  ↓
NodeSynchronizer
  ↓
Node Cache
  ↓
Node Change
  ↓
Node Stream Registry
  ↓
Unix socket
  ↓
Cockpit native channel
  ↓
NodeProvider
  ↓
NodeTable
```

Phase 5 adds:

```text
React
  ↓
Application Command
  ↓
IPC
  ↓
Command Controller
  ↓
Command Service
  ↓
caller-scoped ledger lookup
  ↓
existing command? ── yes ──> verify owner/fingerprint ──> return stored result
   │ no
   ▼
persist authorization_pending claim
  ├── write uncertain → block admissions; reconcile
  └── confirmed durable
       ↓
Authorizer
  ├── GlobalRegistry.RequiredCapability
  └── Capability Resolver (fresh Slurm authorization context)
       ├── denied/error → persist non-executable tombstone; return error
       └── allowed → atomically transition to accepted
              ↓
            durably persist running/dispatch intent
              ↓ confirm durable before dispatch
  ↓
Node Command Adapter
  ↓
Slurm
  ↓
Node Synchronizer
  ↓
Node Cache
  ↓
Node Change
  ↓
Cockpit native channel
  ↓
NodeProvider
  ↓
NodeTable
```

The primary objective is to prove that a frontend command can safely mutate Slurm state and that the resulting frontend state is obtained from the authoritative backend cache and event stream rather than from frontend assumptions.

The fundamental rule is:

```text
command succeeds
      ≠
frontend guesses new state
```

Instead:

```text
command
  ↓
Slurm mutation
  ↓
resource synchronization
  ↓
cache update
  ↓
Node event
  ↓
frontend state update
```

Phase 5 is therefore the first complete **read + synchronize + mutate + authorize** Node vertical slice.

### Phase 5 implementation stages and gates

Implement the stages in order. Stage D command execution and Stage E mutation UI MUST NOT begin until Stages A-C pass their exit criteria. The registry may support later extension, but Phase 5 implements only `node.drain` and `node.resume`.

| Stage | Scope | Entry criteria | Exit criteria |

| B — Protocol and authorization contracts | Typed v1.0 command and capability messages; canonical responses/errors; capability registry; registry consistency; `UserContext`, Authorizer, and fresh resolver tests. | Stage A passed. | `node.drain` requires `nodes.drain`, `node.resume` requires `nodes.resume`; only current resolved Slurm `AdminLevel=admin` receives them; stale context and lookup failures deny; protocol tests pass. |
| C — Persistence and execution security | Systemd-writable durable ledger; schema/recovery; authorization claims and uncertainty quarantine; documented execution identity; restricted helper if direct service-account execution has not passed a real-cluster test. | Stages A-B passed; production service hardening and packaging are available for tests. | Claim/accepted/running transition writes, commit-before-error recovery, true write-failure handling, admission blocking, orphan-claim quarantine, accepted-but-not-dispatched recovery, restart recovery, `unknown` handling, permissions, and failure behavior pass under the production unit. # 2. Core architectural decisions

## 2.1 Phase 5 remains Node-focused

Phase 5 MUST implement commands for the Node resource only.

Do not use Phase 5 to implement:

```text
Jobs
Users
Accounts
Reservations
Partitions
Clusters
```

Do not generalize the entire Resource System during this phase.

The proven sequence is:

```text
Phase 3
    Node Query
       ↓
Phase 4
    Node Live State
       ↓
Phase 5
    Node Commands + Authorization
       ↓
Phase 6
    Resource System Generalization
```

Node remains the reference resource.

---

## 2.2 Backend authorization is authoritative

The backend MUST enforce authorization.

The frontend may hide or disable controls, but frontend visibility is never a security boundary.

For example:

```text
Frontend
    ↓
"Drain Node" button
    ↓
command request
    ↓
backend authorization
    ↓
allowed / denied
```

The backend MUST NOT trust:

```text
frontend role
frontend username
frontend capability
frontend admin flag
frontend-selected account
```

The authoritative identity comes from the server-side connection.

---

## 2.3 Server-derived identity

The Cockpit-user-to-Unix-socket-credentials mapping is a prerequisite to command authorization; the presence of `SO_PEERCRED` code alone does not prove that mapping.

Before treating connection peer identity as the requesting user's identity, Phase 5 MUST validate on the target Cockpit installation that the observed peer UID/GID corresponds to the authenticated Cockpit user. Reuse `connection.NewConnection` or an equivalent shared connection-initialization path for both stream and command handling so command requests cannot bypass peer identity construction. Connection-time Slurm authorization fields are only a snapshot; new commands require the fresh Authorizer flow in Section 7.7.

Conceptually:

```text
Cockpit authenticated user
        ↓
Unix socket connection
        ↓
SO_PEERCRED
        ↓
UID / GID
        ↓
Linux user
        ↓
Slurm user lookup
        ↓
UserContext
```

The backend MUST derive the requesting identity from the connection.

A command request MUST NOT be allowed to override:

```text
username
UID
GID
AdminLevel
Coordinator
Capabilities
```

The command payload identifies the requested operation, not the identity of the caller.

The authenticated-user-to-peer-credentials validation is an explicit Phase 5 gate. Until it passes, Node commands MUST NOT be enabled. Add an acceptance test that exercises a real Cockpit connection and verifies the authenticated Cockpit account against the server-observed Unix peer UID/GID.

Keep these identities separate in code, protocol reasoning, command records, and tests:

```text
service identity
  = Linux account running the cockpit-slurm daemon (normally cockpit-slurm)

requesting-user identity
  = authenticated Cockpit user established from validated connection peer credentials,
    then resolved to Linux identity and Slurm UserContext

command execution identity
  = effective Linux identity under which the fixed Slurm operation actually runs
```

The daemon's service identity is not the requester, and a privileged helper's effective UID is not the requester. Authorization always uses the server-derived requesting user. Audit and ledger records preserve the requesting user and separately record the execution identity and execution boundary used.

---

## 2.4 UserContext is requesting-user context, not frontend state

The backend `UserContext` represents only the authenticated requesting user. It is not the daemon service account and is not the effective identity used to execute Slurm commands. The command record carries the requesting identity and execution identity as separate fields.

Conceptually:

```text
UserContext
├── Username
├── UID
├── GID
├── AdminLevel
├── Coordinator
├── Accounts
└── Capabilities
```

The exact implementation may evolve with the existing codebase.

The important boundary is:

```text
Connection identity
        ↓
UserContext
        ↓
Command Service ledger lookup
        ↓
Authorizer
  ├── GlobalRegistry.RequiredCapability
  └── Capability Resolver (fresh Slurm authorization context)
```

The frontend may receive a safe representation of the user's capabilities, but it MUST NOT become the authority for those capabilities.

## 2.5 Capability request/response contract

Capabilities are requested explicitly on the existing bidirectional IPC connection. They are not implicitly pushed at connection initialization. A client sends `capabilities-request`; the backend returns `capabilities-response` with the request's `messageId` unchanged for correlation. Both use the existing v1.0 envelope and length-prefixed JSON framing; no second envelope or transport is introduced.

Request:

```json
{
  "protocol": "cockpit-slurm",
  "version": "1.0",
  "messageId": "msg-cap-1",
  "type": "capabilities-request",
  "timestamp": "2026-10-15T01:00:00Z",
  "payload": {}
}
```

Successful response (for example, for an authenticated admin):

```json
{
  "protocol": "cockpit-slurm",
  "version": "1.0",
  "messageId": "msg-cap-1",
  "type": "capabilities-response",
  "timestamp": "2026-10-15T01:00:01Z",
  "payload": {
    "capabilities": {
      "nodes.drain": true,
      "nodes.resume": true
    }
  }
}
```

The `capabilities` object always contains explicit Boolean values for both supported names. Non-admin users receive both as `false`; clients must not infer an omitted value. The request payload is empty, and unknown payload/envelope fields are rejected under the strict v1.0 validation policy. An unsupported message type receives the canonical `error` envelope with `protocol-error` / `unsupported-message-type`; malformed payloads receive `validation-error` / `invalid-payload`. These errors preserve the request `messageId`.

If the transport connection is initialized but requesting-user resolution fails while servicing this request, return `authentication-error` / `identity-unavailable`. If peer credentials or Linux identity fail during connection initialization, reject and close the connection as required by Stage A; there is no established application request to correlate. If Slurm user lookup or capability resolution fails after an application request is received, return `internal-error` / `capability-unavailable` (do not return a partially populated or guessed capability set). The canonical error envelope is:

```json
{
  "protocol": "cockpit-slurm",
  "version": "1.0",
  "messageId": "msg-cap-1",
  "type": "error",
  "timestamp": "2026-10-15T01:00:01Z",
  "payload": {
    "code": "capability-unavailable",
    "category": "internal-error",
    "message": "Capabilities are temporarily unavailable",
    "retryable": true
  }
}
```

The response is advisory usability information only and may be cached by the frontend for presentation. It never authorizes a command. For every new `commandId`, the Command Service invokes the single backend `Authorizer`, which obtains a fresh Slurm authorization context through the Capability Resolver and checks the registry-required capability. Connection-time `UserContext` supplies the validated requesting identity but MUST NOT be treated as fresh Slurm authorization data. If Slurm user information cannot be refreshed or validated, deny the new command; never fall back to stale permissions. No authorization-context cache is permitted in Phase 5. If one is introduced later, its maximum staleness must be specified and tested. Capability refresh may update visible controls, but the backend guarantee holds even if the frontend keeps stale capabilities. Add these message types to canonical protocol types and tests before implementing capability-dependent UI.

## 2.6 Settle durable command-ledger storage and retention

Use a local SQLite database for the Phase 5 command ledger, using a pure-Go SQLite driver if avoiding CGO is important.
Proposed defaults:
- Database: /var/lib/cockpit-slurm/commands.db
- Directory: `/var/lib/cockpit-slurm`, owned by `cockpit-slurm:cockpit-slurm`, mode `0750`; database and SQLite journal/WAL, shared-memory, lock, temporary, and recovery files must be creatable and writable by the service account with restrictive permissions.
- Systemd: add `StateDirectory=cockpit-slurm` and `StateDirectoryMode=0750` to the production unit. Keep `ProtectSystem=strict`; grant no broader writable filesystem access. Verify the actual StateDirectory ownership and effective access after installation.
- Retention: 30 days for command records and idempotency keys.
- Uniqueness: authenticated caller identity plus commandId.
- Same ID and same request: return the existing status/result without re-execution.
- Same ID and different request: return command-id-conflict.
- On restart, any record left in running with an uncertain execution outcome becomes unknown; never automatically execute it again.
The ledger must reserve a command ID atomically and durably before dispatch. Deduplication is guaranteed for 30 days; clients must not blindly retry expired command IDs. Keep schema versions and ordered migrations explicit; initialize or migrate the database before accepting mutations. Document SQLite journal mode, durability settings, crash recovery, migration failure behavior, and which files the selected mode creates. Test initialization, migration, locking, recovery, and retention using the production service account and hardening settings. If the ledger is unavailable, corrupt, or unwritable, fail daemon startup or mark mutation service unavailable and reject new mutations; never fall back to memory-only deduplication while accepting mutations.

Use a durable, non-executable `authorization_pending` claim keyed by stable caller identity plus `commandId`, containing the canonical request fingerprint, before invoking the Authorizer. This claim is not an accepted command and cannot dispatch. Only after a fresh allow decision may it be atomically transitioned to an accepted reservation; dispatch is permitted only after that accepted transition is confirmed durable. A deny transitions the claim to a non-executable denial tombstone. Authorization lookup failure transitions it to a non-executable authorization-failure tombstone. Neither tombstone can transition to accepted. If writing either terminal state fails, do not execute; set a process-wide mutation-admission gate to blocked and return a canonical ledger persistence error. Do not accept new command IDs while ledger consistency is uncertain.

Treat every write error as an unknown commit outcome until reconciled; a returned error does not establish that the transaction did not commit. While admission is blocked, reconcile through the configured SQLite transaction/journal recovery and read the row in a fresh transaction. If a terminal state is present, retain and return it. If an `authorization_pending` claim remains, transition it to a non-executable `authorization_uncertain` tombstone and never rerun authorization or execute that ID. If an accepted transition committed but its success was not confirmed, do not dispatch; quarantine the accepted-but-not-running row as `authorization_uncertain`. Persist a `running`/dispatch-intent transition durably before invoking the adapter/helper; if recovery finds that state, report `unknown` and never automatically re-execute. If consistency or commit outcome still cannot be established, keep command admission blocked. On restart, validate/migrate and recover the database before enabling admission; convert orphaned `authorization_pending` and accepted-but-not-running rows to non-executable `authorization_uncertain`, and running commands with uncertain execution to `unknown`. An uncertain ID is never promoted to accepted or dispatched. If startup integrity/recovery fails, keep the service unavailable for mutations until an explicit documented operator recovery procedure resolves the database; never delete or ignore unresolved claims to resume service.

Acceptance: the systemd-managed daemon creates and initializes the ledger under `/var/lib/cockpit-slurm`, persists records, and recovers them after restart. A previously accepted command with an uncertain dispatch outcome is restored as `unknown`, is not automatically re-executed, and remains deduplicated throughout retention.

# 5. Architectural invariants

## 5.1 Backend remains authoritative

The backend remains authoritative for:

```text
identity
authorization
command execution
Node state
generation
events
```

The frontend is responsible for:

```text
command initiation
presentation
loading state
success/error presentation
```

It is NOT authoritative for the resulting Node state.

---

## 5.2 Commands do not directly modify the frontend cache

After a successful command:

```text
DO NOT:

command
  ↓
React
  ↓
mutate Node state directly
```

Instead:

```text
command
  ↓
Slurm
  ↓
NodeSynchronizer
  ↓
NodeCache
  ↓
NodeChange
  ↓
NodeProvider
```

This guarantees that the displayed state represents observed Slurm state.

---

## 5.3 Successful command does not imply immediate state change

A successful Slurm command means that Slurm accepted the operation.

It does not necessarily mean that the next synchronized Node snapshot already contains the expected state.

Therefore:

```text
command response
    =
command execution result
```

and:

```text
Node event
    =
observed authoritative state
```

These are separate concepts.

---

## 5.4 Command response and Node event are separate

A command response reports command execution.

A Node event reports resource state.

For example:

```text
CommandResponse
    commandId: "cmd-123"
    status: "succeeded"
```

followed later by:

```text
Event
    resource: "node"
    event: "updated"
    generation: 44
```

The frontend MUST NOT require the command response to contain the complete updated Node object.

---

# 6. User identity

## 6.1 Peer credentials and requester identity

The IPC connection obtains peer credentials for the requesting-user identity only after the target Cockpit installation proves that those credentials correspond to the authenticated Cockpit account. These credentials do not describe the daemon's service identity or the effective identity of any privileged command helper.

Phase 5 MUST use the shared connection-initialization path (currently `connection.NewConnection` or an equivalent) rather than accepting identity from the command payload. Command handling and Node streaming MUST use that same path.

Conceptually:

```text
Unix socket
    ↓
SO_PEERCRED
    ↓
uid
gid
pid
```

The exact credentials available should follow the platform implementation.

---

## 6.2 Requesting Linux user lookup

The backend resolves the peer UID to the requesting user's corresponding Linux user. Do not populate this field from the daemon's own `os/user` identity or from a frontend value.

Conceptually:

```text
UID
 ↓
OS user database
 ↓
username
```

Failure to resolve the UID to a Linux user MUST reject command requests for that connection with an `identity-unavailable` error and MUST prevent command authorization. An empty username is not an identity and MUST never be authorized. The backend MUST NOT defer this condition to capability resolution or treat it as an ordinary user.

Do not fall back to:

```text
frontend username
request.username
anonymous
root
```

---

## 6.3 Requesting Slurm user lookup

The resolved requesting Linux username is used to obtain the corresponding Slurm user information. This Slurm identity supplies authorization context; it does not select the process identity used by the adapter/helper.

The Slurm user context may contain information such as:

```text
username
AdminLevel
coordinator
accounts
```

The implementation MUST use the existing Slurm account/user interfaces rather than duplicating Slurm authorization semantics in React.

Missing Slurm user information, an unresolved `AdminLevel`, or a failed Slurm user lookup MUST deny Node mutations by default. These conditions MUST NOT be interpreted as `AdminLevel=none` and then handled by a permissive fallback.

---

# 7. AdminLevel and capability model

## 7.1 AdminLevel

Phase 5 introduces the backend mapping from Slurm user information to an application-level authorization context.

Conceptually:

```text
Slurm user
    ↓
AdminLevel
    ↓
capabilities
```

Use the canonical Slurm `AdminLevel` values from the User Context contract: `none`, `operator`, and `admin`. Only the exact resolved value `admin` grants the Phase 5 Node mutation capabilities.

Do not create frontend-only AdminLevel values that have no backend meaning.

`nodes.drain` and `nodes.resume` MUST be granted only when the authenticated Linux identity resolves to a Slurm user whose `AdminLevel` is `admin`. `operator` does not grant either capability. Coordinator relationships do not grant Node administration; coordinators remain relevant to future account-scoped operations. A separate, more permissive application policy is out of scope for Phase 5 and MUST NOT be inferred.

The backend capability check is mandatory. Slurm's own execution result is an additional enforcement outcome, not a replacement for backend authorization. The implementation MUST document and test the effective command execution identity. If a helper executes under a privileged identity, Slurm's result is not proof that Slurm independently authorized the requesting user; the registry-required capability evaluated against that user's server-derived `UserContext` remains authoritative.

---

## 7.2 Capability Resolver

The Capability Resolver obtains authoritative Slurm user information and translates the requesting user's current role/policy into explicit capabilities. For command authorization it supplies fresh data to the `Authorizer`; it does not make a separate allow/deny decision, dispatch commands, or bypass the Authorizer. Capability requests may use it to produce advisory UI information, but that response is not authorization.

Example capability names:

```text
nodes.drain
nodes.resume
```

Only capabilities required by the implemented Node commands should be introduced in Phase 5.

Avoid prematurely creating capabilities for resources that are not implemented.

---

## 7.3 Capability checks

Authorization should be expressed in terms of capabilities.

For example:

```text
Node drain
    ↓
requires:
    nodes.drain
```

and:

```text
Node resume
    ↓
requires:
    nodes.resume
```

The command service MUST NOT rely only on AdminLevel comparisons.

A preferred decision path is:

```text
Command Service: no matching ledger record
  ↓
durable authorization_pending claim
  ├── write uncertain → block admissions and reconcile
  └── confirmed
     ↓
Authorizer
  ├── registry RequiredCapability
  └── fresh Capability Resolver(UserContext identity)
       ↓
    required capability check
  ├── denied/error → durable non-executable tombstone
  └── allowed → durable accepted transition
              ↓ durable running/dispatch intent
              ↓ confirmed before dispatch
```

### 7.4 Operation registry

Phase 5 MUST use a backend-owned operation registry as the authoritative list of supported semantic operations. The client selects the generic Node update command; the backend derives the semantic operation from its validated state parameter:

```text
resource=node, command=update, state=DRAIN
  → OperationID=node.drain

resource=node, command=update, state=RESUME
  → OperationID=node.resume
```

These stable operation IDs describe application intent, not Slurm command-line syntax. Both entries may share trusted handler `node.set_state`. `OperationID`, required capability, handler, executable, and arguments are backend-owned and MUST NOT be supplied or overridden by the client.

The registry is the dispatch, validation, and authorization contract. Each entry declares operation intent, IPC resource/command, exactly one required capability, target and parameter schemas, trusted handler ID, and optional semantic validator ID. The initial mapping is `node.drain` → `nodes.drain` and `node.resume` → `nodes.resume`. Every request MUST be resolved to exactly one entry, validated, authorized, and only then dispatched. Unknown operation mappings and parameter names MUST be rejected.

Recommended conceptual model (adapt names to existing project types; do not duplicate `UserContext`, `CommandRequest`, `CommandResult`, or role types):

```go
type ParameterType string

const (
  ParamString  ParameterType = "string"
  ParamEnum    ParameterType = "enum"
  ParamInteger ParameterType = "integer"
  ParamBoolean ParameterType = "boolean"
)

type ParameterSpec struct {
  Type          ParameterType
  Required      bool
  MinLength     int
  MaxLength     int
  AllowedValues []string
}

type RegistryEntry struct {
  OperationID        string
  Resource           string
  Command            string
  RequiredCapability string
  TargetSchema       map[string]ParameterSpec
  ParameterSchema    map[string]ParameterSpec
  HandlerID          string
  ValidatorID        string
}

type Handler func(
  ctx context.Context,
  caller UserContext,
  operation RegistryEntry,
  req CommandRequest,
) (CommandResult, error)

var HandlerRegistry = map[string]Handler{
  "node.set_state": handleNodeSetState,
}
```

`GlobalRegistry` MUST be keyed by `OperationID` for direct lookup. If a slice is used instead, startup validation MUST reject duplicate IDs. Registry iteration MUST NOT determine authorization or dispatch order. Entries are immutable after initialization.

Startup validation MUST reject mismatched map keys, missing required operation mappings, empty or unsupported required capabilities, unresolved handler or validator IDs, unsupported parameter types, and internally inconsistent constraints. It MUST verify the exact initial operation-to-capability mapping above. Every executable operation must have a valid required capability. Client fields MUST never select a handler, validator, or capability.

### 7.5 Registry and handler responsibilities

- `ParameterSpec` declares an allowed field's primitive type and field-level constraints. The validator rejects missing required fields, wrong JSON types, unknown fields, unsupported types, and invalid values without coercion.
- `RegistryEntry` declares one semantic operation and its required capability. This registry mapping is authoritative; do not duplicate it in a hard-coded command-service role check.
- `HandlerRegistry` maps trusted fixed handler IDs to Go functions. A client-supplied handler ID MUST never be accepted.
- `GlobalRegistry` is the single backend source of truth for supported operations. Frontend metadata may be generated or mirrored later but is never authoritative for permissions.
- Use typed request structures after the protocol boundary where practical; do not propagate `map[string]any` through command execution.

The shared `node.set_state` handler MUST derive its state from the trusted registry operation: `node.drain` maps only to `State=DRAIN`, and `node.resume` maps only to `State=RESUME`. It MUST reject unsupported operation IDs/actions and MUST NOT accept an unrestricted state from the client.

### 7.6 AdminLevel and capability policy

Use canonical Slurm `AdminLevel` values: `none`, `operator`, and `admin`. The Capability Resolver grants `nodes.drain` and `nodes.resume` only to an authenticated, successfully resolved Slurm user whose `AdminLevel=admin`. It resolves both capabilities to `false` for `none`, `operator`, coordinator-only users, and does not produce an authorization result when identity or Slurm-user resolution is unavailable. Coordinator is account-scoped and does not grant Node administration.

For a new command only, after the caller-scoped ledger lookup finds no existing command, the backend MUST validate the complete operation schema and invoke the Authorizer. Existing command retries follow Section 20 and do not require fresh authorization merely to retrieve the caller's own result. The Authorizer MUST deny unknown operations, invalid entries, missing required-capability declarations, unresolved identity, failed Slurm user lookup, unknown roles, and unavailable authorization information. No other component performs a capability authorization check.

There is no duplicated hard-coded command-service policy that can override the registry mapping. Mandatory startup validation and tests MUST ensure no operation is executable without a valid capability mapping. Frontend capability values are never an authorization input.

### 7.7 Authorizer and authorization-context freshness

`Authorizer` is the single authoritative backend component for command authorization. The Command Service invokes it exactly once for each new command that has no existing ledger record; retries of an existing command are handled by ownership/fingerprint verification and never dispatched again.

The Authorizer MUST:

1. resolve the semantic operation in `GlobalRegistry` and obtain `RequiredCapability` only from that entry;
2. request a fresh authorization context from `Capability Resolver` using the stable, server-validated connection identity;
3. require the resolver to obtain current Slurm user information and current role-to-capability policy, rather than relying on the connection-time `UserContext` authorization fields;
4. verify that the fresh context grants the registry-required capability;
5. fail closed for unknown operations, missing capability declarations, unresolved identity, failed Slurm lookup, unknown `AdminLevel`, or unavailable authorization information.

Phase 5 MUST NOT cache authorization context for command decisions. Capability responses may be cached by the frontend for presentation only. If backend authorization caching is introduced in a later phase, that phase must define and test an explicit maximum staleness bound. A failed refresh MUST deny the new command; stale connection-time permissions are never a fallback. The Authorizer returns a decision to the Command Service and does not dispatch, reserve ledger IDs, or execute commands.

### 7.8 Transport refactor prerequisite — shared bidirectional connection

Phase 5 commands MUST NOT be enabled on a stream path that bypasses shared connection initialization or stops reading after a valid subscription. Before implementing commands, inspect/refactor the actual `internal/ipc/server.go`, connection initializer, stream registration, message codec, and Node stream registry. Node streams and commands MUST use the same authenticated connection path and one serialized writer.

The required lifecycle is:

```text
Unix socket accept
  ↓
shared Connection initialization
  ↓
SO_PEERCRED and Linux UID resolution
  ↓
fail-closed identity construction
  ↓
register connection
  ↓
persistent framed-message read loop
  ↓
message dispatcher
  ├── stream/subscription messages
  └── command request
  ↓
one serialized outbound writer
  ↓
Unix socket
```

Initialization MUST retrieve peer credentials and resolve UID to a non-empty Linux username. Failure at either step rejects and closes the connection. Do not construct an empty-username `UserContext` or fall back to frontend identity, anonymous identity, or a privileged default. Build `UserContext` from trusted connection identity and authoritative Slurm user information; missing Slurm records, lookup failures, and unknown `AdminLevel` values fail closed for mutation.

`SO_PEERCRED` alone does not prove that the Unix UID is the authenticated Cockpit browser user. Before commands are enabled, a target-installation integration test MUST establish that the observed peer UID/GID corresponds to the authenticated Cockpit account. If this mapping cannot be demonstrated, commands remain disabled.

Stream registration MUST NOT take ownership of the socket read loop or prevent subsequent command messages from being read. Dispatch each decoded message on the initialized connection, reusing existing codec, logging, cancellation, registration, and error-handling conventions. Malformed frames, EOF, write failures, and cancellation MUST clean up the connection and subscriptions.

All server-originated messages for one connection—including snapshots, Node changes, command responses/statuses, and errors—MUST pass through one serialized writer. Use a bounded outbound queue or equivalent single-writer design. Define backpressure explicitly: terminate a connection that cannot keep up and clean up subscriptions rather than interleaving frames or silently dropping authoritative Node events. Shutdown MUST NOT panic when the queue is closed. Retain existing four-byte big-endian framing and message-size limits; do not add another socket, channel, bridge, or `cockpit.spawn()` path.

# 8. Node command model

Phase 5 reuses the existing IPC v1 envelope and four-byte big-endian framing. The payload uses the generic Node update command; `parameters.state` selects the semantic operation. Do not add a second envelope.

Drain request:

```json
{
  "protocol": "cockpit-slurm",
  "version": "1.0",
  "messageId": "msg-001",
  "type": "command",
  "timestamp": "2026-10-16T10:00:00Z",
  "payload": {
    "commandId": "cmd-123",
    "resource": "node",
    "command": "update",
    "target": { "nodeName": "c21" },
    "parameters": {
      "state": "DRAIN",
      "reason": "scheduled maintenance"
    }
  }
}
```

Resume request:

```json
{
  "protocol": "cockpit-slurm",
  "version": "1.0",
  "messageId": "msg-002",
  "type": "command",
  "timestamp": "2026-10-16T10:01:00Z",
  "payload": {
    "commandId": "cmd-124",
    "resource": "node",
    "command": "update",
    "target": { "nodeName": "c21" },
    "parameters": { "state": "RESUME" }
  }
}
```

`messageId` identifies one IPC request and is echoed for response correlation. `commandId` identifies one logical command and is the idempotency key. The client MUST NOT send `operationId`, `HandlerID`, role, capability, executable path, shell command/template, or raw argument array. Unknown fields MUST be rejected. Missing or unsupported `state` MUST be rejected before handler/Slurm execution. These payloads belong in the existing protocol definitions and MUST NOT introduce a second envelope.

## Parameter schemas and validation

Keep validation declarative and separate from validation execution. `ParameterSpec` defines primitive types and field constraints; `RegistryEntry` declares accepted target and parameter schemas; a validator enforces the schema; operation-specific validators check semantics and trusted resource context.

| Field | Required validation |
|---|---|
| `resource` | Exactly `node`. |
| `command` | Exactly `update`. |
| `target.nodeName` | Required non-empty string, maximum 255 UTF-8 bytes subject to compatibility with the existing Node model and Slurm naming rules, and exact match to one Node in the authoritative cache. Reject ranges, lists, `ALL`, malformed names, and unknown nodes. |
| `parameters.state` | Required enum; only `DRAIN` and `RESUME` are supported. |
| `parameters.reason` | Required for `DRAIN`; trim surrounding whitespace for emptiness checks; non-empty; maximum 256 UTF-8 bytes; reject NUL and disallowed control characters. |
| Resume parameters | `reason` is rejected for `RESUME` unless explicitly added to this contract. |
| Unknown fields/types | Reject unknown fields and incorrect JSON types; do not coerce. Reject duplicate JSON keys if the selected decoder otherwise accepts ambiguous duplicates. |

Validate the target against the actual canonical Node cache and do not invent a conflicting Node-name grammar. First validate the generic command, target, and state discriminator; derive `node.drain` or `node.resume`; then validate the complete request against that operation's registry schema. Validation failures MUST NOT invoke a handler or Slurm. Perform authorization before any privileged execution and avoid disclosing sensitive target details to unauthorized callers.

# 10. Command Controller

The Command Controller is the IPC/application boundary. It validates the v1.0 envelope and generic request shape, establishes the caller-scoped command identity from the initialized connection, derives the semantic operation from the validated request, and delegates to the Command Service. It does not perform authorization, access the command ledger, or dispatch a handler. It MUST NOT invoke a handler based on client-supplied handler ID, shell command, executable path, or argument array.

The controller-to-service path is:

```text
IPC v1 command
  ↓
validate envelope and generic request structure
  ↓
derive node.drain or node.resume
  ↓
Command Service
```

The Controller MUST NOT execute Slurm commands, contain Slurm syntax, determine Linux identity, or implement React logic.

# 11. Command Service

The Command Service is the sole orchestrator of command lifecycle, durable deduplication, authorization delegation, and dispatch. For every request it authenticates the caller from the already validated connection identity, validates/canonicalizes the command payload and caller-scoped `commandId`, then looks up the ledger before authorizing:

```text
authenticated connection identity
  ↓
validate command payload and establish canonical fingerprint
  ↓
ledger lookup by stable caller identity + commandId
  ├── existing: verify ownership and fingerprint
  │     ├── same request → return stored/current result; never execute
  │     └── different request → command-id-conflict
  └── absent: validate operation schema and target
        ↓
      atomically persist non-executable authorization_pending claim
        ├── write error/uncertain → block admissions; reconcile ledger; no authorization/dispatch
        └── durable claim confirmed
              ↓
            Authorizer (exactly once)
              ├── denied/error → persist non-executable tombstone
              │     └── terminal write uncertain → block admissions; reconcile
              └── allowed → atomically transition claim to accepted
                    ├── write error/uncertain → block admissions; reconcile; no dispatch yet
                    └── accepted state confirmed durable
                    ↓
                  durably persist running/dispatch intent
                   ├── write error/uncertain → block/reconcile; no dispatch
                   └── confirmed durable → dispatch handler and record result
```

An existing record is returned only after caller authentication, ownership verification, and canonical fingerprint match; no fresh capability check is required merely to retrieve the caller's own historical result, even after permission revocation. A caller who does not own the record MUST NOT learn its status or result. `running` and `unknown` records return their stored/current status and are never re-executed.

For an absent record, the Service validates the operation schema and target, then atomically persists a durable non-executable `authorization_pending` claim before invoking the `Authorizer`. The claim is not acceptance and cannot dispatch. If this initial claim write fails or its outcome is uncertain, do not invoke the Authorizer; block command admission and reconcile the ledger. If the claim is absent after verified database recovery, no authorization decision was made and the client receives a persistence error, not an authorization denial.

After a confirmed claim, invoke the Authorizer exactly once. On denial, atomically transition the claim to a non-executable `denied` tombstone; on authorization lookup/policy failure, transition it to a non-executable `authorization_failed` tombstone. Return the corresponding authorization error only after the terminal tombstone is confirmed durable. If that write fails or is uncertain, return `ledger-persistence-failed`, block command admission, and reconcile; never dispatch. After an allow, atomically transition the claim to `accepted` with authorization metadata. Then durably transition `accepted` to `running`/dispatch-intent. The adapter/helper MUST NOT be invoked until the `running` transition is confirmed durable. If the accepted transition is found after an uncertain write but no `running` state exists, quarantine it as `authorization_uncertain`; do not dispatch. If a `running` record is recovered after restart, return `unknown` and never automatically re-execute. A persistence error is never treated as proof that the transaction did not commit.

Concurrent requests encountering an `authorization_pending` claim with the same fingerprint wait for its owner to finish, then reload the row and return the terminal/current result; they do not invoke a second Authorizer. A different fingerprint returns `command-id-conflict`. On startup, orphaned `authorization_pending` and accepted-but-not-running rows become non-executable `authorization_uncertain` tombstones and are never reauthorized or dispatched; recovered `running` rows become `unknown`. An `authorization_uncertain` retry returns a canonical error and requires the client to use a new `commandId` after the ledger is healthy. None of `denied`, `authorization_failed`, or `authorization_uncertain` can transition to `accepted`.

For write errors, freeze all command admission until SQLite recovery and a fresh transaction establish consistent ledger state. If a row is in a terminal state, return/use that state. If a committed `authorization_pending` claim remains, quarantine it as `authorization_uncertain`. If consistency or commit outcome cannot be established, remain unavailable for command admission until the documented operator recovery procedure resolves it. Do not delete or ignore a row to resume service. A denied tombstone remains keyed by stable caller identity and `commandId` throughout the 30-day retention period, so it cannot become executable after permission changes. A unique key arbitrates concurrent claims, accepted transitions, and tombstones; at most one execution is possible.

The service MUST remain independent of React and Cockpit channel details. It does not duplicate the Authorizer's capability decision.

# 12. Node Command Adapter

The Node Command Adapter is responsible for translating the application command into a Slurm operation.

For example:

```text
Application:
  resource=node, command=update
  target.nodeName=c21, state=DRAIN, reason=maintenance

Adapter:
  scontrol update NodeName=c21 State=DRAIN Reason=maintenance
```

The adapter owns:

```text
Slurm CLI syntax
Slurm command arguments
Slurm exit status
Slurm stderr/stdout interpretation
```

The daemon remains unprivileged. Direct execution of `scontrol` as the `cockpit-slurm` service account is acceptable only after both supported operations pass the dedicated real-cluster acceptance test under the target Slurm policy. Existing permission tests show this account cannot perform certain privileged Node operations, so direct execution is not approved by default. Until a passing real-cluster test proves otherwise, the supported execution model requires a narrowly scoped privileged helper.

The helper is a deployment-level execution boundary, not an authorization authority. Before invoking it, the daemon MUST authenticate the requesting user from validated connection peer credentials, construct `UserContext`, resolve the operation and its required capability from `GlobalRegistry`, validate the request, and authorize it. Any identity, lookup, validation, or authorization failure MUST prevent helper invocation.

If required, the helper MUST:

1. accept only the explicitly supported `node.drain` and `node.resume` operations with validated Node/reason arguments; it MUST NOT accept arbitrary commands, executable paths, shell text, unrestricted `scontrol` arguments, or other Slurm operations;
2. independently validate operation name, argument count and format, Node target, allowed state, and drain-reason constraints;
3. use a fixed absolute `scontrol` path and argument-array execution without a shell;
4. have documented and tested installation path, root ownership, executable permissions, privilege boundary, service access mechanism, and permitted operations; never grant unrestricted sudo access to `scontrol` or run arbitrary user arguments as `SlurmUser`;
5. preserve the original authenticated caller, requested operation, target Node, backend authorization decision, and execution result in the durable command record. Record the helper's effective execution identity separately and never treat it as the requester;
6. return a bounded, classified result without exposing unnecessary raw command details.

Slurm may see the helper's privileged execution identity rather than the original Cockpit user. Slurm's authorization result is therefore not proof that Slurm independently authorized the original requester. Backend authorization of the requester remains authoritative; the Slurm result is an additional execution outcome.

Acceptance tests MUST assert that unauthorized requests do not invoke the helper and that attempts to escape its permitted-operation boundary (arbitrary operation/path, shell input, state, or argument injection) are rejected. Document and test the exact execution identity and boundary used by each deployment before enabling commands.

For either approved execution model, use a fixed absolute executable path and separate validated arguments through `exec.CommandContext` or the controlled execution boundary. Never use `sh -c`, shell interpolation, or a client-supplied command template. The derived operation fixes the state: `node.drain` maps only to `State=DRAIN`; `node.resume` maps only to `State=RESUME`. Pass `NodeName=<name>`, `State=<fixed-state>`, and for drain `Reason=<reason>` as separate argv elements; the complete `Reason=...` value MUST remain one argument, including spaces. Reject invalid values before execution.

The adapter MUST NOT own:

```text
React state
Cockpit channel state
frontend authorization
UserContext construction
```

# 14. Authorization and command processing flow

The mandatory flow separates connection identity, historical-result retrieval, and authorization of a new mutation:

```text
IPC request + authenticated connection identity
  ↓
Command Controller: envelope/generic validation, derive operation
  ↓
Command Service: canonical fingerprint + lookup (caller UID, commandId)
  ├── existing → verify owner + fingerprint
  │      ├── match → return stored/current result; no authorization or dispatch
  │      └── mismatch → command-id-conflict
  └── absent → validate operation schema and target
       ↓
     persist durable authorization_pending claim
       ├── write error/uncertain → block admission; reconcile; no authorization/dispatch
       └── confirmed durable
             ↓
       Authorizer (single authority)
         ├── fresh Slurm lookup + registry capability
         ├── denied/error → persist non-executable tombstone
         │                    └── uncertain write → block/reconcile
         └── allowed → transition claim to accepted
                       ├── unconfirmed → block/reconcile; no dispatch
                       └── confirmed durable
                ↓
              persist running/dispatch intent
               ├── unconfirmed → block/reconcile; no dispatch
               └── confirmed durable
                    ↓
                  trusted HandlerRegistry
                    ↓
                Node Command Adapter / restricted helper
```

      Only after both accepted and running/dispatch-intent transitions are confirmed durable may dispatch occur. Requests encountering the same `authorization_pending` claim wait for its owner and then reload the terminal/current result; they do not authorize a second time. On a concurrent claim conflict, reload and compare the winning fingerprint; return its result for a match or `command-id-conflict` otherwise. A loser never dispatches. Authorization or persistence failure MUST be handled before invoking any handler, adapter, helper, or Slurm command.

For example:

```text
ordinary user
    ↓
nodes.drain
    ↓
DENIED
    ↓
Slurm is NOT called
```

An authorized Slurm administrator:

```text
AdminLevel=admin
    ↓
nodes.drain
    ↓
ALLOWED
    ↓
Slurm
```

# 15. Command IDs

Every new logical command MUST include a unique `commandId`, generated by the client before the first send and reused unchanged for retries of that command. The backend MUST validate and track it.

Example:

```text
commandId = "cmd-01..."
```

The command ID is distinct from the protocol `messageId`.

Conceptually:

```text
messageId
    =
identity of one IPC request message; the response echoes this value

commandId
    =
identity/idempotency key of one logical command execution
```

`messageId` is used only for request/response correlation and retransmission detection on the same connection. `commandId` is used for command lifecycle tracking and deduplication across requests, including retries that use a new `messageId`. A `commandId` MUST be scoped to the authenticated caller so another user cannot query or retrieve its result.

# 16. Command lifecycle

The command lifecycle should be explicit.

Conceptually:

```text
received
   ↓
validated
   ↓
authorized
   ↓
running
   ↓
succeeded
```

or:

```text
received
   ↓
validated
   ↓
authorized
   ↓
running
   ↓
failed
```

```text

   ↓
validated
   ↓
```

# 17. Command response

A successful command response contains command-level information rather than pretending to be a Node snapshot. The only externally visible command statuses are `running`, `succeeded`, `failed`, `denied`, and `unknown`. `received`, `validated`, and `authorized` MAY be internal lifecycle states, but MUST NOT be presented as completed execution results. Authorization denial MUST be returned as a canonical `error` envelope with request outcome `denied`. It MUST NOT create an accepted/executable command record or reservation. The Service persists a non-executable denial tombstone keyed by caller and `commandId` plus fingerprint; it can only return the denial or conflict and MUST never become an accepted command after a permission change. A successful response has this shape:

```json
{
  "protocol": "cockpit-slurm",
  "version": "1.0",
  "messageId": "msg-001",
  "type": "command-response",
  "timestamp": "2026-10-09T10:00:01Z",
  "payload": {
    "commandId": "cmd-123",
    "resource": "node",
    "command": "update",
    "target": { "nodeName": "c21" },
    "parameters": { "state": "DRAIN" },
    "status": "succeeded"
  }
}
```

The response MUST echo the request `messageId`. Its payload MUST contain `commandId`, `resource`, the generic request `command` (`update`), and `status`; include the validated target and state where supported by the existing response schema. A `command-response` reports the current command status; subsequent status changes MAY use `command-status`, correlated by `commandId` and carrying the same status values. The response MUST NOT claim that the Node state has changed.

Errors MUST use the canonical Error Model payload and preserve the request `messageId`; when applicable, include `commandId` and the Node resource/target. At minimum, use stable codes for `identity-unavailable`, `user-lookup-failed`, `authorization-denied`, `command-id-conflict`, `message-id-conflict`, `command-outcome-unknown`, and `slurm-command-failed`, with the corresponding canonical category, message, and retryable value. Do not expose raw command-line implementation details.

For example:

```json
{
  "protocol": "cockpit-slurm",
  "version": "1.0",
  "messageId": "msg-001",
  "type": "error",
  "timestamp": "2026-10-09T10:00:01Z",
  "payload": {
    "code": "authorization-denied",
    "category": "authorization-error",
    "message": "Not authorized to drain this Node",
    "retryable": false,
    "commandId": "cmd-123"
  }
}
```

For an unknown outcome, report status `unknown` (and `command-outcome-unknown` where represented as an error), set retryable to false, do not automatically resubmit the mutation, and trigger or await normal Node synchronization to reconcile the actual Slurm state. The command result remains unknown until the authoritative state is observed; observed Node state does not rewrite the historical execution result. A retry of a stored `running` or `unknown` command returns that status after caller ownership and fingerprint checks; it does not perform fresh authorization or execute again.

# 20. Idempotence

The backend MUST enforce message-level retransmission handling and logical command deduplication. For each command, authenticate the caller using validated connection identity, validate the v1.0 message, establish the stable caller identity and canonical request fingerprint, then look up `(stable caller identity, commandId)` in the durable ledger before fresh authorization:

| Situation | Required backend behavior |
| --- | --- |
| Same `messageId`, same request, same connection | Return the recorded response or current status; do not execute again. `messageId` is transport/message correlation and is scoped to the connection. |
| Same `messageId`, different request, same connection | Reject with `message-id-conflict`; do not execute. |
| Existing same caller and `commandId`, same command payload | After caller authentication, ownership verification, and canonical fingerprint match, return stored status/result without fresh authorization or execution. This applies after permission changes and across retries with a new `messageId`. |
| Same caller and `commandId`, different command payload | Reject with `command-id-conflict`; do not execute. |
| Caller does not own the record | Do not disclose status/result; return a safe authorization/not-found response consistent with the Error Model. |
| Existing `authorization_pending` with same fingerprint | Wait for the claim owner to finish, then reload and return its current/terminal outcome; do not invoke another Authorizer. A different fingerprint returns `command-id-conflict`. |
| Existing `accepted` while owner is processing | Wait for the owner to persist running/dispatch intent or fail; do not authorize or dispatch independently. On recovery without running intent, quarantine as `authorization_uncertain`. |
| Existing `authorization_uncertain` | Return `authorization-outcome-unknown`; never rerun authorization or execute this ID. Require explicit recovery and a new ID for a new command. |
| New `commandId` with no existing record | Validate schema/target; durably claim `authorization_pending`; invoke Authorizer only after claim durability is confirmed; transition allowed requests to accepted and then running/dispatch-intent; execute only after both transitions are confirmed durable. |
| Initial claim write error/uncertain outcome | Do not invoke Authorizer or execute; block command admission and reconcile ledger integrity/row state before resuming. |
| Terminal tombstone/accepted-transition write error | Do not execute; block admission and reconcile. Do not infer commit/rollback from the returned error. |
| Running/dispatch-intent write error/uncertain outcome | Do not invoke the adapter/helper; block admission and reconcile. If recovered as running, return `unknown` and never automatically execute. |
| Concurrent same-caller/same-`commandId` requests | Atomic unique claim permits one owner. A loser waits/reloads the owner's row, compares fingerprints, and returns the outcome or `command-id-conflict`; it never invokes Authorizer or dispatches independently. |
| Existing command whose outcome is `running` or `unknown` | Return stored/current status; do not execute again automatically. Reconcile through Slurm/Node synchronization. |
| New request denied by Authorizer | Persist a non-executable denial tombstone, then return authorization error. Same-ID retries return denial/conflict and can never become executable; do not invoke a handler/helper. |
| Slurm authorization lookup fails | Persist a non-executable `authorization_failed` tombstone, then return the lookup error; use a new ID after recovery to request a new authorization decision. |

`messageId` is transport/message correlation; `commandId` is logical command deduplication. Compare canonical request semantics (protocol version, message type, and payload) or an equivalent collision-resistant fingerprint; exclude envelope timestamp and `messageId`. Do not include client-supplied identity or capability fields. The stable caller identity is derived from the validated peer identity (UID as the stable key; resolved username may be retained as an audit snapshot), never from payload data.

Command records MUST be durably available for deduplication for the lifetime of the command and its retained result, including across daemon restarts. Persist the minimum command ledger needed to recognize accepted IDs, the authenticated requesting user (stable UID and resolved username), canonical payload fingerprint, derived operation and required capability, authorization decision, execution identity/boundary, target, and status/result. Retain records and idempotency keys for 30 days; IDs MUST NOT become reusable during that window. After expiry, deduplication is no longer guaranteed and clients MUST NOT blindly retry an expired ID. After a restart, any accepted command whose outcome cannot be proven MUST be reported as `unknown` and MUST NOT be automatically re-executed. This is command tracking required for safe mutation, not a requirement for a comprehensive audit subsystem.

The `authorization_pending` claim is a non-executable recovery record, not an accepted command. Only new commands that passed fresh authorization may transition it atomically to accepted. Then persist `running`/dispatch intent; dispatch is forbidden until both accepted and running states are confirmed durable. Persist denied, lookup-failed, and uncertain outcomes as non-executable tombstones for the same 30-day idempotency window so a command ID cannot later become executable after a permission change or recovery. After expiry, clients MUST NOT reuse or retry that old ID; they must generate a new ID for a new command. Store the fresh authorization context timestamp/version with accepted metadata. A unique caller/`commandId` constraint arbitrates pending claims, terminal tombstones, and accepted transitions; no tombstone may transition to accepted.

Any database write error has an unknown commit outcome until the service reconciles it. Freeze command admission, perform configured SQLite integrity/journal recovery, and read the row in a fresh transaction. If a terminal state is confirmed, return/use it. If a committed pending claim remains, convert it to `authorization_uncertain`; never rerun authorization or execute that ID. If the database or transaction state remains uncertain, remain unavailable for all new command admission until explicit operator recovery. Startup performs this recovery before opening the command endpoint. A pre-claim write failure means no Authorizer call or denial occurred; admission remains blocked until absence and database consistency are verified. A persistence error must not be presented as an authorization denial or a Slurm failure.

The ledger database schema MUST be versioned and initialized/migrated before mutation service is available. Document migration ordering and failure behavior, SQLite journal/WAL mode and associated files, durability/locking settings, and crash-recovery behavior. Run initialization, migration, persist, restart, corrupt-database, and unwritable-database tests under the production systemd service account and hardening settings. The unit MUST grant only `/var/lib/cockpit-slurm` as writable state via `StateDirectory=cockpit-slurm` and `StateDirectoryMode=0750`; retain `ProtectSystem=strict`. Do not accept mutations if the ledger cannot be opened, initialized, migrated, locked, or written. No in-memory-only fallback is permitted.

For duplicate comparison, canonicalize the request semantics (protocol version, message type, and payload); exclude envelope timestamps and the correlation `messageId`. Thus a retransmission with the same `messageId` and same command request remains the same request even if the timestamp differs.

# 22. Error model

Every externally visible error uses the canonical v1.0 `error` envelope and includes `code`, `category`, `message`, and `retryable`; preserve the request `messageId`, and include `commandId` and resource/target when known and safe. Do not expose raw command output, database internals, or unnecessary authorization details. Use these stable code/category/retryability mappings consistently in protocol types, backend responses, frontend types, and tests:

| Code | Category | Retryable | Meaning |
|---|---|---:|---|
| `invalid-command` | `validation-error` | false | Unsupported resource/command/operation. |
| `invalid-payload` | `validation-error` | false | Malformed payload, unknown field, or invalid parameter. |
| `identity-unavailable` | `authentication-error` | false | Peer credentials or requesting Linux identity cannot be established. |
| `user-lookup-failed` | `internal-error` | true | Required Slurm user lookup failed; no authorization or execution occurs. |
| `authorization-denied` | `authorization-error` | false | Authenticated requester lacks the registry-required capability. |
| `capability-unavailable` | `internal-error` | true | Capability resolution failed, so no valid capability response can be returned. |
| `ledger-persistence-failed` | `internal-error` | false | Ledger commit/recovery could not be confirmed; command admission is blocked and clients must not automatically resubmit a mutation. |
| `authorization-outcome-unknown` | `internal-error` | false | Recovery found an orphaned authorization claim; this ID is quarantined and cannot be authorized or executed. |
| `command-id-conflict` | `conflict` | false | Reused caller-scoped `commandId` has a different canonical command payload. |
| `message-id-conflict` | `conflict` | false | Reused connection-scoped `messageId` has a different request. |
| `command-outcome-unknown` | `timeout` | false | Execution may have reached Slurm; do not automatically retry. |
| `command-timeout` | `timeout` | false | Execution timed out with a potentially uncertain outcome. |
| `slurm-command-failed` | `slurm-error` | false | Slurm rejected or failed the supported operation. |
| `unsupported-message-type` | `protocol-error` | false | Envelope type is not supported by this v1.0 endpoint. |
| `internal-error` | `internal-error` | true | Unexpected internal failure with no implementation detail exposed. |

`identity-unavailable` is used for failed identity resolution. A Slurm-user lookup failure during capability retrieval maps to `capability-unavailable`; during a command it maps to `user-lookup-failed`. Both deny execution. Authorization denial MUST NOT be reported as a Slurm failure, and an uncertain execution outcome MUST use `unknown` plus `command-outcome-unknown`, with `retryable=false`.

Do not collapse every failure into:

```text
command failed
```

The frontend should be able to distinguish:

```text
not authorized
```

from:

```text
Slurm failed
```

and:

```text
invalid request
```

1. validate required user input;

- authorization is evaluated before handler invocation; missing context or resolver errors deny by default;
- registry and handler tests use a mock execution boundary and cannot invoke the host's real `scontrol`.

## 36.6 Command-ledger and systemd tests

Run these tests under the production `cockpit-slurm` service account and systemd hardening settings, including `ProtectSystem=strict` and the configured state directory:

* installation creates `/var/lib/cockpit-slurm` with intended owner/group and mode `0750`;
* daemon initializes the versioned SQLite schema and creates all journal/WAL/lock/recovery files required by the configured mode;
* command records persist and recover after a service restart;
* an accepted command left `running` with uncertain dispatch becomes `unknown` and is never re-executed;
* schema migration, crash recovery, 30-day retention, locking, and deduplication scope behave as documented;
* unavailable, corrupt, locked, or unwritable ledger prevents mutation acceptance and never falls back to in-memory-only deduplication.
* fault-inject a transaction that commits but returns a write error; reconcile from a fresh transaction and use the committed state without repeating authorization or dispatch;
* fault-inject a true pre-commit write failure for `authorization_pending`; prove the Authorizer and execution boundary are not invoked and command admission remains blocked until integrity and row absence are verified;
* fault-inject denied/lookup-failure tombstone, accepted-transition, and running/dispatch-intent writes, both with commit-before-error and true failure; no path dispatches unless both accepted and running states are confirmed durable;
* restart with orphaned `authorization_pending`, accepted-but-not-running, uncertain tombstone, and running/dispatch-intent rows; convert unresolved authorization claims and accepted-but-not-running rows to non-executable `authorization_uncertain`, running rows to `unknown`, never reauthorize/execute them, and block admission until recovery completes;
* reconcile terminal denial, authorization-failure, authorization-uncertain, accepted, running, and pending rows; verify only a confirmed accepted plus confirmed running transition can dispatch, and a confirmed absent initial claim means the Authorizer was never invoked;
* keep admission blocked when SQLite recovery cannot establish a consistent state; only the documented operator recovery procedure can unblock it, without deleting or ignoring unresolved command IDs;
* verify `ledger-persistence-failed` and `authorization-outcome-unknown` use their canonical error categories, correlation IDs, and non-retryable behavior.

## 36.7 Fresh authorization and deduplication tests

Test the same open IPC connection while changing authoritative Slurm user information:

* change `AdminLevel=admin` to `none`; a subsequent new `commandId` is denied and never reaches the handler/helper;
* change `AdminLevel=none` to `admin`; a subsequent new `commandId` is allowed only after the resolver obtains the updated Slurm record;
* make Slurm user lookup unavailable; a subsequent new command is denied even if the connection-time `UserContext` or frontend capability response still says `admin`;
* retain a stale frontend capability response and prove it cannot bypass fresh backend authorization;
* for a previously authorized command, revoke permission and retry the same caller/ID/fingerprint: return the stored status/result without invoking Authorizer or executing again;
* for a previously denied command, grant permission and retry the same ID/fingerprint: return the stored denial tombstone without execution; a new ID is eligible for fresh authorization;
* verify an existing `running` or `unknown` record returns its status and is never re-executed;
* verify a different fingerprint with the same ID returns `command-id-conflict`, and another authenticated caller cannot retrieve the record;
* race concurrent same-caller/same-ID requests, including identical and conflicting fingerprints; at most one accepted reservation and execution occur, and no denial tombstone is upgraded to accepted;
* count Authorizer invocations and prove the Controller cannot invoke it or dispatch around the Command Service; each new command request reaching authorization has exactly one authoritative decision, and every execution has one successful decision;
* restart after a command is accepted but before running intent is confirmed; quarantine it as `authorization_uncertain` and assert zero authorization/dispatch retries;
* restart after running/dispatch intent is confirmed but execution outcome is uncertain; return `unknown` and assert zero automatic re-executions;
* force a ledger write error with both commit-before-error and true-failure outcomes; assert command admission stays blocked until reconciliation, and no helper is called while the write outcome is unresolved.
