# cockpit-slurm Implementation Phase 5 — Node Commands and Authorization

## 1. Purpose

Phase 5 extends the completed Phase 4 Node live-stream vertical slice with controlled Node mutation.

Phase 3 established:

```text
Slurm
  ↓
Node Adapter
  ↓
Node Cache
  ↓
Node Query Service
  ↓
IPC
  ↓
NodeProvider
  ↓
NodeTable
```

Phase 4 established:

```text
Slurm
  ↓
NodeSynchronizer
  ↓
Node Cache
  ↓
Node Change
  ↓
Node Stream Registry
  ↓
Unix socket
  ↓
Cockpit native channel
  ↓
NodeProvider
  ↓
NodeTable
```

Phase 5 adds:

```text
React
  ↓
Application Command
  ↓
IPC
  ↓
Command Controller
  ↓
UserContext
  ↓
Capability Resolver
  ↓
Authorization
  ↓
Node Command Service
  ↓
Node Command Adapter
  ↓
Slurm
  ↓
Node Synchronizer
  ↓
Node Cache
  ↓
Node Change
  ↓
Cockpit native channel
  ↓
NodeProvider
  ↓
NodeTable
```

The primary objective is to prove that a frontend command can safely mutate Slurm state and that the resulting frontend state is obtained from the authoritative backend cache and event stream rather than from frontend assumptions.

The fundamental rule is:

```text
command succeeds
      ≠
frontend guesses new state
```

Instead:

```text
command
  ↓
Slurm mutation
  ↓
resource synchronization
  ↓
cache update
  ↓
Node event
  ↓
frontend state update
```

Phase 5 is therefore the first complete **read + synchronize + mutate + authorize** Node vertical slice.

---

# 2. Core architectural decisions

## 2.1 Phase 5 remains Node-focused

Phase 5 MUST implement commands for the Node resource only.

Do not use Phase 5 to implement:

```text
Jobs
Users
Accounts
Reservations
Partitions
Clusters
```

Do not generalize the entire Resource System during this phase.

The proven sequence is:

```text
Phase 3
    Node Query
       ↓
Phase 4
    Node Live State
       ↓
Phase 5
    Node Commands + Authorization
       ↓
Phase 6
    Resource System Generalization
```

Node remains the reference resource.

---

## 2.2 Backend authorization is authoritative

The backend MUST enforce authorization.

The frontend may hide or disable controls, but frontend visibility is never a security boundary.

For example:

```text
Frontend
    ↓
"Drain Node" button
    ↓
command request
    ↓
backend authorization
    ↓
allowed / denied
```

The backend MUST NOT trust:

```text
frontend role
frontend username
frontend capability
frontend admin flag
frontend-selected account
```

The authoritative identity comes from the server-side connection.

---

## 2.3 Server-derived identity

Phase 4 establishes the prerequisite that the Unix socket peer identity can be mapped to the authenticated Cockpit user.

Phase 5 uses that identity to construct `UserContext`.

Conceptually:

```text
Cockpit authenticated user
        ↓
Unix socket connection
        ↓
SO_PEERCRED
        ↓
UID / GID
        ↓
Linux user
        ↓
Slurm user lookup
        ↓
UserContext
```

The backend MUST derive the requesting identity from the connection.

A command request MUST NOT be allowed to override:

```text
username
UID
GID
AdminLevel
Coordinator
Capabilities
```

The command payload identifies the requested operation, not the identity of the caller.

---

## 2.4 UserContext is request context, not frontend state

The backend `UserContext` represents the authenticated caller.

Conceptually:

```text
UserContext
├── Username
├── UID
├── GID
├── AdminLevel
├── Coordinator
├── Accounts
└── Capabilities
```

The exact implementation may evolve with the existing codebase.

The important boundary is:

```text
Connection identity
        ↓
UserContext
        ↓
Capability Resolver
        ↓
Authorization
```

The frontend may receive a safe representation of the user's capabilities, but it MUST NOT become the authority for those capabilities.

# 5. Architectural invariants

## 5.1 Backend remains authoritative

The backend remains authoritative for:

```text
identity
authorization
command execution
Node state
generation
events
```

The frontend is responsible for:

```text
command initiation
presentation
loading state
success/error presentation
```

It is NOT authoritative for the resulting Node state.

---

## 5.2 Commands do not directly modify the frontend cache

After a successful command:

```text
DO NOT:

command
  ↓
React
  ↓
mutate Node state directly
```

Instead:

```text
command
  ↓
Slurm
  ↓
NodeSynchronizer
  ↓
NodeCache
  ↓
NodeChange
  ↓
NodeProvider
```

This guarantees that the displayed state represents observed Slurm state.

---

## 5.3 Successful command does not imply immediate state change

A successful Slurm command means that Slurm accepted the operation.

It does not necessarily mean that the next synchronized Node snapshot already contains the expected state.

Therefore:

```text
command response
    =
command execution result
```

and:

```text
Node event
    =
observed authoritative state
```

These are separate concepts.

---

## 5.4 Command response and Node event are separate

A command response reports command execution.

A Node event reports resource state.

For example:

```text
CommandResponse
    commandId: "cmd-123"
    status: "succeeded"
```

followed later by:

```text
Event
    resource: "node"
    event: "updated"
    generation: 44
```

The frontend MUST NOT require the command response to contain the complete updated Node object.

---

# 6. User identity

## 6.1 Peer credentials

The IPC connection already obtains peer credentials in the backend.

Phase 5 MUST use the established mechanism rather than accepting identity from the command payload.

Conceptually:

```text
Unix socket
    ↓
SO_PEERCRED
    ↓
uid
gid
pid
```

The exact credentials available should follow the platform implementation.

---

## 6.2 Linux user lookup

The backend resolves the peer UID to the corresponding Linux user.

Conceptually:

```text
UID
 ↓
OS user database
 ↓
username
```

Failure to resolve the identity MUST prevent command authorization.

Do not fall back to:

```text
frontend username
request.username
anonymous
root
```

---

## 6.3 Slurm user lookup

The resolved Linux username is used to obtain the corresponding Slurm user information.

The Slurm user context may contain information such as:

```text
username
AdminLevel
coordinator
accounts
```

The implementation MUST use the existing Slurm account/user interfaces rather than duplicating Slurm authorization semantics in React.

---

# 7. AdminLevel and capability model

## 7.1 AdminLevel

Phase 5 introduces the backend mapping from Slurm user information to an application-level authorization context.

Conceptually:

```text
Slurm user
    ↓
AdminLevel
    ↓
capabilities
```

The exact AdminLevel values MUST follow the project's existing protocol and context definitions.

Do not create frontend-only AdminLevel values that have no backend meaning.

---

## 7.2 Capability Resolver

The Capability Resolver translates authoritative user information into explicit capabilities.

Example capability names:

```text
nodes.view
nodes.modify
nodes.drain
nodes.resume
nodes.power
nodes.reboot
```

Only capabilities required by the implemented Node commands should be introduced in Phase 5.

Avoid prematurely creating capabilities for resources that are not implemented.

---

## 7.3 Capability checks

Authorization should be expressed in terms of capabilities.

For example:

```text
Node drain
    ↓
requires:
    nodes.drain
```

and:

```text
Node resume
    ↓
requires:
    nodes.resume
```

The command service MUST NOT rely only on AdminLevel comparisons.

A preferred decision path is:

```text
UserContext
    ↓
Capability Resolver
    ↓
required capability
    ↓
Authorization
```

---

# 8. Node command model

Phase 5 introduces an application-level Node command model.

A conceptual command is:

```text
{
    "protocol": "cockpit-slurm",
    "version": "1.0",
    "messageId": "...",
    "type": "command",
    "timestamp": "...",
    "payload": {
        "resource": "node",
        "command": "drain",
        "node": "c21",
        "reason": "maintenance"
    }
}
```

The exact JSON structure MUST follow the existing protocol implementation.

The important separation is:

```text
Envelope
    ↓
command
    ↓
resource = node
    ↓
resource-specific command payload
```

Do not introduce a second command envelope.

---

# 9. Initial Node command set

Phase 5 should begin with a small, useful command set.

Recommended initial commands:

```text
drain
resume
```

For example:

```text
drain:
    NodeName=c21
    State=drain
    Reason="maintenance"
```

and:

```text
resume:
    NodeName=c21
    State=resume
```

The exact Slurm command syntax MUST be implemented by the backend Node Command Adapter.

Do not construct shell command strings in React.

---

## 9.1 Future Node commands

Commands such as:

```text
power
reboot
create
delete
shutdown
```

may be supported by Slurm, but they should not automatically be implemented merely because the adapter is being created.

Each additional command introduces additional:

```text
authorization
validation
audit
operational risk
```

and should be added deliberately.

# 10. Command Controller

The Command Controller is the IPC/application boundary for command requests.

Its responsibilities are:

1. validate the application message;
2. identify the command;
3. obtain the connection `UserContext`;
4. resolve required capability;
5. invoke authorization;
6. invoke the Node Command Service;
7. return a correlated response.

It MUST NOT:

* execute Slurm commands directly;
* contain Node-specific Slurm syntax;
* determine Linux identity;
* implement React logic.

Conceptually:

```text
IPC
 ↓
Command Controller
 ├── validate
 ├── UserContext
 ├── capability
 ├── authorize
 └── dispatch
       ↓
Command Service
```

---

# 11. Command Service

The Node Command Service owns application-level command execution.

Responsibilities:

```text
validate command semantics
        ↓
authorize
        ↓
construct command request
        ↓
invoke adapter
        ↓
track result
        ↓
return command result
```

The service MUST remain independent of React and Cockpit channel details.

---

# 12. Node Command Adapter

The Node Command Adapter is responsible for translating the application command into a Slurm operation.

For example:

```text
Application:
    node.drain("c21", "maintenance")

Adapter:
    scontrol update Nodename=c21 State=drain Reason=maintenance
```

The adapter owns:

```text
Slurm CLI syntax
Slurm command arguments
Slurm exit status
Slurm stderr/stdout interpretation
```

The adapter MUST NOT own:

```text
React state
Cockpit channel state
frontend authorization
UserContext construction
```

---

# 13. Command validation

Command validation occurs before Slurm execution.

Validate at least:

```text
resource
command
Node identity
required fields
field types
field length
allowed command values
```

For example:

```text
resource != node
    → reject

command != supported Node command
    → reject

missing node
    → reject

invalid Node name
    → reject
```

Validation failures MUST NOT invoke Slurm.

---

# 14. Authorization flow

The mandatory authorization flow is:

```text
Command Request
      ↓
Connection UserContext
      ↓
Capability Resolver
      ↓
Required Capability
      ↓
Authorization
      │
      ├── denied → error response
      │
      └── allowed
             ↓
       Command Service
             ↓
       Node Command Adapter
```

An authorization failure MUST be rejected before invoking Slurm.

For example:

```text
ordinary user
    ↓
nodes.drain
    ↓
DENIED
    ↓
Slurm is NOT called
```

An authorized operator:

```text
operator
    ↓
nodes.drain
    ↓
ALLOWED
    ↓
Slurm
```

---

# 15. Command IDs

Every accepted command MUST receive a unique command ID.

Example:

```text
commandId = "cmd-01..."
```

The command ID is distinct from the protocol `messageId`.

Conceptually:

```text
messageId
    =
identity of the IPC request message

commandId
    =
identity of the command execution
```

A command response MUST preserve enough information to correlate the response with the original request.

---

# 16. Command lifecycle

The command lifecycle should be explicit.

Conceptually:

```text
received
   ↓
validated
   ↓
authorized
   ↓
running
   ↓
succeeded
```

or:

```text
received
   ↓
validated
   ↓
authorized
   ↓
running
   ↓
failed
```

Authorization failure is distinct:

```text
received
   ↓
validated
   ↓
denied
```

The implementation may use a smaller internal state machine, but command lifecycle semantics MUST remain explicit.

---

# 17. Command response

A successful command response should contain command-level information rather than pretending to be a Node snapshot.

Conceptually:

```text
{
    "protocol": "cockpit-slurm",
    "version": "1.0",
    "messageId": "...",
    "type": "command-response",
    "timestamp": "...",
    "payload": {
        "commandId": "...",
        "resource": "node",
        "command": "drain",
        "status": "succeeded"
    }
}
```

An error should identify the command failure without exposing unnecessary internal information.

For example:

```text
status: "failed"
error:
    code: "authorization-denied"
```

or:

```text
status: "failed"
error:
    code: "slurm-command-failed"
```

Do not expose raw shell implementation details unless they are intentionally part of the error contract.

---

# 18. Command execution and synchronization

After successful execution:

```text
Node Command Adapter
        ↓
      Slurm
        ↓
NodeSynchronizer
        ↓
NodeCache.Apply()
        ↓
NodeChange
        ↓
NodeStreamRegistry
        ↓
Cockpit channel
        ↓
NodeProvider
```

The command service MUST NOT directly update `NodeCache` with an assumed state.

For example, after:

```text
drain c21
```

do not execute:

```text
cache.Set(c21.State = "drain")
```

Instead, allow the normal synchronization path to observe the actual Slurm state.

This preserves the Phase 4 invariant that events describe committed authoritative cache state.

---

# 19. Command timing

A successful command may be followed by the corresponding Node event asynchronously.

Therefore:

```text
T1 command submitted
T2 command accepted
T3 command response returned
T4 Slurm state changes
T5 NodeSynchronizer observes change
T6 NodeCache commits change
T7 Node event published
T8 NodeProvider applies event
```

The frontend MUST tolerate this separation.

Do not block the command response waiting indefinitely for the Node event.

---

# 20. Idempotence

Phase 5 should establish command idempotence semantics where practical.

The command ID provides the identity of a command execution.

The backend MUST prevent accidental duplicate execution where the protocol or retry mechanism could otherwise submit the same command more than once.

At minimum, document and test:

```text
same request
    ↓
same command ID
    ↓
must not unexpectedly execute twice
```

The exact persistent command-deduplication mechanism may be deferred if it is part of later production hardening, but the command contract MUST not make duplicate execution ambiguous.

---

# 21. Audit information

Phase 5 introduces the minimum audit information necessary to understand Node mutation.

A command record should conceptually identify:

```text
commandId
request messageId
timestamp
username
UID
command
resource
Node
authorization result
execution result
error
```

For example:

```text
2026-10-08T...
user=alice
uid=1001
command=drain
node=c21
authorization=allowed
result=succeeded
```

Phase 5 does not need to implement a complete enterprise audit subsystem.

The objective is to establish the command/audit boundary so that production hardening can extend it later.

---

# 22. Error model

Command errors should remain distinguishable.

At minimum:

```text
invalid-command
invalid-payload
identity-unavailable
user-lookup-failed
authorization-denied
capability-unavailable
command-timeout
slurm-command-failed
internal-error
```

Do not collapse every failure into:

```text
command failed
```

The frontend should be able to distinguish:

```text
not authorized
```

from:

```text
Slurm failed
```

and:

```text
invalid request
```

---

# 23. Frontend Command Service

Phase 5 adds the frontend command path.

Recommended structure:

```text
src/
  ipc/
    client.ts
    framing.ts
    protocol.ts
    errors.ts

  services/
    resource-service.ts
    command-service.ts

  contexts/
    UserProvider.tsx
    NodeProvider.tsx
```

The existing `command-service.ts` should become the frontend abstraction for command requests.

It is a **transport/client abstraction**, not a second authorization or resource framework.

The service should:

```text
create command request
        ↓
send through existing IPC client
        ↓
await correlated response
        ↓
return command result
```

It MUST NOT:

```text
execute scontrol
calculate AdminLevel
decide authoritative authorization
mutate Node cache directly
```

---

# 24. NodeProvider command integration

`NodeProvider` may expose command operations to Node UI components.

For example:

```text
NodeProvider
    ├── nodes
    ├── generation
    ├── connection state
    ├── stream state
    └── commands
          ├── drainNode()
          └── resumeNode()
```

The exact API may follow the existing implementation.

The important boundary is:

```text
NodeProvider
    ↓
CommandService
    ↓
backend
```

and not:

```text
NodeProvider
    ↓
scontrol
```

---

# 25. Frontend command state

The frontend should distinguish:

```text
command pending
command succeeded
command failed
```

from:

```text
Node state
```

For example:

```text
Node state:
    IDLE

Command:
    drain → pending

Command response:
    succeeded

Node state:
    IDLE

later:

Node event:
    DRAIN

Node state:
    DRAIN
```

This is valid and expected.

Do not display the command as the authoritative resource state.

---

# 26. Node UI behavior

The Node UI may expose commands such as:

```text
Drain
Resume
```

A command control should:

1. validate required user input;
2. submit the command;
3. display command progress;
4. display command failure if rejected;
5. wait for the normal Node event/state update;
6. render the resulting authoritative Node state.

The UI MUST NOT optimistically replace the Node state merely because the command request was accepted.

---

# 27. Authorization-aware UI

The frontend may use capability information to improve usability.

For example:

```text
nodes.drain = true
    → show Drain action

nodes.drain = false
    → hide/disable Drain action
```

However:

```text
UI allows action
    ≠
backend authorizes action
```

The backend MUST always perform the final authorization check.

This prevents:

```text
modified browser JavaScript
forged IPC request
manual protocol request
```

from bypassing authorization.

---

# 29. No direct command-to-event shortcut

Do not implement:

```text
Command
  ↓
synthetic Node event
  ↓
React
```

The event MUST originate from committed cache state.

Required:

```text
Command
  ↓
Slurm
  ↓
synchronization
  ↓
cache commit
  ↓
event
```

This preserves the Phase 4 invariant:

> An event MUST NOT describe state that has not been committed to the authoritative cache.

# 30. Package responsibilities

Recommended backend package boundaries:

```text
internal/
  adapter/
  cache/
  command/
  context/
  capability/
  ipc/
  protocol/
  sync/
  event/
  stream/
```

Responsibilities:

### `context`

Server-derived connection identity and `UserContext`.

### `capability`

Capability resolution from authoritative user context.

### `command`

Command controller, command service and command tracking.

### `adapter`

Node-specific translation from application commands to Slurm operations.

### `cache`

Authoritative Node state.

### `sync`

Node synchronization.

### `event`

Committed Node change representation/publication.

### `stream`

Per-connection Node stream management.

### `protocol`

Application framing and message encoding/decoding.

No package should mix:

```text
React code
Cockpit browser code
Slurm authorization
Unix socket transport
```

unless that responsibility explicitly belongs to the package.

# 31. IPC command path

The existing Phase 4 transport remains unchanged:

```text
React
  ↓
cockpit.channel()
  ↓
Cockpit native channel
  ↓
Unix socket
  ↓
cockpit-slurm
```

Phase 5 uses the same application framing established by Phase 4:

```text
[4-byte big-endian length]
        +
[JSON envelope]
```

Do not introduce:

```text
second socket
second channel
command-specific transport
frontend spawn relay
```

The stream remains bidirectional, but Phase 5 defines the application-level command contract over the existing protocol.

---

# 32. Command message direction

The application protocol now has two important directions.

Frontend → backend:

```text
command
```

Backend → frontend:

```text
command-response
event
```

Conceptually:

```text
             ┌───────────────────┐
             │ Cockpit channel   │
             └─────────┬─────────┘
                       │
          ┌────────────┴────────────┐
          │                         │
       command                response/event
          │                         │
          ▼                         ▼
      Backend                    Backend
```

The transport remains bidirectional.

The application semantics remain explicit.

# 33. Command concurrency

Multiple clients may issue commands concurrently.

For example:

```text
User A
    ↓
drain c21

User B
    ↓
resume c21
```

The backend MUST NOT assume that only one command exists globally.

Command execution and state synchronization must remain concurrency-safe.

The authoritative resulting state comes from Slurm and the Node synchronization path.

---

# 34. Command serialization

If a specific Node operation requires serialization, the backend should enforce it explicitly.

Do not rely on:

```text
frontend button disabling
React state
browser timing
```

as concurrency control.

The backend remains responsible for protecting command execution semantics.

---

# 35. Security invariants

Phase 5 MUST preserve these invariants:

### Identity

```text
frontend identity
    ≠
authoritative identity
```

### Authorization

```text
frontend permission
    ≠
backend authorization
```

### Command execution

```text
frontend
    ≠
Slurm execution environment
```

### State

```text
command result
    ≠
Node state
```

### Events

```text
event
    =
committed cache state
```

### Transport

```text
Cockpit channel
    =
transport/lifecycle
```

not:

```text
Cockpit channel
    =
authorization boundary
```

# 41. Real-cluster integration test

A real Slurm environment should be used for the final Node mutation validation.

Recommended sequence:

```text

2. verify initial Node state
3. submit drain command
4. verify command authorization
5. verify command response
6. wait for Node synchronization
7. verify Node event
8. verify NodeProvider state
9. submit resume command
10. verify command response
11. verify Node event
```

Use a dedicated test Node whenever possible.

Do not run destructive commands such as reboot/power operations as part of ordinary automated tests.

The architectural proof required by Phase 5 is:

```text
One resource:

    NodeCache

One transport:
    Cockpit native channel

    Slurm → Synchronizer → Cache → Event → Frontend
```

Phase 6 can then extract the genuinely reusable mechanisms from:

```text

Node Authorization
```

and generalize them into the Resource System.

```text
      Query        Events       Commands
```

Phase 6 may then generalize:

```text

Job
User
Account
Cluster
Partition
Reservation
```

without assuming that all resource models are identical.

The resource-specific canonical models remain resource-specific.

The reusable infrastructure should be extracted around them.

The architectural principle remains:

> Frontend services are transport/client abstractions, not business-logic services.

The backend remains the owner of resource state, synchronization, command execution, authorization, and resource semantics.
