# cockpit-slurm Implementation Phase 5 — Node Commands and Authorization

## 1. Purpose

Phase 5 extends the completed Phase 4 Node live-stream vertical slice with controlled Node mutation.

Phase 3 established:

```text
Slurm
  ↓
Node Adapter
  ↓
Node Cache
  ↓
Node Query Service
  ↓
IPC
  ↓
NodeProvider
  ↓
NodeTable
```

Phase 4 established:

```text
Slurm
  ↓
NodeSynchronizer
  ↓
Node Cache
  ↓
Node Change
  ↓
Node Stream Registry
  ↓
Unix socket
  ↓
Cockpit native channel
  ↓
NodeProvider
  ↓
NodeTable
```

Phase 5 adds:

```text
React
  ↓
Application Command
  ↓
IPC
  ↓
Command Controller
  ↓
UserContext
  ↓
Capability Resolver
  ↓
Authorization
  ↓
Node Command Service
  ↓
Node Command Adapter
  ↓
Slurm
  ↓
Node Synchronizer
  ↓
Node Cache
  ↓
Node Change
  ↓
Cockpit native channel
  ↓
NodeProvider
  ↓
NodeTable
```

The primary objective is to prove that a frontend command can safely mutate Slurm state and that the resulting frontend state is obtained from the authoritative backend cache and event stream rather than from frontend assumptions.

The fundamental rule is:

```text
command succeeds
      ≠
frontend guesses new state
```

Instead:

```text
command
  ↓
Slurm mutation
  ↓
resource synchronization
  ↓
cache update
  ↓
Node event
  ↓
frontend state update
```

Phase 5 is therefore the first complete **read + synchronize + mutate + authorize** Node vertical slice.

### Phase 5 plan to enforce this sequence:

1. Protocol reconciliation: retain v1 command fields and status/error contracts.
2. Transport prerequisite: shared identity-bearing connection initialization, bidirectional dispatch, and serialized writes.
3. Registry and authorization: OperationSpec, RegistryEntry, HandlerRegistry, and GlobalRegistry.
4. Command ledger: persistence, atomic deduplication, retention, and restart recovery.
5. Capabilities and UI: server-derived capability delivery and Node action controls.
6. End-to-end tests: five users, transport identity, accepted/status/error messages, duplicate commands, restart recovery, and authoritative Node synchronization.

The registry framework can be extensible, but Phase 5 should still implement only node.drain and node.resume. The transport, identity, and ledger prerequisites should be completed before enabling those operations.

# 2. Core architectural decisions

## 2.1 Phase 5 remains Node-focused

Phase 5 MUST implement commands for the Node resource only.

Do not use Phase 5 to implement:

```text
Jobs
Users
Accounts
Reservations
Partitions
Clusters
```

Do not generalize the entire Resource System during this phase.

The proven sequence is:

```text
Phase 3
    Node Query
       ↓
Phase 4
    Node Live State
       ↓
Phase 5
    Node Commands + Authorization
       ↓
Phase 6
    Resource System Generalization
```

Node remains the reference resource.

---

## 2.2 Backend authorization is authoritative

The backend MUST enforce authorization.

The frontend may hide or disable controls, but frontend visibility is never a security boundary.

For example:

```text
Frontend
    ↓
"Drain Node" button
    ↓
command request
    ↓
backend authorization
    ↓
allowed / denied
```

The backend MUST NOT trust:

```text
frontend role
frontend username
frontend capability
frontend admin flag
frontend-selected account
```

The authoritative identity comes from the server-side connection.

---

## 2.3 Server-derived identity

The Cockpit-user-to-Unix-socket-credentials mapping is a prerequisite to command authorization; the presence of `SO_PEERCRED` code alone does not prove that mapping.

Before using a connection's `UserContext` for authorization, Phase 5 MUST validate on the target Cockpit installation that the observed peer UID/GID corresponds to the authenticated Cockpit user. Reuse `connection.NewConnection` or an equivalent shared connection-initialization path for both stream and command handling so command requests cannot bypass peer identity construction.

Conceptually:

```text
Cockpit authenticated user
        ↓
Unix socket connection
        ↓
SO_PEERCRED
        ↓
UID / GID
        ↓
Linux user
        ↓
Slurm user lookup
        ↓
UserContext
```

The backend MUST derive the requesting identity from the connection.

A command request MUST NOT be allowed to override:

```text
username
UID
GID
AdminLevel
Coordinator
Capabilities
```

The command payload identifies the requested operation, not the identity of the caller.

The authenticated-user-to-peer-credentials validation is an explicit Phase 5 gate. Until it passes, Node commands MUST NOT be enabled. Add an acceptance test that exercises a real Cockpit connection and verifies the authenticated Cockpit account against the server-observed Unix peer UID/GID.

---

## 2.4 UserContext is request context, not frontend state

The backend `UserContext` represents the authenticated caller.

Conceptually:

```text
UserContext
├── Username
├── UID
├── GID
├── AdminLevel
├── Coordinator
├── Accounts
└── Capabilities
```

The exact implementation may evolve with the existing codebase.

The important boundary is:

```text
Connection identity
        ↓
UserContext
        ↓
Capability Resolver
        ↓
Authorization
```

The frontend may receive a safe representation of the user's capabilities, but it MUST NOT become the authority for those capabilities.

## 2.5 Define capability delivery to React

Add a minimal server-derived capability request/response over the existing transport. For example, a capabilities-request can receive a capabilities response:
{
  "protocol": "cockpit-slurm",
  "version": "1.0",
  "messageId": "msg-cap-1",
  "type": "capabilities",
  "timestamp": "2026-10-15T01:00:00Z",
  "payload": {
    "nodes.drain": true,
    "nodes.resume": true
  }
}

This is a proposed new v1 message type, not an existing contract. Document it and add protocol tests before implementation.
The backend derives capabilities from the authenticated UserContext and registry. React uses them to display or disable actions. The backend must reauthorize every command regardless of the capability response. If capability retrieval fails, disable the controls until it succeeds.

## 2.6 Settle durable command-ledger storage and retention

Use a local SQLite database for the Phase 5 command ledger, using a pure-Go SQLite driver if avoiding CGO is important.
Proposed defaults:
- Database: /var/lib/cockpit-slurm/commands.db
- Access: owned by cockpit-slurm:cockpit-slurm, with restrictive permissions.
- Retention: 30 days for command records and idempotency keys.
- Uniqueness: authenticated caller identity plus commandId.
- Same ID and same request: return the existing status/result without re-execution.
- Same ID and different request: return command-id-conflict.
- On restart, any record left in running with an uncertain execution outcome becomes unknown; never automatically execute it again.
The ledger must reserve a command ID atomically before dispatch. Document that deduplication is guaranteed only within the 30-day retention window; clients must not blindly retry expired command IDs. Keep the database schema versioned and test restart recovery.
Acceptance: deduplication and uncertain-outcome handling survive daemon restarts.

# 5. Architectural invariants

## 5.1 Backend remains authoritative

The backend remains authoritative for:

```text
identity
authorization
command execution
Node state
generation
events
```

The frontend is responsible for:

```text
command initiation
presentation
loading state
success/error presentation
```

It is NOT authoritative for the resulting Node state.

---

## 5.2 Commands do not directly modify the frontend cache

After a successful command:

```text
DO NOT:

command
  ↓
React
  ↓
mutate Node state directly
```

Instead:

```text
command
  ↓
Slurm
  ↓
NodeSynchronizer
  ↓
NodeCache
  ↓
NodeChange
  ↓
NodeProvider
```

This guarantees that the displayed state represents observed Slurm state.

---

## 5.3 Successful command does not imply immediate state change

A successful Slurm command means that Slurm accepted the operation.

It does not necessarily mean that the next synchronized Node snapshot already contains the expected state.

Therefore:

```text
command response
    =
command execution result
```

and:

```text
Node event
    =
observed authoritative state
```

These are separate concepts.

---

## 5.4 Command response and Node event are separate

A command response reports command execution.

A Node event reports resource state.

For example:

```text
CommandResponse
    commandId: "cmd-123"
    status: "succeeded"
```

followed later by:

```text
Event
    resource: "node"
    event: "updated"
    generation: 44
```

The frontend MUST NOT require the command response to contain the complete updated Node object.

---

# 6. User identity

## 6.1 Peer credentials

The IPC connection already obtains peer credentials in the backend.

Phase 5 MUST use the shared connection-initialization path (currently `connection.NewConnection` or an equivalent) rather than accepting identity from the command payload. Command handling and Node streaming MUST use that same path.

Conceptually:

```text
Unix socket
    ↓
SO_PEERCRED
    ↓
uid
gid
pid
```

The exact credentials available should follow the platform implementation.

---

## 6.2 Linux user lookup

The backend resolves the peer UID to the corresponding Linux user.

Conceptually:

```text
UID
 ↓
OS user database
 ↓
username
```

Failure to resolve the UID to a Linux user MUST reject command requests for that connection with an `identity-unavailable` error and MUST prevent command authorization. An empty username is not an identity and MUST never be authorized. The backend MUST NOT defer this condition to capability resolution or treat it as an ordinary user.

Do not fall back to:

```text
frontend username
request.username
anonymous
root
```

---

## 6.3 Slurm user lookup

The resolved Linux username is used to obtain the corresponding Slurm user information.

The Slurm user context may contain information such as:

```text
username
AdminLevel
coordinator
accounts
```

The implementation MUST use the existing Slurm account/user interfaces rather than duplicating Slurm authorization semantics in React.

Missing Slurm user information, an unresolved `AdminLevel`, or a failed Slurm user lookup MUST deny Node mutations by default. These conditions MUST NOT be interpreted as `AdminLevel=none` and then handled by a permissive fallback.

---

# 7. AdminLevel and capability model

## 7.1 AdminLevel

Phase 5 introduces the backend mapping from Slurm user information to an application-level authorization context.

Conceptually:

```text
Slurm user
    ↓
AdminLevel
    ↓
capabilities
```

Use the canonical Slurm `AdminLevel` values from the User Context contract: `none`, `operator`, and `admin`. Only the exact resolved value `admin` grants the Phase 5 Node mutation capabilities.

Do not create frontend-only AdminLevel values that have no backend meaning.

`nodes.drain` and `nodes.resume` MUST be granted only when the authenticated Linux identity resolves to a Slurm user whose `AdminLevel` is `admin`. `operator` does not grant either capability. Coordinator relationships do not grant Node administration; coordinators remain relevant to future account-scoped operations. A separate, more permissive application policy is out of scope for Phase 5 and MUST NOT be inferred.

The backend capability check is mandatory. Slurm's own authorization and execution result are an additional enforcement layer, not a replacement for the backend check. The implementation MUST document and test the Slurm execution identity used by the adapter. If commands execute as a privileged daemon identity, Slurm's result is not proof that Slurm independently authorized the requesting Linux user; the backend Admin-only policy remains authoritative.

---

## 7.2 Capability Resolver

The Capability Resolver translates authoritative user information into explicit capabilities.

Example capability names:

```text
nodes.drain
nodes.resume
```

Only capabilities required by the implemented Node commands should be introduced in Phase 5.

Avoid prematurely creating capabilities for resources that are not implemented.

---

## 7.3 Capability checks

Authorization should be expressed in terms of capabilities.

For example:

```text
Node drain
    ↓
requires:
    nodes.drain
```

and:

```text
Node resume
    ↓
requires:
    nodes.resume
```

The command service MUST NOT rely only on AdminLevel comparisons.

A preferred decision path is:

```text
UserContext
    ↓
Capability Resolver
    ↓
required capability
    ↓
Authorization
```

### 7.4 Operation registry

### 7.4 Operation registry

Phase 5 MUST use a backend-owned operation registry as the authoritative list of supported semantic operations. The client selects the generic Node update command; the backend derives the semantic operation from its validated state parameter:

```text
resource=node, command=update, state=DRAIN
  → OperationID=node.drain

resource=node, command=update, state=RESUME
  → OperationID=node.resume
```

These stable operation IDs describe application intent, not Slurm command-line syntax. Both entries may share trusted handler `node.set_state`. `OperationID`, handler, executable, arguments, role, and authorization rule are backend-owned and MUST NOT be supplied or overridden by the client.

The registry is the dispatch, validation, and authorization contract. Each entry declares operation intent, IPC resource/command, target and parameter schemas, minimum role, optional authorization rule, trusted handler ID, and optional semantic validator ID. Every request MUST be resolved to exactly one entry, validated, authorized, and only then dispatched. Unknown operation mappings and parameter names MUST be rejected.

Recommended conceptual model (adapt names to existing project types; do not duplicate `UserContext`, `CommandRequest`, `CommandResult`, or role types):

```go
type ParameterType string

const (
  ParamString  ParameterType = "string"
  ParamEnum    ParameterType = "enum"
  ParamInteger ParameterType = "integer"
  ParamBoolean ParameterType = "boolean"
)

type ParameterSpec struct {
  Type          ParameterType
  Required      bool
  MinLength     int
  MaxLength     int
  AllowedValues []string
}

type RegistryEntry struct {
  OperationID       string
  Resource          string
  Command           string
  MinRole           SlurmRole
  AuthorizationRule string
  TargetSchema      map[string]ParameterSpec
  ParameterSchema   map[string]ParameterSpec
  HandlerID         string
  ValidatorID       string
}

type Handler func(
  ctx context.Context,
  caller UserContext,
  operation RegistryEntry,
  req CommandRequest,
) (CommandResult, error)

var HandlerRegistry = map[string]Handler{
  "node.set_state": handleNodeSetState,
}
```

`GlobalRegistry` MUST be keyed by `OperationID` for direct lookup. If a slice is used instead, startup validation MUST reject duplicate IDs. Registry iteration MUST NOT determine authorization or dispatch order. Entries are immutable after initialization.

Startup validation MUST reject mismatched map keys, missing required operation mappings, unresolved handler or validator IDs, invalid roles, unknown authorization rules, unsupported parameter types, and internally inconsistent constraints. Client fields MUST never select a handler or validator.

### 7.5 Registry and handler responsibilities

- `ParameterSpec` declares an allowed field's primitive type and field-level constraints. The validator rejects missing required fields, wrong JSON types, unknown fields, unsupported types, and invalid values without coercion.
- `RegistryEntry` declares one semantic operation and its authorization contract. `MinRole` is a coarse threshold, not a complete decision when `AuthorizationRule` is present.
- `HandlerRegistry` maps trusted fixed handler IDs to Go functions. A client-supplied handler ID MUST never be accepted.
- `GlobalRegistry` is the single backend source of truth for supported operations. Frontend metadata may be generated or mirrored later but is never authoritative for permissions.
- Use typed request structures after the protocol boundary where practical; do not propagate `map[string]any` through command execution.

The shared `node.set_state` handler MUST derive its state from the trusted registry operation: `node.drain` maps only to `State=DRAIN`, and `node.resume` maps only to `State=RESUME`. It MUST reject unsupported operation IDs/actions and MUST NOT accept an unrestricted state from the client.

### 7.6 Authorization fields and Slurm roles

Use canonical Slurm `AdminLevel` values: `none`, `operator`, and `admin`. `RoleAdmin` maps only from a successfully resolved Slurm user with `AdminLevel=Administrator`; `RoleOperator` maps from `AdminLevel=Operator`; `RoleNone` maps from `AdminLevel=None`. Missing records, unknown values, lookup failures, or failed identity resolution MUST fail closed.

Coordinator is an account-scoped relationship, not a numeric role between None and Operator, and does not grant Node administration. For Phase 5, both Node operations require `RoleAdmin` and `AuthorizationRule: "admin_only"`. Operator, Coordinator-only status, and direct job ownership do not grant Node mutation.

The authorization engine MUST:

1. validate the request structure and generic resource/command;
2. derive `OperationID` from the validated `state` and resolve it in `GlobalRegistry`;
3. validate the complete target and parameter set against that entry;
4. evaluate `MinRole` against server-derived `UserContext`;
5. evaluate the named authorization rule against trusted caller and resource context;
6. deny on unknown roles/rules, missing context, or evaluation errors;
7. dispatch only after validation and authorization pass.

An unknown authorization rule MUST NOT allow access. Startup registry validation MUST fail for unknown handlers, validators, parameter types, roles, or authorization rules.

### 7.7 Transport refactor prerequisite — shared bidirectional connection

Phase 5 commands MUST NOT be enabled on a stream path that bypasses shared connection initialization or stops reading after a valid subscription. Before implementing commands, inspect/refactor the actual `internal/ipc/server.go`, connection initializer, stream registration, message codec, and Node stream registry. Node streams and commands MUST use the same authenticated connection path and one serialized writer.

The required lifecycle is:

```text
Unix socket accept
  ↓
shared Connection initialization
  ↓
SO_PEERCRED and Linux UID resolution
  ↓
fail-closed identity construction
  ↓
register connection
  ↓
persistent framed-message read loop
  ↓
message dispatcher
  ├── stream/subscription messages
  └── command request
  ↓
one serialized outbound writer
  ↓
Unix socket
```

Initialization MUST retrieve peer credentials and resolve UID to a non-empty Linux username. Failure at either step rejects and closes the connection. Do not construct an empty-username `UserContext` or fall back to frontend identity, anonymous identity, or a privileged default. Build `UserContext` from trusted connection identity and authoritative Slurm user information; missing Slurm records, lookup failures, and unknown `AdminLevel` values fail closed for mutation.

`SO_PEERCRED` alone does not prove that the Unix UID is the authenticated Cockpit browser user. Before commands are enabled, a target-installation integration test MUST establish that the observed peer UID/GID corresponds to the authenticated Cockpit account. If this mapping cannot be demonstrated, commands remain disabled.

Stream registration MUST NOT take ownership of the socket read loop or prevent subsequent command messages from being read. Dispatch each decoded message on the initialized connection, reusing existing codec, logging, cancellation, registration, and error-handling conventions. Malformed frames, EOF, write failures, and cancellation MUST clean up the connection and subscriptions.

All server-originated messages for one connection—including snapshots, Node changes, command responses/statuses, and errors—MUST pass through one serialized writer. Use a bounded outbound queue or equivalent single-writer design. Define backpressure explicitly: terminate a connection that cannot keep up and clean up subscriptions rather than interleaving frames or silently dropping authoritative Node events. Shutdown MUST NOT panic when the queue is closed. Retain existing four-byte big-endian framing and message-size limits; do not add another socket, channel, bridge, or `cockpit.spawn()` path.

# 8. Node command model

Phase 5 reuses the existing IPC v1 envelope and four-byte big-endian framing. The payload uses the generic Node update command; `parameters.state` selects the semantic operation. Do not add a second envelope.

Drain request:

```json
{
  "protocol": "cockpit-slurm",
  "version": "1.0",
  "messageId": "msg-001",
  "type": "command",
  "timestamp": "2026-10-16T10:00:00Z",
  "payload": {
    "commandId": "cmd-123",
    "resource": "node",
    "command": "update",
    "target": { "nodeName": "c21" },
    "parameters": {
      "state": "DRAIN",
      "reason": "scheduled maintenance"
    }
  }
}
```

Resume request:

```json
{
  "protocol": "cockpit-slurm",
  "version": "1.0",
  "messageId": "msg-002",
  "type": "command",
  "timestamp": "2026-10-16T10:01:00Z",
  "payload": {
    "commandId": "cmd-124",
    "resource": "node",
    "command": "update",
    "target": { "nodeName": "c21" },
    "parameters": { "state": "RESUME" }
  }
}
```

`messageId` identifies one IPC request and is echoed for response correlation. `commandId` identifies one logical command and is the idempotency key. The client MUST NOT send `operationId`, `HandlerID`, role, capability, executable path, shell command/template, or raw argument array. Unknown fields MUST be rejected. Missing or unsupported `state` MUST be rejected before handler/Slurm execution. These payloads belong in the existing protocol definitions and MUST NOT introduce a second envelope.

## Parameter schemas and validation

Keep validation declarative and separate from validation execution. `ParameterSpec` defines primitive types and field constraints; `RegistryEntry` declares accepted target and parameter schemas; a validator enforces the schema; operation-specific validators check semantics and trusted resource context.

| Field | Required validation |
|---|---|
| `resource` | Exactly `node`. |
| `command` | Exactly `update`. |
| `target.nodeName` | Required non-empty string, maximum 255 UTF-8 bytes subject to compatibility with the existing Node model and Slurm naming rules, and exact match to one Node in the authoritative cache. Reject ranges, lists, `ALL`, malformed names, and unknown nodes. |
| `parameters.state` | Required enum; only `DRAIN` and `RESUME` are supported. |
| `parameters.reason` | Required for `DRAIN`; trim surrounding whitespace for emptiness checks; non-empty; maximum 256 UTF-8 bytes; reject NUL and disallowed control characters. |
| Resume parameters | `reason` is rejected for `RESUME` unless explicitly added to this contract. |
| Unknown fields/types | Reject unknown fields and incorrect JSON types; do not coerce. Reject duplicate JSON keys if the selected decoder otherwise accepts ambiguous duplicates. |

Validate the target against the actual canonical Node cache and do not invent a conflicting Node-name grammar. First validate the generic command, target, and state discriminator; derive `node.drain` or `node.resume`; then validate the complete request against that operation's registry schema. Validation failures MUST NOT invoke a handler or Slurm. Perform authorization before any privileged execution and avoid disclosing sensitive target details to unauthorized callers.

# 10. Command Controller

The Command Controller is the IPC/application boundary for command requests. It MUST resolve the generic request to the trusted registry entry, obtain the connection's server-derived `UserContext`, validate the request, call backend authorization, and dispatch by the entry's trusted `HandlerID`. It MUST NOT invoke a handler based on client-supplied handler ID, shell command, executable path, or argument array.

The mandatory request path is:

```text
IPC v1 command
  ↓
validate structure and resource=node, command=update
  ↓
validate target and state; derive node.drain or node.resume
  ↓
resolve GlobalRegistry entry and validate complete schema
  ↓
server-derived UserContext
  ↓
MinRole + AuthorizationRule evaluation
  ├── denied/error → canonical error; no handler invocation
  └── allowed
      ↓
commandId/messageId deduplication and lifecycle tracking
      ↓
HandlerRegistry lookup by trusted HandlerID
      ↓
typed command handler builds fixed Slurm argv
      ↓
controlled execution boundary
      ↓
command result + normal Node synchronization
```

The Controller MUST NOT execute Slurm commands, contain Slurm syntax, determine Linux identity, or implement React logic.

## Command Controller
The Command Controller is the IPC/application boundary for command requests.

Its responsibilities are:

1. validate the application message and generic Node update structure;
2. resolve the semantic operation from the validated state discriminator;
3. obtain the connection `UserContext`;
4. validate the target and operation-specific parameters;
5. resolve required capability and evaluate role/rule authorization;
6. enforce request correlation and command idempotency;
7. dispatch only through the trusted handler registry and encode the canonical response/error.

It MUST NOT:

* execute Slurm commands directly;
* contain Node-specific Slurm syntax;
* determine Linux identity;
* implement React logic.

Conceptually:

```text
IPC
 ↓
Command Controller
 ├── validate
 ├── UserContext
 ├── capability
       ↓
Command Service
```

# 11. Command Service

The Node Command Service owns application-level command execution.

Responsibilities:

```text
validate command semantics
        ↓
authorize
        ↓
construct command request
        ↓
invoke adapter
        ↓
track result
        ↓
return command result
```

The service MUST remain independent of React and Cockpit channel details.

# 12. Node Command Adapter

The Node Command Adapter is responsible for translating the application command into a Slurm operation.

For example:

```text
Application:
  resource=node, command=update
  target.nodeName=c21, state=DRAIN, reason=maintenance

Adapter:
  scontrol update NodeName=c21 State=DRAIN Reason=maintenance
```

The adapter owns:

```text
Slurm CLI syntax
Slurm command arguments
Slurm exit status
Slurm stderr/stdout interpretation
```

The handler MUST use a fixed absolute executable path and separate validated arguments through `exec.CommandContext` or the existing controlled execution boundary. Never use `sh -c`, shell interpolation, or a client-supplied command template. The derived operation fixes the state: `node.drain` maps only to `State=DRAIN`; `node.resume` maps only to `State=RESUME`. Pass `NodeName=<name>`, `State=<fixed-state>`, and for drain `Reason=<reason>` as separate argv elements; the complete `Reason=...` value MUST remain one argument, including spaces. Reject invalid values before execution.

Keep the daemon unprivileged. If execution requires elevated privileges, use a narrowly scoped root-owned helper with a fixed operation interface. Never grant unrestricted sudo access to `scontrol` or run arbitrary client arguments as `SlurmUser`. Backend authorization of the original requester MUST happen before invoking any helper; a helper's Linux identity is not proof that the requester was authorized. Document and test the execution identity used by the adapter.

The adapter MUST NOT own:

```text
React state
Cockpit channel state
frontend authorization
UserContext construction
```

# 13. Command validation

Command validation uses the declarative parameter schemas and rules in Section 8. It MUST validate `resource=node`, `command=update`, exactly one `target.nodeName`, supported state, state-specific parameters, field types and lengths, unknown/duplicate JSON keys, and the exact target's presence in the authoritative Node cache. Then derive the semantic operation and validate its complete registry schema. Validation failures MUST NOT invoke a handler or Slurm. Do not coerce malformed values or accept client-selected operation/handler metadata.

# 14. Authorization flow

The mandatory authorization flow is:

```text
Command Request
      ↓
Shared initialized connection + server-derived UserContext
      ↓
Capability Resolver
      ↓
Required Capability
      ↓
MinRole + AuthorizationRule
      │
      ├── denied → error response
      │
      └── allowed
             ↓
       trusted HandlerRegistry
         ↓
```

An authorization failure MUST be rejected before invoking Slurm.

For example:

```text

    ↓

    ↓

    ↓

```

An authorized Slurm administrator:

```text

    ↓

    ↓
ALLOWED
    ↓
Slurm
```

# 15. Command IDs

Every new logical command MUST include a unique `commandId`, generated by the client before the first send and reused unchanged for retries of that command. The backend MUST validate and track it.

Example:

```text
commandId = "cmd-01..."
```

The command ID is distinct from the protocol `messageId`.

Conceptually:

```text
messageId
    =
identity of one IPC request message; the response echoes this value

commandId
    =
identity/idempotency key of one logical command execution
```

`messageId` is used only for request/response correlation and retransmission detection on the same connection. `commandId` is used for command lifecycle tracking and deduplication across requests, including retries that use a new `messageId`. A `commandId` MUST be scoped to the authenticated caller so another user cannot query or retrieve its result.

# 16. Command lifecycle

The command lifecycle should be explicit.

Conceptually:

```text
received
   ↓
validated
   ↓
authorized
   ↓
running
   ↓
succeeded
```

or:

```text
received
   ↓
validated
   ↓
authorized
   ↓
running
   ↓
failed
```

Authorization failure is distinct:

```text
received
   ↓
validated
   ↓
denied
```

If execution may have reached Slurm but the backend cannot determine the result (for example, a timeout after dispatch), the terminal/observable status MUST be `unknown`, not `failed`. The implementation may use additional intermediate states, but these lifecycle meanings MUST remain explicit.

# 17. Command response

A successful command response contains command-level information rather than pretending to be a Node snapshot. The only externally visible command statuses are `running`, `succeeded`, `failed`, `denied`, and `unknown`. `received`, `validated`, and `authorized` MAY be internal lifecycle states, but MUST NOT be presented as completed execution results. Authorization denial MUST be returned as a canonical `error` envelope; its corresponding command record/status is `denied`. A successful response has this shape:

```json
{
  "protocol": "cockpit-slurm",
  "version": "1.0",
  "messageId": "msg-001",
  "type": "command-response",
  "timestamp": "2026-10-09T10:00:01Z",
  "payload": {
    "commandId": "cmd-123",
    "resource": "node",
    "command": "update",
    "target": { "nodeName": "c21" },
    "parameters": { "state": "DRAIN" },
    "status": "succeeded"
  }
}
```

The response MUST echo the request `messageId`. Its payload MUST contain `commandId`, `resource`, the generic request `command` (`update`), and `status`; include the validated target and state where supported by the existing response schema. A `command-response` reports the current command status; subsequent status changes MAY use `command-status`, correlated by `commandId` and carrying the same status values. The response MUST NOT claim that the Node state has changed.

Errors MUST use the canonical Error Model payload and preserve the request `messageId`; when applicable, include `commandId` and the Node resource/target. At minimum, use stable codes for `identity-unavailable`, `user-lookup-failed`, `authorization-denied`, `command-id-conflict`, `message-id-conflict`, `command-outcome-unknown`, and `slurm-command-failed`, with the corresponding canonical category, message, and retryable value. Do not expose raw command-line implementation details.

For example:

```json
{
  "protocol": "cockpit-slurm",
  "version": "1.0",
  "messageId": "msg-001",
  "type": "error",
  "timestamp": "2026-10-09T10:00:01Z",
  "payload": {
    "code": "authorization-denied",
    "category": "authorization-error",
    "message": "Not authorized to drain this Node",
    "retryable": false,
    "commandId": "cmd-123"
  }
}
```

For an unknown outcome, report status `unknown` (and `command-outcome-unknown` where represented as an error), set retryable to false, do not automatically resubmit the mutation, and trigger or await normal Node synchronization to reconcile the actual Slurm state. The command result remains unknown until the authoritative state is observed; observed Node state does not rewrite the historical execution result.

# 19. Command timing

A successful command may be followed by the corresponding Node event asynchronously.

Therefore:

```text
T1 command submitted
T2 command accepted
T3 command response returned
T4 Slurm state changes
T5 NodeSynchronizer observes change
T6 NodeCache commits change
T7 Node event published
T8 NodeProvider applies event
```

The frontend MUST tolerate this separation.

Do not block the command response waiting indefinitely for the Node event.

# 20. Idempotence

The backend MUST enforce both message-level retransmission handling and logical command deduplication:

| Situation | Required backend behavior |
| --- | --- |
| Same `messageId`, same request, same connection | Return the recorded response or current status; do not execute again. |
| Same `messageId`, different request, same connection | Reject with `message-id-conflict`; do not execute. |
| Same caller and `commandId`, same command payload | Return the existing status/result; do not execute again. This also applies when the retry has a new `messageId`. |
| Same caller and `commandId`, different command payload | Reject with `command-id-conflict`; do not execute. |
| New `commandId` | Validate, authorize, record, and execute normally. |
| Existing command whose outcome is unknown | Return `unknown`; do not execute again automatically. Reconcile through Slurm/Node synchronization. |

Compare canonicalized validated payloads (or an equivalent collision-resistant payload fingerprint) when deciding whether a reused ID has the same request. Do not include client-supplied identity or capability fields in that payload.

Command records MUST be durably available for deduplication for the lifetime of the command and its retained result, including across daemon restarts. Persist the minimum command ledger needed to recognize accepted IDs, their authenticated caller, canonical payload fingerprint, and status/result. The retention period MUST be explicit; an ID MUST NOT become reusable while a retry could still reasonably arrive. After a restart, any accepted command whose outcome cannot be proven MUST be reported as `unknown` and MUST NOT be automatically re-executed. This is command tracking required for safe mutation, not a requirement for a comprehensive audit subsystem.

For duplicate comparison, canonicalize the request semantics (protocol version, message type, and payload); exclude envelope timestamps and the correlation `messageId`. Thus a retransmission with the same `messageId` and same command request remains the same request even if the timestamp differs.

# 26. Node UI behavior

The Node table MUST expose the Phase 5 per-Node commands through a rightmost Actions column using PatternFly's table action-cell pattern:

https://www.patternfly.org/components/table#actions

```text

```

A command control should:

1. validate required user input;
2. submit the command;
3. display command progress;
4. display command failure if rejected;
5. wait for the normal Node event/state update;
6. render the resulting authoritative Node state.

Keep command status separate from Node state. While a command for a Node is pending or has an unknown outcome, prevent accidental duplicate submissions for that Node and clearly present its command status.
