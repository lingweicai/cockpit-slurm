# cockpit-slurm Implementation Phase 5 — Node Commands and Authorization

## 1. Purpose

Phase 5 extends the completed Phase 4 Node live-stream vertical slice with controlled Node mutation.

Phase 3 established:

```text
Slurm
  ↓
Node Adapter
  ↓
Node Cache
  ↓
Node Query Service
  ↓
IPC
  ↓
NodeProvider
  ↓
NodeTable
```

Phase 4 established:

```text
Slurm
  ↓
NodeSynchronizer
  ↓
Node Cache
  ↓
Node Change
  ↓
Node Stream Registry
  ↓
Unix socket
  ↓
Cockpit native channel
  ↓
NodeProvider
  ↓
NodeTable
```

Phase 5 adds:

```text
React
  ↓
Application Command
  ↓
IPC
  ↓
Command Controller
  ↓
UserContext
  ↓
Capability Resolver
  ↓
Authorization
  ↓
Node Command Service
  ↓
Node Command Adapter
  ↓
Slurm
  ↓
Node Synchronizer
  ↓
Node Cache
  ↓
Node Change
  ↓
Cockpit native channel
  ↓
NodeProvider
  ↓
NodeTable
```

The primary objective is to prove that a frontend command can safely mutate Slurm state and that the resulting frontend state is obtained from the authoritative backend cache and event stream rather than from frontend assumptions.

The fundamental rule is:

```text
command succeeds
      ≠
frontend guesses new state
```

Instead:

```text
command
  ↓
Slurm mutation
  ↓
resource synchronization
  ↓
cache update
  ↓
Node event
  ↓
frontend state update
```

Phase 5 is therefore the first complete **read + synchronize + mutate + authorize** Node vertical slice.

# 2. Core architectural decisions

## 2.1 Phase 5 remains Node-focused

Phase 5 MUST implement commands for the Node resource only.

Do not use Phase 5 to implement:

```text
Jobs
Users
Accounts
Reservations
Partitions
Clusters
```

Do not generalize the entire Resource System during this phase.

The proven sequence is:

```text
Phase 3
    Node Query
       ↓
Phase 4
    Node Live State
       ↓
Phase 5
    Node Commands + Authorization
       ↓
Phase 6
    Resource System Generalization
```

Node remains the reference resource.

---

## 2.2 Backend authorization is authoritative

The backend MUST enforce authorization.

The frontend may hide or disable controls, but frontend visibility is never a security boundary.

For example:

```text
Frontend
    ↓
"Drain Node" button
    ↓
command request
    ↓
backend authorization
    ↓
allowed / denied
```

The backend MUST NOT trust:

```text
frontend role
frontend username
frontend capability
frontend admin flag
frontend-selected account
```

The authoritative identity comes from the server-side connection.

---

## 2.3 Server-derived identity

The Cockpit-user-to-Unix-socket-credentials mapping is a prerequisite to command authorization; the presence of `SO_PEERCRED` code alone does not prove that mapping.

Before using a connection's `UserContext` for authorization, Phase 5 MUST validate on the target Cockpit installation that the observed peer UID/GID corresponds to the authenticated Cockpit user. Reuse `connection.NewConnection` or an equivalent shared connection-initialization path for both stream and command handling so command requests cannot bypass peer identity construction.

Conceptually:

```text
Cockpit authenticated user
        ↓
Unix socket connection
        ↓
SO_PEERCRED
        ↓
UID / GID
        ↓
Linux user
        ↓
Slurm user lookup
        ↓
UserContext
```

The backend MUST derive the requesting identity from the connection.

A command request MUST NOT be allowed to override:

```text
username
UID
GID
AdminLevel
Coordinator
Capabilities
```

The command payload identifies the requested operation, not the identity of the caller.

The authenticated-user-to-peer-credentials validation is an explicit Phase 5 gate. Until it passes, Node commands MUST NOT be enabled. Add an acceptance test that exercises a real Cockpit connection and verifies the authenticated Cockpit account against the server-observed Unix peer UID/GID.

---

## 2.4 UserContext is request context, not frontend state

The backend `UserContext` represents the authenticated caller.

Conceptually:

```text
UserContext
├── Username
├── UID
├── GID
├── AdminLevel
├── Coordinator
├── Accounts
└── Capabilities
```

The exact implementation may evolve with the existing codebase.

The important boundary is:

```text
Connection identity
        ↓
UserContext
        ↓
Capability Resolver
        ↓
Authorization
```

The frontend may receive a safe representation of the user's capabilities, but it MUST NOT become the authority for those capabilities.

# 5. Architectural invariants

## 5.1 Backend remains authoritative

The backend remains authoritative for:

```text
identity
authorization
command execution
Node state
generation
events
```

The frontend is responsible for:

```text
command initiation
presentation
loading state
success/error presentation
```

It is NOT authoritative for the resulting Node state.

---

## 5.2 Commands do not directly modify the frontend cache

After a successful command:

```text
DO NOT:

command
  ↓
React
  ↓
mutate Node state directly
```

Instead:

```text
command
  ↓
Slurm
  ↓
NodeSynchronizer
  ↓
NodeCache
  ↓
NodeChange
  ↓
NodeProvider
```

This guarantees that the displayed state represents observed Slurm state.

---

## 5.3 Successful command does not imply immediate state change

A successful Slurm command means that Slurm accepted the operation.

It does not necessarily mean that the next synchronized Node snapshot already contains the expected state.

Therefore:

```text
command response
    =
command execution result
```

and:

```text
Node event
    =
observed authoritative state
```

These are separate concepts.

---

## 5.4 Command response and Node event are separate

A command response reports command execution.

A Node event reports resource state.

For example:

```text
CommandResponse
    commandId: "cmd-123"
    status: "succeeded"
```

followed later by:

```text
Event
    resource: "node"
    event: "updated"
    generation: 44
```

The frontend MUST NOT require the command response to contain the complete updated Node object.

---

# 6. User identity

## 6.1 Peer credentials

The IPC connection already obtains peer credentials in the backend.

Phase 5 MUST use the shared connection-initialization path (currently `connection.NewConnection` or an equivalent) rather than accepting identity from the command payload. Command handling and Node streaming MUST use that same path.

Conceptually:

```text
Unix socket
    ↓
SO_PEERCRED
    ↓
uid
gid
pid
```

The exact credentials available should follow the platform implementation.

---

## 6.2 Linux user lookup

The backend resolves the peer UID to the corresponding Linux user.

Conceptually:

```text
UID
 ↓
OS user database
 ↓
username
```

Failure to resolve the UID to a Linux user MUST reject command requests for that connection with an `identity-unavailable` error and MUST prevent command authorization. An empty username is not an identity and MUST never be authorized. The backend MUST NOT defer this condition to capability resolution or treat it as an ordinary user.

Do not fall back to:

```text
frontend username
request.username
anonymous
root
```

---

## 6.3 Slurm user lookup

The resolved Linux username is used to obtain the corresponding Slurm user information.

The Slurm user context may contain information such as:

```text
username
AdminLevel
coordinator
accounts
```

The implementation MUST use the existing Slurm account/user interfaces rather than duplicating Slurm authorization semantics in React.

Missing Slurm user information, an unresolved `AdminLevel`, or a failed Slurm user lookup MUST deny Node mutations by default. These conditions MUST NOT be interpreted as `AdminLevel=none` and then handled by a permissive fallback.

---

# 7. AdminLevel and capability model

## 7.1 AdminLevel

Phase 5 introduces the backend mapping from Slurm user information to an application-level authorization context.

Conceptually:

```text
Slurm user
    ↓
AdminLevel
    ↓
capabilities
```

Use the canonical Slurm `AdminLevel` values from the User Context contract: `none`, `operator`, and `admin`. Only the exact resolved value `admin` grants the Phase 5 Node mutation capabilities.

Do not create frontend-only AdminLevel values that have no backend meaning.

`nodes.drain` and `nodes.resume` MUST be granted only when the authenticated Linux identity resolves to a Slurm user whose `AdminLevel` is `admin`. `operator` does not grant either capability. Coordinator relationships do not grant Node administration; coordinators remain relevant to future account-scoped operations. A separate, more permissive application policy is out of scope for Phase 5 and MUST NOT be inferred.

The backend capability check is mandatory. Slurm's own authorization and execution result are an additional enforcement layer, not a replacement for the backend check. The implementation MUST document and test the Slurm execution identity used by the adapter. If commands execute as a privileged daemon identity, Slurm's result is not proof that Slurm independently authorized the requesting Linux user; the backend Admin-only policy remains authoritative.

---

## 7.2 Capability Resolver

The Capability Resolver translates authoritative user information into explicit capabilities.

Example capability names:

```text
nodes.drain
nodes.resume
```

Only capabilities required by the implemented Node commands should be introduced in Phase 5.

Avoid prematurely creating capabilities for resources that are not implemented.

---

## 7.3 Capability checks

Authorization should be expressed in terms of capabilities.

For example:

```text
Node drain
    ↓
requires:
    nodes.drain
```

and:

```text
Node resume
    ↓
requires:
    nodes.resume
```

The command service MUST NOT rely only on AdminLevel comparisons.

A preferred decision path is:

```text
UserContext
    ↓
Capability Resolver
    ↓
required capability
    ↓
Authorization
```

---

# 8. Node command model

Phase 5 introduces an application-level Node command model.

A command uses the existing version 1.0 envelope. The exact request is:

```json
{
  "protocol": "cockpit-slurm",
  "version": "1.0",
  "messageId": "msg-001",
  "type": "command",
  "timestamp": "2026-10-09T10:00:00Z",
  "payload": {
    "commandId": "cmd-123",
    "resource": "node",
    "command": "drain",
    "target": {
      "nodeName": "c21"
    },
    "parameters": {
      "reason": "maintenance"
    }
  }
}
```

For `resume`, `parameters` is an empty object. `reason` is required for `drain` and MUST be validated as a string with a documented maximum length; `nodeName` MUST be validated before invoking Slurm. Reject unknown fields rather than silently ignoring them. The request envelope's `messageId` and this payload's `commandId` are separate identifiers and MUST NOT be used interchangeably; their semantics are defined in Sections 15 and 20. Implement these payloads in the existing protocol definitions (including `message.go` or corresponding typed protocol definitions); do not add a second envelope.

The important separation is:

```text
Envelope
    ↓
command
    ↓
resource = node
    ↓
resource-specific command payload
```

Do not introduce a second command envelope.

# 10. Command Controller

The Command Controller is the IPC/application boundary for command requests.

Its responsibilities are:

1. validate the application message;
2. identify the command;
3. obtain the connection `UserContext`;
4. resolve required capability;
5. invoke authorization;
6. invoke the Node Command Service;
7. return a correlated response.

It MUST NOT:

* execute Slurm commands directly;
* contain Node-specific Slurm syntax;
* determine Linux identity;
* implement React logic.

Conceptually:

```text
IPC
 ↓
Command Controller
 ├── validate
 ├── UserContext
 ├── capability
 ├── authorize
 └── dispatch
       ↓
Command Service
```

---

# 11. Command Service

The Node Command Service owns application-level command execution.

Responsibilities:

```text
validate command semantics
        ↓
authorize
        ↓
construct command request
        ↓
invoke adapter
        ↓
track result
        ↓
return command result
```

The service MUST remain independent of React and Cockpit channel details.

---

# 12. Node Command Adapter

The Node Command Adapter is responsible for translating the application command into a Slurm operation.

For example:

```text
Application:
    node.drain("c21", "maintenance")

Adapter:
    scontrol update Nodename=c21 State=drain Reason=maintenance
```

The adapter owns:

```text
Slurm CLI syntax
Slurm command arguments
Slurm exit status
Slurm stderr/stdout interpretation
```

The adapter MUST NOT own:

```text
React state
Cockpit channel state
frontend authorization
UserContext construction
```

---

# 13. Command validation

Command validation occurs before Slurm execution.

Validate at least:

```text
resource
command
Node identity
required fields
field types
field length
allowed command values
```

For example:

```text
resource != node
    → reject

command != supported Node command
    → reject

missing node
    → reject

invalid Node name
    → reject
```

Validation failures MUST NOT invoke Slurm.

---

# 14. Authorization flow

The mandatory authorization flow is:

```text
Command Request
      ↓
Connection UserContext
      ↓
Capability Resolver
      ↓
Required Capability
      ↓
Authorization
      │
      ├── denied → error response
      │
      └── allowed
             ↓
       Command Service
             ↓
       Node Command Adapter
```

An authorization failure MUST be rejected before invoking Slurm.

For example:

```text
ordinary user
    ↓
nodes.drain
    ↓
DENIED
    ↓
Slurm is NOT called
```

An authorized Slurm administrator:

```text
AdminLevel=admin
    ↓
nodes.drain
    ↓
ALLOWED
    ↓
Slurm
```

# 15. Command IDs

Every new logical command MUST include a unique `commandId`, generated by the client before the first send and reused unchanged for retries of that command. The backend MUST validate and track it.

Example:

```text
commandId = "cmd-01..."
```

The command ID is distinct from the protocol `messageId`.

Conceptually:

```text
messageId
    =
identity of one IPC request message; the response echoes this value

commandId
    =
identity/idempotency key of one logical command execution
```

`messageId` is used only for request/response correlation and retransmission detection on the same connection. `commandId` is used for command lifecycle tracking and deduplication across requests, including retries that use a new `messageId`. A `commandId` MUST be scoped to the authenticated caller so another user cannot query or retrieve its result.

---

# 16. Command lifecycle

The command lifecycle should be explicit.

Conceptually:

```text
received
   ↓
validated
   ↓
authorized
   ↓
running
   ↓
succeeded
```

or:

```text
received
   ↓
validated
   ↓
authorized
   ↓
running
   ↓
failed
```

Authorization failure is distinct:

```text
received
   ↓
validated
   ↓
denied
```

If execution may have reached Slurm but the backend cannot determine the result (for example, a timeout after dispatch), the terminal/observable status MUST be `unknown`, not `failed`. The implementation may use additional intermediate states, but these lifecycle meanings MUST remain explicit.

---

# 17. Command response

A successful command response contains command-level information rather than pretending to be a Node snapshot. The only externally visible command statuses are `running`, `succeeded`, `failed`, `denied`, and `unknown`. `received`, `validated`, and `authorized` MAY be internal lifecycle states, but MUST NOT be presented as completed execution results. Authorization denial MUST be returned as a canonical `error` envelope; its corresponding command record/status is `denied`. A successful response has this shape:

```json
{
  "protocol": "cockpit-slurm",
  "version": "1.0",
  "messageId": "msg-001",
  "type": "command-response",
  "timestamp": "2026-10-09T10:00:01Z",
  "payload": {
    "commandId": "cmd-123",
    "resource": "node",
    "command": "drain",
    "status": "succeeded"
  }
}
```

The response MUST echo the request `messageId`. Its payload MUST contain `commandId`, `resource`, `command`, and `status`. A `command-response` reports the current command status; subsequent status changes MAY use `command-status`, correlated by `commandId` and carrying the same status values. The response MUST NOT claim that the Node state has changed.

Errors MUST use the canonical Error Model payload and preserve the request `messageId`; when applicable, include `commandId` and the Node resource/target. At minimum, use stable codes for `identity-unavailable`, `user-lookup-failed`, `authorization-denied`, `command-id-conflict`, `message-id-conflict`, `command-outcome-unknown`, and `slurm-command-failed`, with the corresponding canonical category, message, and retryable value. Do not expose raw command-line implementation details.

For example:

```json
{
  "protocol": "cockpit-slurm",
  "version": "1.0",
  "messageId": "msg-001",
  "type": "error",
  "timestamp": "2026-10-09T10:00:01Z",
  "payload": {
    "code": "authorization-denied",
    "category": "authorization-error",
    "message": "Not authorized to drain this Node",
    "retryable": false,
    "commandId": "cmd-123"
  }
}
```

For an unknown outcome, report status `unknown` (and `command-outcome-unknown` where represented as an error), set retryable to false, do not automatically resubmit the mutation, and trigger or await normal Node synchronization to reconcile the actual Slurm state. The command result remains unknown until the authoritative state is observed; observed Node state does not rewrite the historical execution result.

# 18. Command execution and synchronization

After successful execution:

```text
Node Command Adapter
        ↓
      Slurm
        ↓
NodeSynchronizer
        ↓
NodeCache.Apply()
        ↓
NodeChange
        ↓
NodeStreamRegistry
        ↓
Cockpit channel
        ↓
NodeProvider
```

The command service MUST NOT directly update `NodeCache` with an assumed state.

For example, after:

```text
drain c21
```

do not execute:

```text
cache.Set(c21.State = "drain")
```

Instead, allow the normal synchronization path to observe the actual Slurm state.

This preserves the Phase 4 invariant that events describe committed authoritative cache state.

---

# 19. Command timing

A successful command may be followed by the corresponding Node event asynchronously.

Therefore:

```text
T1 command submitted
T2 command accepted
T3 command response returned
T4 Slurm state changes
T5 NodeSynchronizer observes change
T6 NodeCache commits change
T7 Node event published
T8 NodeProvider applies event
```

The frontend MUST tolerate this separation.

Do not block the command response waiting indefinitely for the Node event.

---

# 20. Idempotence

The backend MUST enforce both message-level retransmission handling and logical command deduplication:

| Situation | Required backend behavior |
| --- | --- |
| Same `messageId`, same request, same connection | Return the recorded response or current status; do not execute again. |
| Same `messageId`, different request, same connection | Reject with `message-id-conflict`; do not execute. |
| Same caller and `commandId`, same command payload | Return the existing status/result; do not execute again. This also applies when the retry has a new `messageId`. |
| Same caller and `commandId`, different command payload | Reject with `command-id-conflict`; do not execute. |
| New `commandId` | Validate, authorize, record, and execute normally. |
| Existing command whose outcome is unknown | Return `unknown`; do not execute again automatically. Reconcile through Slurm/Node synchronization. |

Compare canonicalized validated payloads (or an equivalent collision-resistant payload fingerprint) when deciding whether a reused ID has the same request. Do not include client-supplied identity or capability fields in that payload.

Command records MUST be durably available for deduplication for the lifetime of the command and its retained result, including across daemon restarts. Persist the minimum command ledger needed to recognize accepted IDs, their authenticated caller, canonical payload fingerprint, and status/result. The retention period MUST be explicit; an ID MUST NOT become reusable while a retry could still reasonably arrive. After a restart, any accepted command whose outcome cannot be proven MUST be reported as `unknown` and MUST NOT be automatically re-executed. This is command tracking required for safe mutation, not a requirement for a comprehensive audit subsystem.

For duplicate comparison, canonicalize the request semantics (protocol version, message type, and payload); exclude envelope timestamps and the correlation `messageId`. Thus a retransmission with the same `messageId` and same command request remains the same request even if the timestamp differs.

# 22. Error model

Command errors should remain distinguishable.

At minimum:

```text
invalid-command
invalid-payload
identity-unavailable
user-lookup-failed
authorization-denied
capability-unavailable
command-id-conflict
message-id-conflict
command-outcome-unknown
command-timeout
slurm-command-failed
internal-error
```

Do not collapse every failure into:

```text
command failed
```

The frontend should be able to distinguish:

```text
not authorized
```

from:

```text
Slurm failed
```

and:

```text
invalid request
```

# 23. Frontend Command Service

Phase 5 adds the frontend command path.

Recommended structure:

```text
src/
  ipc/
    client.ts
    framing.ts
    protocol.ts
    errors.ts

  services/
    resource-service.ts
    command-service.ts

  contexts/
    UserProvider.tsx
    NodeProvider.tsx
```

The existing `command-service.ts` should become the frontend abstraction for command requests.

It is a **transport/client abstraction**, not a second authorization or resource framework.

The service should:

```text
create command request
        ↓
send through existing IPC client
        ↓
await correlated response
        ↓
return command result
```

It MUST NOT:

```text
execute scontrol
calculate AdminLevel

mutate Node cache directly
```

# 24. NodeProvider command integration

`NodeProvider` may expose command operations to Node UI components.

For example:

```text
NodeProvider
    ├── nodes

    ├── stream state
```

The exact API may follow the existing implementation.

```text
    ↓

    ↓
```

and not:

```text
NodeProvider
    ↓
scontrol
```

# 25. Frontend command state

The frontend should distinguish:

```text
command pending
command succeeded
command failed
```

from:

```text
Node state
```

For example:

```text
Node state:
    IDLE

Command:
    drain → pending

Command response:
    succeeded

Node state:
    IDLE

later:

Node event:
    DRAIN

Node state:
    DRAIN
```

This is valid and expected.

Do not display the command as the authoritative resource state.

# 26. Node UI behavior

The Node table MUST expose the Phase 5 per-Node commands through a rightmost Actions column using PatternFly's table action-cell pattern:

https://www.patternfly.org/components/table#actions

Use an `ActionsColumn`/overflow menu in the final cell of each row rather than adding separate Drain and Resume buttons to every row. The action column header is empty, and its cells contain the row-specific menu. Preserve the existing table's compact and responsive behavior, including accessible labels for interactive controls.

The menu may expose commands such as:

```text
Drain
Resume
```

Only show or enable an action when it is applicable to the row's latest observed Node state and available frontend capability information. The frontend MAY use capabilities to hide or disable actions for usability, but this presentation is not an authorization decision. If Node state or capability information is unavailable, do not guess that an action is applicable; disable or omit it and let the backend remain authoritative.

Selecting `Drain` MUST open a form/dialog that collects and validates the required drain reason before submission. Present the target Node name and requested action for confirmation before executing the mutation. `Resume` MUST identify the target Node and may use a confirmation dialog consistent with the existing UI patterns.

A command control should:

1. validate required user input;
2. submit the command;
3. display command progress;
4. display command failure if rejected;
5. wait for the normal Node event/state update;
6. render the resulting authoritative Node state.

Keep command status separate from Node state. While a command for a Node is pending or has an unknown outcome, prevent accidental duplicate submissions for that Node and clearly present its command status. The UI MUST NOT optimistically replace the Node state merely because the command request was accepted; only the normal Node stream updates authoritative state.

# 27. Authorization-aware UI

The frontend may use capability information to improve usability.

For example:

```text
nodes.drain = true
    → show Drain action

nodes.drain = false
    → hide/disable Drain action
```

Apply the same presentation rule to `nodes.resume`. The Node table action menu is a client-side affordance only; it MUST NOT infer or cache authoritative capabilities from a prior action result as a substitute for the current backend decision.

However:

```text
UI allows action
    ≠
backend authorizes action
```

The backend MUST always perform the final authorization check.

This prevents:

```text
modified browser JavaScript
forged IPC request
manual protocol request
```

from bypassing authorization.

# 31. IPC command path

The existing Phase 4 transport remains unchanged:

```text
React
  ↓
cockpit.channel()
  ↓
Unix socket: /run/cockpit-slurm/cockpit-slurm.sock
  ↓
cockpit-slurm
```

This is the Phase 4 native Cockpit channel-to-Unix-socket architecture; Phase 5 MUST NOT introduce a separate channel executable, bridge, socket, or frontend Slurm command path. The backend default path is `DefaultSocketPath` in `internal/ipc/server.go`; `COCKPIT_SLURM_SOCKET_PATH` may override it for configured environments. The transport options and stream payload follow Phase 4's `cockpit.channel()` contract.

Phase 5 uses the same application framing established by Phase 4:

```text
[4-byte big-endian length]
        +
[JSON envelope]
```

Do not introduce:

```text
second socket
second channel
command-specific transport
frontend spawn relay
```

The stream remains bidirectional, but Phase 5 defines the application-level command contract over the existing protocol.

# 33. Command concurrency

Multiple clients may issue commands concurrently.

For example:

```text
User A
    ↓
drain c21

User B
    ↓
resume c21
```

The backend MUST NOT assume that only one command exists globally.

Command execution and state synchronization must remain concurrency-safe.

The authoritative resulting state comes from Slurm and the Node synchronization path.

# 34. Command serialization

If a specific Node operation requires serialization, the backend should enforce it explicitly.

Do not rely on:

```text

React state
browser timing
```

as concurrency control.

The backend remains responsible for protecting command execution semantics.

# 36. Testing strategy

Phase 5 requires unit, integration and end-to-end tests.

Test:

* valid peer UID;

```text
    → nodes.resume
```
