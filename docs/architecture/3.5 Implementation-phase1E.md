# Implementation Phase 1E — Connection, Session, and Identity Foundation

**Status:** Planned
**Phase:** 1E
**Depends on:** Phase 1B, Phase 1C, Phase 1D
**Next phase:** Phase 1F

---

# 1. Purpose

Implement the connection and identity foundation of
`cockpit-slurm-bridge`.

Phase 1E establishes:

- Connection lifecycle management.
- Connection and session identifiers.
- Server-derived Linux peer identity.
- The initial `UserContext` / `SecurityContext`.
- Connection-scoped context propagation.
- Clean connection shutdown.

This phase prepares the bridge for later authorization, resource access,
commands, and subscriptions.

---

# 2. Scope

### In scope

- Wrap each accepted `net.Conn` in a connection object.
- Assign server-generated connection and session IDs.
- Obtain authenticated Unix peer identity.
- Construct a server-owned user context.
- Associate the context with the connection.
- Integrate connection processing with the existing dispatcher.
- Handle connection closure and cleanup.
- Support multiple concurrent connections.
- Add unit and integration tests.

### Out of scope

- Slurm resource models and cache.
- Slurm command execution.
- Resource adapters.
- Command adapters.
- Event bus and subscription manager.
- Complete authorization policy evaluation.
- Slurm AdminLevel lookup.
- Capability resolution.
- Persistent session storage.
- Session resumption.
- Role-specific UI behavior.

# 3. Architecture Boundary

The bridge remains the application boundary.

```text
Cockpit Authentication
        │
        ▼
Unix Peer Identity
        │
        ▼
Connection / Session
        │
        ▼
UserContext / SecurityContext
        │
        ▼
Protocol Dispatcher
        │
        ├── Query Controller
        └── Command Controller
```

The connection layer owns connection state and authenticated identity.

The dispatcher owns protocol message routing.

Future application services own authorization, Slurm access, resource management, commands, and subscriptions.

The connection layer must not contain Slurm-specific business logic.

## 3.1 Implementation Contract

Phase 1E must implement a minimal connection foundation without
introducing Slurm-specific identity or authorization logic.

The implementation must use the following canonical types:

- `connection.Connection`
- `connection.Session`
- `connection.UserContext`
- `connection.PeerIdentity`

`SecurityContext` is the architectural name for the security context.
It must not be implemented as a second competing Go model.

The connection package owns:

- Connection lifecycle.
- Connection and session identifiers.
- Server-derived peer identity.
- Initial user context.
- Connection-scoped cancellation.
- Cleanup of connection-owned resources.

The connection package must not own:

- Slurm user lookup.
- Slurm AdminLevel resolution.
- Slurm account resolution.
- Capability resolution.
- Authorization policy evaluation.
- Resource subscriptions.
- Slurm command execution.

The dispatcher remains responsible for protocol message routing.
The connection layer must provide the dispatcher with the server-owned
connection context.

# 4. Canonical Naming and Ownership

## 4.1 Canonical Context Type

`UserContext` is the canonical Go implementation type for the security
context associated with a connection.

The architectural term `SecurityContext` refers to the same concept.
`SecurityContext` must not be implemented as a second Go type.

All Phase 1E code must use:

    connection.UserContext

The type must be defined in:

    internal/connection/

The following names must not be introduced as alternative models:

- `SecurityContext`
- `IdentityContext`
- `SessionContext`
- `UserSecurityContext`

Future phases may enrich `UserContext`, but must not replace it with
another competing context model.

## 4.2 Type Ownership

The `internal/connection` package owns:

- `Connection`
- `Session`
- `PeerIdentity`
- `UserContext`
- Connection lifecycle state
- Connection-scoped cancellation
- Connection and session identifiers
- Connection manager interfaces

The `internal/protocol` package owns:

- Protocol envelopes
- Message types
- Encoding and decoding
- Protocol validation

The `internal/dispatcher` package owns:

- Message dispatch
- Handler registration
- Request routing
- Protocol-level response generation

The `internal/ipc` package owns:

- Unix socket listening
- Accepting connections
- Reading and writing transport data
- Transport shutdown

The connection package must not own Slurm-specific resource models,
Slurm command execution, subscriptions, or event delivery.

## 4.3 Required and Future-Only Fields

Phase 1E requires the following fields to be available:

- Connection ID
- Session ID
- Peer UID
- Peer GID
- Peer username

The following fields are future-only and must not be resolved in Phase 1E:

- Slurm AdminLevel
- Slurm accounts
- Default account
- Slurm capabilities
- Resource permissions
- Authorization decisions

Future-only fields must have an explicit unresolved state. They must
not be interpreted as granting privileges.

## 4.4 Zero-Value Semantics

A zero-valued `UserContext` represents an uninitialized context.

An uninitialized context must not be treated as:

- An authenticated user
- An anonymous user
- An administrator
- An operator
- A user with Slurm capabilities

A `Connection` must not become active until a valid peer identity has
been obtained and a corresponding `UserContext` has been created.

If peer identity retrieval fails, the connection must be closed rather
than activated with a zero-valued context.


## 4.5 Canonical Go Types

### PeerIdentity

`PeerIdentity` represents identity obtained from the trusted Unix socket.

Required fields:

- UID
- GID
- Username

The implementation must distinguish between:

- Successfully retrieved identity.
- Failed identity retrieval.

A zero-valued UID, GID, or Username must not be interpreted as proof
of a valid authenticated identity.

### UserContext

`UserContext` is the only implementation model for the connection's
security context.

Required fields:

- UID
- GID
- Username

Future fields may include:

- AdminLevel
- Accounts
- DefaultAccount
- Capabilities

Phase 1E must not resolve those future fields.

The initial context must represent unresolved Slurm-specific information
explicitly and must not grant privileges.

### Session

`Session` contains:

- Session ID
- Owning connection ID
- Connection-scoped context

Phase 1E uses one session per connection.

Session persistence, resumption, and sharing between connections are
out of scope.


# 5. Canonical Go API

The following types define the minimum Phase 1E API.

The exact private fields may be adjusted for implementation, but the
public meaning and required behavior must remain unchanged.

### 5.1 Connection

```Go
type Connection struct {
    ID       string
    Session  *Session
    Context  context.Context
    Cancel   context.CancelFunc
}
```

Connection represents one accepted Unix socket connection.

The implementation may keep transport handles, lifecycle state, and synchronization fields private.

The connection must have:

* A server-generated connection ID.
* Exactly one associated session.
* One server-owned UserContext.
* A connection-scoped cancellation function.
* A defined lifecycle state.

### 5.2 Session
```Go
type Session struct {
    ID           string
    ConnectionID string
    UserContext  UserContext
}
```
A session represents the logical interaction context associated with one connection.

For Phase 1E:

* One connection creates one session.
* The session ID is server-generated.
* The session ID is distinct from the connection ID.
* The session is not persistent.
* The session is not resumed or shared between connections.
* The session does not represent a resource subscription.

### 5.3 PeerIdentity
```Go
type PeerIdentity struct {
    UID      uint32
    GID      uint32
    Username string
}
```
PeerIdentity contains identity obtained from the trusted Unix socket.

The client must not be able to provide or override these values.

A valid identity requires successful retrieval of the peer credentials. The implementation must not silently replace a failed lookup with an empty identity.

### 5.4 UserContext
```Go
type UserContext struct {
    UID      uint32
    GID      uint32
    Username string
}
```
UserContext is the canonical Phase 1E context model.

It must be constructed from server-derived PeerIdentity.

Phase 1E does not populate Slurm-specific identity or authorization fields. Those fields may be added in a later phase without introducing a second context type.

### 5.5 ConnectionManager
```Go
type ConnectionManager interface {
    Register(*Connection) error
    Unregister(connectionID string)
    Get(connectionID string) (*Connection, bool)
    Close(connectionID string) error
    CloseAll()
    Count() int
}
```
ConnectionManager owns the active connection registry.

It must:

* Register active connections.
* Prevent duplicate active connection IDs.
* Retrieve connections by ID.
* Remove connections during cleanup.
* Close individual connections.
* Close all connections during server shutdown.
* Be safe for concurrent use.

The manager must not own Slurm resources, subscriptions, or event delivery.


### One small refinement

For production Go code, I would actually recommend that the fields of `Connection`, `Session`, and `UserContext` be private, with constructors and accessors, for example:

```Go
func NewConnection(...) (*Connection, error)
func (c *Connection) ID() string
func (c *Connection) Session() *Session
func (c *Connection) UserContext() UserContext
```

However, for the first implementation, the public-field shape above is useful as a contract sketch. You can tell Copilot:

>Use the documented types and semantics as the contract. Private fields, constructors, mutexes, and transport references may be added as necessary, but do not introduce alternative context or session models.

## 5.6 Connection Model

Each accepted socket connection must be represented by one connection object.

The connection object must contain:

* Connection ID.

* Session ID.

* Underlying network connection.

* Protocol encoder and decoder.

* Connection state.

* Server-derived user context.

* Connection-scoped cancellation or shutdown mechanism.

* Synchronization required for concurrent access.

The connection object must not be shared between unrelated socket connections.

### Connection states

```
New → Active → Closing → Closed
```

State transitions must be explicit.

No message may be processed after the connection has entered `Closed`.

## 5.7 Connection ID

The connection ID identifies one accepted socket connection.

Requirements:

* Generated by the server.

* Unique among active connections.

* Opaque to clients.

* Not derived from client-supplied data.

* Not used as an authorization credential.

The connection ID is an operational identifier, not a user identity.

# 6. Session ID

The session ID identifies the logical bridge session associated with a connection.

For Phase 1E:

* A new session ID may be created for each accepted connection.

* The session ID must be server-generated.

* The session ID must be opaque to clients.

* The session ID must not be treated as a user identity.

* Persistent sessions and session resumption are deferred.

Connection ID and session ID must remain separate concepts, even if their initial lifecycle is identical.

## 7. Peer Identity

The server must derive peer identity from the trusted Unix socket connection.

The initial Linux implementation must obtain:

* UID.

* GID.

* Username, when required.

* Any additional identity information required by the user-context model.

The server must not trust client-supplied values for:

* Username.

* UID.

* GID.

* AdminLevel.

* Accounts.

* Capabilities.

* Authorization decisions.

Client-supplied identity fields must not override server-derived identity.

## 7.1 Peer Identity Failure

Peer identity is mandatory for an accepted connection.

If the server cannot retrieve the Unix peer credentials, the connection
must not become active.

The implementation must:

1. Record the identity retrieval error.
2. Close the connection.
3. Remove the connection from the active connection registry.
4. Release connection-scoped resources.
5. Return or log the error according to the existing IPC error policy.

The implementation must not continue with an empty or anonymous context.

A failed identity lookup must never produce a privileged context.

Phase 1E does not implement anonymous connections.

### Identity Error

The connection package must expose a sentinel error:

`ErrPeerIdentityUnavailable`

The error indicates that the server could not obtain trusted peer
credentials.

The error must not be sent as a successful application response.
The connection must be closed.

The underlying operating-system error may be retained for logging or
diagnostics, but must not change the externally defined error category.

### Platform boundary

Linux peer-credential retrieval must be isolated from generic connection and protocol logic.

Platform-specific identity extraction belongs in the identity implementation, not in the protocol package.

# 8. UserContext and SecurityContext

The bridge architecture uses `SecurityContext` as the identity and capability context associated with an IPC connection.

The existing implementation contract may use the name `UserContext`. The implementation must not create two competing context models.

The selected UserContext model must contain, as defined by the Phase 0 contracts:

* Username.

* UID.

* GID.

* AdminLevel.

* Accounts.

* Default account, if defined.

* Capabilities.

Every IPC connection owns one server-created context.

### UserContext construction

At connection establishment:

* Username, UID, and GID come from authenticated peer identity.

* Slurm-specific identity information is resolved by a future identity service.

* Capabilities are resolved by a future capability resolver.

* Unresolved fields must use the explicit representation defined by the context model.

* Missing information must not produce elevated privileges.

Phase 1E must establish the UserContext boundary without implementing the complete Slurm lookup or capability-resolution workflow.

## 8.1 Future Identity and Capability Stubs

Phase 1E must provide a minimal implementation seam for future
identity enrichment.

The initial implementation may use interfaces such as:

- `PeerIdentityProvider`
- `UserContextFactory`

The default Phase 1E implementation must:

- Obtain UID/GID/Username from the Unix socket.
- Construct UserContext from those values.
- Leave Slurm-specific fields unresolved.
- Leave capabilities unresolved.
- Grant no elevated privileges.

A future phase may add:

- Slurm user lookup.
- AdminLevel resolution.
- Account and default-account resolution.
- Capability resolution.
- Authorization policy evaluation.

Phase 1E must not call Slurm commands or Slurm REST APIs for identity
resolution.


# 9. Identity and Authorization Boundary

Phase 1E establishes who is connected.

It does not establish the complete answer to what the user may do.

The connection layer must not decide whether a user may:

* Read a Slurm resource.

* Modify a Slurm resource.

* Execute a Slurm command.

* Subscribe to an event.

* Access another user's data.

Those decisions belong to the future authorization and application-service layers.

The future command flow must evaluate the server-owned security context before invoking Slurm.

```
Command
    ↓
SecurityContext
    ↓
Capability Check
    ↓
Command Service
    ↓
Slurm
```

# 10. Connection Processing

For each accepted connection, the bridge must:

1. Create a connection object.

2. Assign a connection ID.

3. Assign a session ID.

4. Obtain the Unix peer identity.

5. Construct the server-owned user context.

6. Initialize the protocol encoder and decoder.

7. Mark the connection active.

8. Read and decode protocol frames.

9. Pass valid messages to the dispatcher.

10. Send responses through the connection.

11. Close and remove the connection when processing ends.

The connection layer must not parse Slurm commands or invoke Slurm commands.

# 11. Hello and Handshake

The existing Phase 1D `hello` behavior must remain valid.

Phase 1E must associate the connection and its user context with the connection-processing context before application messages are handled.

The implementation must not accept client-provided identity information as proof of authentication.

If handshake enforcement is introduced, it must be explicit and documented. It must not silently change the Phase 1D protocol contract.


## 11.1 Connection and Session Protocol Contract

Connection and session creation are server-side operations.

Phase 1E does not introduce a new client request for creating a
connection or session.

The IPC server creates the connection and session before processing
application messages.

The server must associate the following values with the connection:

- Connection ID
- Session ID
- UserContext

These values are not accepted from the client as authoritative identity.

The existing Phase 1D protocol contract remains unchanged.

The existing `hello` request and `hello-response` behavior must remain
compatible with Phase 1D.

If connection or session metadata is included in a response, it must be
server-generated and must not be treated as authentication credentials.


**Recommended handshake behavior**

For Phase 1E, keep it simple:
```text
Accepted Unix connection
        ↓
Create Connection
        ↓
Generate Connection ID
        ↓
Generate Session ID
        ↓
Retrieve peer credentials
        ↓
Create UserContext
        ↓
Register active connection
        ↓
Read protocol frames
        ↓
Dispatch hello / ping / other messages
```
Do not introduce a new session.create message in Phase 1E. That would unnecessarily expand the protocol and make the session concept look like a client-managed resource.

## 11.2 Identifier Semantics

Phase 1E uses three different identifier concepts:

| Identifier | Owner | Purpose |
|---|---|---|
| Connection ID | Server | Identifies one accepted socket connection |
| Session ID | Server | Identifies the logical session associated with that connection |
| Request ID | Client/protocol | Correlates a request with its response |

Connection ID and Session ID are server-generated.

Request ID follows the existing Phase 1C/1D protocol contract.

Connection ID and Session ID must not replace Request ID.

Phase 1E does not introduce a new correlation mechanism.

# 12. Error Handling

The connection layer must distinguish:

* Invalid peer identity.

* Failure to construct the user context.

* Protocol decoding errors.

* Dispatcher errors.

* Connection read errors.

* Connection write errors.

* Normal client disconnect.

* Server shutdown.

The implementation must:

* Avoid panics for ordinary connection failures.

* Close invalid or unusable connections.

* Avoid sending responses after connection closure.

* Avoid leaking connection resources.

* Preserve Phase 1C protocol error semantics.

Identity failures must not result in an elevated or privileged context.

# 13. Shutdown and Cleanup

When a connection closes, the implementation must:

* Stop its read/write processing.

* Release the underlying socket.

* Remove the connection from the active connection registry.

* Cancel connection-scoped work.

* Release connection-scoped resources.

* Prevent further message processing.

Server shutdown must close active connections and allow all connection goroutines to terminate.

Persistent session storage is not required in Phase 1E.

# 20. Implementation Decision

1. UserContext is the canonical Go type, it lives in internal/connection.
2. SecurityContext is the architectural concept only; it is not a second Go type.
3. Connection, Session, PeerIdentity, and UserContext are owned by internal/connection.
4. ConnectionManager owns active connection registration and lifecycle.
5. Phase 1E defines safe zero-value semantics explicitly.

The implementation must not make independent naming decisions.

Use the following canonical mapping:

| Architectural concept | Go implementation |
|---|---|
| Security context | `connection.UserContext` |
| Connection | `connection.Connection` |
| Session | `connection.Session` |
| Peer identity | `connection.PeerIdentity` |
| Active connection registry | `connection.ConnectionManager` |


1. `UserContext` is the only context model.
2. The implementation must not create a second `SecurityContext` type.
3. The implementation must not use zero-valued context as an authenticated,
anonymous, administrator, or operator identity.
4. If peer identity cannot be obtained, the connection must fail closed.
5. The implementation must not resolve Slurm identity, AdminLevel,
capabilities, accounts, or authorization in Phase 1E.
