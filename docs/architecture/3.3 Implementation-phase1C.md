# 3.3 Implementation Phase 1C — IPC Protocol

## 1. Purpose

Phase 1C implements the **cockpit-slurm IPC protocol layer** on top of the Unix-domain socket transport implemented in Phase 1B.

The objective is to provide a stable protocol implementation for:

* message framing;
* JSON encoding and decoding;
* the common message envelope;
* protocol message types;
* protocol-level validation;
* protocol-level errors.

Phase 1C does **not** implement application request dispatch or Slurm operations.

---

## 2. Scope

Phase 1C SHALL implement:

1. Protocol constants.
2. Common `Envelope`.
3. `MessageType`.
4. Length-prefixed JSON encoder.
5. Length-prefixed JSON decoder.
6. Envelope validation.
7. Protocol-level error definitions.
8. Definitions for `hello`, `hello-response`, `ping`, `pong`, and all other defined protocol message types.
9. Unit tests for framing, encoding, decoding, and validation.

The envelope payload SHALL remain `json.RawMessage` so that the protocol package is not coupled to Slurm resource models.

---

## 3. Non-goals

Phase 1C SHALL NOT implement:

* request dispatcher;
* connection/session management;
* `UserContext`;
* authentication or authorization;
* Slurm commands;
* `sacctmgr`, `scontrol`, `squeue`, `sinfo`, etc.;
* `slurmrestd`;
* canonical resource models;
* cache;
* query service;
* command service;
* subscription service;
* event service;
* Cockpit `channel()` integration.

These functions belong to later implementation phases.

---

The responsibilities SHALL remain separated as follows:

```text

                ┌─────────────────┐
                │   internal/ipc  │
                │                 │
                │ Listen           │

                         │

                         │

                ┌─────────────────┐
                │ internal/protocol│
                │                 │
                │ Decoder         │
                │ Envelope        │
                │ Validation      │
                │ Encoder         │
                └────────┬────────┘
                         │
                      Envelope
                         │
                         ▼
                ┌─────────────────┐
                │     Phase 1D    │
                │    Dispatcher   │
                └─────────────────┘
```

### `internal/ipc`

Owns Unix-domain socket transport and connection lifecycle.

### `internal/protocol`

Owns:

* frame encoding;
* frame decoding;
* JSON encoding/decoding;
* `Envelope`;
* protocol message types;
* structural validation.

The protocol package MUST NOT dispatch application requests.

### Phase 1D Dispatcher

Owns:

```text
Envelope
    ↓
message type
    ↓
message handler
```

## 5. Frame Format

The IPC transport SHALL use a length-prefixed frame:

```text
┌──────────────────────┬─────────────────────────────┐
│ 4-byte length        │ JSON payload                │
│ unsigned, big endian │ UTF-8                       │
└──────────────────────┴─────────────────────────────┘
```

### Rules

* The length field SHALL be a 32-bit unsigned integer.
* Byte order SHALL be big-endian.
* The length SHALL represent the JSON payload size only.
* The 4-byte header SHALL NOT be included in the length.
* A zero-length frame SHALL be rejected.
* A frame larger than `MaxPayloadSize` SHALL be rejected.
* The decoder SHALL validate the length before allocating the payload buffer.
* `io.ReadFull()` SHALL be used to read the complete header and payload.
* The protocol SHALL NOT use newline delimiters.

Recommended initial limit:

```go
const (
    FrameHeaderSize = 4
    MaxPayloadSize  = 4 * 1024 * 1024
)
```

---

## 6. Envelope

Every IPC message SHALL use the following common envelope:

```json
{
  "protocol": "cockpit-slurm",
  "version": "1.0",
  "messageId": "MSG001",
  "type": "ping",
  "timestamp": "2026-08-31T00:00:00Z",
  "payload": {}
}
```

Go representation:

```go
type Envelope struct {
    Protocol  string          `json:"protocol"`
    Version   string          `json:"version"`
    MessageID string          `json:"messageId"`
    Type      MessageType     `json:"type"`
    Timestamp string          `json:"timestamp,omitempty"`
    Payload   json.RawMessage `json:"payload"`
}
```

### Required fields

| Field       | Required | Description                  |
| ----------- | -------- | ---------------------------- |
| `protocol`  | Yes      | MUST be `cockpit-slurm`      |
| `version`   | Yes      | Supported protocol version   |
| `messageId` | Yes      | Non-empty message identifier |
| `type`      | Yes      | Known protocol message type  |
| `timestamp` | No       | UTC timestamp                |
| `payload`   | Yes      | JSON payload                 |

`messageId` generation is outside Phase 1C. Phase 1C only validates that it is non-empty.

Unknown JSON fields SHALL be ignored for forward compatibility.

---

## 7. Message Types

Phase 1C SHALL define the following message types:

```text
hello
hello-response

ping
pong

query
query-response

subscribe
subscribe-response

unsubscribe
unsubscribe-response

command
command-response
command-status

event

error

close
```

A known message type MAY be defined even when its application behavior is not yet implemented.

For example:

```text
query
```

is a valid protocol message in Phase 1C, even though query handling belongs to a later phase.

An unknown type such as:

```text
bogus-type
```

SHALL be rejected by protocol validation.

---

## 8. Payload Schemas

Phase 1C defines only the minimum payload structures required by the protocol.

### `ping`

```json
{}
```

### `pong`

```json
{}
```

### `hello`

```json
{
  "client": "cockpit-slurm-channel",
  "clientVersion": "0.1.0"
}
```

### `hello-response`

```json
{
  "server": "cockpit-slurm-bridge",
  "serverVersion": "0.1.0"
}
```

### `error`

```json
{
  "code": "INVALID_MESSAGE",
  "message": "Missing messageId",
  "details": {}
}
```

For `error`:

* `code` SHALL be present.
* `message` SHALL be present.
* `details` MAY be present.

The richer application error model defined in `error-model.md` belongs to later phases.

Message-specific payload validation SHALL remain outside the generic protocol validation layer unless explicitly required by Phase 1C.

---

## 9. Validation Rules

`ValidateEnvelope()` SHALL validate the common envelope structure.

### Protocol

```text
protocol MUST be present.
protocol MUST equal "cockpit-slurm".
```

### Version

```text
version MUST be present.
version MUST be supported.
```

### Message ID

```text
messageId MUST be present.
messageId MUST NOT be empty.
```

### Message type

```text
type MUST be present.
type MUST be a known MessageType.
```

### Payload

```text
payload MUST be present.
payload MUST contain valid JSON.
```

An empty JSON object is valid:

```json
{}
```

A zero-length frame is not valid.

### JSON / UTF-8

The payload MUST be valid UTF-8 JSON.

Malformed JSON SHALL be rejected.

Invalid UTF-8 SHALL NOT be accepted as valid protocol text.

### Unknown fields

Unknown JSON fields SHOULD be ignored unless a future protocol version explicitly requires strict validation.

### Known versus unknown messages

```text
known type
    ↓
protocol-valid
    ↓
may be handled by later dispatcher

unknown type
    ↓
protocol error
```

---

## 10. Error Model

Phase 1C defines only **protocol-level errors**.

A protocol error SHALL use the normal `Envelope` with:

```text
type = "error"
```

Example:

```json
{
  "protocol": "cockpit-slurm",
  "version": "1.0",
  "messageId": "MSG001",
  "type": "error",
  "payload": {
    "code": "INVALID_MESSAGE",
    "message": "Missing messageId"
  }
}
```

Initial protocol error codes MAY include:

```text
INVALID_PROTOCOL
UNSUPPORTED_VERSION
INVALID_MESSAGE
UNKNOWN_MESSAGE_TYPE
INVALID_FRAME
INVALID_JSON
MESSAGE_TOO_LARGE
```

Protocol validation errors belong to Phase 1C.

Application/service errors belong to the canonical error model defined in `error-model.md`.

## 12. Implementation Requirements

### Encoder

The encoder SHALL:

1. JSON-marshal an `Envelope`.
2. Check the payload size.
3. Create a 4-byte big-endian length prefix.
4. Write the complete header.
5. Write the complete payload.
6. Handle partial writes correctly.

A private `writeFull()` helper MAY be used to guarantee complete writes.

### Decoder

The decoder SHALL:

1. Read exactly 4 bytes.
2. Decode the big-endian length.
3. Reject zero length.
4. Reject a length greater than `MaxPayloadSize`.
5. Allocate the payload only after the size check.
6. Read exactly the declared payload length.
7. Decode JSON.
8. Validate the envelope.
9. Return one complete `Envelope`.

The decoder MUST NOT allocate memory based on an unchecked length value.

### Message IDs

Phase 1C SHALL treat `messageId` as an opaque non-empty string.

Message ID generation belongs to Phase 1D or a later request/connection layer.

### Concurrency

The protocol encoder/decoder does not need to provide shared concurrent access to the same stream. Synchronization of concurrent writes, if required, belongs to the IPC/connection layer.

Phase 1C SHALL provide unit tests for at least:

### Encoding / decoding

```text
[ ] valid encode
[ ] valid decode
[ ] encode/decode round trip
[ ] correct big-endian length prefix
```

### Stream behavior

```text
[ ] one frame split across multiple reads
[ ] multiple frames in one stream
[ ] truncated length header
[ ] truncated payload
```

### Frame validation

```text
[ ] zero-length frame rejected

[ ] MaxPayloadSize + 1 rejected
```

### JSON validation

```text

[ ] invalid UTF-8 rejected
[ ] valid UTF-8 accepted
```

### Envelope validation

```text

[ ] invalid protocol rejected

[ ] unsupported version rejected
[ ] missing messageId rejected
[ ] empty messageId rejected
```

### Message types

## 14. Acceptance Criteria

Phase 1C is complete when all of the following are true:

* [ ] `internal/protocol` implements the defined envelope.
* [ ] All defined protocol message types are represented.
* [ ] Length-prefixed JSON encoding works.
* [ ] Length-prefixed JSON decoding works.
* [ ] Big-endian framing is verified by tests.
* [ ] Partial reads are handled correctly.
* [ ] Partial writes are handled correctly.
* [ ] Multiple frames can be decoded from one stream.
* [ ] Oversized frames are rejected before allocation.
* [ ] Invalid JSON is rejected.
* [ ] Invalid UTF-8 is rejected.
* [ ] Envelope validation is implemented.
* [ ] Unknown message types are rejected.
* [ ] Known-but-unimplemented message types remain valid.
* [ ] Protocol-level errors are defined.
* [ ] `go test ./...` passes.
* [ ] `go vet ./...` passes.
* [ ] No dispatcher or application/Slurm logic exists in `internal/protocol`.

Phase 1C does not need to implement `hello → hello-response` or `ping → pong` dispatch. It only needs to define and encode/decode those message types.

---

## 15. Phase 1D Boundary

Phase 1D begins after the Phase 1C acceptance criteria are satisfied.

Phase 1D SHALL introduce the **request dispatcher**:

```text
Envelope
    │
    ▼
Dispatcher
    │
    ├── hello          → hello-response
    ├── ping           → pong
    ├── query          → not implemented
    ├── subscribe      → not implemented
    ├── unsubscribe    → not implemented
    └── command        → not implemented
```

Phase 1D owns message dispatch and response selection.

Phase 1D SHALL NOT yet implement:

* Slurm resource operations;
* canonical resource cache;
* authorization;
* UserContext;
* subscription manager;
* event manager;
* Slurm command execution.

Those concerns belong to subsequent phases.

The architectural sequence remains:

```text
Phase 1B
Unix socket transport
       ↓
Phase 1C
Protocol encode/decode
       ↓
Phase 1D
Request dispatcher
       ↓
Phase 1E
Connection / UserContext
       ↓
Later phases
Slurm services / cache / events / commands
```
