# Implementation Plan for `cockpit-slurm` Project — Version 3.7

## 1. Purpose

This document defines the implementation plan for `cockpit-slurm` Version 3.7.

It defines implementation sequencing, dependencies, verification, and acceptance for Version 3.7. The normative architecture reference is:

`docs/architecture/0.1 development-cockpit-slurm-_v3.7.md`

This plan is subordinate to that architecture and MUST NOT establish
implementation behavior that conflicts with it. Existing accepted Version 3.6
transport, resource, event, and authorization work remains the foundation;
completed phases are not restarted merely because the version changes.

Version 3.6 continued the backend and frontend work established in Version 3.5 and changed the transport architecture:

* `cockpit-slurm` is the application and persistent backend service.
* `cockpit-slurm-channel` is removed.
* The React frontend communicates with the backend through `cockpit.channel()`.
* Cockpit provides the transport path between the frontend and the backend Unix socket.
* The `cockpit-slurm` application protocol remains independent of the Cockpit protocol.
* The backend owns resource state, cache, synchronization, commands, per-connection event streams, authorization, and IPC.
* The frontend owns presentation, UI state, and frontend-facing protocol handling.
* The backend must remain usable and testable without Cockpit.

The Version 3.6 implementation plan is retained as the implementation and
project-history baseline. Historical v3.6 references remain historical unless
this plan explicitly identifies a current v3.7 requirement.

The accepted Phase 4 stream specification further defines event delivery: each IPC connection receives automatic resource snapshots and events through the existing event envelope. Application-level `subscribe`/`unsubscribe` messages and `subscriptionId` are not part of the v3.6 protocol. Older phase-planning text below is historical where it conflicts with the accepted Phase 4/5 specifications.

## 2.2 Removed Version 3.5 component

The following Version 3.5 component is removed:

```text

```

The following are therefore no longer part of the v3.6 target architecture:

* `cockpit-slurm-channel` executable
* channel-specific Go package
* channel executable manifest entry
* channel-specific Unix socket forwarding process
* channel-specific application transport layer

The existing v3.5 channel implementation may remain temporarily in Git history or be removed from the working tree, but it must not be required for the v3.6 runtime architecture.

## 2.3 Persistent backend

The backend remains a persistent system service:

```text
cockpit-slurm.service
        │
        ▼
cockpit-slurm
```

The backend is not started once per `cockpit.channel()` request.

It remains alive independently of frontend connections and maintains the authoritative Slurm state cache.

The service owns:

* Slurm synchronization
* canonical resources
* resource cache
* event bus
* per-connection event streams
* IPC server
* query processing
* command processing
* authorization
* audit information where required

## 2.4 Version 3.6 → Version 3.7 identity and execution changes

Version 3.7 retains the accepted v3.6 transport, resource, event, command,
and application authorization architecture. It adds implementation gates for
the daemon identity model:

* The daemon runs as Linux user and primary group `cockpit-slurm`, with a
  dedicated UID. It does not run as root or as the configured SlurmUser, and
  does not require membership in the SlurmUser-associated Unix group solely
  for Slurm authorization.
* The corresponding SlurmDB user is `cockpit-slurm`, configured with
  `AdminLevel=Administrator`. Validate this identity before relying on it for
  Slurm operations.
* SlurmDB user creation does not imply that all operation-specific accounting
  associations exist. Validate and configure associations separately for
  accounting or job-submission operations that require them; do not require
  association with every Slurm account merely to obtain `AdminLevel`, and do
  not hardcode a cluster or account such as `devel`.
* Keep the SlurmDB configuration spelling `Administrator`, CLI-facing
  representation `Admin`, normalized requester `UserContext` value `admin`,
  and application role `Administrator` distinct.
* The authenticated Cockpit user remains the requester. Resolve peer
  credentials, Linux identity, the requester's SlurmDB information and current
  AdminLevel, coordinator scope, and application policy into the requester's
  server-derived `UserContext`. Never use the daemon's identity or
  Administrator privilege as requester authorization context.
* **`UserContext` represents only the authenticated IPC requester.** The
  Resource Synchronizer's Linux/SlurmDB execution identity is service-level
  acquisition context and MUST NOT be stored in, copied into, or substituted
  for `UserContext`. Resource acquisition is independent of each IPC
  requester's identity.
* The Resource Synchronizer performs normal Slurm acquisition as Linux
  `cockpit-slurm` and SlurmDB user `cockpit-slurm`, populating one shared
  canonical cache from data Slurm permits that identity to retrieve.
* Normal supported Slurm commands run through fixed backend adapters as the
  daemon's own Linux and SlurmDB identity, only after requester authorization,
  operation validation, and command-ledger handling. Slurm's authorization
  does not replace application authorization.
* Classify each operation as safe under the daemon identity, requiring the
  original requester's execution identity, requiring additional OS
  privileges, or unsupported until an approved execution mechanism exists.
  Do not assume all Slurm commands work as `cockpit-slurm`.
* A privileged D-Bus or sudo helper is not mandatory for Slurm operations
  verified under the daemon identity. Do not remove existing helpers until
  each dependent operation has a validated replacement. A remaining helper
  requires a documented OS-privilege or requester-identity need, an
  allowlisted validated interface, prior requester authorization, separate
  audit identity, and boundary tests.
* `PrivateData` governs what Slurm permits the daemon identity to retrieve;
  `visibility.yaml` filters retrieved canonical data per IPC connection.
  Neither layer bypasses the other. Tests under `PrivateData=none` establish
  behavior only for that configuration.

The Phase 5 `node.drain` and `node.resume` policy is unchanged: both continue
to require the currently resolved requesting user's Slurm
`AdminLevel=Administrator` using `slurm_admin_level_admin`. Neither the
daemon's AdminLevel, application role `Administrator`, nor the broader
`slurm_admin` predicate grants these operations to the requester.

## 4.2 Application IPC framing

The application protocol remains length-prefixed.

Conceptually:

```text
┌──────────────┬──────────────────────┐
│ frame length │ application payload  │
└──────────────┴──────────────────────┘
```

The application frame may contain:

```json
{
  "protocol": "cockpit-slurm",
  "version": "1.0",
  "messageId": "01...",
  "type": "query",
  "resource": "nodes",
  "payload": {}
}
```

The backend must parse application frames independently of Cockpit.

The frontend integration layer must also reconstruct complete application frames from the arbitrary byte chunks delivered by `cockpit.channel()`.

---

## 4.3 UserContext

The server remains authoritative for user identity and authorization.

The backend derives identity from the server-side connection rather than trusting frontend-supplied identity.

The conceptual model remains:

```text
Cockpit authenticated user
        │
        ▼
Unix socket peer identity
        │
        ▼
UserContext
        │
        ├── Username
        ├── UID
        ├── GID
        ├── AdminLevel
        ├── Coordinator
        ├── Accounts
        └── Capabilities
```

The frontend may receive a safe representation of `UserContext`, but it must not establish the authoritative identity itself.

For Version 3.7, `UserContext` represents exclusively the authenticated
requesting Cockpit user. Its username, UID/GID, Slurm AdminLevel, coordinator
scope, accounts, and requester capabilities are resolved from that user's
trusted connection and server-side Slurm data. Do not add the daemon's Linux
UID, daemon SlurmDB identity, or Resource Synchronizer identity to
`UserContext`. The Resource Synchronizer uses service-level daemon identity
for backend acquisition; it is not an IPC requester and does not inherit or
reuse a requester's `UserContext`.

## 5.3 IPC server

The IPC server must:

* create/listen on the configured Unix socket;
* accept concurrent connections;
* read application frames;
* enforce frame-size limits;
* reject malformed frames;
* derive peer identity;

The IPC server must not contain Slurm-specific business logic.

## 6.2 Important transport rule

Cockpit `stream` is a byte stream.

Application message boundaries must therefore not depend on:

```text
channel.onmessage
```

being one application message.

A single application frame may arrive as:

```text
chunk A
chunk B
chunk C
```

or multiple application frames may arrive in:

```text
one chunk
```

Therefore:

```text
Cockpit stream framing
        ≠
cockpit-slurm application framing
```

The application length-prefix decoder must remain in the frontend integration layer and backend IPC layer.

---

## 6.3 Frontend Cockpit channel

The intended frontend transport is conceptually:

```typescript
const channel = cockpit.channel({
    payload: "stream",
    unix: "/run/cockpit-slurm/cockpit-slurm.sock",
    binary: true,
});
```

The exact API behavior must be verified against the Cockpit version supported by the project before freezing the implementation.

The current Cockpit protocol specifies `unix` for the `stream` payload and describes `stream` as raw data whose boundaries are arbitrary.

The v3.7 architecture defines one authoritative production socket:


# 10. Phase 6 — Resource System Generalization

Phase 6 establishes the reusable Resource System by generalizing the Node implementation completed in Phase 3,4,5.

The phase must demonstrate that additional Slurm resources can be introduced through resource-specific adapters and canonical models without duplicating the IPC, Query Service, Cache, generation,snapshot, or frontend transport infrastructure.

### 10.1 Central operation authorization matrix

Phase 6 must generalize the authorization mechanism proven by the Node
vertical slice into a data-driven operation registry. The operation policy
must be defined once and consumed by the Go backend. Do not hardcode separate
role-to-permission tables in individual handlers or duplicate the policy in
the React frontend.

#### Policy source and runtime configuration

Repository source:

```text
config/authorization/operations.yaml
```

Installed runtime file:

```text
/etc/cockpit-slurm/operations.yaml
```

Go implementation:

```text
internal/authorization/
    registry.go
    registry_loader.go
    policy.go
    evaluator.go
    testdata/
```

The exact filenames may follow the existing package conventions, but the responsibilities must remain separated: parse and validate configuration, construct immutable policy registries, and evaluate policy against trusted server-derived context and canonical resources. Operation authorization and resource visibility MUST use separate policy sources and separate evaluators. The operation policy maintains separate query-policy and command registries. Every operation entry MUST declare `operation_type: query` or `operation_type: command` in addition to `status`.

Enabled query entries are
registered only in the query-policy registry; enabled command entries are
registered only in the command registry. Planned entries are validated but
registered in neither registry. Query and command dispatch remain separate.
The configuration file must be owned by root (or the system package manager)
and must not be writable by the `cockpit-slurm` service account. The daemon
needs read access only. The initial implementation loads and validates the
configuration during startup. Missing, unreadable, malformed, incomplete, or
semantically invalid configuration MUST fail daemon startup/readiness. Neither
query nor command services may become available with a partial registry,
permissive defaults, or a fallback policy. Publish both registries atomically
only after complete validation. Runtime reload is out of scope unless a
separate atomic-reload design is implemented.

#### YAML and registry contract

Each operation entry must define:

* an `operation_type` of `query` or `command`;
* a `status` of `enabled` or `planned`;
* a stable, allowlisted Go `handler` name;
* a unique `operation_id` used by the application protocol/registry;
* the canonical `resource` and operation `action`;
* a `policy_basis` identifying application policy or Slurm-native policy;
* exactly one permission cell for each of `Administrator`, `Operator`,
  `Coordinator`, and `User`.

The YAML must not contain executable paths, shell fragments, arbitrary
command templates, or Go function names supplied by an administrator. A
handler name is only a key resolved against a compiled allowlist of registered
handlers. Unknown enabled handlers and duplicate operation IDs must fail
validation. Planned entries are validated as policy data but are not registered
or executable.
validation. An enabled query entry is registered only in the query-policy
registry; an enabled command entry is registered only in the command registry.
Planned entries are validated as policy data but are registered in neither
registry and are not executable. A query entry must never become command
dispatchable, or vice versa.
The loader must validate the schema version, supported Slurm version, role
set, permission tokens, resource/action values, required fields,
`operation_type`, status,
duplicate enabled operation IDs, and completeness of all four role cells. Unknown
permission tokens and incomplete entries must fail closed. The resulting
registry must be immutable while requests are being evaluated.

Permission values have the semantics defined in architecture §8.5. The
evaluator must return a structured authorization decision (allowed/denied,
reason, operation ID, and relevant scope), not only a Boolean. `allow` means
only that application policy permits invoking the operation; it does not
bypass Slurm-native checks, request validation, resource scope, or execution
identity requirements.

#### Identity, scope, and execution requirements

* Derive the requesting UID/GID and username from the authenticated IPC
  connection. Never accept identity, role, ownership, or coordinator scope
  from the request payload.
* Evaluate ownership and coordinator rules against the canonical target
  resource and trusted requester SlurmDB/association data. The daemon's
  service identity is not requester scope data.
* Preserve the original requesting user's authorization identity when a
  privileged helper is used. The helper's UID must not be substituted for the
  requester when evaluating policy.
* Keep `UserContext` exclusive to the authenticated requester; do not place
  daemon Linux or SlurmDB identity in it or reuse it for Resource Synchronizer
  acquisition.
* Classify each command's execution semantics. Execute an operation as daemon
  `cockpit-slurm` only after its behavior under that Linux/SlurmDB identity is
  verified. If Slurm semantics require the original user's execution
  identity, use a separately approved identity-preserving mechanism or keep
  the operation disabled. Do not assume daemon, root, or SlurmUser execution
  is equivalent to requester execution.
* Apply resource-level filtering through the separate resource visibility policy to query snapshots, query responses, individual lookups, and streamed resource-change events. Collection-level `allow` does not grant unrestricted visibility.
* Enable `node.list` and `job.list` as query operations for Phase 6 and register
  them only in the query-policy registry. Their collection permission does not
  bypass per-resource filtering of snapshots, query responses, or events.
* Re-evaluate authorization for every new command ID before dispatch.
  Existing idempotent retries are resolved only through the accepted
  caller-scoped ledger ownership/fingerprint rules and are never redispatched.
  Frontend capabilities are derived presentation data, not authorization
  credentials.

For all policy evaluation, the requester `UserContext` remains distinct from
the daemon's service-level SlurmDB identity. Resource acquisition uses the
daemon identity outside `UserContext`; it does not create an administrative
requester or grant visibility to any IPC connection.

#### Slurm command policy boundaries

The matrix must describe the Cockpit operations actually implemented, not
every possible CLI subcommand or option. Keep command families distinct:

* `sinfo` and `squeue`: application permission to request node/job data is
  separate from per-user visibility filtering and Slurm `PrivateData` rules.
* `sbatch`, `salloc`, and `srun`: application permission to submit, allocate,
  or launch does not bypass Slurm association, account, partition, QOS, limit,
  or identity checks.
* `scontrol`: define separate entries for each supported resource/action;
  do not apply one broad permission to all `scontrol` operations.
* `scancel`: distinguish direct job ownership, Operator/Administrator
  privileges, and account-coordinator scope.
* `sacctmgr`: define entity/action/field-specific operations. Do not create a
  generic `sacctmgr.modify` permission that grants Coordinators unrestricted
  accounting database administration.

The initial YAML is a policy baseline, not a substitute for verification
against the installed Slurm 25.05.7 manuals and cluster behavior. Any entry
whose native authorization semantics have not been verified must not be
enabled in a production build.

#### Tests and acceptance criteria

Phase 6 authorization work is complete when:

* the YAML loads into the backend registry without hardcoded duplicate
  permission tables;
* invalid schema versions, unknown handlers/tokens, duplicate IDs, and
  missing role cells are rejected;
* each permission token has positive and negative unit tests;
* direct-owner, effective-owner, and account-coordinator decisions are tested
  with resources from both inside and outside the user's scope;
* query snapshots and streamed events apply the same per-user visibility
  policy;
* command authorization uses the original IPC requester identity, including
  through privileged-helper execution;
* frontend capabilities are derived from backend policy and cannot grant
  access independently;
* Slurm 25.05.7 integration tests cover each enabled command operation;
* `go test ./...` and `go vet ./...` pass.

### 10.2 Resource visibility policy

Phase 6 MUST establish and implement a resource-oriented visibility policy
separate from the operation authorization matrix.

Policy source:

```text
config/authorization/visibility.yaml
```

Installed runtime configuration:

```text
/etc/cockpit-slurm/visibility.yaml
```

`operations.yaml` determines whether a role may invoke an operation.
`visibility.yaml` determines which canonical records of a resource may be
returned to an authenticated IPC connection. A resource-returning query
operation MUST reference its resource policy using a `visibility_policy`
identifier. The identifier MUST resolve to a policy defined in
`visibility.yaml`. Automatic resource-change events MUST select and apply the
same policy by canonical resource kind.

The visibility policy is resource-oriented, not command-oriented. It MUST
define explicit role scopes and the trusted canonical attributes needed to
evaluate them. It MUST use default-deny behavior for unknown resources,
unknown policies, unsupported roles/scopes, and missing or invalid required
attributes. The frontend MUST NOT supply or override identity, ownership,
account membership, role, or coordinator scope.

Phase 6 implementation is limited to Node and active Job visibility:

* All authenticated application roles may see all Nodes in the configured
  cluster. Node visibility does not grant Node mutation permission.
* Administrator and Operator may see all active Jobs in the configured
  cluster.
* Coordinator may see Jobs directly owned by that user OR Jobs whose
  canonical Slurm account is in the user's server-derived
  `CoordinatorAccounts`.
* User may see only directly owned Jobs.

Direct Job ownership MUST compare the authenticated `UserContext.UID` with
the canonical Job owner's numeric `UserID`. Coordinator scope MUST compare
the canonical Job `Account` with server-derived `UserContext.CoordinatorAccounts`.
The two branches are independent: missing or invalid owner data denies the
direct-owner branch only, and missing or invalid account/scope data denies the
coordinator-account branch only. A valid direct-owner match remains sufficient
when the Job account is missing, and a valid coordinator-account match remains
sufficient when the Job owner is missing. Missing data MUST NOT grant access;
if neither applicable branch establishes access, deny visibility. Cluster
identity and authenticated connection context remain mandatory. Administrator
and Operator visibility remains governed by their existing privileged-role
policy.

The authoritative backend cache MAY retain complete canonical collections,
but MUST NOT be sent directly to a frontend connection. The same visibility
evaluator MUST filter initial snapshots, explicit query responses,
individual lookups, subsequent resource-change events, and reconnect or
snapshot-recovery responses. If a record becomes invisible to a connection,
the backend MUST remove it from that connection's frontend projection without
representing the change as deletion of the underlying Slurm resource.

Slurm `PrivateData` remains a separate Slurm-native setting configured only
in `slurm.conf`. It MUST NOT be configured through either application YAML
file. Cockpit-slurm MUST enforce its own per-connection visibility policy
regardless of Slurm's default information visibility, and MUST respect
Slurm-native authorization. Enabling a `PrivateData` restriction that
prevents complete backend data acquisition requires a separately reviewed
and tested acquisition design; the backend MUST NOT silently treat an
incomplete collection as complete.

For v3.7 resource acquisition, Slurm evaluates retrieval under the daemon's
Linux and SlurmDB identity, not under each IPC requester's `UserContext`.
`visibility.yaml` filters only the data actually acquired and cannot bypass
Slurm's restrictions. The current test environment reports `PrivateData=none`;
that evidence applies only to that configuration. Record the intended target
configuration and separately identify untested restrictive settings.

Slurm accounting events, Cockpit-slurm resource-change events, and
Cockpit-slurm audit events are distinct data categories and MUST NOT
implicitly share one visibility policy. Resource-change events use the
visibility policy of their related canonical resource. Slurm accounting
events and audit records require separately specified policies before they
are exposed.

Phase 6 MUST validate both policy files during startup. Missing, unreadable,
malformed, incomplete, or semantically invalid policy configuration MUST
prevent service readiness; no partial registry, permissive fallback, or
implicit unrestricted visibility is permitted. The operation and visibility
registries MUST be published only after successful validation.

Phase 6 acceptance tests MUST verify the Node and active Job role scopes,
direct-owner and coordinator-account decisions, rejection of client-supplied
identity/scope claims, fail-closed handling of missing attributes, consistent
filtering across snapshots/queries/events, visibility-removal behavior,
reconnect recovery, and rejection of invalid policy configuration.
They MUST include a direct-owner match with an empty or missing account, a
coordinated-account match with a missing or invalid owner, negative tests for
each unresolved branch, and denial when neither branch establishes access.

Accounts, Users, Partitions, Reservations, Slurm accounting Events, Usage,
and other future resources are not implemented by this Phase 6 requirement.
Each future resource MUST define and test an explicit visibility policy
before it is exposed.

# 11. Phase 7 — React Architecture

Only after the first vertical slice works should the frontend architecture be generalized.

Recommended structure:

```text
Backend:
    authoritative Slurm/application state
        ↓
    Resource Cache

Frontend:
    client-side resource presentation state
        ↓
    NodeProvider / JobProvider / AccountProvider

UI:
    component-local presentation state
        ↓
    tables/forms/dialogs/etc.
```

Providers should own frontend resource state and frontend-facing
communication for the resources they expose.

Providers are not authoritative application-state owners.

The authoritative Slurm/application state remains in the backend
Resource Cache.

Frontend services are transport/client abstractions, not
business-logic services.

The frontend must not:
  * execute Slurm commands;
  * implement Slurm business rules;
  * implement backend authorization;
  * maintain an authoritative resource cache;
  * duplicate backend synchronization logic.

Frontend providers may:
  * request resource snapshots;
  * consume resource updates from the shared IPC stream;
  * maintain client-side resource state;
  * expose loading/error/connection state;
  * coordinate data required by React components.

```text
Backend
┌────────────────────────────────────┐

│ Resource Cache                     │

│ Query Service                      │

                 │ IPC
                 ▼
Frontend
┌────────────────────────────────────┐
│ IPC Client                         │
│ Resource Services                  │
│ NodeProvider                       │
│   - Node snapshot                  │
│   - Node event state               │
│   - loading/error state            │
└────────────────────────────────────┘
                 │
                 ▼

```
Do not create a separate `cockpit.channel()` for every React component.

A provider should normally share the connection and state among the components that consume the same resource.

```text
React
    = presentation and frontend state
```

No component should blur these boundaries.

# 20. Version 3.7 Implementation Acceptance

This section defines the current v3.7 implementation acceptance criteria and
is subordinate to the normative v3.7 architecture. These are requirements to
verify, not claims that the checks have already passed.

## 20.1 Daemon and requester identity separation

Acceptance must verify:

* systemd runs the daemon as Linux user and primary group `cockpit-slurm`,
  with the dedicated UID; the daemon is not root or the configured SlurmUser;
* SlurmUser-associated Unix group membership is not required solely for
  SlurmDB authorization, and the daemon has only documented OS permissions;
* the corresponding SlurmDB user `cockpit-slurm` exists and is configured
  with `AdminLevel=Administrator`;
* SlurmDB `Administrator`, CLI-facing `Admin`, normalized requester
  `UserContext` value `admin`, and application role `Administrator` are
  treated as distinct spellings/concepts and mapped only where specified;
* the authenticated Cockpit requester is derived from validated IPC peer
  credentials and the target installation proves the Cockpit-user-to-peer
  mapping before protected commands are enabled; and
* `UserContext` contains only the authenticated requester identity and its
  trusted authorization/scope data. It MUST NOT contain the daemon's Linux
  UID, daemon SlurmDB identity, or Resource Synchronizer identity. The
  Resource Synchronizer MUST NOT receive or reuse a requester's `UserContext`.

## 20.2 Resource acquisition and visibility

Acceptance must verify:

* the Resource Synchronizer runs as Linux `cockpit-slurm` and authenticates
  to Slurm as SlurmDB user `cockpit-slurm` with
  `AdminLevel=Administrator` for normal supported resource acquisition;
* acquisition is independent of the IPC requester and updates one shared
  canonical Node/Job cache;
* Node and Job acquisition success, failure, and completeness are tracked;
  failed, restricted, truncated, malformed, or ambiguous data is not treated
  as an empty complete collection and cannot cause partial cache mutation,
  removals, or a false complete generation/snapshot baseline;
* the approved Phase 6 Job source, target Slurm/parser version scope,
  required fields, active-state classification, normal/array identity
  normalization, and valid array task ID zero behavior are verified using
  Stage A evidence; this plan does not silently change the selected source;
* per-connection visibility is applied after acquisition to initial
  snapshots, collection queries, individual lookups, incremental events, and
  reconnect/snapshot recovery, using the same evaluator; the global cache is
  never sent directly to a frontend connection; and
* existing Node and Job generation, event sequence, visibility-removal,
  disconnect, and recovery semantics remain unchanged.

Slurm `PrivateData` governs what the daemon identity can retrieve, while
`visibility.yaml` filters retrieved canonical data per authenticated IPC
connection. Application visibility cannot bypass Slurm restrictions, and
SlurmDB Administrator must not be assumed to bypass every restriction.
Record and validate the intended deployment configuration. Tests under
`PrivateData=none` establish behavior only under that setting; do not claim
restrictive settings are validated without separate evidence.

## 20.3 Requester authorization and command execution

Acceptance must verify:

* every command is authorized using the requesting user's fresh,
  server-derived authorization context and operation policy before invoking
  an adapter or helper;
* frontend-supplied identity, role, capability, ownership, and scope values
  cannot alter the decision;
* ordinary Users, Coordinators, and Operators do not inherit daemon SlurmDB
  Administrator privileges;
* `node.drain` and `node.resume` retain the Phase 5
  `slurm_admin_level_admin` predicate: only a requester with currently
  resolved Slurm `AdminLevel=Administrator` is allowed. The daemon identity,
  application role alone, and broader `slurm_admin` predicate do not satisfy
  it;
* denied, invalid, unknown, or unsupported requests never invoke Slurm; and
* each enabled operation has an explicit execution classification: safe
  under daemon identity, requires original-user execution, requires OS-level
  privilege, or remains disabled until a supported mechanism exists.

Supported direct Slurm operations use fixed backend adapters and validated
arguments under the daemon's Linux and SlurmDB identity. No frontend may
select execution identity, executable, shell command, arbitrary arguments,
or privilege escalation. Job submission, ownership-sensitive operations,
user-specific associations/limits/defaults, and commands with special Slurm
authorization semantics require operation-specific validation; do not infer
equivalent behavior from the daemon's AdminLevel.

## 20.4 Command ledger and audit

Acceptance must verify the existing command ID, IPC request correlation,
validation, idempotency, ledger ordering/durability, uncertainty/recovery,
error, and post-command synchronization guarantees remain intact. Ledger and
audit records must distinguish requester from executor and retain, where
applicable:

* requester username/UID, resolved Slurm AdminLevel, and application role;
* IPC connection/request correlation, OperationID, target, and scope;
* authorization decision and policy result;
* Linux execution identity and SlurmDB execution identity;
* lifecycle/outcome, timestamps, and error information.

Records must distinguish `Requested by: dev` from `Executed by:
cockpit-slurm`. The daemon must never be recorded as the requester because it
executed the operation. Sensitive internal command details must not be
exposed to unauthorized frontend users.

## 20.5 Deployment readiness and privileged helpers

Acceptance must verify provisioning and deployment cover:

1. Dedicated Linux user and primary group `cockpit-slurm`.
2. Corresponding SlurmDB user `cockpit-slurm` with
   `AdminLevel=Administrator`.
3. Operation-specific accounting associations only where the relevant
  operation requires them; user creation alone does not establish those
  associations, and no test account or cluster is hardcoded.
4. systemd execution as Linux `cockpit-slurm`, with runtime/socket/state
   permissions limited to documented needs and no `SupplementaryGroups=slurm`
   solely for Slurm authorization.
5. Slurm authentication and target Cockpit/peer identity mapping.
6. Supported Slurm reads and mutations under the daemon identity, plus
   independent rejection of unauthorized requesters.

Missing or incorrectly configured service identity leaves affected
Slurm-dependent functionality unready/degraded and commands fail-closed; do
not substitute requester, root, SlurmUser, frontend claims, or an unapproved
helper.

Validated Slurm operations must not depend on unnecessary privileged D-Bus or
sudo helpers. Do not remove existing helpers until every dependent operation
has a validated replacement. Each remaining helper must have a documented
OS-level privilege or original-requester identity requirement, a narrow
allowlisted interface, validated inputs, requester authorization before
invocation, separate requester/executor audit, and dedicated security tests.
Helper invocation must not bypass authorization or permit arbitrary command
execution.

## 20.6 Phase 6 Stage A and v3.6 compatibility

Stage A must meet the additional v3.7 identity and acquisition criteria in
Section 10.3 as well as every existing source, parser, array identity,
completeness, hidden-partition, event sequence, and recovery gate in
`4.5 Implementation-phase6.md`. Stage B remains blocked until explicit Stage
A acceptance. Preserve the accepted Node-plus-Job Phase 6 scope and the
existing `scontrol show job` candidate-source decision; do not invent Stage A
results or broaden resource scope.

The v3.6 IPC, frontend transport, cache, resource, event, authorization
registry, visibility policy, and Phase 5 behavior remain the foundation.
Completed phases are not restarted. Do not block unrelated Phase 6 work or
verified direct Slurm operations because a separate identity-sensitive
operation remains unresolved. Do not make helper removal a prerequisite for
resource work.

Existing Phase 4, Phase 5, and Phase 6 documents are not modified by this
plan. Their accepted history remains intact; any older helper or execution
identity language must be interpreted under this normative v3.7 plan and the
v3.7 architecture for current work. A follow-up documentation update should
reconcile those phase documents' current instructions, especially Phase 5
Stage C's direct-execution/helper gate and Phase 6 authorization/execution
identity wording, before they are used as standalone v3.7 implementation
guides.

## 20.7 Verification reporting

Report the exact checks performed. Distinguish unit/mock evidence from
real-cluster evidence, identify the Slurm and parser versions/configuration,
and record untested operation semantics and `PrivateData` settings. Never
claim an identity mapping, command behavior, completeness property, or
acceptance gate passed without evidence.
