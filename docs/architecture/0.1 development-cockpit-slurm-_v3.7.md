# cockpit-slurm Architecture and Development Plan Version 3.7

# 1. Purpose

This document defines the software architecture and development direction for
`cockpit-slurm` Version 3.7.

Version 3.7 retains the Version 3.6 transport, resource, event, and application
authorization architecture. It updates the daemon's Slurm execution identity:

- `cockpit-slurm` is the application and persistent backend service.
- The persistent daemon runs as Linux user and primary group `cockpit-slurm`.
- The corresponding SlurmDB user `cockpit-slurm` is configured with
  `AdminLevel=Administrator` for supported Slurm operations.
- Requester authorization remains based on the authenticated Cockpit user,
  never on the daemon's SlurmDB privileges.
- The React frontend communicates with `cockpit-slurm` through
  `cockpit.channel()`.
- The persistent backend owns the Slurm state cache, resource synchronization,
  commands, per-connection event streams, and IPC server.
- The IPC protocol remains independent of Cockpit.
- Cockpit is treated as the frontend transport provider, not as the owner of
  Slurm application state.

This document is normative for the Version 3.7 architecture. It carries
forward the accepted Version 3.6 architecture except where this document
explicitly defines the daemon identity, command execution, data acquisition,
helper, deployment, migration, or acceptance requirements differently.

# 2. Version 3.7 Architectural Decisions

### 2.1 Application name

The application is named:

`cockpit-slurm`

The name is used for:

* the Go module;

* the persistent backend service;

* the application architecture;

* the systemd service;

* the application-level IPC server;

* the frontend project;

* documentation and source-code packages.

The term `Cockpit bridge` refers only to Cockpit's own bridge process and protocol infrastructure.

The project must not use `cockpit-slurm-bridge` as the primary application name in Version 3.7 documentation.

### 2.2 Persistent backend

`cockpit-slurm` runs as a persistent systemd service.

The service:

* initializes the Slurm adapters;

* maintains the canonical resource cache;

* synchronizes Slurm state;

* publishes resource events;

* accepts IPC connections;

* manages per-connection event streams;

* processes queries and commands;

* performs authorization;

* records audit information where required.

The service is started by systemd, not created or destroyed for every frontend request.
It runs as the dedicated Linux account `cockpit-slurm`, with primary group
`cockpit-slurm`; it must not run as Linux root or as the configured SlurmUser.
The service account receives only the operating-system permissions required
for its documented runtime, configuration, logs, socket, state, and other
explicitly approved resources.

```text
systemd
  │
  ▼
cockpit-slurm.service
  │
  ├── Resource Synchronizer
  ├── Resource Cache
  ├── Event Bus
  ├── Per-connection Stream Registry
  ├── IPC Server
  ├── Dispatcher
  ├── Query Service
  ├── Command Service
  └── Unix socket
```

### The cockpit-slurm service owns the Unix socket.

* The socket is created under /run/cockpit-slurm.
* Socket ownership and permissions must allow authorized Cockpit users to connect.
* The socket must not be world-writable.
* The backend must validate the peer identity and derive UserContext from the server-side identity. 

Recommended unit: 

```INI
[Unit]
Description=Cockpit Slurm Persistent Service
After=slurmctld.service
Wants=slurmctld.service

[Service]
Type=simple
ExecStart=/usr/local/bin/cockpit-slurm
Restart=on-failure
RestartSec=5

User=cockpit-slurm
Group=cockpit-slurm

RuntimeDirectory=cockpit-slurm
RuntimeDirectoryMode=0750

[Install]
WantedBy=multi-user.target
```

The service must not use `SupplementaryGroups=slurm` as a substitute for
SlurmDB authorization. Membership in a Unix group associated with the
configured SlurmUser is not required solely to obtain Slurm administrative
authorization. Any additional group or filesystem permission requires a
separate operating-system justification.

### 2.3 Removal of `cockpit-slurm-channel`

The separate executable named:

`cockpit-slurm-channel`

is removed from the Version 3.7 target architecture.

It must not be required for normal communication between the React frontend and the persistent `cockpit-slurm` service.

The following concepts are therefore removed:

* a separate channel executable;

* a channel-specific Go package;

* a channel executable manifest entry;

* a channel process responsible for forwarding application messages;

* a second application-level transport layer between Cockpit and `cockpit-slurm`.

### 2.4 Cockpit transport

The React frontend uses:

```
cockpit.channel()
```

as its Cockpit-facing transport API.

The exact Cockpit channel configuration must be verified against the Cockpit version supported by the project.

For the direct Unix-socket architecture, the intended configuration is not in a manifest file, instead in the frontend JavaScript:
```TS
const channel = cockpit.channel({
    payload: "stream",
    unix: "/run/cockpit-slurm/cockpit-slurm.sock",
    binary: true,
});
```
The stream payload explicitly supports a unix option for opening a Unix socket. 

So the architecture would be:
```text
React
  │
  │ cockpit.channel({ payload: "stream", unix: ... })
  ▼
Cockpit
  │
  │ Unix socket connection
  ▼
cockpit-slurm
  │
  │ Application IPC protocol
  ▼
Resource Cache / Dispatcher / Services
```
No package-bridge manifest entry is needed for that direct socket connection at cockpit version [cockpit doc protocol](https://github.com/cockpit-project/cockpit/blob/main/doc/protocol.md#payload-stream).

cockpit-slurm communication architecture diagram:
```text

                               │
                               │ cockpit.channel()
                               │ payload: "stream"
                               │ unix: /run/cockpit-slurm/...
                               ▼
                    Cockpit Unix socket transport
                               │
                               ▼
                    cockpit-slurm IPC Server
                               │
                               ▼
                         Dispatcher
                               │
              ┌────────────────┴────────────────┐
              ▼                                 ▼
        Query Controller                 Command Controller
              │                                 │
              ▼                                 ▼
        Resource Cache                    UserContext
              │                                 │
              │                                 ▼
              │                           Authorization
              │                                 │
              │                                 ▼

              │                                 │
              │                                 ▼
              │                           Slurm Adapter
              │                                 │
              └────────────────┬────────────────┘
                               ▼
                         Slurm Cluster
```
The application must not assume that one Cockpit `message` event represents one application message. A Cockpit stream is a byte stream and may split or combine application frames.

### 2.5 Application IPC protocol

The application IPC protocol remains owned by `cockpit-slurm`.

The protocol is independent of:

* React;

* TypeScript;

* Cockpit UI components;

* Cockpit channel event boundaries;

* Cockpit bridge internal framing;

* any particular frontend implementation.

The same IPC protocol should be usable over:

* Unix domain sockets;

* Go `net.Pipe` in tests;

* other stream transports in future implementations.

### 2.6 Frontend Resource Tables

Resource-specific tables such as NodeTable, JobTable, UserTable,
AccountTable, and AssociationTable should use a shared project-level
table abstraction where appropriate.

The shared table abstraction should be implemented using the
supported PatternFly React Table components.

Resource-specific table components own resource-specific columns,
formatting, actions, and presentation behavior.

The shared table component owns common table behavior and presentation
patterns.

The Cockpit internal table implementation is not part of the
cockpit-slurm frontend component architecture.

```text
Frontend UI
    ↓
Resource-specific Table
    ↓
Shared GenericTable<T>
    ↓
PatternFly React Table
```

### 2.7 Daemon Slurm identity and execution policy

The daemon's normal Slurm identity is the SlurmDB user `cockpit-slurm`, whose
SlurmDB configuration is `AdminLevel=Administrator`. This is a Slurm-level
authorization identity, separate from the daemon's Linux UID and from every
requesting user's identity. It grants neither Linux root privileges nor access
to arbitrary operating-system resources, does not make the daemon the
configured SlurmUser, and does not authorize arbitrary command execution.
Slurm continues to perform its own authorization and input validation.

Supported Slurm commands and APIs are invoked directly by the daemon under
its own Linux account after application authorization, using fixed adapters,
validated operation specifications, and safely separated executable and
argument values. A privileged D-Bus or sudo helper is not a mandatory
dependency for Slurm operations verified to work under this identity. A
narrowly scoped helper remains a possible exception only for an explicitly
approved operation that requires operating-system privileges unavailable to
the daemon or must preserve the original user's execution identity. Any such
helper requires its own documented security boundary, allowlisted operations,
input validation, requester authorization before invocation, requester-aware
audit records, and acceptance tests. It must not duplicate SlurmDB
authorization or provide arbitrary command execution.

Every operation must be classified before enablement as one of:

1. Safe to execute as the daemon's SlurmDB identity after requester
  authorization and operation-specific validation.
2. Requiring the original requesting user's identity to be preserved.
3. Requiring operating-system privileges beyond the daemon's permissions.
4. Unsupported and therefore rejected until a reviewed execution mechanism
  exists.

Job submission, job ownership, user-specific accounting associations, limits,
defaults, direct-owner rules, and commands with special Slurm authorization
semantics require operation-specific review. SlurmDB Administrator privileges
must not be assumed to satisfy every special command rule or to make execution
as `cockpit-slurm` equivalent to execution as the requester.

### 2.8 Deployment and configuration requirements

Deployment must conceptually:

1. Create a dedicated Linux user and primary group named `cockpit-slurm`, with
  a dedicated UID.
2. Create or configure the corresponding SlurmDB user named `cockpit-slurm`.
3. Configure that SlurmDB user with `AdminLevel=Administrator`.
4. Keep the daemon outside the Unix group associated with the configured
  SlurmUser unless a separately justified OS permission requires membership.
5. Run the daemon as Linux user and group `cockpit-slurm`.
6. Verify required Slurm reads and each supported command under this identity.
7. Verify application authorization still rejects unauthorized requesters.

Creating the SlurmDB user does not imply that required accounting
associations exist. Configure associations separately only where the
individual accounting or job-submission operation requires them; do not
require associations with every Slurm account merely to obtain
`AdminLevel=Administrator`. Do not hardcode a cluster name or account name in
the architecture.

If the SlurmDB service identity is missing, unresolved, or incorrectly
configured, Slurm-dependent readiness and operations must fail closed or be
reported degraded/unready. No implementation-specific configuration
mechanism is mandated here, but the service must not silently fall back to a
requester's identity, root, SlurmUser, or an unapproved helper.

# 3. Design Goals

Version 3.7 has the following goals:

1. Maintain one authoritative in-memory state cache.

2. Separate read operations from write operations.

3. Keep Slurm-specific details inside adapters.

4. Provide a stable canonical resource model.

5. Support multiple concurrent Cockpit sessions.

6. Support multiple IPC connections per logical session.

7. Perform authorization on the server.

8. Avoid trusting client-supplied identity information.

9. Support snapshot and event-based synchronization.

10. Keep the IPC protocol transport-independent.

11. Remove unnecessary forwarding processes.

12. Make the backend testable without Cockpit or React.

13. Support future non-Cockpit clients.

14. Keep the architecture compatible with Slurm REST/OpenAPI models.

15. Use the daemon's dedicated SlurmDB identity for verified Slurm operations
  without transferring its privilege to requesting users.

16. Reduce unnecessary operating-system privileged helpers while retaining a
  narrowly scoped, reviewed exception for operations that genuinely require
  OS privileges or original-user execution semantics.

# 4. Non-Goals

Version 3.7 does not attempt to:

* implement a complete Slurm replacement;

* expose every Slurm command immediately;

* make React responsible for authorization;

* make the frontend maintain the authoritative cluster state;

* make Cockpit understand the application protocol;

* implement a general-purpose message broker;

* introduce a distributed cache;

* introduce persistent database storage for all Slurm resources;

* support arbitrary remote clients over TCP;

* guarantee that every frontend request is completed synchronously;

* preserve the removed `cockpit-slurm-channel` executable.

It also does not grant Linux root privileges to the daemon, treat SlurmDB
Administrator as an operating-system privilege, execute arbitrary commands,
or assume every Slurm operation is safe under the daemon's identity.

```
                               │
                               ▼
                       cockpit-slurm
                    Persistent systemd service
                               │
       ┌───────────────────────┴────────────────────────┐
       │                                                │
       ▼                                                ▼
 Application IPC Server                         Resource Synchronizer
       │                                                │
       ▼                                                ▼

       │                                                │
       ├───────────────────────┐                        ▼
       ▼                       ▼                 Canonical Resources

```

    Slurm command execution and resource acquisition use the daemon's Linux
    account `cockpit-slurm` and its corresponding SlurmDB identity
    `cockpit-slurm` (`AdminLevel=Administrator`). Command authorization instead
    uses the authenticated requesting user's server-derived `UserContext`:

    ```text
    Cockpit / React
      |
      v
    Unix Socket IPC -> SO_PEERCRED -> Authenticated Requesting User
      |                                  |
      |                                  v
      |                         Server-side UserContext
      |                                  |
      |                                  v
      +-------------------------v
             Command Service
          (validate, ledger, lifecycle)
    ```

    The SlurmDB identity does not replace the requesting identity. A successful
    Slurm authorization is not a substitute for application authorization, which
    must complete before the adapter is invoked.

The persistent backend owns all application state and business logic.

Cockpit provides the frontend transport mechanism, but does not own:

* Slurm state;

* resource cache;

* command execution;

* event streams;

* authorization decisions;

* application protocol semantics.

# 6. Main Architectural Layers

### 6.1 Cockpit Integration Layer

Responsibilities:

* create and configure the Cockpit channel;

* send and receive application bytes;

* convert received binary data into application frames;

* encode outgoing application frames;

* translate channel closure into frontend connection state;

* expose a frontend-friendly API to React providers.

This layer must not:

* execute Slurm commands directly;

* implement authorization;

* maintain the authoritative resource cache;

* interpret Slurm-specific command semantics.

Suggested frontend location:

```
src/ipc/
src/services/
```

### 6.2 Application IPC Server Layer

Responsibilities:

* listen on the Unix domain socket;

* accept concurrent connections;

* maintain connection lifecycle;

* read application frames;

* write application frames;

* enforce frame-size limits;

* reject malformed frames;

* associate each connection with server-derived identity;

* pass validated messages to the dispatcher.

This layer knows nothing about individual Slurm resources.

It must not contain:

* Slurm command execution;

* resource-specific business rules;

* React-specific logic;

* UI state.

### 6.3 Protocol Dispatcher

Responsibilities:

* decode the application envelope;

* validate required envelope fields;

* validate message type;

* validate payload structure;

* route requests to the appropriate controller;

* encode responses and events;

* return protocol errors for invalid messages.

The dispatcher does not directly execute Slurm commands.

### 6.4 Query Controller

Responsibilities:

* handle read-only requests;

* validate query parameters;

* read canonical resources from the cache;

* return snapshots;

* return resource metadata;

* return current generation information.

The Query Controller must never communicate directly with Slurm.

```
Query
  ↓
Query Controller
  ↓
Query Service
  ↓
Resource Cache
  ↓
Snapshot
```

### 6.5 Command Controller

Responsibilities:

* validate commands;

* resolve the current server-side user context;

* check capabilities;

* apply command-level authorization;

* enforce idempotency where required;

* create command-tracking records;

* invoke the Command Service;

* return command results or command status.

The Command Controller must not update the resource cache directly.

Authorization is evaluated for the requesting user's `UserContext` against
the operation registry and `operations.yaml`, not against the daemon's
SlurmDB identity. Frontend capabilities and roles are presentation data only.
The validated operation and its schema determine a fixed backend adapter;
clients cannot select an executable, execution identity, shell command, or
unregistered arguments.

```
Command
  ↓
Command Controller
  ↓
Validated request and connection UserContext
  ↓
Command Service (ledger and lifecycle)
  ↓
Requester-scoped Authorizer
  - operation registry / operations.yaml
  - fresh requester authorization context
  - deny -> reject; allow -> continue
  ↓
Fixed Slurm Command Adapter
  ↓
Slurm as daemon execution identity
```
**Capability Model:** server-derived capabilities, frontend presentation, and mandatory backend authorization.

### 6.6 Command Service

Responsibilities:

* coordinate command execution;

* manage command lifecycle;

* invoke command adapters;

* handle command errors;

* create audit records;

* trigger resource refresh after successful mutations.

The Command Service must not modify canonical resources directly.

Before dispatch, the service obtains the requesting user's authorization
decision, validates the operation and target, and durably applies the command
ledger and idempotency rules. It then invokes only the fixed adapter for the
resolved operation. Slurm execution occurs as Linux `cockpit-slurm` and
SlurmDB user `cockpit-slurm`; audit records retain the original requester
separately. A successful adapter result triggers the existing resource
refresh and event path, not a direct cache mutation.

**Command Execution and Idempotency:** durable ledger, command identity, duplicate semantics, and crash recovery.

### 6.7 Resource Service

Responsibilities:

* coordinate resource synchronization;

* invoke resource adapters;

* normalize Slurm data;

* update the canonical resource layer;

* update the resource cache;

* publish resource events.

Only the Resource Service or its controlled cache-update path may modify canonical resource state.

### 6.8 Command Adapter Layer

Purpose:

Translate canonical application commands into Slurm operations.

Examples:

```
CreateAccount
  ↓
sacctmgr add account

CancelJob
  ↓
scancel

DrainNode
  ↓
scontrol update

UpdateQOS
  ↓
sacctmgr modify qos
```

The Command Adapter Layer performs writes only.

Each adapter is an allowlisted, fixed mapping from a validated semantic
operation to a supported Slurm executable/API and validated arguments. It
must not construct shell commands from client input. The default is direct
execution under the daemon's own Linux and SlurmDB identities, after requester
authorization. If a reviewed operation needs the original user's execution
identity or additional OS privilege, it remains disabled until its approved
helper or other execution boundary and tests exist.

It must not:

* update the cache directly;

* publish frontend events directly;

* make authorization decisions;

* contain React-specific logic.

### 6.9 Resource Adapter Layer

Purpose:

Translate Slurm state into canonical resources.

Possible sources:

```
slurmrestd
squeue
scontrol
sacct
sacctmgr
Slurm event or trigger mechanisms
polling fallback
```

Example:

```
squeue
  ↓
Job Resource Adapter
  ↓
Canonical Job
  ↓
Resource Cache
```

The Resource Adapter Layer performs reads and synchronization.

Normal backend acquisition runs under the daemon's Linux service account
`cockpit-slurm` and corresponding SlurmDB identity `cockpit-slurm`. The
Resource Synchronizer acquires one shared canonical collection from the data
Slurm actually permits this identity to retrieve; the cache is not a
per-requester Slurm session. A failed or restricted acquisition must be
reported as incomplete/degraded and must not be presented as a complete
collection.

### 6.10 Canonical Resource Layer

Purpose:

Provide stable domain models independent of Slurm CLI commands.

Each canonical resource contains:

```
Metadata
Spec
Status
```

Typical metadata:

```
Resource ID
Kind
Generation
UpdatedAt
Source
```

The `Spec` and `Status` structures may use generated Slurm OpenAPI models where appropriate, but the frontend must not depend directly on raw CLI output.

### 6.11 Resource Cache

The resource cache is the authoritative application state within the `cockpit-slurm` service.

Responsibilities:

* store canonical resources;

* maintain indexes;

* perform resource lookup;

* generate snapshots;

* maintain generation values;

* compare resource changes;

* provide consistent read access;

* support event generation after updates.

The cache must not store:

* UI state;

* form state;

* unsent commands;

* frontend component state;

* arbitrary client identity claims.

### 6.12 Event Bus

The Event Bus publishes changes after the cache has been updated.

Typical event types:

```
Created
Updated
Deleted
```

Examples:

```
AccountCreated
JobUpdated
NodeUpdated
PartitionDeleted
```

Events must describe changes to authoritative canonical resources.

The Event Bus must not publish an event before the corresponding cache update has succeeded.

### 6.13 Per-connection Stream Registry

Responsibilities:

The registry maintains one automatic resource stream for each IPC connection. It sends initial snapshots, serializes subsequent committed resource events through a bounded per-connection queue, and removes the stream when its IPC connection closes.

There are no application-level `subscribe` or `unsubscribe` messages, `subscriptionId`, or client-selected resource filters. The IPC connection is the stream lifetime and scope. A logical Cockpit session may own multiple IPC connections; do not conflate their lifetimes or identities.

# 7. Session and Connection Model

The architecture distinguishes a logical session from an IPC connection.

```
Cockpit Login
      │
      ▼
Logical Session
      │
      ├── IPC Connection A
      ├── IPC Connection B
      └── IPC Connection C
```

A logical session represents the user's authenticated Cockpit session.

An IPC connection represents one active transport connection between Cockpit and `cockpit-slurm`.

Each connection has:

```
Connection ID
Session ID, when available
Server-derived UserContext
Connection lifecycle
Subscription references
```

The Connection ID identifies one transport connection.

The Session ID identifies the logical session to which the connection belongs.

The server owns the identity associated with the connection.

The client must not be allowed to select or override:

```
Username
UID
GID
AdminLevel
Capabilities
Accounts
DefaultAccount
```

# 8. Identity and Authorization Model

### 8.1 Identity flow

```
Cockpit Authentication
        │
        ▼
Server-derived Linux Identity
        │
        ▼
Slurm User Lookup
        │
        ▼
Slurm AdminLevel
        │
        ▼
Capability Resolver
        │
        ▼
UserContext
        │
        ▼
Authorization
```

The system has three independent identities. They are distinct in code,
authorization decisions, command records, deployment, and tests.

#### 8.1.1 Daemon operating-system identity

The persistent daemon runs as Linux username `cockpit-slurm`, with a dedicated
UID and dedicated primary group `cockpit-slurm`. It never runs as Linux root
or as the configured SlurmUser. `SlurmUser` means the Slurm-configured Linux
user account, not a Unix group. The daemon must not join a Unix group
associated with that account solely to obtain Slurm administrative
authorization. Its OS permissions are limited to those required for the
runtime, configuration, logs, socket, ledger/state, and other explicitly
approved resources.

#### 8.1.2 Daemon SlurmDB identity

The daemon's corresponding SlurmDB user is named `cockpit-slurm` and is
configured with `AdminLevel=Administrator`. This Slurm-level privilege does
not grant Linux root privileges, access to arbitrary OS files, or permission
to perform privileged operating-system operations. It does not make the
daemon the configured SlurmUser and does not permit arbitrary shell or
command execution. Slurm still applies its own authorization and validation;
the daemon uses only fixed, validated command adapters and arguments.

SlurmDB user configuration and accounting associations are separate. An
association is not the source of `AdminLevel`, and associations with every
Slurm account are not required merely to obtain SlurmDB Administrator
authorization. An association such as the test environment's `devel`
association must not be interpreted as limiting that user's AdminLevel to
that account. Associations and account context can still affect accounting
and job-submission operations and must be reviewed per operation. The account
name `devel` is not a deployment default or a hardcoded requirement.

The SlurmDB setting is written `AdminLevel=Administrator`. Slurm command or
API output may represent the value as `Admin`; the existing normalized
requester `UserContext` uses the canonical value `admin`. These are
representations of Slurm authorization data, not interchangeable configuration
values. Identity resolution must document and test the mapping. The application
role `Administrator` is a separate concept.

#### 8.1.3 Requesting-user identity

The requester is the authenticated Cockpit user represented by the IPC
connection. The backend obtains peer credentials through the trusted
server-side mechanism, validates the Linux identity and Cockpit-to-peer
mapping, resolves that user's SlurmDB record and current AdminLevel, resolves
coordinator-account and other trusted scope data, and constructs that user's
`UserContext`. It then evaluates `operations.yaml` and the applicable
visibility policy. The daemon's identity and privileges must never replace
the requester or be inherited by a frontend user. The Cockpit-user-to-
`SO_PEERCRED` mapping must be validated on the target installation before
protected command paths are enabled.

#### 8.1.4 Command and resource execution flow

For every command, the application authorizes the requesting user's current
server-derived context before invoking Slurm. The Command Service resolves and
validates the operation, obtains the required authorization decision, applies
idempotency and ledger rules, and only then dispatches the fixed adapter.
The adapter executes as Linux `cockpit-slurm`; Slurm authenticates and
authorizes the corresponding SlurmDB user `cockpit-slurm`. A successful
SlurmDB authorization never replaces the application's requester
authorization.

Resource acquisition is a separate backend path: the Resource Synchronizer
uses the daemon's SlurmDB identity to acquire Slurm data into the shared
canonical cache, then applies the same per-connection visibility evaluator to
queries, snapshots, and events. Acquisition identity is not a frontend
identity or a visibility grant.

#### 8.1.5 Identity-sensitive operations and helper exception

Every operation must be reviewed to determine whether it is safe under the
daemon's SlurmDB identity, must preserve the original user's execution
identity, requires OS privileges beyond the daemon, or must remain rejected
until a supported mechanism exists. This review is required for job
submission, ownership-sensitive actions, user-specific associations, limits
or defaults, direct-owner rules, and commands with special Slurm
authorization semantics. Do not assume SlurmDB Administrator authorization
makes every command succeed or makes daemon execution equivalent to requester
execution.

A privileged D-Bus or sudo helper is not required for supported Slurm
operations verified under the daemon identity. A narrowly scoped helper may
be introduced only where a documented operation genuinely requires OS-level
privileges or original-user identity. It must expose only approved operations,
validate inputs, be called only after requester authorization, forbid
arbitrary command execution, preserve requester identity in audit records,
and have a separate security boundary and acceptance tests. It must not be
added merely to duplicate Slurm authorization.

### 8.2 UserContext

The server-owned context may contain:

```Go
type UserContext struct {
    Username         string
    UID              uint32
    GID              uint32

    AdminLevel       AdminLevel
    CoordinatorAccounts []string
    Capabilities     CapabilitySet

    Accounts         []string
    DefaultAccount   string
}
```
**Important**: CoordinatorAccounts should represent the accounts for which the user is a Slurm coordinator. It should not be interpreted as “all accounts the user can access.”

The exact Go structure is defined by the identity and connection implementation documents.

Every active connection must have a server-owned user context before it can execute an authorized application operation.
`UserContext` describes only the requesting user. It must not be populated
from the daemon's Linux account or SlurmDB identity. Fresh requester
authorization required for a new command must be resolved using the
established Authorizer flow; the daemon's administrative SlurmDB identity is
never an authorization fallback.

### 8.3 Capability-based authorization

Authorization must be based on capabilities rather than direct UI checks against Slurm's internal enum values.

Examples:

```
ManageAccounts
ManageUsers
ManageNodes
ManagePartitions
ManageQOS
SubmitJobs
CancelJobs
ViewAccounting
ViewClusterState
```

Application services must check capabilities such as:

```
Capabilities.ManageAccounts
Capabilities.CancelJobs
```
Application needs coordinator-specific operations:
```
ManageCoordinatorAccounts
```
The capability resolver should decide what a coordinator may do. Do not make every coordinator automatically equivalent to an operator.


The frontend may use capabilities to build navigation, but the backend must repeat all authorization checks.

|Cockpit-Slurm AdminLevel|Application role|Home page|
| --- | --- | --- |
|Not Set|Visitor|Welcome / Not Configured|
|None|User|User Dashboard|
|Coord| Coordinator | Coordinators Dashboard|
|Operator|Operator|Operations Dashboard|
|Admin|Administrator|Administration Dashboard|

Users should see application roles and capabilities rather than raw internal Slurm authorization values.

In this table, `Admin` is the CLI representation where Slurm emits that
spelling; the backend maps it to the normalized UserContext value `admin`.
Neither spelling replaces the SlurmDB configuration value
`AdminLevel=Administrator`, and none of them is the application role by
itself. The mapping must resolve the requester's current Slurm authorization
data, not the daemon's.

### 8.5 Operation registry and authorization policy

`cockpit-slurm` must use one central operation policy to define which
application operations each application role may invoke. The policy is the
input to the backend operation registry; authorization rules must not be
duplicated independently in command handlers, query handlers, and React
components.

The repository policy source is:

```text
config/authorization/operations.yaml
```

The installed runtime configuration is:

```text
/etc/cockpit-slurm/operations.yaml
```

The matrix defines four application roles:

```text
Administrator
Operator
Coordinator
User
```

These are application roles, not substitutes for Linux identity or Slurm
authorization identity. In particular, the `Administrator` application role
must not by itself be treated as Linux `root` or the configured SlurmUser.
The backend must derive the requesting identity from the authenticated IPC
connection and resolve Slurm `AdminLevel` and coordinator-account membership
from trusted server-side data.

Permission cells use explicit policy values rather than ambiguous Boolean
flags:

| Value | Meaning |
| --- | --- |
| `allow` | Application policy permits invoking the operation. |
| `deny` | The operation is denied. |
| `direct_owner` | The requesting user owns the target job or step. |
| `effective_owner` | The requesting user is the direct owner or a coordinator of the target job's account. |
| `account_coordinator` | The target account is in the requesting user's coordinator-account set. |
| `slurm_admin` | The requesting identity is root, SlurmUser, or Slurm AdminLevel=Administrator. |
| `slurm_admin_level_admin` | The requesting identity has a currently resolved Slurm `AdminLevel=Administrator`; root and SlurmUser do not satisfy this predicate unless they independently have that AdminLevel. |
| `slurm_privileged` | The requesting identity is a Slurm administrator or AdminLevel=Operator. |
| `direct_owner_or_slurm_admin_identity` | The requester is the direct owner, root, or SlurmUser. |
| `direct_owner_or_account_coordinator` | The requester is the direct owner or a coordinator of the target account. |

The backend evaluates the selected cell against the server-derived
`UserContext` and the canonical target resource. Unknown policy values,
missing role cells, unknown operations, and unresolved resource scope must
fail closed. A role label or frontend-supplied account/resource identifier
must never establish ownership or coordinator scope.

All predicates in this registry are evaluated against the requesting user's
`UserContext`. The daemon's Linux identity and SlurmDB `AdminLevel` are never
inputs to requester authorization. `SlurmUser` in policy terminology refers
to the configured Slurm Linux account, not a Unix group. The accepted
`node.drain` and `node.resume` predicate remains
`slurm_admin_level_admin`: the requesting user must have a currently resolved
Slurm AdminLevel Administrator (normalized as `admin` where the User Context
contract requires it). Neither the daemon's `AdminLevel=Administrator` nor
the application role `Administrator` grants these operations to a requester.

The `node.drain` and `node.resume` operations MUST preserve the accepted
Phase 5 authorization predicate: only a requester whose current, server-resolved
Slurm `AdminLevel` is `Administrator` is permitted. Their policy cells MUST
use `slurm_admin_level_admin`, not `slurm_admin`, because `slurm_admin` also
includes root and the configured SlurmUser. The application role
`Administrator` alone is not sufficient.

Each operation entry MUST declare `operation_type: query` or
`operation_type: command`, independently of `status` (`enabled` or `planned`).
Use one validated policy source and one evaluator, but build separate
registries: enabled query entries are registered only in the query-policy
registry; enabled command entries are registered only in the command registry.
Planned entries are validated but registered in neither registry and cannot
be invoked. Query registration MUST NOT make an entry command-dispatchable,
or vice versa.

The policy file is required trusted startup configuration. Missing, unreadable,
malformed, incomplete, or semantically invalid configuration MUST prevent
daemon startup/readiness. Neither query nor command services may become
available with a partial registry, permissive defaults, or a fallback policy.
Publish both registries atomically only after complete validation succeeds.

The operation registry is authoritative for application-level permission to
invoke a handler. It does not replace Slurm's own authorization and validation
of associations, accounts, partitions, QOS, limits, or resource state. A
successful application authorization decision is necessary but is not, by
itself, proof that Slurm will accept the operation.

Operation authorization and record visibility are separate mandatory checks.
An operation policy such as `allow` permits a request to reach its handler; it
does not grant access to every record returned by that handler. The resource
visibility policy defined in Section 8.6 determines which canonical records
may be included in a connection's response or event stream.

For every resource-returning query operation, the operation entry MUST
reference the applicable resource visibility policy using a
`visibility_policy` identifier. The identifier MUST resolve to a policy in
`visibility.yaml`. This reference connects the operation to the resource
policy; it MUST NOT duplicate or override the policy's record-level rules.
Automatic resource events MUST use the same resource visibility policy even
though they are not initiated by a query operation.

The global canonical cache may retain the complete resource collection
available to the backend, but it MUST never be sent directly to a frontend
connection. The backend MUST produce per-connection snapshots, query
responses, and subsequent resource events using the same visibility
evaluator. Changes to a connection's effective access MUST be reflected in
its subsequent projection, including removal of records that are no longer
visible. Such a visibility removal is not deletion of the underlying Slurm
resource.

The frontend may consume effective capabilities derived from this policy to
show or hide navigation and actions. These capabilities are advisory UI data;
the backend must independently evaluate every query and command request.

### 8.6 Resource visibility policy

Cockpit-slurm MUST maintain a resource visibility policy independently of the
operation authorization policy. The two policies answer different questions:

* `operations.yaml`: May this application role invoke this operation?
* `visibility.yaml`: Which canonical records of this resource may this
authenticated connection receive?

Neither policy replaces Slurm's native authorization. A request or record
must pass every applicable security check before it is returned or acted on.

#### 8.6.1 Policy source and responsibility

The repository policy source is:

```text
config/authorization/visibility.yaml
```

The installed runtime configuration is:

```text
/etc/cockpit-slurm/visibility.yaml
```

`visibility.yaml` is resource-oriented. It defines the visibility policy for
each canonical resource type, the role-specific scope rules, and the trusted
canonical attributes required to evaluate those rules. It MUST NOT be a copy
of Slurm's `PrivateData` configuration or a list of Slurm CLI commands.

`operations.yaml` remains authoritative for permission to invoke handlers.
For a query that returns canonical resources, its `visibility_policy`
identifier MUST reference the applicable policy in `visibility.yaml`.
Resource event delivery MUST select the policy by canonical resource type
and apply it independently for each IPC connection.

The same resource policy SHOULD be reusable by collection queries, individual
resource lookups, initial snapshots, subsequent change events, and any future
read interface that returns the same canonical resource type. A caller-supplied
filter, account name, owner, role, or resource identifier MUST NOT weaken or
bypass the policy.

#### 8.6.2 Policy evaluation requirements

The visibility evaluator MUST use the server-derived `UserContext` and
trusted canonical resource attributes. It MUST NOT trust identity, role,
ownership, account membership, or coordinator scope supplied by the frontend.

The policy MUST use default-deny behavior:

* an unknown resource type or policy identifier MUST be denied;
* an unknown role or unsupported scope rule MUST be denied;
* a missing or invalid attribute required by a rule MUST not grant visibility;
* unresolved ownership denies only a direct-owner branch, and unresolved
  account scope denies only a coordinator-account branch; either condition
  MUST NOT invalidate an independently established match in the other branch;
* if neither applicable branch establishes visibility, access MUST be denied;
* a missing policy entry MUST NOT imply cluster-wide visibility.

Policy loading and validation MUST complete before query services or
per-connection resource streams become ready. Missing, unreadable, malformed,
incomplete, or semantically invalid visibility configuration MUST prevent
service readiness. The daemon MUST NOT start with a partial policy, a
permissive fallback, or an implicit unrestricted policy. The operation and
visibility policy registries MUST be validated before they are published for
use.

#### 8.6.3 Phase 6 resource policies

Phase 6 implements visibility policies only for Nodes and active Jobs. The
following rules are normative for Phase 6:

| Resource | Administrator | Operator | Coordinator | User |
| --- | --- | --- | --- | --- |
| Node | All Nodes | All Nodes | All Nodes | All Nodes |
| Active Job | All active Jobs | All active Jobs | Directly owned Jobs and Jobs belonging to coordinated accounts | Directly owned Jobs |

Node visibility is cluster-wide for all authenticated application roles.
Node visibility does not grant permission to change Node state; command
authorization remains governed by `operations.yaml` and Slurm's own checks.

For Job visibility:

* **Administrator** and **Operator** may see all active Jobs in the configured
  cluster.
* **Coordinator** may see a Job if the user directly owns it OR the Job's
  canonical Slurm account is in that user's server-derived
  `CoordinatorAccounts`.
* **User** may see a Job only if the user directly owns it.

Direct ownership and account coordination are independent conditions. A
Coordinator MUST be able to see a directly owned Job even when its account is
not in `CoordinatorAccounts`.

The Phase 6 evaluator MUST use these trusted attributes:

| Context/resource | Canonical attribute | Visibility purpose |
| --- | --- | --- |
| `UserContext` | `UID` | Authenticated Linux UID used for direct ownership comparison |
| `UserContext` | `AdminLevel` and resolved application role | Determine privileged role scope |
| `UserContext` | `CoordinatorAccounts` | Server-derived set of accounts coordinated by the user |
| Canonical Job | `UserID` | Numeric UID of the Job owner |
| Canonical Job | `Account` | Slurm account associated with the Job |
| Canonical Job | `JobID` and cluster identity | Identify the canonical Job record |
| Canonical Node | `NodeName` and cluster identity | Identify the canonical Node record |

Direct Job ownership MUST be evaluated by comparing the authenticated
`UserContext.UID` with the canonical Job `UserID`. The Job adapter MUST
normalize the Slurm owner identity into a numeric UID before this comparison.
If that mapping cannot be established reliably, the evaluator MUST NOT infer
ownership from a frontend display name or an unverified username.

Coordinator scope MUST be evaluated by comparing the canonical Job `Account`
with the server-derived `UserContext.CoordinatorAccounts`. The general
`UserContext.Accounts` membership list MUST NOT be treated as the coordinator
account set. Direct ownership and coordinated-account scope are independent
authorization branches. The direct-owner branch requires valid trusted
`UserContext.UID` and Job `UserID` values that match; a missing or invalid Job
account MUST NOT invalidate an otherwise established direct-owner match. The
coordinator-account branch requires a valid trusted Job `Account` and resolved
server-derived `CoordinatorAccounts` containing it; missing or invalid Job
owner information MUST NOT invalidate an otherwise established account match.
Missing or invalid attributes deny the branch that depends on them and MUST
never themselves grant access. If neither applicable branch establishes access,
visibility MUST be denied. Cluster identity and authenticated connection context
remain mandatory for every decision. Administrator and Operator visibility
remains governed by their existing privileged-role policy.

The cluster identity is part of the resource scope. A policy decision for one
configured cluster MUST NOT accidentally authorize a record from another
cluster if multi-cluster support is introduced.

#### 8.6.4 Future resource policies

The visibility framework is intended to support additional canonical
resources in later phases. The following resource families are anticipated;
their final scopes and role rules MUST be specified and accepted when each
resource is introduced. This list does not authorize access or expand Phase 6
implementation scope.

| Future resource | Examples of visibility dimensions to define |
| --- | --- |
| Accounts | Account hierarchy, coordinator scope, and user associations |
| Users | Self, account associations, coordinated accounts, and privileged scope |
| Partitions | Cluster scope and any future partition-specific restrictions |
| Reservations | Reservation users, accounts, and permitted reservation access |
| Slurm accounting events | Event type, cluster, related resource, and role scope |
| Usage/accounting records | Job owner, user, account, cluster, and reporting scope |

These are design dimensions, not approved visibility rules. Each future
resource MUST receive an explicit policy and acceptance tests before it is
exposed through a query, snapshot, or event.

#### 8.6.5 Event categories

The word *event* refers to different data in this architecture and MUST NOT
imply one shared visibility policy:

1. **Resource change events** are IPC notifications about changes to
   canonical Nodes, Jobs, Accounts, or other resources. They MUST use the
   visibility policy of the related canonical resource.
2. **Slurm accounting events** are Slurm-maintained event/history records.
   They are a future resource type and MUST have their own explicit
   record-visibility policy before exposure.
3. **Cockpit-slurm audit events** record application actions and outcomes.
   They require a separately defined audit-access policy and MUST NOT inherit
   resource-change or Slurm accounting-event visibility automatically.

In particular, a User may receive an allowed Node state-change notification
without thereby receiving permission to query Slurm's accounting event
history.

#### 8.6.6 Relationship with Slurm PrivateData

Slurm's `PrivateData` setting remains a Slurm-native configuration in
`slurm.conf`. It is independent of both `operations.yaml` and
`visibility.yaml`.

`PrivateData` controls what Slurm permits the backend execution identity to
retrieve. For normal acquisition that identity is the daemon's Linux account
`cockpit-slurm` and SlurmDB user `cockpit-slurm` (`AdminLevel=Administrator`).
`visibility.yaml` controls which records already retrieved into the canonical
model may be returned to each authenticated IPC connection. These are
separate security layers: application visibility MUST NOT bypass Slurm's
restrictions, and SlurmDB Administrator privileges MUST NOT be assumed to
bypass every `PrivateData` restriction.

The application MUST enforce visibility even when Slurm's default visibility
is broad, and Slurm's own authorization MUST always be respected. The backend
service acquires shared data under its daemon identity, not separately under
each Cockpit requester's identity; Slurm `PrivateData` therefore does not
implement per-user Coordinator or User visibility. Conversely,
`visibility.yaml` is not a way to override Slurm authorization.

The actual `PrivateData` value is configured and managed only in
`slurm.conf`; it MUST NOT be configured through `operations.yaml` or
`visibility.yaml`. If a configured setting prevents acquisition of required
canonical resources, the acquisition design and its completeness semantics
must be reviewed and tested. The backend MUST NOT represent a partial result
as a complete collection, generation, snapshot, or event baseline.

The existing test environment is reported as:

```text
SlurmUser=slurm
PrivateData=none
AccountingStorageType=accounting_storage/slurmdbd
AuthType=auth/munge
```

In that environment, the daemon runs as Linux `cockpit-slurm` and the
corresponding SlurmDB user is configured with `AdminLevel=Administrator`.
Tests under `PrivateData=none` establish behavior only for that configuration;
they do not establish behavior under more restrictive `PrivateData` values.
Each supported deployment configuration requires its own validation.

#### 8.6.7 Cache, snapshots, queries, and event delivery

The authoritative cache SHOULD retain one shared canonical collection rather
than maintaining a separate authoritative cache for each user. Visibility
filtering MUST occur at the per-connection response and delivery boundary.

The same evaluator MUST be applied to:

1. initial resource snapshots;
2. explicit collection query responses;
3. individual resource lookups;
4. subsequent resource change events; and
5. reconnection and snapshot-recovery responses.

When a record becomes invisible to a connection because its ownership,
account scope, role, or other trusted authorization context changes, the
backend MUST remove it from that connection's frontend projection. This
removal MUST NOT be represented as deletion of the underlying Slurm resource.
Changes to trusted scope data, including coordinator-account membership,
MUST take effect for subsequent visibility decisions and event delivery.

The frontend is a presentation layer only. Client-side filtering MAY improve
presentation, but MUST NOT be relied upon to protect records received from
the backend.

#### 8.6.8 Visibility acceptance requirements

For each implemented resource policy, tests MUST verify:

* each role receives only records allowed by its declared scope;
* direct ownership and coordinator scope are evaluated from trusted
  canonical attributes;
* a valid direct-owner match remains visible with an empty or missing account,
  while an invalid or missing owner cannot establish direct ownership;
* a valid coordinated-account match remains visible with a missing or invalid
  owner, while an invalid, missing, or unrelated account cannot establish
  coordinator scope; neither failed branch grants access;
* frontend-supplied identity, role, owner, account, or scope values cannot
  alter the decision;
* missing or invalid required attributes fail closed;
* collection queries, individual lookups, initial snapshots, and subsequent
  events produce consistent visibility results;
* a record that becomes invisible is removed from the affected connection's
  projection without being deleted from the global cache;
* reconnect and snapshot recovery apply the same policy; and
* unknown or invalid policies cannot result in unrestricted visibility.

Phase 6 acceptance tests MUST cover the Node and active Job rules in Section
8.6.3. Future resource policies MUST add resource-specific tests before those
resources are enabled.

## 9. IPC Transport Architecture

### 9.1 Transport path

```
React
  ↓
cockpit.channel()
  ↓
Cockpit transport
  ↓
Unix socket
  ↓
cockpit-slurm IPC Server
  ↓
Protocol Dispatcher
  ↓
Application Services
```

There is no intermediate `cockpit-slurm-channel` executable.

### 9.2 Unix socket

The persistent service listens on a Unix domain socket.

Recommended production path:

```
/run/cockpit-slurm/cockpit-slurm.sock
```

A development-specific per-user path may be used when required.

The socket must have controlled ownership and permissions.

The service must not expose an unauthenticated world-writable socket.

### 9.3 Connection concurrency

The IPC server must support multiple concurrent connections.

Each connection must have:

* independent receive buffering;

* independent send handling;

* independent connection lifecycle;

* independent subscription references;

* independent request correlation;

* access to shared application services and cache.

A slow client must not block unrelated clients.

### 9.4 Application framing

The IPC transport is a byte stream.

The application protocol uses explicit length-prefixed frames.

Each frame consists of:

```
4-byte unsigned big-endian payload length
UTF-8 JSON payload
```

The length excludes the four-byte prefix.

```
+----------------------+----------------------+
| Payload length       | JSON payload         |
| uint32, big-endian   | UTF-8 bytes          |
+----------------------+----------------------+
        4 bytes              N bytes
```

The receiver must support:

* partial frames;

* multiple frames in one read;

* one frame split across multiple reads;

* arbitrary Cockpit message boundaries.

The receiver must reject:

* invalid lengths;

* frames larger than the configured maximum;

* invalid UTF-8;

* invalid JSON;

* invalid application envelopes.

The initial maximum frame size should be explicitly configured, for example:

```
1 MiB
```

The final value must be defined by the implementation configuration.

### 9.5 Binary mode

The frontend should use binary mode for the Cockpit stream when the selected Cockpit API and version support the required configuration:

TypeScript

```
cockpit.channel({
    payload: "stream",
    binary: true,
});
```

The exact Unix-socket option must be verified against the supported Cockpit version before implementation is finalized.

The application framing code must not depend on Cockpit event boundaries.

### 9.6 Text mode

Newline-delimited JSON is not the Version 3.7 target protocol.

Text mode may be used for temporary diagnostics or a standalone test client, but production IPC must use the length-prefixed framing contract.

## 10. Application Message Envelope

Every application message must contain a common envelope.

A conceptual envelope is:

JSON

```
{
  "version": 1,
  "type": "request",
  "request_id": "req-123",
  "operation": "list_nodes",
  "payload": {}
}
```

The final envelope schema is defined by the IPC protocol document.

The envelope should support at least:

```
hello
hello-response
ping
pong
request
response
event
error
```

### 10.1 Request correlation

Requests that expect a response must contain a unique request ID.

The response must contain the same request ID.

The frontend must not assume that responses arrive in the same order as requests.

### 10.2 Events

Events are asynchronous messages generated by the backend.

Events must not require a request ID unless the protocol explicitly defines such a relationship.

### 10.3 Errors

Protocol errors, validation errors, authorization errors, Slurm errors, and internal errors must be distinguishable.

The frontend must not depend on parsing human-readable error text to determine the error category.

## 11. Read Path

```
React
  ↓
cockpit.channel()
  ↓
IPC Server
  ↓
Protocol Dispatcher
  ↓
Query Controller
  ↓
Query Service
  ↓
Resource Cache
  ↓
Snapshot
  ↓
React
```

The read path must not access Slurm directly.

The cache is the source of truth for normal frontend queries.

If the cache is unavailable or not initialized, the service must return a defined application error rather than silently executing an uncontrolled fallback query.

## 12. Write Path

```
React
  ↓
cockpit.channel()
  ↓
IPC Server
  ↓
Protocol Dispatcher
  ↓
Command Controller
  ↓
Validated request and requester UserContext
  ↓
Command Service (ledger and idempotency)
  ↓
Requester-scoped Authorizer
  - operations.yaml policy and fresh requester context
  - deny -> reject; allow -> continue
  ↓
Command dispatch
  ↓
Fixed Slurm Command Adapter
  ↓ execute as Linux cockpit-slurm / SlurmDB cockpit-slurm
  ↓
Slurm
  ↓
Resource Service
  ↓
Resource Adapter
  ↓
Canonical Resource
  ↓
Resource Cache
  ↓
Event Bus
  ↓
Per-connection Stream Registry
  ↓
React
```

The Command Adapter must not update the cache directly.

The backend must reject an unauthorized or invalid request before Slurm
command execution. A frontend cannot choose the Linux execution user, SlurmDB
identity, executable, arbitrary arguments, shell command, or privilege
escalation mechanism. A SlurmDB authorization result cannot replace the
requester's application authorization result.

After a successful mutation:

1. the command result is returned or tracked;

2. the affected resource is refreshed;

3. the Resource Service normalizes the new Slurm state;

4. the cache is updated;

5. the Event Bus publishes the resulting change;

6. each connected stream receives the event.

# 13. Synchronization Model

### 13.1 Automatic stream baseline

```
Accept IPC connection
  ↓
Atomically register stream and capture cache baseline
  ↓
Queue initial snapshots
  ↓
Queue subsequent committed events
```

Stream registration and snapshot capture must be ordered with cache publication so a committed change is not lost between the baseline and subsequent event delivery.

### 13.2 Normal operation

```
Slurm state changes
  ↓
Resource Adapter
  ↓
Resource Service
  ↓
Cache update
  ↓
Event Bus
  ↓
Per-connection Stream Registry
  ↓
IPC connection
  ↓
React
```

The frontend should not poll Slurm directly.

If polling is used internally, it belongs to the Resource Synchronizer and must not be implemented separately by every React component.

The Resource Synchronizer uses Linux `cockpit-slurm` and its SlurmDB identity
`cockpit-slurm` for normal backend acquisition. It populates one shared cache
with the records Slurm permits that identity to retrieve. It must track
acquisition completeness; a restricted or failed source must not be silently
treated as a complete collection or establish a misleading generation
baseline. Per-connection visibility remains mandatory after acquisition.

### 13.3 Generation tracking

The cache should maintain a monotonically increasing generation value.

Generation values are used for:

* snapshot identification;

* event ordering;

* detecting missed events;

* reconnect recovery;

* debugging;

* consistency checks.

The exact generation semantics must be defined in the IPC and cache documents.

# 14. Command Tracking

The backend maintains a command ledger/tracking store for mutating operations.
It must implement the operation's approved idempotency, ordering, durability,
and recovery requirements; an in-memory cache alone is not sufficient where
the command contract requires durable deduplication. Command IDs and IPC
request correlation IDs remain distinct.

Responsibilities:

* idempotency;

* duplicate detection;

* progress tracking;

* command status lookup;

* correlation between frontend requests and Slurm operations.

Suggested states:

```
Pending
Running
Succeeded
Failed
Cancelled
```

Retention must follow the approved command contract and be configurable where
that contract permits. A repeated command ID must not execute a second time.
The ledger must retain the requester and execution identities separately.

Long-running operations must not require the IPC connection to remain blocked until Slurm finishes.

# 15. Audit Logging

Commands that change cluster state should produce audit records.

An audit record may contain:

```
Requesting username and UID
Requesting user's resolved Slurm AdminLevel and application role, where relevant
IPC connection ID and request/correlation ID
OperationID
Target resource and scope
Authorization decision and policy result
Linux execution username and UID
SlurmDB execution identity
Timestamp(s), outcome, duration, and error information
```

The record must make it possible to distinguish `Requested by: dev` from
`Executed by: cockpit-slurm`. The daemon must never record its own account as
the requester merely because it executed the command. Do not expose sensitive
internal command details to frontend users who are not authorized to see them.

Audit logging must not record every UI interaction.

Sensitive values must be excluded or appropriately protected.

The exact audit policy is defined separately from the transport protocol.

# 16. React Architecture

The React frontend should contain a single reusable IPC client layer. 

Keep the frontend thinner, the frontend look conceptually like:

```text
src/
  ipc/
    client.ts
    framing.ts
    protocol.ts
    errors.ts

  services/
    resource-service.ts
    command-service.ts
    subscription-service.ts

  contexts/
    UserProvider.tsx
    AccountProvider.tsx
    NodeProvider.tsx
    JobProvider.tsx

  components/
    tables/
      generic-table.tsx
```

**The frontend services are transport/client abstractions, not business-logic services.**

For example:
```text
NodeProvider
   ↓
resourceService.list<Node>()
   ↓
IPC
   ↓
backend Query Service
   ↓
Resource Cache
```
not:
```text
NodeProvider
   ↓
frontend NodeService
   ↓
frontend NodeCache
   ↓
frontend NodeEventBus
   ↓
IPC
```

### 16.1 IPC client responsibilities

The IPC client owns:

* channel creation;

* frame encoding;

* frame decoding;

* receive buffering;

* request correlation;

* connection state;

* protocol error handling;

* reconnect behavior, if implemented.

React components must not implement framing directly.

### 16.2 Resource providers

Providers consume their resource events from the shared IPC connection stream. They do not create application-level subscriptions.

Examples:

```
IPC connection stream
  ├── Account events → AccountProvider, when implemented
  ├── Node events → NodeProvider
  └── Job events → JobProvider, when implemented
```

Each provider receives:

```
Snapshot
  ↓
Events
  ↓
Context state update
```

The frontend cache is a presentation cache only.

It must not replace the authoritative backend cache.

### 16.3 Dynamic navigation

Navigation should be derived from the server-provided user context and capabilities.

```
UserContext
  ↓
Capability Resolver
  ↓
Navigation Builder
  ↓
React Sidebar
  ↓
Pages
```

Every page must still rely on backend authorization.

# 18. Lifecycle and Shutdown

The persistent service must:

1. initialize configuration;

2. initialize logging;

3. initialize identity and authorization dependencies;

4. initialize adapters;

5. initialize the canonical resource cache;

6. initialize synchronization;

7. create the Unix socket;

8. start the IPC server;

9. accept connections;

10. handle termination signals;

11. stop accepting new connections;

12. close or drain active connections;

13. stop synchronization;

14. flush required audit information;

15. remove the socket if appropriate;

16. exit cleanly.

Before Slurm-dependent readiness or command dispatch, the service must
validate that the daemon's SlurmDB identity is available and that the
configured operation can be performed under it. A missing, unresolved, or
misconfigured service identity must leave affected Slurm functionality
unready/degraded and commands fail-closed; the backend must not substitute
the requester, root, SlurmUser, a frontend claim, or an unapproved helper.
Resource acquisition that is partial must be reported as incomplete rather
than as a complete global collection.

The service must not leave a stale socket that prevents a later startup.

# 19. Security Requirements

The implementation must:

* restrict Unix socket permissions;

* validate peer identity where supported;

* derive identity on the server;

* reject client-supplied identity overrides;

* enforce authorization for every command;

* validate all message envelopes;

* enforce maximum frame size;

* avoid shell command construction from untrusted strings;

* use safe argument handling for Slurm commands;

* avoid logging secrets;

* prevent one client from reading another client's private state;

* enforce backend authorization before exposing protected resource snapshots or events;

* close connections on unrecoverable protocol violations.

It must also:

* keep daemon Linux identity, daemon SlurmDB identity, and requesting-user
  identity distinct;
* authorize every command as the requesting user before adapter/helper
  invocation;
* execute only fixed, validated adapter operations and arguments;
* record requester and execution identities separately in the ledger/audit;
* never assume SlurmDB Administrator is Linux root or the configured
  SlurmUser;
* keep `PrivateData` restrictions separate from application visibility and
  report incomplete acquisition honestly; and
* allow a helper only for a separately approved OS-privilege or
  identity-preservation requirement, never as a way to bypass application
  authorization.

The frontend is not a security boundary.

# 23. Version 3.6 to Version 3.7 Compatibility and Migration

Version 3.7 retains the Version 3.6 IPC framing and envelope, Cockpit
`cockpit.channel()` transport, direct Unix socket, resource and event model,
shared canonical cache, automatic per-IPC-connection streams, server-derived
identity, operation registry, `operations.yaml`, `visibility.yaml`, and
accepted Phase 5 authorization policy, except for the explicit daemon
execution and resource-acquisition identity clarifications in this document.

The Linux service account remains `cockpit-slurm`. The new deployment
requirement is the corresponding SlurmDB user `cockpit-slurm` configured with
`AdminLevel=Administrator`. Existing installations must configure and
validate this SlurmDB identity before relying on the v3.7 execution model;
updating this document alone does not change a deployed service or cluster.

Do not remove an existing privileged helper merely because this identity
model is introduced. First verify that every operation previously depending
on that helper has a supported replacement under the daemon's SlurmDB
identity. Review identity-sensitive commands and OS-level operations
separately. Commands without a validated execution model remain disabled.

The existing test configuration reports `PrivateData=none`; this provides no
evidence for more restrictive settings. Validate Slurm authentication,
identity mapping, supported reads and mutations, associations where
operation-specific, and `PrivateData` behavior on the target cluster before
claiming deployment compatibility.

# 24. Acceptance Criteria

The preserved Version 3.6 architecture is considered implemented only when
its original transport, protocol, resource, stream, and service criteria
remain satisfied:

* the persistent service is named `cockpit-slurm`;

* the separate `cockpit-slurm-channel` executable is removed;

* the frontend uses `cockpit.channel()`;

* the frontend can communicate with the Unix socket without the removed forwarding executable;

* the application protocol uses explicit length-prefixed framing;

* the frontend handles fragmented and coalesced stream data;

* the IPC server supports multiple concurrent connections;

* identity is server-derived;

* authorization is performed by the backend;

* queries read from the cache;

* commands do not update the cache directly;

* resource refresh updates the cache;

* cache updates produce events;

* each IPC connection receives an initial snapshot and subsequent events;

* protocol errors are structured;

* frame-size limits are enforced;

* unit and integration tests pass;

* `go test ./...` passes;

* `go vet ./...` passes;

* the supported Cockpit version and Unix-socket channel configuration are documented and verified.

## 24.1 Daemon operating-system identity

Acceptance must verify:

* the daemon runs as Linux user `cockpit-slurm` with its dedicated UID and
  primary group `cockpit-slurm`;
* it does not run as root or as the configured SlurmUser;
* it does not depend on membership in the SlurmUser-associated Unix group for
  Slurm administrative authorization; and
* it has only the OS permissions required by its documented responsibilities.

## 24.2 SlurmDB identity and operation behavior

Acceptance must verify:

* the SlurmDB user `cockpit-slurm` exists and has
  `AdminLevel=Administrator`;
* supported administrative reads work under this identity;
* supported administrative mutations, including Node drain and resume, work
  under this identity, with each command-specific exception reviewed
  separately;
* SlurmDB `Administrator`, any CLI-facing `Admin` representation, normalized
  requester `admin`, and application role `Administrator` are not confused;
  and
* an accounting association such as `devel` is not treated as the source or
  account-scope limit of SlurmDB Administrator privileges, while
  operation-specific accounting and submission association needs are tested.

These are acceptance requirements, not claims that the current environment
has already passed them.

## 24.3 Requester authorization

Acceptance must verify:

* a requester can perform only operations allowed by `operations.yaml` and
  the applicable backend checks;
* an ordinary User and an Operator cannot inherit the daemon's SlurmDB
  Administrator privileges;
* frontend-supplied identity, role, capability, or account values cannot
  change an authorization decision;
* `node.drain` and `node.resume` continue to use the accepted
  `slurm_admin_level_admin` predicate against the requesting user's currently
  resolved Slurm AdminLevel; neither the daemon's AdminLevel, the application
  role alone, nor a broader root/SlurmUser predicate grants them; and
* denied or invalid requests are rejected before invoking a Slurm command or
  helper.

## 24.4 Identity separation and audit

Acceptance must verify:

* the requesting user remains distinct from both daemon execution identities;
* authorization never substitutes daemon identity for requester identity;
* command ledger and audit records preserve requester username/UID,
  requester authorization context and role where relevant, connection/request
  correlation, OperationID, target/scope, policy decision, Linux execution
  identity, SlurmDB execution identity, outcome, timestamps, and errors; and
* records distinguish, for example, `Requested by: dev` from
  `Executed by: cockpit-slurm` without exposing sensitive command details to
  unauthorized users.

## 24.5 Resource acquisition and visibility

Acceptance must verify:

* global backend acquisition under the tested Slurm configuration and the
  daemon SlurmDB identity;
* one shared canonical cache remains authoritative;
* visibility is evaluated independently for each IPC connection; and
* snapshots, queries, and events use the same visibility evaluator and
  preserve the existing generation, recovery, and automatic-stream
  semantics.

The intended test configuration is documented in Section 8.6.6. Tests under
`PrivateData=none` establish behavior only under that configuration. Record
restrictive `PrivateData` settings separately as untested until individually
validated. Verify that Slurm's restrictions are respected and that incomplete
acquisition is never presented as a complete collection.

## 24.6 Helper reduction and exceptions

Acceptance must verify:

* validated Slurm operations do not depend on unnecessary privileged D-Bus or
  sudo helpers;
* each remaining helper has a documented OS-level privilege or
  identity-preservation requirement, allowlisted operations, input
  validation, audit behavior, and separate boundary tests; and
* helper invocation cannot bypass requester authorization or permit
  arbitrary command execution.
