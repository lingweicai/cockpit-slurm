## 5. Add a v3.6 → v3.7 change section

Add a section describing the implementation changes introduced by v3.7.

Include at least:

### 5.1 Daemon operating-system identity

The daemon continues to run as Linux user and primary group `cockpit-slurm`.

It must not run as root or as the configured SlurmUser.

Do not require membership in the Unix group associated with SlurmUser merely to obtain Slurm administrative authorization.

### 5.2 Daemon SlurmDB identity

The corresponding SlurmDB user `cockpit-slurm` must be configured with:

`AdminLevel=Administrator`

The implementation must verify this identity before relying on it for supported Slurm operations.

Do not confuse:
- SlurmDB configuration value `Administrator`;
- CLI-facing representation `Admin`;
- normalized requester UserContext value `admin`;
- application role `Administrator`.

These are related but distinct representations or concepts.

### 5.3 Requester identity

The authenticated Cockpit user remains the requester.

The backend continues to derive the requester from trusted IPC peer credentials and resolve the requester's own SlurmDB information and application authorization context.

The daemon's SlurmDB Administrator privilege must never be used as the requester's authorization context.

### 5.4 Resource acquisition

The Resource Synchronizer runs inside the persistent daemon and uses the daemon's Linux and SlurmDB identity for normal backend Slurm data acquisition.

It acquires the data Slurm actually permits this identity to retrieve and populates one shared canonical resource cache.

Per-connection visibility filtering remains mandatory for:
- Initial snapshots.
- Collection queries.
- Individual resource lookups.
- Incremental events.
- Reconnection and snapshot recovery.

Do not create a separate authoritative cache for each requesting user.

Do not expose the global canonical cache directly to a frontend connection.

### 5.5 Command execution

Supported Slurm operations are executed by fixed backend adapters under the daemon's own Linux and SlurmDB identity after requester authorization and operation-specific validation.

The command flow remains:

`Authenticated requester → UserContext → operations.yaml authorization → validation and command ledger → fixed adapter → Slurm execution as cockpit-slurm`

A successful SlurmDB authorization does not replace application authorization.

### 5.6 Privileged-helper reduction

A privileged D-Bus or sudo helper is not a mandatory dependency for Slurm operations verified to work under the daemon identity.

Do not remove existing helpers without reviewing each operation that depends on them.

Retain a narrowly scoped helper only when an operation genuinely requires:
- OS-level privileges beyond the daemon's permissions; or
- preservation of the original requester's execution identity.

Operations without a validated execution model must remain disabled.

## 6. Update the implementation requirements for identity resolution and authorization

Review the existing UserContext and authorization implementation sections.

Preserve the following requirements:

- Requester UID, GID, and username are derived from the authenticated IPC connection.
- The backend resolves the requester's SlurmDB identity and current AdminLevel.
- Coordinator account scope is derived from trusted server-side information.
- The backend constructs the requester's UserContext.
- Authorization is evaluated using the requester's UserContext and the operation registry.
- Frontend-supplied identity, role, ownership, and coordinator scope are never trusted.
- Authorization is re-evaluated for every command request.
- Unknown or invalid policy entries fail closed.

The daemon's Linux identity and SlurmDB Administrator identity must never be inputs to requester authorization.

- The broader `slurm_admin` predicate.

The implementation plan must explicitly preserve this Phase 5 decision.

## 7. Update resource acquisition and Resource Synchronizer implementation

Review all sections describing resource acquisition, resource adapters, cache population, synchronization, and events.

The implementation plan must explicitly define the Resource Synchronizer's execution identity:

- Linux execution account: `cockpit-slurm`.
- SlurmDB identity: `cockpit-slurm`.
- SlurmDB configuration: `AdminLevel=Administrator`.

The Resource Synchronizer is a backend data-acquisition component, not an IPC requester.

Its responsibilities are to:
1. Execute supported Slurm resource queries using the daemon identity.
2. Normalize results into canonical resource models.
3. Update the shared canonical cache.
4. Track source acquisition success, failure, and completeness.
5. Publish cache changes through the existing event mechanism.
6. Preserve existing generation and recovery semantics.

The implementation must not treat a restricted or failed source as a complete global collection.

The implementation must not silently establish a complete generation baseline from partial data.

### PrivateData

Keep Slurm `PrivateData` separate from application visibility.

- Slurm `PrivateData` determines what Slurm permits the daemon identity to retrieve.
- `visibility.yaml` determines what an authenticated IPC connection may receive from the retrieved canonical data.
- Application visibility cannot bypass Slurm restrictions.
- SlurmDB Administrator must not be assumed to bypass every `PrivateData` restriction.

The existing test environment reports `PrivateData=none`. This validates only that configuration. Do not claim that restrictive `PrivateData` configurations have been tested unless repository evidence establishes this.

## 8. Update command execution and privileged-helper implementation

Review all existing command execution, command adapter, helper, audit, and command-ledger requirements.

For each enabled operation, require an explicit execution classification:

1. Safe to execute as daemon identity after requester authorization and operation-specific validation.
2. Requires original requesting-user execution identity.
3. Requires OS-level privileges beyond daemon permissions.
4. Unsupported until an approved execution mechanism is implemented.

Do not assume all Slurm commands work under SlurmDB Administrator.

Do not assume job submission, ownership-sensitive commands, user-specific accounting operations, or commands with special Slurm authorization rules are equivalent when executed as `cockpit-slurm`.

For normal supported Slurm operations:
- Use fixed executable and argument construction.
- Do not use arbitrary shell commands.
- Do not permit frontend selection of execution identity.
- Do not permit arbitrary executable or argument injection.
- Preserve command validation, authorization, idempotency, ledger, audit, and post-command synchronization.

For any remaining helper:
- Document the operation requiring it.
- Document why direct daemon execution is insufficient.
- Define the allowlisted interface.
- Validate inputs.
- Require requester authorization before helper invocation.
- Preserve requester identity in audit and command tracking.
- Add dedicated helper security tests.

A helper must not duplicate SlurmDB authorization unnecessarily.

## 13. Update acceptance criteria

Add a v3.7 acceptance section or update existing acceptance criteria to include the following.

### A. Daemon OS identity

- Daemon runs as Linux user `cockpit-slurm`.
- Daemon does not run as root or configured SlurmUser.
- Daemon does not depend on SlurmUser-associated Unix group membership for Slurm authorization.
- Daemon has only documented OS permissions.

### B. SlurmDB identity

- SlurmDB user `cockpit-slurm` exists.
- Its AdminLevel is `Administrator`.
- Required Slurm reads work under the daemon identity.
- Supported administrative mutations work under the daemon identity.
- Command-specific exceptions are individually reviewed.

### C. Resource acquisition

- Resource Synchronizer uses daemon identity.
- Shared canonical cache remains authoritative.
- Resource acquisition is independent of the IPC requester.
- Acquisition completeness is tracked.
- Partial results are not represented as complete global state.
- PrivateData behavior is validated for the intended configuration.

### D. Requester authorization

- Requester identity remains server-derived.
- Application authorization is evaluated against the requester.
- Ordinary users and Operators cannot inherit daemon Administrator privileges.
- Node drain/resume retain the accepted Phase 5 predicate.
- Denied requests are rejected before Slurm execution.

### E. Visibility and events

- Per-connection visibility remains mandatory.
- Snapshots, queries, lookups, and events use the same visibility evaluator.
- Existing generation, recovery, and automatic-stream semantics remain unchanged.

### F. Command execution and audit

- Fixed adapters execute supported operations.
- No arbitrary shell or frontend-controlled execution identity is allowed.
- Requester and executor identities are separately recorded.
- Identity-sensitive operations have an explicit supported mechanism or remain disabled.

### G. Privileged helpers

- Supported Slurm operations do not depend on unnecessary D-Bus or sudo helpers.
- Remaining helpers have documented OS-level or identity-preservation requirements.
- Helper interfaces are allowlisted and validated.
- Helper execution cannot bypass requester authorization.
