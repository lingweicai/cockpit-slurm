# cockpit-slurm Implementation Phase 4 — Node Events and Subscriptions

## 1. Purpose

Phase 4 implements the second part of the first complete Node vertical slice:

```text
Phase 3
Node query / snapshot
        ↓
Phase 4
Node events / subscriptions
```

Phase 3 proved that a real Slurm Node resource can be read, normalized, cached, queried through the application IPC protocol, and displayed by React.

Phase 4 extends that same Node resource so that changes in the backend authoritative state can be propagated to subscribed frontend clients.

The target path is:

```text
Slurm state
    ↓
Node Resource Synchronizer
    ↓
Node Resource Adapter
    ↓
Canonical Node
    ↓
Node Resource Cache
    ↓
Change Detection
    ↓
Event Bus
    ↓
Subscription Manager
    ↓
IPC
    ↓
Frontend IPC Client
    ↓
Subscription Service
    ↓
NodeProvider
    ↓
Node Table
```

The primary objective is to prove:

> A Node state change is detected by the backend, committed to the authoritative cache, converted into a resource event, and delivered to subscribed frontend clients without React executing Slurm commands or maintaining authoritative resource state.

This phase is subordinate to:

```text
docs/architecture/0.1 development-cockpit-slurm-_v3.6.md
docs/architecture/1.0 implementation-plan-v3.6.md
docs/architecture/4.2 Implementation-phase3.md
```

The v3.6 development architecture is the normative architectural reference.

## 2. Phase 4 implementation principle

Phase 4 is an incremental extension of the completed Phase 3 Node vertical slice.

Do not redesign the Phase 3 query path.

Implementation sequence:

```text
Phase 4A
    Verify Phase 3 baseline
        ↓
Phase 4B
    Freeze the application wire contract
        ↓
Phase 4C
    Define Node event and generation semantics
        ↓
Phase 4D
    Implement backend Node synchronizer
        ↓
Phase 4E
    Implement cache change detection
        ↓
Phase 4F
    Implement Event Bus
        ↓
Phase 4G
    Implement Node subscription manager
        ↓
Phase 4H
    Integrate subscriptions with IPC/Dispatcher
        ↓
Phase 4I
    Implement asynchronous frontend IPC routing
        ↓
Phase 4J
    Implement frontend Subscription Service
        ↓
Phase 4K
    Extend NodeProvider for snapshot + events
        ↓
Phase 4L
    Integrate Node Table
        ↓
Phase 4M
    Test recovery, reconnect, backpressure and disconnect
        ↓
Phase 4N
    End-to-end Node event test
        ↓

```

The key principle is:

> The backend cache is authoritative. Events describe committed changes to that cache. The frontend consumes snapshots and events as a client of backend state.

# 5. Architectural invariants

## 5.1 Backend cache is authoritative

The backend Resource Cache is the authoritative in-memory representation of Node state.

Frontend state is client/presentation state only.

## 5.2 Events follow committed cache changes

Required ordering:

```text
refresh Slurm
    ↓
normalize
    ↓
validate complete snapshot
    ↓
compare with cache
    ↓
commit changed state
    ↓
advance generation
    ↓
construct event
    ↓
publish event
    ↓
deliver to subscribers
```

An event must never describe state that has not been committed to the cache.

## 5.3 Unchanged state produces no resource event

If a synchronization cycle produces semantically equal state:

```text
new snapshot == cached snapshot
```

then:

- cache state is unchanged;
- generation is unchanged;
- no resource-change event is published.

A synchronization attempt may still be recorded for diagnostics, but it is not a resource event.

## 5.4 Frontend does not poll Slurm

React and frontend services must not execute:

```text
scontrol
sinfo
squeue
sacct
sacctmgr
```

or any other Slurm command.

The backend synchronizer is the only Phase 4 component responsible for refreshing Node state.

## 5.5 Backend owns subscriptions

Subscriptions belong to backend connections.

The backend understands:

```text
resource = nodes
```

not:

```text
component = NodeTable
```

## 5.6 Existing IPC framing remains authoritative

Phase 4 does not introduce another framing protocol.

The existing length-prefixed application framing remains unchanged.

All Phase 4 messages are normal application envelopes carried by that framing.

## 5.7 Frontend services are transport/client abstractions

`SubscriptionService` may own:

- request creation;
- subscription IDs;
- event routing;
- subscription lifecycle;
- connection-error handling.

It must not own:

- Slurm synchronization;
- Slurm execution;
- backend authorization;
- authoritative resource state;
- change detection;
- backend event generation.

# 7. Phase 4B — Freeze the application wire contract

This section is normative.

The existing Go application envelope is:

```go
type Envelope struct {
    Protocol  string          `json:"protocol"`
    Version   string          `json:"version"`
    MessageID string          `json:"messageId"`
    Type      MessageType    `json:"type"`
    Timestamp string          `json:"timestamp,omitempty"`
    Payload   json.RawMessage `json:"payload"`
}
```

Therefore Phase 4-specific fields MUST NOT be added beside `type` in the envelope.

Fields such as:

```text
resource
subscriptionId
generation
event
eventSequence
snapshot
node
```

belong inside `payload`.

The existing envelope structure is not changed by Phase 4.

## 7.1 Subscribe request

Normative form:

```json
{
  "protocol": "cockpit-slurm",
  "version": "1.0",
  "messageId": "req-001",
  "type": "subscribe",
  "timestamp": "2026-09-29T12:00:00Z",
  "payload": {
    "resource": "nodes"
  }
}
```

Required payload fields:

```text
resource = "nodes"
```

Unknown resource values must produce an application protocol error.

## 7.2 Subscribed response

The successful response MUST contain the subscription identifier and the complete initial Node snapshot.

Normative form:

```json
{
  "protocol": "cockpit-slurm",
  "version": "1.0",
  "messageId": "req-001",
  "type": "subscribed",
  "timestamp": "2026-09-29T12:00:00Z",
  "payload": {
    "subscriptionId": "sub-001",
    "resource": "nodes",
    "generation": 42,
    "snapshot": {
      "nodes": []
    }
  }
}
```

The `messageId` is the request correlation ID.

The frontend MUST NOT treat `subscriptionId` as a request ID.

The snapshot and generation form one consistent baseline.

## 7.3 Unsubscribe request

Normative form:

```json
{
  "protocol": "cockpit-slurm",
  "version": "1.0",
  "messageId": "req-002",
  "type": "unsubscribe",
  "timestamp": "2026-09-29T12:00:01Z",
  "payload": {
    "subscriptionId": "sub-001"
  }
}
```

The backend MUST verify that the subscription belongs to the requesting connection.

## 7.4 Unsubscribed response

Normative form:

```json
{
  "protocol": "cockpit-slurm",
  "version": "1.0",
  "messageId": "req-002",
  "type": "unsubscribed",
  "timestamp": "2026-09-29T12:00:01Z",
  "payload": {
    "subscriptionId": "sub-001"
  }
}
```

## 7.5 Asynchronous event

Normative form:

```json
{
  "protocol": "cockpit-slurm",
  "version": "1.0",
  "messageId": "evt-001",
  "type": "event",
  "timestamp": "2026-09-29T12:00:05Z",
  "payload": {
    "subscriptionId": "sub-001",
    "resource": "nodes",
    "event": "updated",
    "generation": 43,
    "eventSequence": 1,
    "node": {}
  }
}
```

`messageId` for an asynchronous event is a server-generated event message ID. It is not a frontend request ID.

`eventSequence` is scoped to the subscription.

## 7.6 Node payload

For Phase 4, an event representing a changed Node MUST contain the complete canonical Node representation required by the existing NodeProvider.

Do not expose generated OpenAPI implementation details unless the canonical Node model already defines them as the application contract.

The same canonical Node representation is used by:

```text
initial snapshot
NodeUpdated event
```

This avoids requiring the frontend to reconstruct Node state from partial raw Slurm fields.

## 7.7 Event kinds

The protocol reserves:

```text
added
updated
removed
```

The initial implementation MUST support `updated`.

`added` and `removed` may be implemented when the valid complete snapshot comparison supports reliable classification.

A failed or incomplete Slurm query MUST NOT generate `removed` events.

# 8. Phase 4C — Node generation and event sequencing

## 8.1 Generation scope

Phase 4 uses **one generation for the complete Node collection snapshot**.

Generation means:

> the version of the authoritative Node collection currently committed in the backend cache.

Example:

```text
generation 100
    nodes = [c21, c22, c23]

generation 101
    nodes = [c21, c22, c23]
    c22 state changed

generation 102
    nodes = [c21, c23]
    c22 removed from a valid complete snapshot
```

A generation advances once for each committed changed Node collection.

It does not advance for every synchronization attempt.

It does not represent a single Node.

## 8.2 Multiple events may share one generation

If one synchronization cycle changes multiple Nodes, all changes committed by that collection update may have the same generation.

Example:

```text
generation 101:
    eventSequence 10 → c21 updated
    eventSequence 11 → c22 updated
    eventSequence 12 → c23 updated
```

Therefore the frontend MUST NOT deduplicate events solely by:

```text
incomingGeneration <= currentGeneration
```

`generation` represents the resource collection version.

`eventSequence` represents ordered delivery within a subscription.

## 8.3 Event sequence

Each subscription maintains a monotonically increasing `eventSequence`.

Example:

```text
sub-001:
    1
    2
    3
    4
```

The sequence is subscription-local.

The frontend may use it to detect duplicate or out-of-order delivery.

It is not a global backend event counter.

## 8.4 Generation-gap rule

If a client has:

```text
current generation = 101
```

and receives an event with:

```text
generation = 105
```

the client MUST NOT assume that generations 102–104 are irrelevant.

Phase 4 does not provide historical event replay.

The recovery action is:

```text
detect gap
    ↓
discard/hold incremental event application
    ↓
request a fresh Node snapshot
    ↓
replace client baseline with fresh snapshot generation
    ↓
continue subscription
```

If the existing subscription cannot safely resynchronize, the frontend may unsubscribe and establish a new subscription.

A reconnect always establishes a fresh authoritative snapshot.

# 9. Phase 4D — Backend Node Synchronizer

Phase 4 requires a backend-owned mechanism that refreshes Node state after startup.

The current backend startup path performs an initial Node load. That is insufficient for live events.

## 9.1 Ownership

The synchronizer belongs to the persistent backend daemon.

There MUST be exactly one backend Node synchronization loop for the process, independent of the number of Cockpit clients.

Incorrect:

```text
Cockpit client A → Node poller A
Cockpit client B → Node poller B
Cockpit client C → Node poller C
```

Correct:

```text
persistent backend
        ↓
one NodeSynchronizer
        ↓
one Node cache
        ↓
many subscriptions
```

## 9.2 Synchronizer responsibilities

The Node synchronizer owns:

- refresh scheduling;
- invoking the Node adapter;
- obtaining the complete Node snapshot;
- distinguishing successful complete results from failures;
- passing valid results to the cache;
- lifecycle and cancellation.

It must not own:

- frontend connections;
- subscription IDs;
- React state;
- event delivery;
- UI logic.

## 9.3 Refresh source

The Node adapter continues to use:

```text
scontrol show nodes --JSON
```

The synchronizer must use the existing adapter rather than executing Slurm commands directly.

## 9.4 Refresh lifecycle

Normative lifecycle:

```text
backend start
    ↓
initial Node synchronization
    ↓
commit initial cache state
    ↓
start periodic synchronizer
    ↓
wait for interval
    ↓
query Slurm through Node Adapter
    ↓
validate complete result
    ↓
compare with cache
    ↓
unchanged → no event
changed → commit generation + publish event
    ↓
repeat
    ↓
context cancellation
    ↓
stop synchronizer
```

The refresh interval MUST be centralized in the backend synchronizer.

A 5-second interval is consistent with the v3.6 backend polling design and should be used unless the architecture document or deployment configuration explicitly overrides it.

## 9.5 Synchronization failure

If a Slurm query fails:

```text
query failure
    ↓
retain previous valid cache
    ↓
retain generation
    ↓
publish no resource-change event
```

A transient failure must not erase the cache.

A partial or malformed result must likewise not be treated as a complete snapshot.

## 9.6 Synchronizer tests

Required:

```text
[ ] initial synchronization
[ ] periodic synchronization
[ ] unchanged state produces no event
[ ] changed state advances generation
[ ] synchronization failure preserves cache
[ ] incomplete result preserves cache
[ ] cancellation stops the loop
[ ] no goroutine leak
[ ] only one synchronizer is created
[ ] synchronizer is independent of client count
```

# 10. Phase 4E — Cache change detection

Change detection operates on canonical Node state.

```text
new snapshot
    ↓
normalize
    ↓
validate complete snapshot
    ↓
semantic compare
    ↓
┌───────────────────┬────────────────────┐
│ unchanged         │ changed            │
│                   │                    │
│ no cache commit   │ commit new state   │
│ no generation     │ generation++       │
│ no event          │ publish event(s)   │
└───────────────────┴────────────────────┘
```

## 10.1 Stable Node identity

Use the canonical Node identity established in Phase 3.

Do not use:

- array position;
- table row position;
- React key;
- pointer identity;
- synchronization sequence.

## 10.2 Semantic equality

Compare canonical application data, not raw JSON bytes.

JSON field ordering or irrelevant serialization differences must not create false events.

## 10.3 Added and removed Nodes

A valid complete snapshot can produce:

```text
old set = {c21, c22}
new set = {c21, c23}
```

which means:

```text
c22 → removed
c23 → added
```

A failed query producing an empty result is not automatically a valid empty snapshot.

The adapter/synchronizer must make completeness explicit enough for the cache to distinguish:

```text
valid complete snapshot
```

from:

```text
query failure / incomplete source data
```

# 11. Phase 4F — Event Bus

The Event Bus owns in-process publication.

It must:

- accept committed resource events;
- deliver events to registered subscribers;
- isolate publishers from individual connections;
- avoid React knowledge;
- avoid UI logic;
- avoid becoming an authoritative cache.

Conceptually:

```text
Node Cache
    ↓
Event Bus
    ├── Subscription A
    ├── Subscription B
    └── Subscription C
```

## 11.1 Publication ordering

Required:

```text
cache commit
    ↓
generation assigned
    ↓
event constructed
    ↓
Event Bus publish
```

Forbidden:

```text
publish event
    ↓
attempt cache commit
```

## 11.2 Event isolation

One subscriber failure must not terminate the Event Bus or affect other subscribers.

# 12. Phase 4G — Subscription Manager

The Subscription Manager owns:

- subscription creation;
- subscription ID;
- resource;
- connection ownership;
- Event Bus registration;
- initial snapshot coordination;
- event sequencing;
- event delivery;
- unsubscribe;
- connection cleanup.

It must not execute Slurm commands.

## 12.1 Subscription ownership

A subscription belongs to exactly one backend connection.

```text
Connection A
    ├── sub-A1: nodes
    └── sub-A2: ...

Connection B
    └── sub-B1: nodes
```

When a connection closes:

```text
connection close
    ↓
remove subscriptions
    ↓
remove Event Bus registrations
    ↓
release delivery queues
```

## 12.2 Duplicate subscriptions

For Phase 4, repeated `subscribe nodes` requests create independent subscriptions only when they have distinct request lifecycles.

The implementation MUST NOT accidentally create multiple untracked Event Bus registrations.

If the implementation chooses idempotent behavior instead, it must return the existing subscription and document/test that behavior.

# 13. Phase 4H — Atomic initial snapshot and subscription ordering

This is a mandatory correctness rule.

Unsafe:

```text
read snapshot
    ↓
send snapshot
    ↓
register subscription
```

A resource change can occur between the snapshot and registration.

## 13.1 Normative baseline

The backend MUST establish a subscription baseline atomically with respect to cache updates.

The observable contract is:

> The `subscribed` response contains a snapshot at generation G, and every committed change after that baseline is either delivered as an event or causes the connection to be recovered through a fresh snapshot. No committed change may be silently lost.

Recommended implementation:

```text
lock cache/subscription coordination
    ↓
capture generation G
    ↓
create subscription with baseline G
    ↓
register subscription with Event Bus
    ↓
capture snapshot at G
unlock
    ↓
send subscribed response containing snapshot G
    ↓
deliver queued events with generation/eventSequence after baseline
```

An equivalent atomic mechanism is acceptable.

The exact mutex structure is implementation-defined; the observable guarantee is normative.

## 13.2 Initial response

The `subscribed` response contains:

```text
subscriptionId
resource
generation
snapshot
```

This removes ambiguity about how the frontend obtains its initial state.

# 14. Phase 4I — IPC / Dispatcher integration

The existing Dispatcher is extended only to route:

```text
subscribe
unsubscribe
```

The backend must additionally support asynchronous:

```text
event
```

messages.

## 14.1 Dispatcher responsibilities

The Dispatcher:

- validates the existing application envelope;
- validates message type;
- validates payload;
- routes subscribe;
- routes unsubscribe;
- preserves request IDs;
- returns protocol errors.

The Dispatcher must not:

- inspect React component names;
- perform Node change detection;
- execute Slurm;
- publish events itself.

## 14.2 One outbound writer per connection

Asynchronous events introduce concurrent server-originated writes.

Each IPC connection MUST have exactly one serialized outbound writer.

Recommended structure:

```text
Connection
    ├── reader
    ├── dispatcher
    └── writer
```

All outbound responses and events enter one bounded outbound queue:

```text
dispatcher ─┐
             ├──→ outbound queue → writer → Unix socket
event bus ───┘
```

No independent goroutine may write directly to the same socket.

This prevents frame interleaving and preserves application framing.

## 14.3 Bounded backpressure

Each connection MUST have a bounded outbound queue.

If the queue becomes full:

```text
queue full
    ↓
connection is unhealthy
    ↓
terminate connection
    ↓
remove subscriptions
```

Phase 4 does not silently drop events.

Because Phase 4 has no event replay, connection termination is the recovery boundary:

```text
disconnect
    ↓
frontend reconnect
    ↓
new subscription
    ↓
fresh snapshot
```

The Event Bus must continue serving other connections.

# 15. Phase 4J — Frontend IPC client routing

The existing frontend IPC client was initially request/response oriented.

Phase 4 requires it to handle asynchronous events.

Incoming messages MUST be classified independently:

```text
incoming envelope
        ↓
    message type
       /   \
      /     \

    ↓         ↓

```

Conceptually:

```ts
pendingRequests[messageId]
subscriptionHandlers[subscriptionId]
```

A server event MUST NOT be interpreted as an unmatched response and silently discarded.

The IPC client remains a transport/client abstraction.

It does not apply Node business logic.

# 17. Phase 4L — NodeProvider live state

The NodeProvider becomes the frontend consumer of the subscription stream.

Required flow:

```text
NodeProvider mounts
    ↓
subscribe nodes
    ↓
receive subscribed response
    ↓
set snapshot + generation
    ↓
mark subscription active
    ↓
receive events
    ↓
apply event
    ↓
render
```

The NodeProvider MUST NOT create a competing polling loop.

## 17.1 Provider state

NodeProvider may own:

- client-side Node collection;
- current generation;
- latest event sequence;
- loading state;
- subscription state;
- connection state;
- recovery state;
- error state.

It is not the authoritative backend cache.

## 17.2 Event handling

For each event:

```text
receive event
    ↓
validate subscription ID
    ↓
validate resource
    ↓
validate eventSequence
    ↓
validate generation relationship
    ↓
apply complete canonical Node state
    ↓
update client state
```

## 17.3 Multiple events with the same generation

Do not reject a later event solely because:

```text
event.generation == currentGeneration
```

Example:

```text
snapshot generation 101

eventSequence 10, generation 102, c21
eventSequence 11, generation 102, c22
eventSequence 12, generation 102, c23
```

All three events are valid.

The provider uses `eventSequence` to establish event ordering and `generation` to identify resource-state version.

## 17.4 Generation gap recovery

If:

```text
current generation = 101
incoming generation = 105
```

the provider MUST enter recovery.

Phase 4 recovery:

```text
generation gap
    ↓
stop incremental application
    ↓
request fresh Node snapshot
    ↓
replace Node collection
    ↓
set returned generation
    ↓
resume event processing
```

If a fresh snapshot cannot be obtained through the existing subscription, unsubscribe and resubscribe.

Phase 4 does not replay historical events.

# 19. Error and recovery model

## 19.1 Invalid subscribe

Reject:

- missing resource;
- unsupported resource;
- malformed payload;
- invalid protocol version.

Return an application-level protocol error.

## 19.2 Invalid unsubscribe

Reject:

- missing subscription ID;
- unknown subscription ID;
- subscription owned by another connection.

## 19.3 Synchronization failure

A Slurm synchronization failure:

```text
does not terminate subscriptions
does not erase valid cache
does not advance generation
does not publish a resource-change event
```

The next valid synchronization may update the cache normally.

## 19.4 Delivery failure

If a connection cannot accept an event:

```text
delivery failure
    ↓
close connection
    ↓
remove subscriptions
    ↓
frontend reconnect
    ↓
fresh subscription snapshot
```

One client failure must not stop the Event Bus.

## 19.5 Generation gap

There is one recovery mechanism in Phase 4:

```text
fresh authoritative Node snapshot
```

Do not introduce event replay.

---

# 20. Reconnection

A disconnected frontend must not attempt to reconstruct missed generations.

Example:

```text
last client generation = 50
backend currently = 57
```

After reconnect:

```text
new subscription
    ↓
snapshot generation 57
    ↓
client baseline becomes 57
```

Generations 51–56 are not replayed.

This is intentional for Phase 4.

---

# 21. Security and authorization

Phase 4 is read/subscription functionality.

The backend remains authoritative for subscription access.

A client may subscribe only to resources it is permitted to observe under the existing server-side policy.

Command authorization remains Phase 5.

Frontend authorization state must never be trusted as the enforcement boundary.

# 27. Phase 4 completion criteria

Phase 4 is complete only when all of the following are true:

1. The backend continuously refreshes Node state through one daemon-owned synchronizer.
2. A valid changed Node snapshot commits to the authoritative cache.
3. A changed Node collection advances the collection generation exactly once.
4. Unchanged synchronization cycles produce no resource-change event.
5. The Event Bus publishes only committed changes.
6. Subscriptions are owned by backend connections.
7. The initial subscription snapshot has a well-defined generation baseline.
8. No committed event can be silently lost during subscription establishment.
9. Events and responses use the existing application envelope and framing.
10. Phase 4-specific fields are contained inside `Envelope.payload`.
11. Each connection has serialized outbound IPC writes.
12. Slow/broken clients cannot block or terminate unrelated subscriptions.
13. Frontend IPC routes asynchronous events separately from request responses.
14. NodeProvider consumes the authoritative snapshot/event stream.
15. Multiple events with the same generation are handled correctly.
16. Generation gaps trigger fresh-snapshot recovery.
17. Reconnect establishes a new authoritative baseline.
18. NodeTable remains a presentation consumer of NodeProvider.
19. No frontend component executes Slurm commands.
20. All Phase 4 tests and build checks pass.
