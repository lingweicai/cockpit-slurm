# cockpit-slurm Implementation Phase 4 — Node Live Stream

## 1. Purpose

Phase 4 extends the completed Phase 3 Node vertical slice from **snapshot/query** to **continuous live state**.

Phase 3 established:

```text
Slurm
  ↓
Node Adapter
  ↓
Canonical Node
  ↓
Node Cache
  ↓
Node Query Service
  ↓
IPC
  ↓
Frontend
  ↓
NodeProvider
  ↓
NodeTable
```

Phase 4 adds:

```text
Slurm
  ↓
Node Synchronizer
  ↓
Canonical Node
  ↓
Node Cache
  ↓
Change Detection
  ↓
Node Change Publication
  ↓
Active Node Streams
  ↓
Unix socket
  ↓
Cockpit native channel
  ↓
NodeProvider
  ↓
NodeTable
```

The Phase 4 architectural decision is:

> **Cockpit owns frontend channel lifecycle and transport multiplexing. The persistent cockpit-slurm daemon owns authoritative Slurm state and backend fan-out. React Context owns browser-local presentation state, not cluster state.**

The frontend uses a native Cockpit channel:

```ts
cockpit.channel({
    payload: "stream",
    unix: "/run/cockpit-slurm/cockpit-slurm.sock",
    binary: true,
});
```

The persistent backend daemon remains independent of browser and channel lifetimes.

# 2. Core architectural decisions

## 2.1 Use Cockpit native channels

Phase 4 MUST use Cockpit's native channel mechanism.

Do not introduce:

```text
cockpit-slurm-channel
custom channel executable
frontend spawn() relay
custom Cockpit transport
custom bridge process
```

The intended path is:

```text
React
  ↓
cockpit.channel()
  ↓
Cockpit channel transport
  ↓
Unix socket
  ↓
cockpit-slurm daemon
```

Cockpit already multiplexes logical channels over its transport.

`cockpit-slurm` MUST NOT recreate Cockpit's channel multiplexing.

---

## 2.2 Keep the persistent backend

The backend daemon remains persistent:

```text
systemd
  ↓
cockpit-slurm
  ↓
NodeSynchronizer
  ↓
NodeCache
```

The daemon MUST NOT start or stop synchronization according to browser/channel state.

Therefore:

```text
No browser
    ≠
no Node synchronization
```

and:

```text
Browser disconnect
    ≠
Node cache destruction
```

A reconnect obtains the current authoritative snapshot from the backend.

---

## 2.3 React Context is browser-local state

`NodeProvider` remains the frontend global-state boundary.

It owns:

```text
current Node state
current generation
connection state
loading state
stream error state
```

It does NOT own:

```text
authoritative cluster state
Slurm synchronization
change detection
event generation
backend fan-out
```

Do not describe React Context as the cluster-wide cache.

### Snapshot size policy

Node snapshots MUST fit within the existing 4 MiB protocol message limit enforced by codec.go.

For the expected Slurm cluster sizes targeted by this phase, a complete Node snapshot is expected to fit within this limit.

If a snapshot exceeds 4 MiB, the backend MUST reject the snapshot rather than truncate or split it. The existing Node cache MUST remain unchanged, and no removal events may be generated.

Snapshot chunking or pagination is out of scope for Phase 4 and may be introduced later if required.

# 5. Architectural invariants

## 5.1 Backend cache is authoritative

The Node cache is the authoritative representation of Node state.

```text
NodeCache
    =
authoritative Node state
```

The frontend may maintain client state but MUST NOT become authoritative.

---

## 5.2 Synchronization is independent of clients

The Node synchronizer runs whether or not any browser is connected.

```text
browser connected
    → synchronization continues

browser disconnected
    → synchronization continues
```

---

## 5.3 Events follow committed cache changes

The required ordering is:

```text
refresh Slurm
    ↓
parse
    ↓
normalize
    ↓
validate
    ↓
compare
    ↓
commit changed state
    ↓
advance generation
    ↓
publish NodeChange
    ↓
deliver to active streams
```

An event MUST NOT describe state that has not been committed to the cache.

---

## 5.4 Failed refresh does not delete state

If the Slurm query fails or produces incomplete data:

```text
previous cache
    ↓
preserved
```

Do not interpret missing Nodes from a failed query as `NodeRemoved`.

Only a valid complete snapshot may produce removal events.

### Complete Slurm snapshot validation

A Node snapshot is considered complete and valid only when:

1. The Slurm command/query completed successfully.
2. The response was successfully parsed according to the expected Slurm JSON schema.
3. The Node collection is present, even when it is empty.
4. Every returned Node object passes the required Node model validation.
5. No parse, transport, schema, or command error indicates that the result is incomplete.

An empty nodes: [] result is valid and represents a complete snapshot containing zero Nodes.

If any validation criterion fails, the refresh MUST be rejected as incomplete. The existing Node cache MUST remain unchanged, and no removal events may be generated.

Add one concise implementation rule:

>Removal events are calculated only after a complete snapshot has been successfully committed to the cache.

This gives you the important distinction:
```text
valid complete snapshot
    ├── nodes: [...]  → update/add/remove
    └── nodes: []     → remove all existing Nodes

invalid/incomplete snapshot
    └── cache unchanged
        no removal events
```
---

## 5.5 Frontend does not poll Slurm

React MUST NOT execute:

```text
scontrol
sinfo
squeue
sacct
sacctmgr
```

The backend owns Slurm access.

---

## 5.6 Cockpit owns channel lifecycle

The frontend creates and closes its native Cockpit channel.

A channel is a frontend transport object.

The persistent daemon is not tied to its lifetime.

# 6. Why `payload: "stream"`

Phase 4 MUST initially use:

```text
payload: "stream"
```

rather than:

```text
payload: "packet"
```

The Cockpit `stream` payload is appropriate for a Unix socket but has arbitrary message boundaries.

Therefore:

```text
Cockpit stream
    ↓
arbitrary chunks
    ↓
application framing
```

must be supported.

`packet` should not be selected merely to avoid application framing because its message-size constraints are unsuitable for potentially large Node snapshots.

# 8. Node stream contract

Keep existing message.go message types and put the resource-specific information inside the existing Envelope.Payload. That is cleaner and preserves the protocol contract you already established in v3.6.

Make type: "event" the only unsolicited Node stream message type, and discriminate the event inside payload.

"node" is intentionally the stream resource identifier while existing queries can use "nodes".

For example:

Initial snapshot
```json
{
  "protocol": "cockpit-slurm",
  "version": "1.0",
  "messageId": "...",
  "type": "event",
  "timestamp": "...",
  "payload": {
    "resource": "node",
    "event": "snapshot",
    "generation": 42,
    "nodes": []
  }
}
```
Node changes
```json
{
  "protocol": "cockpit-slurm",
  "version": "1.0",
  "messageId": "...",
  "type": "event",
  "timestamp": "...",
  "payload": {
    "resource": "node",
    "event": "changes",
    "generation": 43,
    "changes": [
      {
        "kind": "updated",
        "node": {}
      },
      {
        "kind": "added",
        "node": {}
      },
      {
        "kind": "removed",
        "node": {}
      }
    ]
  }
}
```
This gives you a very clean rule:
```text
Envelope.type
    ↓
"event"

Envelope.payload.resource
    ↓
"node"

Envelope.payload.event
    ↓
"snapshot" | "changes"

Envelope.payload.changes[].kind
    ↓
"added" | "updated" | "removed"
```

It preserves the existing protocol vocabulary:
```text
hello
hello-response
query
query-response
subscribe
...
event
error
ping
pong
close
```
and uses payload exactly for what you wanted earlier: resource-specific information.

It also makes future resources straightforward:
```text
type = event
resource = node
event = changes
changes = [ ... ]
```
then later:
```text
type = event
resource = job
event = changes
changes = [ ... ]
```
without expanding MessageType for every resource/event combination. Each changes
event contains the complete, non-empty set of changes committed for its
generation. No changes event is sent when a refresh leaves the cache unchanged.


That gives you a very useful separation:
```text
┌─────────────────────────────────┐
│ Existing v3.6 Envelope          │
│                                 │
│ protocol                        │
│ version                         │
│ messageId                       │
│ type                            │
│ timestamp                       │
│                                 │
│ payload ─────────────────────┐  │
└──────────────────────────────┼──┘
                               │
                               ▼
                    resource-specific data
```
Putting more message/resource information inside payload.

The key is that Phase 4 should extend the existing protocol rather than invent another envelope.


The exact Node fields MUST follow the canonical Phase 3 Node model.

# 9. Generation semantics

Generation represents committed cache state.

It is NOT a polling-cycle counter.
The Node collection generation advances by exactly one for each successful
cache commit that changes canonical Node state. An unchanged refresh does not
advance the generation. A changed refresh, regardless of how many Nodes it
changes, produces one complete `NodeChangeBatch` at the new generation.

Example:

```text
refresh
    unchanged
    generation = 42

refresh
    unchanged
    generation = 42

refresh
    Node changed
    generation = 43
    one complete changes event for generation 43

refresh
    unchanged
    generation = 43
```

Therefore:

```text
refresh count != generation
```
There is exactly one changes event for each generation that contains changes.
That event carries every Node change committed at that generation. Because
generations advance only for changed commits, consecutive changes events on a
stream have consecutive generations. For example:

```text
generation 43
    changes event
      ├── c21 updated
      ├── c22 updated
      └── c23 updated
```

The frontend applies the complete batch atomically. It MUST NOT expect one
separately framed event per changed Node, nor treat equal generations as
duplicate events: a second batch at the same generation violates the stream
contract.

```text

    ↓

```

This is deliberate.

A fresh authoritative snapshot is the recovery mechanism.

# 11. Atomic stream baseline

Define one atomic "baseline + publication" boundary.

Registration, baseline capture, and the point at which subsequent cache changes become visible to the stream must be ordered atomically with respect to cache publication.

> A change committed after the stream baseline is established MUST NOT be silently lost.


```text
LOCK
  register
  capture baseline
  enqueue snapshot
UNLOCK

cache changes
  ↓
enqueue events

single writer
  ↓
snapshot
event
event
event
  ↓
Unix socket
```
Do not solve this race with sleeps or frontend timing assumptions.

Something like:
```text
lock cache/stream publication boundary
    ↓
register stream
    ↓
capture cache snapshot + generation
    ↓
record stream baseline generation
    ↓
enqueue initial snapshot
unlock
    ↓
subsequent cache commits may publish changes
    ↓
per-stream queue
    ↓
single writer
    ↓
Unix socket
```

The initial snapshot MUST be enqueued before the synchronization boundary is released. A cache change committed after the boundary is released MUST be published after that initial snapshot in the same stream's outbound queue.

The snapshot does not need to be written to the Unix socket while the boundary is held. It only needs to be placed in the stream's serialized outbound queue before subsequent changes can be enqueued.

# 13. Node change detection

Change detection operates on canonical Node state.

Do not compare raw JSON.

Do not compare:

```text
array position
React key
object pointer
raw JSON field order
```

Use stable Node identity from Phase 3.

For a valid complete snapshot:

```text
new identities - cached identities
    = added

cached identities - new identities
    = removed

same identity + changed canonical state
    = updated
```

Failed/incomplete refreshes MUST NOT run removal classification.

# 14. NodeChange

A small typed backend change model is recommended:

```go
type NodeChangeKind string

const (
    NodeAdded   NodeChangeKind = "added"
    NodeUpdated NodeChangeKind = "updated"
    NodeRemoved NodeChangeKind = "removed"
)

type NodeChange struct {
    Kind NodeChangeKind `json:"kind"`
    Node Node           `json:"node"`
}

type NodeChangeBatch struct {
    Resource   string       `json:"resource"`
    Event      string       `json:"event"`
    Generation uint64       `json:"generation"`
    Changes    []NodeChange `json:"changes"`
}
```

`NodeChange` represents one resource-level change. `NodeChangeBatch` is the
unit committed and published for one generation, and its `Changes` slice MUST
contain every addition, update, and removal from that cache commit. Its
`Resource` MUST be `"node"` and its `Event` MUST be `"changes"`. `Changes` MUST
be non-empty; do not publish an empty batch or one batch per Node.

`NodeChange` MUST NOT contain:

```text
Cockpit channel ID
subscription ID
React component
frontend request ID
browser state
```

It represents backend resource state.

# 16. Per-connection NodeStream

Each Unix connection gets one `NodeStream`.

Conceptually:

```text
NodeStream
    ├── connection
    ├── lifecycle
    ├── outbound queue
    └── writer
```

The server sends:

```text

event
event
event
...
```

until the connection closes.

The client does not need to send an application-level subscribe message.

# 17. Backend writer discipline

Each stream MUST have exactly one serialized outbound writer.

Do NOT allow multiple goroutines to write directly to the same socket.

Preferred:

```text
NodeChange
    ↓
per-stream bounded queue
    ↓
single writer goroutine
    ↓
Unix socket
```

This prevents application-frame interleaving.

The writer is necessary because Cockpit provides channel transport/multiplexing; it does not remove the backend's requirement to serialize writes to one Unix stream.

---

# 18. Slow consumers

Each stream MUST have a bounded outbound queue.

Preferred policy:

```text
queue full
    ↓
close affected stream
    ↓
unregister stream
```

Do not silently discard events.

The frontend then recovers by:

```text
channel close
    ↓
reconnect
    ↓
fresh snapshot
```

This prevents an unbounded queue from turning one stalled browser into daemon memory growth.

# 24. Generation-gap recovery

Each stream begins with exactly one complete snapshot at generation `g`.
After applying that snapshot, the provider's current generation is `g`. For
every subsequent `event: "changes"` batch, the provider MUST require:

```text
batch generation = current generation + 1
```

The provider MUST validate and apply the whole batch atomically, then advance
its current generation to the batch generation. This strict rule is valid
because every changed cache commit advances generation exactly once and emits
exactly one complete batch; unchanged refreshes emit no batch.

If a batch has the current generation or a lower generation, the client has
received a duplicate/stale batch or the stream is inconsistent. If a batch
generation is greater than `current generation + 1`, one or more batches were
missed. In either case, the provider MUST NOT ignore the batch or partially
modify state; it MUST close the current channel and recover using a new
connection and authoritative snapshot.

The initial snapshot is valid only as the first message on a newly opened
stream. A later snapshot on the same connection is a protocol/state
inconsistency and triggers the same recovery path.

Phase 4 does not implement replay.

Recovery is:

```text
close/reconnect
    ↓
snapshot
    ↓
new authoritative baseline
```

Do not attempt to reconstruct missing cluster state from incomplete events.

Make the frontend types mirror the Go envelope.

Conceptually:
```ts
interface Envelope<TPayload> {
    protocol: string;
    version: string;
    messageId: string;
    type: "event";
```

Then:
```ts
interface NodeSnapshotPayload {

    kind: "added" | "updated" | "removed";

    resource: "node";

    changes: NodeChange[];
```

And:

```ts
type NodeStreamMessage =
    | Envelope<NodeSnapshotPayload>
    | Envelope<NodeChangePayload>;
```
This is much more faithful to the architecture.

Please reuse the existing common envelope interface Envelope from ipc/types.ts.

Do not use `any` for decoded stream messages.

External stream data must be validated before entering React state.

# 27. Reconnect

A channel close caused by a recoverable transport problem SHOULD trigger controlled reconnect.

Do not create an immediate infinite reconnect loop.

Preferred:

```text
channel closes
    ↓
mark reconnecting
    ↓
short backoff
    ↓
new Cockpit channel
    ↓
fresh snapshot
```

The reconnect timer MUST be cancelled when `NodeProvider` unmounts.

---

# 28. React lifecycle and Strict Mode

The implementation must remain correct under development lifecycle patterns where an effect can be mounted, cleaned up, and mounted again.

This sequence must be safe:

```text
mount
    ↓
channel A

cleanup
    ↓
channel A closed

mount
    ↓
channel B
```

There must not be:

```text
two permanent channels
```

or:

```text
handlers retained on closed channels
```

Do not use a global mutable singleton channel merely to hide lifecycle bugs.

---

# 29. Do not introduce `cockpit.cache()` in Phase 4

Cockpit provides `cockpit.cache()` for sharing data between frontend components/frames.

That mechanism solves a different problem.

The architectural distinction is:

```text
NodeCache
    =
backend authoritative cluster state

React NodeProvider
    =
browser-local application state

cockpit.cache()
    =
optional Cockpit-side sharing mechanism
```

Phase 4 does not need `cockpit.cache()`.

A future optimization may consider it independently.

# 30. Unix socket security

The Unix socket is a security boundary. Only local users who are members of the cockpit-slurm Unix group can access the socket.

Phase 4 MUST explicitly define:

```text
socket owner
socket group
socket mode
runtime directory mode
```

The implementation must also establish how the daemon identifies the connecting Unix user.

Using UID/PID of sub-process generated by cockpit-bridge with cockpit.channel as identity.

```text
/run/cockpit-slurm/
    owner: cockpit-slurm
    group: cockpit-slurm
    mode: 0750

/run/cockpit-slurm/cockpit-slurm.sock
    owner: cockpit-slurm
    group: cockpit-slurm
    mode: 0660
```
Then:
```text
ordinary users in cockpit-slurm group
        │
        │ member of cockpit-slurm group
        ▼
cockpit-bridge
        │
        │ cockpit.channel({
        │   payload: "stream",
        │   unix: "..."
        │ })
        ▼
/run/cockpit-slurm/cockpit-slurm.sock
        │
        │ filesystem permission: group cockpit-slurm
        ▼
cockpit-slurm daemon
```
Only users in group of cockpit-slurm can communicate with socket from frontend.

```go
// In server.go, tighten the directory creation:
if err := os.MkdirAll(filepath.Dir(s.socketPath), 0750); err != nil {
    return fmt.Errorf("create socket directory: %w", err)
}
```

There are two separate layers:

Layer 1 — filesystem authorization
```text
socket mode 0660
       +
group cockpit-slurm
       ↓
Can this process connect?
```
Layer 2 — server-side identity

After accept():
```text
Unix socket
    ↓
SO_PEERCRED
    ↓
UID/GID
    ↓
Linux account
    ↓
UserContext
```
So the daemon can still construct:
```json
UserContext{
    UID:  1001,
    GID:  1001,
    User: "alice",
    ...
}
```
The distinction is important:

The group controls access; peer credentials establish identity.

Integration gate — user identity

Before using SO_PEERCRED to construct UserContext, verify on the target Cockpit installation that:

1. An authorized user is a member of the cockpit-slurm Unix group.
2. The user can establish the native cockpit.channel() connection.
3. cockpit-slurm obtains the peer UID/GID through SO_PEERCRED.
4. The observed UID/GID matches the authenticated user's Linux account.
5. A user not in cockpit-slurm cannot connect.

The result of this test is a prerequisite for relying on peer credentials as UserContext identity.

Authorized users MUST be members of the cockpit-slurm Unix group.

Detailed command authorization remains Phase 5.

These lifetimes MUST remain separate:

```text
Browser
   │
   └── NodeProvider
          │
          └── Cockpit channel
                 │
                 └── Unix connection
                        │
```

versus:

```text

   │
   └── cockpit-slurm daemon
          │
          ├── NodeSynchronizer

```

```text
MUST NOT:
    stop NodeSynchronizer
    clear NodeCache
    terminate daemon
```

This is one of the most important Phase 4 invariants.

# 33. Publication path

The mandatory backend path is:

```text
NodeSynchronizer
    ↓
NodeAdapter
    ↓
canonical Node snapshot
    ↓
NodeCache.Apply()
    ↓
NodeChangeBatch{resource: "node", event: "changes", ...}
    ↓
NodeChangePublisher
    ↓
NodeStreamRegistry.Publish(batch)
    ↓
per-stream queue
    ↓
single writer
    ↓
Unix socket
```

A useful conceptual API is:

```go
batch, committed := nodeCache.Apply(snapshot)

if committed {
    publisher.Publish(batch)
}
```

`NodeCache.Apply()` and stream registration MUST participate in the same cache/publication synchronization protocol. `NodeStreamRegistry.Publish()` MUST NOT be able to publish a change to a newly registered stream before that stream's initial snapshot has been enqueued.

A stream therefore becomes eligible for change publication only after its baseline snapshot has been captured and enqueued.

The ordering guarantee is:
```
baseline snapshot enqueue → subsequent batch enqueue → serialized socket write
```
A cache change may occur concurrently with stream creation, but it MUST be ordered either before the stream's baseline or after it. It MUST never fall into an unobservable gap between baseline capture and stream publication.

---

# 34. Stream registration

Recommended:

```text
accept Unix socket
    ↓
create NodeStream
    ↓
acquire cache/stream publication boundary
    ↓
register stream
    ↓
capture snapshot + generation
    ↓
record baseline generation
    ↓
enqueue snapshot
    ↓
release boundary
    ↓
subsequent NodeChangeBatch publications may enqueue to stream
    ↓
single writer serializes snapshot before later events
```

The stream MUST NOT be considered publication-ready until its initial snapshot has been enqueued.


There is no:

```text
subscribe request
```

because the connection itself is the subscription.

# 35. Disconnect cleanup

When a socket closes:

```text
EOF/error
    ↓
mark stream closed
    ↓
unregister stream
    ↓
stop writer
    ↓
release queue
```

Cleanup MUST be idempotent.

A disconnected browser MUST NOT remain in the registry.

A disconnected client MUST NOT cause the daemon to fail.

# 36. Error handling

## Backend

Distinguish:

```text
Slurm refresh failure
Unix connection failure
client disconnect
protocol error
queue overflow
internal synchronization error
```

A client failure is not a daemon failure.

A malformed client must not terminate the daemon.

A slow client must not block unrelated clients.

## Frontend

Expose appropriate:

```text
loading
connected
reconnecting
error
```

states.

A temporary stream failure should not permanently destroy the current UI state.

A successful reconnect replaces the client state with a fresh authoritative snapshot.

```text

    → cache preserved
    → no removals
```

## 37.2 Stream registration

Test:

```text

    → snapshot received
```


```text

```

## 37.3 Multiple clients

Test:

```text

B connected

Node changes

A receives change
B receives change
```

Then:

```text

Node changes

B still receives change
```

## 37.4 Serialization

Concurrent publishers MUST never interleave frames.

Bad:

```text
frame A + partial frame B + rest of A
```

Good:

```text
frame A
frame B
```

### 37.4 Snapshot/register race

Test that registration and cache publication cannot create a
snapshot/event gap.

Case 1:

    cache generation = 42
    register stream
    capture/enqueue snapshot 42
    commit generation 43

Expected:

    snapshot 42
    changes event 43

Case 2:

    cache generation = 42
    commit generation 43
    register stream

Expected:

    snapshot 43

Case 3:

    concurrently register stream and commit generation 43

Expected:

    either:

        snapshot 42
        changes event 43

    or:

        snapshot 43

    but never:

        snapshot 42
        [missing event 43]


The test MUST verify outbound queue ordering, not merely
that both messages were eventually produced.

## 37.5 Queue overflow

Test:

```text
queue full
    → affected stream closes
    → stream unregisters
    → daemon continues
```

```text
                         Slurm
                           │
                           ▼
                  NodeSynchronizer
                           │
                           ▼
                     Node Adapter
                           │
                           ▼
                      Node Cache
                   authoritative state
                       │       │
                    query    change
                       │       │
                       │       ▼
                       │   NodeChange
                       │       │
                       │       ▼
                       │ NodeStreamRegistry
                       │       │
                       │   ┌───┴────┐
                       │   │        │
                       ▼   ▼        ▼
                    Query  Stream A Stream B
                             │        │
                             ▼        ▼
                          Unix sockets
                              │
                              ▼
                    Cockpit native channels
                              │
                       ┌──────┴──────┐
                       ▼             ▼
                 NodeProvider A  NodeProvider B
                       │             │
                       ▼             ▼
                   NodeTable A   NodeTable B
```

The central rule is:

> **Cockpit channels provide frontend transport and lifecycle. `cockpit-slurm` provides persistent authoritative state and resource-specific fan-out. React Context provides browser-local state. No layer should impersonate the responsibility of another.**
