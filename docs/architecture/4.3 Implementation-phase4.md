# cockpit-slurm Implementation Phase 4 — Node Live Stream

## 1. Purpose

Phase 4 extends the completed Phase 3 Node vertical slice from **snapshot/query** to **continuous live state**.

Phase 3 established:

```text
Slurm
  ↓
Node Adapter
  ↓
Canonical Node
  ↓
Node Cache
  ↓
Node Query Service
  ↓
IPC
  ↓
Frontend
  ↓
NodeProvider
  ↓
NodeTable
```

Phase 4 adds:

```text
Slurm
  ↓
Node Synchronizer
  ↓
Canonical Node
  ↓
Node Cache
  ↓
Change Detection
  ↓
Node Change Publication
  ↓
Active Node Streams
  ↓
Unix socket
  ↓
Cockpit native channel
  ↓
NodeProvider
  ↓
NodeTable
```

The Phase 4 architectural decision is:

> **Cockpit owns frontend channel lifecycle and transport multiplexing. The persistent cockpit-slurm daemon owns authoritative Slurm state and backend fan-out. React Context owns browser-local presentation state, not cluster state.**

The frontend uses a native Cockpit channel:

```ts
cockpit.channel({
    payload: "stream",
    unix: "/run/cockpit-slurm/cockpit-slurm.sock",
});
```

The persistent backend daemon remains independent of browser and channel lifetimes.

---

# 2. Core architectural decisions

## 2.1 Use Cockpit native channels

Phase 4 MUST use Cockpit's native channel mechanism.

Do not introduce:

```text
cockpit-slurm-channel
custom channel executable
frontend spawn() relay
custom Cockpit transport
custom bridge process
```

The intended path is:

```text
React
  ↓
cockpit.channel()
  ↓
Cockpit channel transport
  ↓
Unix socket
  ↓
cockpit-slurm daemon
```

Cockpit already multiplexes logical channels over its transport.

`cockpit-slurm` MUST NOT recreate Cockpit's channel multiplexing.

---

## 2.2 Keep the persistent backend

The backend daemon remains persistent:

```text
systemd
  ↓
cockpit-slurm
  ↓
NodeSynchronizer
  ↓
NodeCache
```

The daemon MUST NOT start or stop synchronization according to browser/channel state.

Therefore:

```text
No browser
    ≠
no Node synchronization
```

and:

```text
Browser disconnect
    ≠
Node cache destruction
```

A reconnect obtains the current authoritative snapshot from the backend.

---

## 2.3 React Context is browser-local state

`NodeProvider` remains the frontend global-state boundary.

It owns:

```text
current Node state
current generation
connection state
loading state
stream error state
```

It does NOT own:

```text
authoritative cluster state
Slurm synchronization
change detection
event generation
backend fan-out
```

Do not describe React Context as the cluster-wide cache.

---

# 5. Architectural invariants

## 5.1 Backend cache is authoritative

The Node cache is the authoritative representation of Node state.

```text
NodeCache
    =
authoritative Node state
```

The frontend may maintain client state but MUST NOT become authoritative.

---

## 5.2 Synchronization is independent of clients

The Node synchronizer runs whether or not any browser is connected.

```text
browser connected
    → synchronization continues

browser disconnected
    → synchronization continues
```

---

## 5.3 Events follow committed cache changes

The required ordering is:

```text
refresh Slurm
    ↓
parse
    ↓
normalize
    ↓
validate
    ↓
compare
    ↓
commit changed state
    ↓
advance generation
    ↓
publish NodeChange
    ↓
deliver to active streams
```

An event MUST NOT describe state that has not been committed to the cache.

---

## 5.4 Failed refresh does not delete state

If the Slurm query fails or produces incomplete data:

```text
previous cache
    ↓
preserved
```

Do not interpret missing Nodes from a failed query as `NodeRemoved`.

Only a valid complete snapshot may produce removal events.

---

## 5.5 Frontend does not poll Slurm

React MUST NOT execute:

```text
scontrol
sinfo
squeue
sacct
sacctmgr
```

The backend owns Slurm access.

---

## 5.6 Cockpit owns channel lifecycle

The frontend creates and closes its native Cockpit channel.

A channel is a frontend transport object.

The persistent daemon is not tied to its lifetime.

---

# 6. Why `payload: "stream"`

Phase 4 MUST initially use:

```text
payload: "stream"
```

rather than:

```text
payload: "packet"
```

The Cockpit `stream` payload is appropriate for a Unix socket but has arbitrary message boundaries.

Therefore:

```text
Cockpit stream
    ↓
arbitrary chunks
    ↓
application framing
```

must be supported.

`packet` should not be selected merely to avoid application framing because its message-size constraints are unsuitable for potentially large Node snapshots.

---

# 7. Application framing

Cockpit's stream channel does not provide application message boundaries.

Therefore the existing Phase 2 length-prefixed JSON framing SHOULD be reused.

Conceptually:

```text
<decimal byte length>\n<JSON payload>
```

Example:

```text
87\n{"type":"snapshot","generation":42,"nodes":[...]}
```

The existing framing implementation MUST be reused or extended.

Do not create a second framing implementation.

The frontend MUST NOT assume:

```text
one Cockpit message = one application message
```

A received chunk may contain:

```text
partial frame
```

or:

```text
multiple frames
```

or:

```text
complete frame + partial next frame
```

---

# 8. Node stream contract

## 8.1 Connection equals subscription

The existence of a Node stream is the subscription.

The frontend does NOT send:

```json
{
  "type": "subscribe",
  "resource": "nodes"
}
```

There is no `subscriptionId`.

The lifecycle is:

```text
Unix connection accepted
    ↓
Node stream registered
    ↓
snapshot sent
    ↓
events sent
    ↓
connection closed
    ↓
stream unregistered
```

---

## 8.2 Initial snapshot

The first application message MUST be:

```json
{
  "type": "snapshot",
  "generation": 42,
  "nodes": []
}
```

The `nodes` array contains the canonical Node representation established in Phase 3.

The generation identifies the cache state represented by the snapshot.

---

## 8.3 Update event

Example:

```json
{
  "type": "event",
  "event": "updated",
  "generation": 43,
  "node": {}
}
```

Added Node:

```json
{
  "type": "event",
  "event": "added",
  "generation": 44,
  "node": {}
}
```

Removed Node:

```json
{
  "type": "event",
  "event": "removed",
  "generation": 45,
  "node": {
    "name": "c21"
  }
}
```

The exact Node fields MUST follow the canonical Phase 3 Node model.

---

# 9. Generation semantics

Generation represents committed cache state.

It is NOT a polling-cycle counter.

Example:

```text
refresh
    unchanged
    generation = 42

refresh
    unchanged
    generation = 42

refresh
    Node changed
    generation = 43

refresh
    unchanged
    generation = 43
```

Therefore:

```text
refresh count != generation
```

Multiple Node changes from one synchronization cycle may share one generation:

```text
generation 43
    ├── c21 updated
    ├── c22 updated
    └── c23 updated
```

The frontend MUST NOT interpret equal generations as duplicate events.

---

# 10. No event replay in Phase 4

Phase 4 does not implement an event replay log.

If a stream is lost:

```text
disconnect
    ↓
reconnect
    ↓
new snapshot
    ↓
continue events
```

This is deliberate.

A fresh authoritative snapshot is the recovery mechanism.

---

# 11. Atomic stream baseline

The backend MUST prevent this race:

```text
T1  stream connects
T2  snapshot generation 42 selected
T3  cache changes to generation 43
T4  snapshot 42 sent
T5  event 43 lost
```

The implementation MUST establish the stream baseline atomically relative to cache publication.

Conceptually:

```text
lock cache/stream boundary
    ↓
register stream
    ↓
capture snapshot + generation
    ↓
record stream baseline
unlock
    ↓
send snapshot
    ↓
deliver subsequent changes
```

The exact synchronization mechanism is an implementation detail.

The invariant is mandatory:

> A change committed after the stream baseline is established MUST NOT be silently lost.

Do not solve this race with sleeps or frontend timing assumptions.

---

# 12. NodeSynchronizer

`NodeSynchronizer` owns periodic refresh:

```text
every configured interval
    ↓
query Slurm
    ↓
Node adapter
    ↓
canonical Node snapshot
    ↓
validate
    ↓
compare
    ↓
commit
    ↓
publish changes
```

The initial target remains approximately 5 seconds.

The interval SHOULD be configurable.

A new browser stream MUST NOT cause an independent Slurm polling loop.

---

# 13. Node change detection

Change detection operates on canonical Node state.

Do not compare raw JSON.

Do not compare:

```text
array position
React key
object pointer
raw JSON field order
```

Use stable Node identity from Phase 3.

For a valid complete snapshot:

```text
new identities - cached identities
    = added

cached identities - new identities
    = removed

same identity + changed canonical state
    = updated
```

Failed/incomplete refreshes MUST NOT run removal classification.

---

# 14. NodeChange

A small typed backend change model is recommended:

```go
type NodeChangeKind string

const (
    NodeAdded   NodeChangeKind = "added"
    NodeUpdated NodeChangeKind = "updated"
    NodeRemoved NodeChangeKind = "removed"
)

type NodeChange struct {
    Generation uint64
    Kind       NodeChangeKind
    Node       Node
}
```

Exact field names may follow the existing codebase.

`NodeChange` MUST NOT contain:

```text
Cockpit channel ID
subscription ID
React component
frontend request ID
browser state
```

It represents backend resource state.

---

# 15. Node Stream Registry

The backend still requires a small registry because multiple clients can be connected simultaneously.

This is NOT a generic Subscription Manager.

Its sole responsibility is:

```text
active connection
      ↕
Node stream
```

Recommended conceptual interface:

```go
type NodeStreamRegistry interface {
    Register(stream *NodeStream)
    Unregister(stream *NodeStream)
    Publish(change NodeChange)
}
```

It MUST NOT own:

```text
Node cache
Slurm synchronization
React state
Cockpit channel IDs
subscription IDs
request correlation
```

---

# 16. Per-connection NodeStream

Each Unix connection gets one `NodeStream`.

Conceptually:

```text
NodeStream
    ├── connection
    ├── lifecycle
    ├── outbound queue
    └── writer
```

The server sends:

```text
snapshot
event
event
event
...
```

until the connection closes.

The client does not need to send an application-level subscribe message.

---

# 17. Backend writer discipline

Each stream MUST have exactly one serialized outbound writer.

Do NOT allow multiple goroutines to write directly to the same socket.

Preferred:

```text
NodeChange
    ↓
per-stream bounded queue
    ↓
single writer goroutine
    ↓
Unix socket
```

This prevents application-frame interleaving.

The writer is necessary because Cockpit provides channel transport/multiplexing; it does not remove the backend's requirement to serialize writes to one Unix stream.

---

# 18. Slow consumers

Each stream MUST have a bounded outbound queue.

Preferred policy:

```text
queue full
    ↓
close affected stream
    ↓
unregister stream
```

Do not silently discard events.

The frontend then recovers by:

```text
channel close
    ↓
reconnect
    ↓
fresh snapshot
```

This prevents an unbounded queue from turning one stalled browser into daemon memory growth.

---

# 19. Native Cockpit channel

The frontend SHOULD create:

```ts
const channel = cockpit.channel({
    payload: "stream",
    unix: socketPath,
});
```

The socket path MUST be centralized in the frontend configuration.

Do not hard-code the path in multiple components.

Do not use:

```ts
cockpit.spawn(["cockpit-slurm-channel"])
```

The removed `cockpit-slurm-channel` executable MUST remain removed.

---

# 20. NodeProvider lifecycle

`NodeProvider` owns the Node channel.

Conceptually:

```tsx
useEffect(() => {
    const channel = cockpit.channel({
        payload: "stream",
        unix: socketPath,
    });

    // register handlers

    return () => {
        // remove handlers
        channel.close();
    };
}, [socketPath]);
```

The exact TypeScript API must follow the installed Cockpit declarations.

The channel MUST be closed when the provider is unmounted.

---

# 21. NodeProvider responsibilities

`NodeProvider` owns:

* opening the Node channel;
* application-frame decoding;
* snapshot validation;
* snapshot application;
* event application;
* generation tracking;
* reconnect;
* generation-gap recovery;
* connection state;
* cleanup.

It MUST NOT own:

* Slurm polling;
* Slurm commands;
* backend cache;
* backend change detection;
* backend authorization;
* backend fan-out.

---

# 22. NodeProvider snapshot handling

On:

```json
{
  "type": "snapshot",
  "generation": 42,
  "nodes": [...]
}
```

the provider MUST:

```text
replace current Node state
set generation = 42
set loading = false
set connected = true
clear recoverable stream error
```

Do not merge a complete snapshot into stale state.

A snapshot is the authoritative baseline for that frontend connection.

---

# 23. NodeProvider event handling

For:

```json
{
  "type": "event",
  "event": "updated",
  "generation": 43,
  "node": {}
}
```

replace the Node with the same stable identity.

For:

```text
added
```

insert it.

For:

```text
removed
```

delete it.

Never identify Nodes by table row position.

---

# 24. Generation-gap recovery

Suppose:

```text
current generation = 42
event generation = 43
```

The event may be applied.

If the frontend detects that it cannot establish a valid contiguous state because intermediate committed changes were missed, it MUST recover with a fresh snapshot.

Phase 4 does not implement replay.

Recovery is:

```text
close/reconnect
    ↓
snapshot
    ↓
new authoritative baseline
```

Do not attempt to reconstruct missing cluster state from incomplete events.

The precise generation validation rule MUST be implemented consistently between backend and frontend tests.

---

The preferred Phase 4 frontend structure becomes:

```text
src/
  ipc/
    client.ts
    framing.ts
    protocol.ts
    errors.ts

  services/
    resource-service.ts
    command-service.ts

  contexts/
    UserProvider.tsx

```

The Phase 4-specific:

```text
services/subscription-service.ts
```

is no longer required.

If a reusable stream client abstraction is later useful, it should live under `ipc/`, not become a business-logic service.

# 26. Frontend protocol types

Use explicit types.

For example:

```ts
type NodeStreamMessage =
    | NodeSnapshotMessage
    | NodeEventMessage;

interface NodeSnapshotMessage {
    type: "snapshot";
    generation: number;
    nodes: Node[];
}

interface NodeEventMessage {
    type: "event";
    event: "added" | "updated" | "removed";
    generation: number;
    node: Node;
}
```

Do not use `any` for decoded stream messages.

External stream data must be validated before entering React state.

---

# 27. Reconnect

A channel close caused by a recoverable transport problem SHOULD trigger controlled reconnect.

Do not create an immediate infinite reconnect loop.

Preferred:

```text
channel closes
    ↓
mark reconnecting
    ↓
short backoff
    ↓
new Cockpit channel
    ↓
fresh snapshot
```

The reconnect timer MUST be cancelled when `NodeProvider` unmounts.

---

# 28. React lifecycle and Strict Mode

The implementation must remain correct under development lifecycle patterns where an effect can be mounted, cleaned up, and mounted again.

This sequence must be safe:

```text
mount
    ↓
channel A

cleanup
    ↓
channel A closed

mount
    ↓
channel B
```

There must not be:

```text
two permanent channels
```

or:

```text
handlers retained on closed channels
```

Do not use a global mutable singleton channel merely to hide lifecycle bugs.

---

# 29. Do not introduce `cockpit.cache()` in Phase 4

Cockpit provides `cockpit.cache()` for sharing data between frontend components/frames.

That mechanism solves a different problem.

The architectural distinction is:

```text
NodeCache
    =
backend authoritative cluster state

React NodeProvider
    =
browser-local application state

cockpit.cache()
    =
optional Cockpit-side sharing mechanism
```

Phase 4 does not need `cockpit.cache()`.

A future optimization may consider it independently.

---

# 30. Unix socket security

The Unix socket is a security boundary.

Phase 4 MUST explicitly define:

```text
socket owner
socket group
socket mode
runtime directory mode
```

The implementation must also establish how the daemon identifies the connecting Unix user.

Do not trust a frontend-supplied:

```json
{
    "user": "alice"
}
```

as identity.

Do not solve socket permissions by blindly using:

```text
0666
```

without documenting the resulting security boundary.

Likewise, do not automatically use:

```ts
superuser: "require"
```

just to make the socket accessible.

Running the channel with elevated identity can interfere with the backend's ability to associate the connection with the actual Cockpit user.

Detailed command authorization remains Phase 5.

---

# 31. Cockpit channel versus daemon lifecycle

These lifetimes MUST remain separate:

```text
Browser
   │
   └── NodeProvider
          │
          └── Cockpit channel
                 │
                 └── Unix connection
                        │
                        └── NodeStream
```

versus:

```text
systemd
   │
   └── cockpit-slurm daemon
          │
          ├── NodeSynchronizer
          ├── NodeCache
          └── Node change publication
```

Closing the channel:

```text
MUST:
    remove that client stream

MUST NOT:
    stop NodeSynchronizer
    clear NodeCache
    terminate daemon
```

This is one of the most important Phase 4 invariants.

---

# 32. Backend package boundaries

Recommended responsibilities:

```text
internal/
  adapter/
  cache/
  query/
  sync/
  event/
  stream/
  protocol/
```

### `sync`

Periodic Node synchronization.

### `cache`

Authoritative Node state, generation and semantic comparison.

### `event`

NodeChange representation/publication boundary.

This does NOT need to become a generic event-bus framework.

### `stream`

Active Node streams, registration, fan-out, queues and writers.

### `protocol`

Application framing and stream-message encoding/decoding.

Do not put React/Cockpit browser code in backend packages.

---

# 33. Publication path

The mandatory backend path is:

```text
NodeSynchronizer
    ↓
NodeAdapter
    ↓
canonical Node snapshot
    ↓
NodeCache.Apply()
    ↓
NodeChange[]
    ↓
NodeChangePublisher
    ↓
NodeStreamRegistry.Publish()
    ↓
per-stream queue
    ↓
single writer
    ↓
Unix socket
```

A useful conceptual API is:

```go
changes, committed := nodeCache.Apply(snapshot)

if committed {
    publisher.Publish(changes)
}
```

This makes cache/event ordering explicit.

---

# 34. Stream registration

Recommended:

```text
accept Unix socket
    ↓
create NodeStream
    ↓
atomically register + capture cache baseline
    ↓
enqueue snapshot
    ↓
begin event delivery
```

There is no:

```text
subscribe request
```

because the connection itself is the subscription.

---

# 35. Disconnect cleanup

When a socket closes:

```text
EOF/error
    ↓
mark stream closed
    ↓
unregister stream
    ↓
stop writer
    ↓
release queue
```

Cleanup MUST be idempotent.

A disconnected browser MUST NOT remain in the registry.

A disconnected client MUST NOT cause the daemon to fail.

---

# 36. Error handling

## Backend

Distinguish:

```text
Slurm refresh failure
Unix connection failure
client disconnect
protocol error
queue overflow
internal synchronization error
```

A client failure is not a daemon failure.

A malformed client must not terminate the daemon.

A slow client must not block unrelated clients.

## Frontend

Expose appropriate:

```text
loading
connected
reconnecting
error
```

states.

A temporary stream failure should not permanently destroy the current UI state.

A successful reconnect replaces the client state with a fresh authoritative snapshot.

# 37. Backend tests

```text

    → no generation change
    → no event
```

```text
    → NodeUpdated
```


Test:

```text

```

```text
unregister

```

```text
    → registry cleanup
```

## 37.3 Multiple clients

Test:

```text

Node changes

A receives change
B receives change
```

Then:

```text

Node changes

B still receives change
```

## 37.4 Serialization

Concurrent publishers MUST never interleave frames.

Bad:

```text
frame A + partial frame B + rest of A
```

Good:

```text
frame A
frame B
```

## 37.5 Queue overflow

Test:

```text
queue full
    → affected stream closes
    → stream unregisters
    → daemon continues
```

# 40. Implementation sequence

## Phase 4A — Freeze Phase 3 baseline

Verify:

```text
Node adapter
Node cache
Node query
NodeProvider
```

# 45. Final Phase 4 architecture

```text
                         Slurm
                           │
                           ▼
                  NodeSynchronizer
                           │
                           ▼
                     Node Adapter
                           │
                           ▼
                      Node Cache
                   authoritative state
                       │       │
                    query    change
                       │       │
                       │       ▼
                       │   NodeChange
                       │       │
                       │       ▼
                       │ NodeStreamRegistry
                       │       │
                       │   ┌───┴────┐
                       │   │        │
                       ▼   ▼        ▼
                    Query  Stream A Stream B
                             │        │
                             ▼        ▼
                          Unix sockets
                              │
                              ▼
                    Cockpit native channels
                              │
                       ┌──────┴──────┐
                       ▼             ▼
                 NodeProvider A  NodeProvider B
                       │             │
                       ▼             ▼
                   NodeTable A   NodeTable B
```

The central rule is:

> **Cockpit channels provide frontend transport and lifecycle. `cockpit-slurm` provides persistent authoritative state and resource-specific fan-out. React Context provides browser-local state. No layer should impersonate the responsibility of another.**
