# cockpit-slurm Implementation Phase 4 — Node Events and Subscriptions

# 1. Purpose

Phase 4 implements the second part of the first complete Node vertical slice:

```text
Phase 3
Node query / snapshot
        ↓
Phase 4
Node events / subscriptions
```

Phase 3 proved that a real Slurm Node resource can be read, normalized,
cached, queried through the application IPC protocol, and displayed by
React.

Phase 4 extends that same Node resource so that changes in the backend
authoritative state can be propagated to subscribed frontend clients.

The target path is:

```text
Slurm state
    ↓
Node Resource Adapter / Synchronizer
    ↓
Canonical Node
    ↓
Node Resource Cache
    ↓
Change Detection
    ↓
Event Bus
    ↓
Subscription Manager
    ↓
IPC
    ↓
Frontend IPC Client
    ↓
Subscription Service
    ↓
NodeProvider
    ↓
Node Table
```

The primary objective is to prove:

> A Node state change is detected by the backend, committed to the
> authoritative cache, converted into a resource event, and delivered
> to subscribed frontend clients without React executing Slurm commands
> or maintaining authoritative resource state.

This phase is subordinate to:

```text
docs/architecture/0.1 development-cockpit-slurm-_v3.6.md
docs/architecture/1.0 implementation-plan-v3.6.md
docs/architecture/4.2 Implementation-phase3.md
```

The v3.6 development architecture is the normative architectural
reference.

---

# 2. Phase 4 implementation principle

Phase 4 must be implemented as an incremental extension of the
completed Phase 3 Node vertical slice.

Do not redesign the Phase 3 query path.

The implementation sequence is:

```text
Phase 4A
    Verify Phase 3 Node/query baseline
        ↓
Phase 4B
    Define Node event contract
        ↓
Phase 4C
    Define cache change-detection semantics
        ↓
Phase 4D
    Implement Event Bus
        ↓
Phase 4E
    Implement Node subscription contract
        ↓
Phase 4F
    Implement Subscription Manager
        ↓
Phase 4G
    Integrate subscriptions with existing IPC/Dispatcher
        ↓
Phase 4H
    Implement frontend Subscription Service
        ↓
Phase 4I
    Extend NodeProvider for snapshot + events
        ↓
Phase 4J
    Integrate Node Table with live Node state
        ↓
Phase 4K
    Test reconnect, unsubscribe, disconnect, and missed-event handling
        ↓
Phase 4L
    End-to-end Node event test
        ↓
Phase 4 complete
```

The key principle is:

> The backend cache is authoritative. Events describe committed
> changes to that cache. The frontend consumes snapshots and events as
> a client of the backend state.

Do not make the frontend responsible for determining whether a Slurm
resource changed.

# 5. Architectural invariants

The following invariants are mandatory.

## 5.1 Backend cache is authoritative

The backend Resource Cache is the authoritative in-memory representation
of Node state.

The frontend may maintain presentation/client state, but that state is
not authoritative.

```text
Backend Resource Cache
        =
authoritative Node state
```

## 5.2 Events follow committed cache changes

The required ordering is:

```text
resource refresh
    ↓
normalize
    ↓
compare with cached state
    ↓
commit changed state to cache
    ↓
increment generation
    ↓
publish event
    ↓
deliver to subscribers
```

An event must never describe a state that has not been committed to the
backend cache.

## 5.3 Unchanged state produces no update event

If a synchronization cycle produces a Node representation that is
semantically equal to the cached representation:

```text
new Node == cached Node
```

then:

- the cache generation must not advance merely because a refresh
  occurred;
- no NodeUpdated event is published;
- subscribers must not receive a false update.

The implementation may record synchronization activity separately if
required for diagnostics, but that is not a resource-change event.

## 5.4 Frontend does not poll Slurm

React must not execute:

```text
scontrol
sinfo
squeue
sacct
sacctmgr
```

or any other Slurm command.

Frontend subscriptions operate only through the existing application
IPC client.

## 5.5 Backend owns subscriptions

Subscriptions belong to backend connections.

The backend understands:

```text
resource = node
```

not:

```text
component = NodeTable
```

The backend must not contain React component names.

## 5.6 Existing IPC framing remains authoritative

Phase 4 does not introduce a second framing protocol.

The existing length-prefixed application framing remains unchanged.

Subscription messages and event messages are application messages carried
by the existing IPC stream.

## 5.7 Frontend services remain transport/client abstractions

The frontend Subscription Service may own:

- subscribe request creation;
- unsubscribe request creation;
- subscription identifiers;
- event routing;
- client-side subscription lifecycle;
- connection error handling.

It must not own:

- Slurm synchronization;
- Slurm command execution;
- backend authorization;
- authoritative resource state;
- change detection rules;
- backend event generation.

# 7. Phase 4B — Node event contract

## 7.1 Event purpose

A Node event represents a committed change to Node state in the
authoritative backend cache.

The event is not a raw Slurm command result.

The event is not a UI event.

The event is not a notification that a synchronization cycle happened.

It is a resource-state change.

## 7.2 Event identity

A Node event should contain enough information for a client to:

- identify the resource;
- identify the resource instance;
- identify the new generation;
- determine the event kind;
- obtain the new resource state or an appropriate resource payload.

Conceptually:

```json
{
  "type": "event",
  "resource": "nodes",
  "event": "updated",
  "generation": 12,
  "payload": {
    "node": {}
  }
}
```

The exact envelope must follow the existing application protocol model.

Do not introduce a separate event framing format.

## 7.3 Recommended event fields

The implementation should support the following conceptual fields:

```text
protocol
version
messageId
type
resource
event
generation
payload
```

The `messageId` semantics for server-originated events must be defined
consistently with the existing protocol. A server-generated event may
use its own event identifier if the application protocol distinguishes
request IDs from event IDs.

Do not overload the frontend request message ID.

## 7.4 Node event kinds

The initial implementation should support at least:

```text
NodeUpdated
NodeAdded
NodeRemoved
```

If the Phase 3 Node cache is snapshot-replacement based and cannot yet
distinguish additions/removals cleanly, `NodeUpdated` may be the only
initial externally visible event.

However, the cache comparison layer should be designed so that
resource-specific event classification can be added without redesigning
the subscription transport.

## 7.5 NodeStateChanged

A Node state transition is a semantic change within a NodeUpdated event.

For example:

```text
NodeUpdated
    ├── generation
    ├── node identity
    ├── previous state
    └── current state
```

A separate `NodeStateChanged` event is optional.

Do not create multiple overlapping event types merely to represent
different UI presentations.

The preferred initial model is:

```text
resource event:
    NodeUpdated

payload may include:
    changed fields
    previous state
    current state
```

The exact payload must be defined from the existing canonical Node model
and should not expose generated OpenAPI implementation details directly
unless that is already the application contract.

# 8. Phase 4C — Cache change detection

## 8.1 Purpose

Change detection determines whether a newly synchronized Node
representation differs from the cached representation.

Conceptually:

```text
new snapshot
    ↓
normalize
    ↓
compare
    ↓
┌───────────────┬────────────────┐
│ unchanged     │ changed        │
│               │                │
│ no event      │ update cache   │
│ no generation │ increment      │
│ increment     │ publish event  │
└───────────────┴────────────────┘
```

## 8.2 Stable identity

Node identity must be based on the canonical Node identity established
in Phase 3.

Do not use:

- array position;
- table row position;
- frontend React key alone;
- transient object pointer;
- synchronization sequence number.

The identity must remain stable across refreshes.

## 8.3 Semantic equality

The comparison must be performed on canonical Node state.

Do not compare raw JSON byte strings unless the canonical representation
is explicitly defined as byte-identical.

For example, harmless changes in JSON field order must not produce
NodeUpdated events.

The comparison should operate on normalized application data.

## 8.4 Generation semantics

The Node generation must advance when the authoritative Node state
changes according to the cache's defined semantics.

Example:

```text
generation 10
    ↓
same Node state
    ↓
generation remains 10

generation 10
    ↓
Node state changes
    ↓
generation 11
```

Generation values must be monotonic for the relevant cache/resource
scope.

## 8.5 Removed Nodes

If a synchronization snapshot no longer contains a previously cached
Node, the implementation must determine whether that means:

- NodeRemoved;
- temporary synchronization failure;
- incomplete source data;
- source/API failure.

A failed or incomplete Slurm query must not automatically be interpreted
as deletion of all missing Nodes.

The implementation must distinguish:

```text
valid complete snapshot
```

from:

```text
failed/incomplete synchronization
```

before producing removal events.

# 9. Phase 4D — Event Bus

## 9.1 Responsibilities

The Event Bus owns in-process event publication.

It must:

- accept a committed resource event;
- deliver it to registered subscribers;
- isolate publishers from individual connections;
- avoid requiring the publisher to know about React;
- avoid embedding resource-specific UI logic.

Conceptually:

```text
Resource Cache
      ↓
   Event Bus
      ↓
┌─────┼─────┐
▼     ▼     ▼
Sub A Sub B Sub C
```

## 9.2 Event Bus must not own cache state

The Event Bus must not become another cache.

It may maintain:

- subscriber registrations;
- routing metadata;
- bounded delivery queues if required.

It must not maintain an authoritative Node snapshot.

## 9.3 Publication ordering

The event must be published only after the cache update has committed.

Required:

```text
cache update
    ↓
generation assigned
    ↓
event constructed
    ↓
event published
```

Forbidden:

```text
event published
    ↓
cache update attempted
```

## 9.4 Event delivery isolation

A slow subscriber must not block unrelated subscribers indefinitely.

The implementation should define a bounded strategy for slow clients.

At minimum, tests must verify that one disconnected or failing subscriber
does not terminate the Event Bus.

The exact backpressure strategy may be implemented as:

- per-subscription queue;
- serialized delivery with bounded buffering;
- disconnect on unrecoverable overflow.

Do not silently drop events without a defined recovery mechanism.

# 10. Phase 4E — Subscription protocol

## 10.1 Subscribe request

The initial subscription request should be resource-oriented.

Example:

```json
{
  "type": "subscribe",
  "resource": "nodes",
  "payload": {}
}
```

Do not use UI component names:

```json
{
  "type": "subscribe",
  "component": "NodeTable"
}
```

The backend knows resources, not React components.

## 10.2 Subscribe response

A successful subscription should provide a subscription identifier.

Conceptually:

```json
{
  "type": "subscribed",
  "resource": "nodes",
  "subscriptionId": "sub-01...",
  "generation": 12
}
```

The exact response envelope must follow the existing protocol conventions.

## 10.3 Unsubscribe request

Example:

```json
{
  "type": "unsubscribe",
  "resource": "nodes",
  "subscriptionId": "sub-01..."
}
```

The backend must validate that the subscription belongs to the
requesting connection.

A client must not be able to unsubscribe another connection's
subscription.

## 10.4 Event message

A subscribed client receives resource events through the same
application IPC stream.

Conceptually:

```json
{
  "type": "event",
  "resource": "nodes",
  "subscriptionId": "sub-01...",
  "event": "updated",
  "generation": 13,
  "payload": {
    "node": {}
  }
}
```

The event must be associated with the subscription so that the frontend
can route it correctly.

# 11. Phase 4F — Initial subscription ordering

This is a critical correctness requirement.

The implementation must not create a race in which an event occurs between
the initial snapshot and subscription registration and is therefore
lost.

Unsafe sequence:

```text
read snapshot
    ↓
send snapshot
    ↓
register subscription
```

An event can occur between the snapshot and registration.

The preferred conceptual sequence is:

```text
validate subscription
    ↓
establish subscription registration
    ↓
capture baseline generation
    ↓
obtain current snapshot
    ↓
send initial snapshot
    ↓
deliver events after the baseline
```

The implementation may use a lock or another atomic coordination
mechanism to guarantee this ordering.

A valid alternative is:

```text
capture generation G
register subscription with baseline G
send snapshot at G
queue/deliver all events with generation > G
```

The exact internal mechanism is implementation-defined, but the observable
contract must guarantee:

> A valid resource change committed after the subscription baseline is
> not silently lost.

## 11.1 Initial snapshot

The initial subscription response should contain enough information for
the frontend to establish a consistent starting state.

Conceptually:

```text
subscribe
    ↓
subscription established at generation G
    ↓
snapshot generation G
    ↓
future events G+1, G+2, ...
```

## 11.2 Duplicate event handling

The frontend should be able to tolerate a repeated event without
corrupting state.

The preferred rule is generation-aware processing:

```text
incoming generation <= current generation
    ↓
ignore or safely coalesce

incoming generation > current generation
    ↓
apply
```

The exact behavior must be consistent with the protocol and cache
semantics.

# 12. Phase 4G — Subscription Manager

## 12.1 Responsibilities

The Subscription Manager owns:

- subscription creation;
- subscription identity;
- resource type;
- connection ownership;
- registration with the Event Bus;
- initial snapshot coordination;
- event delivery;
- unsubscribe;
- cleanup on connection close.

It must not own:

- Slurm synchronization;
- Node canonicalization;
- Node command execution;
- authorization business logic beyond any subscription-specific access
  check required by the existing contract.

## 12.2 Connection ownership

Conceptually:

```text
Connection A
 ├── Subscription A1: nodes
 └── Subscription A2: ...

Connection B
 └── Subscription B1: nodes
```

A subscription belongs to exactly one backend connection.

When a connection closes:

```text
connection close
    ↓
remove all subscriptions owned by connection
    ↓
remove Event Bus registrations
    ↓
release delivery resources
```

## 12.3 Multiple clients

Multiple clients may subscribe to the same resource:

```text
Node cache
    ↓
Event Bus
    ├── Client A
    ├── Client B
    └── Client C
```

Each client receives the same logical resource event according to its
subscription.

One client must not mutate the event before another client receives it.

The implementation may serialize or copy event payloads as necessary.

## 12.4 Duplicate subscriptions

The implementation must define behavior for:

```text
same connection
    ↓
subscribe nodes
    ↓
subscribe nodes again
```

The preferred initial behavior is to create a distinct subscription only
when the client explicitly requests one with a new lifecycle, or return
the existing subscription when the protocol defines subscriptions as
idempotent.

Do not accidentally create untracked duplicate Event Bus registrations.

The chosen behavior must be tested and documented in the implementation.

# 13. Phase 4H — IPC / Dispatcher integration

The existing Dispatcher must be extended only enough to route:

```text
subscribe
unsubscribe
```

and the backend must be able to send:

```text
snapshot
event
```

messages asynchronously.

## 13.1 Dispatcher responsibilities

The Dispatcher should:

- validate the application envelope;
- validate message type;
- validate required fields;
- route subscribe requests;
- route unsubscribe requests;
- preserve request IDs;
- return protocol errors.

It must not:

- inspect React component names;
- perform Node change detection;
- access Slurm directly;
- publish Node events itself.

## 13.2 Asynchronous server messages

The existing IPC implementation was initially request/response oriented.

Phase 4 adds server-originated messages.

The implementation must therefore support:

```text
Client → Server
    request

Server → Client
    response

Server → Client
    event
```

without assuming every incoming frontend message has exactly one
corresponding response before any other server message.

The frontend IPC client must route responses and events independently.

The frontend should extend the existing IPC client architecture with:

```text
src/services/subscription-service.ts
```

The Subscription Service is a client abstraction.

It should own:

- subscribe request creation;
- unsubscribe request creation;
- subscription IDs;
- event listeners;
- event routing;
- subscription lifecycle;
- connection-close cleanup.

It should not own:

- Slurm synchronization;
- canonical Node definitions;
- change detection;
- backend authorization;
- command execution.

## 14.1 Frontend service boundary

Good:

```text
NodeProvider
    ↓
SubscriptionService
    ↓
IPC Client
    ↓
cockpit.channel()
    ↓
backend Subscription Manager
```

Bad:

```text
NodeProvider
    ↓

    ↓
frontend NodeCache
    ↓
```

The frontend remains a client of the backend application.

# 15. Phase 4J — NodeProvider live state

The NodeProvider established in Phase 3 must be extended to support:

```text
initial snapshot
      ↓
subscription established
      ↓
Node events
      ↓
frontend Node state update
```

## 15.1 Provider responsibilities

NodeProvider may own:

- current client-side Node collection;
- current client-side generation;
- loading state;
- subscription state;
- connection state;
- error state;
- event application.

NodeProvider must not become the authoritative cache.

## 15.2 Provider initialization

Recommended flow:

```text
NodeProvider mounts
    ↓
request/establish Node subscription
    ↓
receive initial snapshot
    ↓
set Node state
    ↓
mark subscription active
    ↓
receive subsequent events
    ↓
apply events
```

Do not independently start a competing polling loop.

## 15.3 Event application

For a NodeUpdated event:

```text
receive event
    ↓
validate resource
    ↓
validate subscription
    ↓
validate generation
    ↓
update client-side Node state
    ↓
render
```

The provider should not recalculate Slurm state from raw fields.

The backend event payload is the authoritative representation for the
client's current subscribed state.

## 15.4 Generation handling

NodeProvider should retain the latest accepted generation.

Example:

```text
snapshot generation 20
    ↓
event generation 21
    ↓
accept

event generation 20
    ↓
stale
    ↓
ignore/coalesce according to protocol
```

If a generation gap is detected:

```text
current = 20
incoming = 23
```

the provider must not silently assume that generations 21 and 22 are
irrelevant.

The implementation should trigger a resynchronization according to the
defined recovery behavior, such as requesting a fresh snapshot or
re-establishing the subscription.

# 16. Phase 4K — Node Table integration

The Node Table should continue to consume NodeProvider state.

The table must not subscribe directly to IPC.

Correct:

```text
NodeTable
    ↓
NodeProvider
    ↓
SubscriptionService
    ↓
IPC
```

Incorrect:

```text
NodeTable
    ↓
cockpit.channel()
```

The Node Table should update naturally when NodeProvider state changes.

The table must not implement:

- Slurm event parsing;
- generation tracking;
- subscription protocol;
- reconnect logic;
- Slurm command execution.

# 17. Synchronization source

Phase 4 requires a mechanism that causes Node state to be refreshed after
the underlying Slurm state changes.

The exact synchronization mechanism must follow the v3.6 architecture.

If the backend uses periodic polling, it belongs to the backend Resource
Synchronizer.

Conceptually:

```text
Resource Synchronizer
        ↓
Node Adapter
        ↓
new Node snapshot
        ↓
Resource Service
        ↓
Node Cache
        ↓
Change Detection
```

The frontend must not create its own Slurm polling loop.

## 17.1 Polling interval

Phase 4 must not introduce a frontend polling interval.

Any backend refresh interval must be centralized in the backend
synchronization mechanism and remain independent of the number of
frontend clients.

For example:

```text
10 Cockpit clients
       ↓
one backend Node synchronization cycle
       ↓
one cache update
       ↓
one logical event
       ↓
10 subscribers
```

not:

```text
10 Cockpit clients
       ↓
10 independent scontrol calls
```

---

# 18. Cache update and event publication transaction

The implementation should treat a resource update as one logical
operation:

```text
1. Obtain source data.
2. Decode source data.
3. Normalize to canonical Node.
4. Validate the Node.
5. Compare against cached Node.
6. If unchanged, stop.
7. If changed, assign the new generation.
8. Commit the new Node to cache.
9. Construct the event from committed state.
10. Publish the event.
11. Deliver to subscribers.
```

The Command Adapter must not be introduced in this phase.

The Node Adapter remains responsible for reading Slurm state.

## 18.1 Failure before cache commit

If synchronization fails:

```text
Slurm query fails
```

then:

- the previous valid cache state remains;
- generation does not advance;
- no NodeUpdated event is published;
- the synchronization failure may be recorded separately.

Do not replace valid cached Nodes with empty data merely because a query
failed.

---

# 19. Event payload design

The initial implementation should prefer complete resource state in a
NodeUpdated event rather than requiring the frontend to independently
query individual fields.

Conceptually:

```json
{
  "type": "event",
  "resource": "nodes",
  "subscriptionId": "sub-01",
  "event": "updated",
  "generation": 42,
  "payload": {
    "node": {
      "name": "c21"
    }
  }
}
```

The exact canonical Node fields must come from the Phase 3 contract.

## 19.1 Why complete state is preferred initially

Complete state makes the first event implementation easier to reason
about:

```text
snapshot
    ↓
complete Node
    ↓
event
    ↓
replace/update client state
```

Avoid making Phase 4 depend on complex field-level patch semantics.

Patch/delta events may be considered later after the resource event
contract is proven.

---

# 20. Event ordering

For one resource stream, event ordering must be deterministic.

If:

```text
generation 10
generation 11
generation 12
```

is delivered, the frontend must not observe:

```text
10
12
11
```

for the same subscription.

The backend must preserve generation order for events emitted from the
same resource/cache sequence.

If concurrent synchronization is introduced later, generation assignment
must still provide a single authoritative ordering for committed Node
state.

---

# 21. Reconnection and recovery

Phase 4 must define behavior when the frontend connection is lost.

A subscription belongs to a connection.

Therefore:

```text
connection lost
    ↓
subscription invalid
```

The frontend must not assume the old subscription remains active.

On reconnection:

```text
new connection
    ↓
new subscription
    ↓
new initial snapshot
    ↓
current generation
    ↓
future events
```

This is safer than attempting to replay an old connection's subscription
state unless a future protocol explicitly supports resumable
subscriptions.

## 21.1 Generation-based recovery

If the frontend has:

```text
last generation = 50
```

and reconnects when the backend is at:

```text
generation = 57
```

the initial snapshot at generation 57 becomes the new authoritative
frontend baseline.

The frontend must not attempt to reconstruct generations 51–56 unless
the protocol explicitly supports event replay.

---

# 22. Disconnect cleanup

The backend must clean up subscriptions when:

- the client explicitly unsubscribes;
- the IPC connection closes;
- the connection encounters an unrecoverable protocol error;
- the server shuts down.

Required invariant:

```text
closed connection
    ↓
zero active subscriptions owned by that connection
```

Tests must verify that subscriptions do not leak after repeated connect /
disconnect cycles.

# 23. Error handling

## 23.1 Invalid subscribe request

Examples:

```text
missing resource
unsupported resource
malformed payload
invalid protocol version
```

must return an application-level protocol error.

## 23.2 Invalid unsubscribe

Examples:

```text
missing subscription ID
unknown subscription ID
subscription belongs to another connection
```

must be rejected.

## 23.3 Synchronization failure

A Slurm synchronization failure must not automatically terminate all
subscriptions.

The existing cached Node state remains valid until a newer valid state is
committed.

The backend may expose synchronization status separately in a future
phase.

## 23.4 Subscriber delivery failure

If an IPC connection cannot accept an event:

```text
event delivery fails
    ↓
connection cleanup
    ↓
subscription cleanup
```

The failure of one client must not stop the Event Bus or affect other
clients.

# 24. Security and authorization

Phase 4 is primarily read/subscription functionality.

The backend remains authoritative for access control.

A subscription must not allow a client to access a resource that it is
not permitted to read under the existing server-side policy.

However, Phase 4 must not introduce the complete Node mutation
authorization model.

The important distinction is:

```text
subscription authorization
    =
permission to observe resource state

command authorization
    =
permission to change resource state
```

Command authorization belongs to Phase 5.

The frontend must never be trusted to enforce either policy.

```text
      ↓
```

```text
      ↓

      ↓

      ↓
```

```text
      ↓
```

The following must remain true:

```text

Frontend services do not contain Slurm business logic.

The frontend cache is not authoritative.

The backend cache is authoritative.

Events are published only after cache updates are committed.

A synchronization failure does not silently delete valid cached state.

A connection failure removes its subscriptions.

A reconnect establishes a fresh subscription and snapshot.

The existing Phase 2 IPC framing is reused.

cockpit-slurm-channel is not required.
```

This satisfies the Phase 4 milestone:

> **M4 — Node Events and Subscriptions**

and establishes the event/subscription behavior required before Phase 5
implements Node commands and authorization.
