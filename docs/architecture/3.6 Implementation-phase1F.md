# Implementation Phase 1F — Cockpit Channel Integration

**Status:** Planned
**Phase:** 1F
**Depends on:** Phase 1B, Phase 1C, Phase 1D, Phase 1E
**Next phase:** Phase 2 — First vertical slice

---

# 1. Purpose

Implement the thin `cockpit-slurm-channel` integration between Cockpit's
`cockpit.channel()` and the persistent `cockpit-slurm-bridge`.

Phase 1F establishes:

- Cockpit channel lifecycle handling.
- Channel-to-bridge Unix socket connection.
- Bidirectional transport forwarding.
- Connection and session metadata propagation.
- Clean channel and bridge disconnection.
- Integration with the existing Phase 1E connection foundation.

This phase validates the Cockpit transport boundary before implementing
Slurm resource access.

---

# 2. Scope

### In scope

- Implement the `cockpit-slurm-channel` executable.
- Accept and process Cockpit channel input.
- Connect to the bridge Unix socket.
- Forward valid protocol messages to the bridge.
- Forward bridge responses to Cockpit.
- Preserve the existing protocol envelope and message types.
- Associate channel processing with the Phase 1E connection context.
- Handle channel closure and bridge disconnection.
- Support multiple concurrent channel processes.
- Add unit and integration tests.

### Out of scope

- Slurm resource models and cache.
- Slurm command execution.
- Resource adapters.
- Command adapters.
- Event bus and subscription manager.
- Complete authorization policy evaluation.
- Slurm AdminLevel lookup.
- Capability resolution.
- Role-specific UI behavior.
- Resource-specific frontend providers.
- Persistent session storage.
- Session resumption.
- Channel-side Slurm business logic.

# 3. Architecture Boundary

The channel remains a transport adapter.

```text
React
    │
    │ cockpit.channel()
    ▼
Cockpit
    │
    │ Cockpit channel protocol
    ▼
cockpit-slurm-channel
    │
    │ Unix socket
    ▼
cockpit-slurm-bridge
    │
    ├── IPC Server
    ├── Connection
    ├── UserContext
    └── Protocol Dispatcher
```

The channel owns:

* Cockpit transport lifecycle.

* stdin/stdout processing.

* Unix socket client.

* Bidirectional forwarding.

* Transport shutdown.

The bridge owns:

* Connection and session state.

* Peer identity.

* UserContext.

* Protocol validation.

* Message dispatch.

* Future Slurm application services.

The channel must not contain Slurm-specific business logic.

# 4. Implementation Contract

Phase 1F must implement a minimal Cockpit transport adapter.

The implementation must preserve the existing Phase 1C protocol contract and the Phase 1D dispatcher behavior.

The channel must:

1. Accept a Cockpit channel connection.

2. Establish a Unix socket connection to the bridge.

3. Forward valid client protocol messages.

4. Forward bridge responses to Cockpit.

5. Preserve message ordering.

6. Preserve message identifiers.

7. Preserve protocol errors.

8. Close both sides when either side terminates.

9. Avoid interpreting application payloads.

10. Avoid implementing Slurm-specific logic.

The channel must not become a second application service layer. 

# 4.1 Normative Clarifications

## Exact IPC framing

Use length-prefixed frame. 

Phase 1F must use the existing Phase 1C/1D protocol framing.

The channel must not introduce a new framing format.

The channel must forward complete protocol frames unchanged.

If the existing implementation has not yet defined the byte-level framing,
the framing contract must be defined before Phase 1F coding begins.

## Socket path configuration

The bridge socket path must have one authoritative configuration source,
shared by the bridge and channel.

The channel must not hard-code a development-only socket path.

If the socket path is absent or invalid, the channel must report the error
and exit.

The channel must not silently fall back to another socket path.

## Failure model

The channel is a thin transport adapter.

- Socket unavailable: report the error and close the channel.
- Bridge connect timeout: report the error and close the channel.
- Bridge disconnect: close the Cockpit channel.
- Cockpit closure: close the bridge connection.
- Invalid bridge message: report a protocol error and close the connection.

The channel must not implement retry loops or fabricate application responses.

## Test-first requirements

Before implementation, add failing tests for:

- Message ID preservation.
- Bridge disconnect closes the channel.
- No forwarding after close.
- Concurrent channel isolation.

First failing tests checklist:

- [ ] `hello` round-trip preserves message ID and payload.
- [ ] `ping` round-trip preserves message ID and payload.
- [ ] socket connect failure exits cleanly without retry loops.
- [ ] bridge disconnect closes the Cockpit channel.
- [ ] closed channel does not forward any further messages.
- [ ] two concurrent channel instances remain isolated.

Implementation is complete only when these tests pass.

## No feature creep

Phase 1F is transport integration only.

Do not add Slurm commands, resource models, cache, authorization,
AdminLevel logic, or UI behavior.

The channel must remain a thin transport adapter.

# 5. Canonical Naming and Ownership

## 5.1 Channel executable

The executable name is:

cockpit-slurm-channel

The executable is a lightweight transport adapter.

## 5.2 Package ownership

The channel implementation may use the following package structure:

```
cmd/
└── cockpit-slurm-channel/

internal/
└── channel/
    ├── channel.go
    ├── client.go
    ├── forward.go
    └── channel_test.go
```

The exact filenames may differ, but responsibilities must remain separated.

## 5.3 Ownership rules

| Component | Responsibility|
| --- | --- |
|Cockpit| Starts the channel and owns the Cockpit transport |
|Channel| Forwards transport data between Cockpit and bridge|
|IPC client |Connects to the bridge Unix socket|
|Bridge IPC server |Accepts Unix socket connections|
|Connection|Owns connection and session context|
|Protocol|Owns encoding, decoding, and validation|
|Dispatcher |Owns message routing|
|Future services|Own Slurm access and authorization |

The channel must not import Slurm adapters, resource models, cache, or command services.

# 6. Channel Lifecycle

For each Cockpit channel process:

```
Start
  ↓
Initialize channel transport
  ↓
Connect to bridge Unix socket
  ↓
Forward client messages
  ↓
Forward bridge responses
  ↓
Detect closure or error
  ↓
Close both transports
  ↓
Exit
```

The channel must not create a persistent application session.

The bridge creates the connection and session according to Phase 1E.

# 7. Cockpit Transport

The channel must use the Cockpit channel transport contract.

The implementation must:

* Read channel input from Cockpit.

* Write channel output to Cockpit.

* Preserve the protocol message payload.

* Avoid modifying application message fields.

* Avoid introducing a second application envelope.

* Handle channel closure.

* Handle bridge disconnection.

* Avoid writing after the Cockpit transport is closed.

The channel must not interpret:

* `query`

* `command`

* `subscribe`

* `unsubscribe`

* `hello`

* `ping`

* Resource names

* UserContext fields

* Slurm-specific payloads

Those concerns belong to the bridge.

# 8. Unix Socket Connection

The channel must connect to the bridge using the configured Unix socket.

The socket path must be configurable.

The implementation must not hard-code a development-only path.

For example:

```
/run/cockpit-slurm/bridge.sock
```

The exact production path must follow the repository's IPC configuration.

The channel must:

* Connect to the bridge socket.

* Detect connection failure.

* Report transport failure according to the existing error policy.

* Close the Cockpit channel if the bridge cannot be reached.

* Avoid retry loops that create uncontrolled processes.

* Avoid creating or managing the bridge daemon.

The channel is a client of the bridge.

# 9. Message Forwarding

The channel must provide bidirectional forwarding.

```
Cockpit
    │
    ▼
Channel stdin
    │
    ▼
Unix socket client
    │
    ▼
Bridge
    │
    ▼
Unix socket client
    │
    ▼
Channel stdout
    │
    ▼
Cockpit
```

The channel must preserve:

* Message type.

* Message identifier.

* Resource.

* Payload.

* Protocol version.

* Response ordering.

The channel must not:

* Generate application request IDs.

* Modify UserContext.

* Resolve identity.

* Perform authorization.

* Execute Slurm commands.

* Update the bridge cache.

* Generate application events.

# 10. Connection and Session Context

Phase 1E establishes the server-owned connection and session context.

Phase 1F must preserve this boundary.

The channel must not create or override:

* Connection ID.

* Session ID.

* Peer UID.

* Peer GID.

* Username.

* AdminLevel.

* Accounts.

* Capabilities.

* Authorization decisions.

The bridge remains responsible for creating and owning these values.

The channel may forward bridge-generated connection metadata if the existing protocol contract permits it, but must not treat that metadata as authentication credentials.

# 11. Handshake and Protocol Compatibility

The existing Phase 1D `hello` behavior must remain valid.

Phase 1F must not introduce a new application handshake unless explicitly required by the existing protocol contract.

The channel must not introduce:

* `session.create`

* `session.resume`

* `session.destroy`

* A second protocol version

* A second request ID

* A second application envelope

The channel must forward the existing `hello` and `ping` messages unchanged.

The bridge must continue to perform protocol validation.

# 12. Concurrency and Isolation

Each Cockpit channel process must have its own:

* Cockpit transport.

* Unix socket connection.

* Forwarding loops.

* Shutdown state.

The channel must not share transport state between unrelated processes.

Multiple channel processes may connect to the bridge concurrently.

The bridge must continue to maintain independent connection and session state for each accepted Unix socket connection.

The channel must not maintain a global application cache.

# 13. Error Handling

The channel must distinguish:

* Cockpit transport errors.

* Bridge connection errors.

* Unix socket read errors.

* Unix socket write errors.

* Protocol errors received from the bridge.

* Normal client disconnect.

* Bridge shutdown.

The implementation must:

* Avoid panics for ordinary transport failures.

* Close invalid or unusable connections.

* Avoid sending responses after channel closure.

* Avoid leaking goroutines.

* Avoid leaking Unix socket connections.

* Preserve Phase 1C protocol error semantics.

* Preserve Phase 1D dispatcher error behavior.

The channel must not convert bridge application errors into fabricated application responses.

# 14. Shutdown and Cleanup

When the Cockpit channel closes, the channel must:

* Stop reading from Cockpit.

* Stop writing to Cockpit.

* Close the Unix socket connection.

* Stop forwarding goroutines.

* Release transport resources.

* Exit cleanly.

When the bridge connection closes, the channel must:

* Stop reading from the bridge.

* Stop writing to the bridge.

* Close the Cockpit channel.

* Release transport resources.

* Exit cleanly.

The implementation must prevent:

* Goroutine leaks.

* Double-close panics.

* Writes after closure.

* Continued forwarding after shutdown.
