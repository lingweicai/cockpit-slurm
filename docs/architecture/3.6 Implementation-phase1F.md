# 3.6 Implementation Phase 1F — First Authenticated Application Service

## 1. Purpose

Phase 1F builds the first authenticated application-service layer above the connection/session foundation established in Phase 1E.

The purpose of Phase 1F is to move from transport- and identity-only code into the first real bridge application behavior:

- resolve the remote Linux user into the Bridge's server-owned `UserContext`;
- enrich the context with Slurm identity data, where available;
- evaluate the first authorization checks;
- expose the first authenticated application query path;
- keep the service layer separated from the IPC/protocol and connection code;
- prove that the dispatcher can invoke a real service without touching Slurm resource logic.

Phase 1F is deliberately narrow. It does not implement the full cache, canonical resource model, command layer, or event system.

---

## 2. Scope

Phase 1F SHALL implement:

1. service-layer integration on top of `internal/connection`;
2. server-owned `UserContext` enrichment;
3. Slurm user lookup for the connected peer;
4. `AdminLevel` resolution where the architecture permits it;
5. capability resolution for the first authenticated checks;
6. a minimal authorization policy evaluator;
7. the first authenticated application query path;
8. service-layer error responses consistent with the protocol and error model;
9. unit tests for identity enrichment, authorization decisions, and service-mapping logic;
10. basic service-to-dispatcher integration tests where practical.

The implementation SHALL remain bounded by the architecture defined in the Phase 1E connection/session contract.

---

## 3. Non-goals

Phase 1F SHALL NOT implement:

* full canonical resource models;
* resource cache;
* events or subscriptions;
* command execution;
* command adapters;
* Slurm write operations;
* role-based UI behavior;
* persistent session storage;
* session resumption;
* multi-connection session sharing;
* full authorization matrix across all future resources;
* broad resource queries beyond the first authenticated service call.

These concerns belong to later phases.

---

## 4. Architecture Boundary

The architecture remains:

```text
Unix socket
    │
    ▼
  internal/ipc
    │
    ▼
  internal/protocol
    │
    ▼
  Envelope / Validate
    │
    ▼
  internal/dispatcher
    │
    ▼
  internal/connection
    │
    ▼
  internal/service
    │
    ├── identity / user lookup
    ├── authorization / capability check
    └── first authenticated query
```

### `internal/connection`

Owns:

* connection lifecycle;
* session lifecycle;
* peer identity;
* server-owned `UserContext`;
* connection-scoped cancellation.

### `internal/service`

Owns:

* identity enrichment;
* application service orchestration;
* first authenticated query behavior;
* authorization policy evaluation;
* conversion of service results into protocol responses.

### `internal/dispatcher`

Owns:

* routing;
* handler registration;
* response selection;
* protocol-level response generation.

The dispatcher MUST NOT own Slurm user lookup or authorization logic.

The service layer MUST NOT bypass the server-owned `UserContext` established for the connection.

The service layer MUST NOT write directly to the cache or resource model.

---

## 5. Phase 1F Responsibility Split

Phase 1F defines the first version of an explicit service boundary.

### Connection layer responsibilities

The connection layer MUST provide:

* connection ID;
* session ID;
* peer identity;
* server-owned `UserContext`;
* access to the active connection context.

### Service layer responsibilities

The service layer MUST provide:

* `UserContext` enrichment with Slurm identity info;
* minimal authorization checks;
* guarded query execution;
* explicit error mapping to protocol error semantics.

### Dispatcher responsibilities

The dispatcher MUST:

* route a request to the service layer;
* pass the connection-scoped context;
* return a valid protocol envelope;
* not perform identity resolution itself.

---

## 6. Service Interfaces

The service layer SHOULD expose a small interface that is consistent with the architecture.

Recommended form:

```go
type IdentityService interface {
    EnrichUserContext(ctx context.Context, user connection.UserContext) (connection.UserContext, error)
}

type AuthorizationService interface {
    Authorize(ctx context.Context, user connection.UserContext, action string, resource string) error
}

type QueryService interface {
    Query(ctx context.Context, user connection.UserContext, request interface{}) (interface{}, error)
}
```

The exact implementation may vary, but the responsibilities SHALL remain the same.

Phase 1F SHOULD use a concrete service type such as:

```go
type ApplicationService struct {
    identity IdentityService
    auth     AuthorizationService
    query    QueryService
}
```

The implementation MAY contain additional internal helpers, but it SHALL NOT introduce a large application framework before the concrete service needs exist.

---

## 7. UserContext Enrichment

The connection layer provides the initial server-owned `UserContext`.

Phase 1F SHALL enrich that context by resolving the additional fields needed for the first authenticated service path.

Examples of fields that MAY be resolved in Phase 1F:

* Slurm username mapping;
* `AdminLevel` or equivalent server-side role metadata;
* capability set or derived permission metadata;
* default account or account association metadata when required by the service path.

The enrichment MUST be explicit and MUST NOT silently mutate the `UserContext` without a clear server-owned source.

The implementation MUST distinguish:

* identity established from Unix peer information;
* identity enriched by Slurm data;
* authorization resolved by policy evaluation.

If identity enrichment fails, the service MUST fail closed.

If the user is not authorized for the requested action or resource, the service MUST return an authorization error response, not a success response.

---

## 8. First Authenticated Query Path

Phase 1F SHALL implement the first authenticated request path.

The target behavior is:

```text
valid connection
   ↓
UserContext present
   ↓
identity enrichment
   ↓
authorization check
   ↓
service query
   ↓
protocol response
```

The service path SHOULD be intentionally narrow. The Phase 1F query MAY be:

* an identity/self query;
* a minimal authorized query returning the user's context and capabilities;
* a first resource snapshot limited to a single service/resource kind.

The exact resource or payload subject MUST be defined by the implementation contract for the chosen query.

Important rules:

* the service MUST use the server-owned `UserContext` from the connection;
* the service MUST NOT trust a client-supplied identity field;
* the service MUST NOT accept unsigned authorization decisions from the client;
* the service MUST return a valid protocol response envelope for both success and failure.

---

## 9. Authorization Policy

Phase 1F SHALL implement a minimal authorization policy evaluator for the first authenticated service.

The policy MUST evaluate:

* whether the connection has a valid `UserContext`;
* whether the user has the required capability or role for the request;
* whether the request is allowed for the current connection/session context;
* whether the operation is incompatible with the user's effective access.

### Authorization semantics

The authorization layer SHALL:

* fail closed on missing or invalid context;
* return an explicit authorization error when access is denied;
* not grant privileges simply because a user has a Linux UID;
* not infer capabilities from client-supplied data.

Phase 1F MAY implement a simple action/resource permission map, but it MUST remain intentionally small and explicit.

---

## 10. Known-but-Unimplemented Behavior

The dispatcher SHALL route some known message types to the first authenticated service path during Phase 1F.

Examples of types that may now become implemented in Phase 1F:

```text
query
command
subscribe
```

but only for the narrow service path selected by this phase.

If a message reaches a handler that is known by protocol but intentionally not implemented for the current phase, the dispatcher SHALL return an explicit `NOT_IMPLEMENTED` response exactly as defined in Phase 1D.

The service layer MUST NOT silently accept a request for a later resource or action that has not yet been implemented.

---

## 11. Error Handling

Phase 1F SHALL distinguish between:

### Protocol errors

Examples:

```text
INVALID_PROTOCOL
UNSUPPORTED_VERSION
INVALID_MESSAGE
UNKNOWN_MESSAGE_TYPE
INVALID_JSON
MESSAGE_TOO_LARGE
```

These remain in the protocol layer.

### Dispatcher errors

Examples:

```text
NOT_IMPLEMENTED
HANDLER_ERROR
UNKNOWN_MESSAGE_TYPE
```

These remain in the dispatcher / protocol boundary.

### Identity and authorization errors

Examples:

```text
USER_NOT_FOUND
IDENTITY_RESOLUTION_FAILED
AUTHORIZATION_DENIED
INSUFFICIENT_CAPABILITY
```

These belong to Phase 1F.

### Application / Slurm errors

These SHALL NOT be implemented broadly in Phase 1F.

The service layer MUST map errors to the documented error model without inventing new semantics outside the architecture.

## 12. Go Package Structure

Recommended structure:

```text
internal/
├── connection/
│   ├── connection.go
│   ├── session.go
│   ├── identity.go
│   └── connection_test.go
│
├── dispatcher/
│   ├── dispatcher.go
│   ├── handler.go
│   └── dispatcher_test.go
│
├── service/
│   ├── service.go
│   ├── identity.go
│   ├── auth.go
│   ├── query.go
│   └── service_test.go
│
├── ipc/
│   └── ...
│
└── protocol/
    └── ...
```

The `internal/service` package SHOULD depend on:

* `internal/connection`;
* `internal/protocol` for response shape and validation;
* `internal/dispatcher` only via interface boundaries when needed.

It SHOULD NOT depend on:

* Slurm resource cache;
* Slurm command execution;
* event manager;
* subscription manager;
* UI packages;
* Cockpit-specific channels.

---

## 13. Implementation Requirements

The Phase 1F implementation SHALL:

1. use a server-owned `UserContext` created in Phase 1E;
2. enrich that context with the minimum identity data needed for the first query;
3. resolve Slurm user and/or capability metadata only in the service layer;
4. reject requests missing valid connection identity;
5. reject unauthorized access with an explicit protocol error response;
6. route the request to the first authenticated service handler;
7. return a valid response envelope for success or failure;
8. preserve existing Phase 1B–1E behavior;
9. never access the canonical resource cache in Phase 1F;
10. never invoke Slurm commands as part of the initial authenticated query path;
11. never authorize on client-supplied identity data;
12. never panic on invalid external input.

Service registration SHOULD occur during service initialization.

For example:

```text
NewService()
    │
    ├── register identity enricher
    ├── register authorization evaluator
    └── register first authenticated query service
```

---

## 14. Test Requirements

### Identity enrichment

```text
[ ] connection with valid peer identity creates valid UserContext
[ ] identity enrichment adds required Slurm metadata
[ ] missing peer identity fails closed
[ ] invalid or empty identity is rejected
```

### Authorization

```text
[ ] authorized user passes the first authenticated query
[ ] unauthorized user gets authorization error
[ ] missing UserContext is denied
[ ] capability mismatch is denied
```

### Service execution

```text
[ ] authenticated query returns a valid protocol envelope
[ ] response has non-empty messageId
[ ] response payload is valid JSON
[ ] service error maps to protocol error semantics
```

### Isolation

```text
[ ] service does not require a Unix socket for unit tests
[ ] service does not access cache
[ ] service does not execute Slurm commands
[ ] service does not depend on event or subscription logic
```

The Phase 1F tests SHOULD construct service inputs directly rather than relying on a live socket unless an integration test is expressly needed.

---

## 15. Acceptance Criteria

Phase 1F is complete when:

* [ ] service package exists;
* [ ] connection-owned `UserContext` is used consistently;
* [ ] Slurm identity enrichment works for the first authenticated path;
* [ ] authorization is evaluated in the service layer;
* [ ] unauthorized requests fail explicitly;
* [ ] the first authenticated query works end-to-end through the dispatcher;
* [ ] service responses pass protocol validation;
* [ ] dispatcher and protocol behavior from earlier phases remain unchanged;
* [ ] Phase 1F unit tests pass;
* [ ] existing Phase 1B–1E tests continue to pass;
* [ ] `go test ./...` passes;
* [ ] `go vet ./...` passes;
* [ ] no Slurm command execution is introduced;
* [ ] no resource cache dependency is introduced;
* [ ] no event system is introduced;
* [ ] no session-sharing abstraction is forced into this phase.

---

## 16. Phase 2 Boundary

Phase 2 SHALL introduce the resource/cache foundation and the first real persistent bridge data path.

The expected progression is:

```text
Phase 1E
    connection and session foundation
        ↓
Phase 1F
    first authenticated application service
        ↓
Phase 2
    resource/cache foundation
        ↓
Phase 3
    event and subscription foundation
        ↓
Later phases
    commands, full authorization, full resource services
```

Phase 2 is where the project moves from identity and service scaffolding into the first stable resource model and cache boundary.

Phase 1F MUST remain intentionally narrow so that the resource/cache architecture remains clean and well-defined.

---

## 17. Implementation Decision

The implementation MUST respect the following canonical boundaries:

```text
Connection owns identity.
Service owns authorization and application behavior.
Dispatcher owns routing and protocol response formatting.
Protocol owns validation and message semantics.
```

The first service query in Phase 1F is intentionally a proving step, not a full business domain implementation.

It exists to validate:

* the server-owned identity model;
* the service-layer authorization path;
* the bridge-to-dispatcher integration;
* the separation between transport protocol and application logic.

This is the correct boundary for the next coding step.
