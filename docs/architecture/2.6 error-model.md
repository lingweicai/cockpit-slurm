# cockpit-slurm Error Model


**location:** docs/architecture/error-model.md  
**Version:** 1.0    
**Architecture:** cockpit-slurm v3.5    
**Status:** Architecture Contract   
**Scope:** IPC, Bridge, Channel, Command, Query, Resource, Authorization, Slurm Adapter, Event, and UI error handling

---

## 1. Purpose

This document defines the canonical error model for the `cockpit-slurm`
architecture.

The purpose is to provide a single error contract across all layers:

- React UI
- cockpit.channel()
- cockpit-slurm-channel
- IPC
- cockpit-slurm-bridge
- UserContext
- Query Service
- Command Service
- Authorization
- Resource Service
- Resource Adapter
- Command Adapter
- Slurm
- Cache
- Event and Subscription services

The architecture MUST NOT allow each layer to invent its own incompatible
error representation.

The canonical error model provides:

- stable error categories
- machine-readable error codes
- human-readable messages
- error details
- command correlation
- request correlation
- resource correlation
- retry guidance
- authorization information
- Slurm error information
- safe error propagation to the UI

---

# 2. Architectural Principle

The most important rule is:

```text
    Internal errors
          ↓
    Error classification
          ↓
    Canonical Error
          ↓
    IPC error response
          ↓
    React error handling
```
For example:

```text
    sacctmgr
       ↓
    exit code 1
       ↓
    Slurm adapter
       ↓
    canonical error
       ↓
    IPC error response
       ↓
    UI
```
The UI must not need to understand:

- Linux errno
- Go errors
- subprocess exit codes
- Slurm CLI output formats
- database driver errors
- Unix socket errors

Those are internal implementation details.

---

# 3. Error Contract

Every externally visible error MUST contain:

    code
    message

It SHOULD contain:

    category
    retryable
    details
    requestId/messageId
    commandId
    resource
    target

Conceptual Go representation:

```go
type Error struct {
    Code       ErrorCode
    Category   ErrorCategory
    Message    string

    Retryable  bool

    Details    map[string]any

    MessageID  string
    CommandID  string

    Resource   *ResourceReference

    Cause      *ErrorCause
}
```
The implementation may use a different internal representation, but the
external semantic contract must remain stable.

---

# 4. Error Categories

The initial v3.5 error categories are:

```
authentication-error
authorization-error
validation-error
not-found
conflict
slurm-error
timeout
internal-error
transport-error
```

These categories are explicitly part of the v3.5 architecture contract.

They provide the first-level classification of errors.

---

# 5. Error Category vs Error Code

The architecture should distinguish:

```
category
```

from:

```
code
```

For example:

```
category = authorization-error
code     = permission-denied
```

or:

```
category = slurm-error
code     = job-cancel-failed
```

The category provides broad classification.

The code provides a stable machine-readable reason.

Example:

```json
{
  "category": "authorization-error",
  "code": "permission-denied",
  "message": "User is not authorized to cancel this job"
}
```

---

# 6. Recommended Error Categories

## 6.1 authentication-error

The Bridge cannot establish or validate the identity associated with the
request.

Examples:

* no authenticated user
* invalid identity information
* failed identity resolution
* unavailable authentication context

Example:

```json
{
  "category": "authentication-error",
  "code": "identity-unavailable",
  "message": "Unable to determine the authenticated user"
}
```

Authentication errors are different from authorization errors.

---

## 6.2 authorization-error

The authenticated user is known but is not permitted to perform the requested
operation.

Examples:

* insufficient capability
* AdminLevel insufficient
* Coordinator scope does not include target
* resource operation is not allowed for the user

Example:

```json
{
  "category": "authorization-error",
  "code": "permission-denied",
  "message": "User is not authorized to cancel this job"
}
```

The distinction is:

```
authentication-error
    = Who are you?

authorization-error
    = You are known, but are you allowed to do this?
```

---

## 6.3 validation-error

The request is structurally or semantically invalid.

Examples:

* missing required field
* invalid operation
* invalid resource kind
* invalid parameter
* invalid parameter combination
* malformed resource reference

Example:

```json
{
  "category": "validation-error",
  "code": "invalid-parameter",
  "message": "Account name is required"
}
```

Validation errors normally are not retryable unless the request is changed.

---

## 6.4 not-found

The requested resource does not exist.

Examples:

* Job/12345 does not exist
* Account/research does not exist
* User/alice does not exist

Example:

```json
{
  "category": "not-found",
  "code": "resource-not-found",
  "message": "Account 'research' was not found"
}
```

A resource may disappear between query and command execution.

Therefore the Bridge must be prepared to return `not-found` even when the
frontend previously displayed the resource.

---

## 6.5 conflict

The requested operation conflicts with the current resource state.

Examples:

* resource version mismatch
* duplicate resource
* concurrent modification
* operation incompatible with current state
* command already completed with a different request

Example:

```json
{
  "category": "conflict",
  "code": "resource-version-conflict",
  "message": "The account has changed since it was loaded"
}
```

Conflict errors are generally not automatically retryable.

The client should normally refresh the resource first.

---

## 6.6 slurm-error

Slurm accepted the request at the application boundary but Slurm itself
reported a failure.

Examples:

* `scontrol` failure
* `sacctmgr` failure
* `scancel` failure
* `suspend` failure
* `resume` failure
* Slurm REST API error
* Slurm controller unavailable

Example:

```json
{
  "category": "slurm-error",
  "code": "job-cancel-failed",
  "message": "Slurm rejected the job cancellation request"
}
```

Slurm-specific details may be included in `details`.

---

## 6.7 timeout

The requested operation did not complete within the configured timeout.

Example:

```json
{
  "category": "timeout",
  "code": "command-timeout",
  "message": "The command did not complete within the configured timeout"
}
```

A timeout MUST NOT automatically imply that the operation did not happen.

For example:

```
command
   ↓
Slurm
   ↓
operation may have succeeded
   ↓
Bridge timeout
   ↓
timeout error
```

The Bridge should refresh the affected resource where possible.

---

## 6.8 internal-error

An unexpected Bridge or application failure occurred.

Examples:

* programming error
* unexpected state
* cache failure
* event bus failure
* serialization failure
* unavailable internal service

Example:

```json
{
  "category": "internal-error",
  "code": "internal-failure",
  "message": "An unexpected internal error occurred"
}
```

Internal implementation details MUST NOT normally be exposed to the UI.

---

## 6.9 transport-error

Communication between components failed.

Examples:

* Unix socket unavailable
* broken IPC connection
* malformed IPC frame
* Channel disconnected
* Bridge unavailable
* unexpected connection closure

Example:

```json
{
  "category": "transport-error",
  "code": "bridge-unavailable",
  "message": "Unable to connect to the Slurm bridge"
}
```

Transport errors are especially relevant to the Channel.

---

# 7. Error Code Naming

Error codes should be:

* lowercase
* stable
* machine-readable
* semantic
* independent of implementation details

Recommended examples:

```
identity-unavailable
permission-denied
capability-required
invalid-request
invalid-parameter
invalid-operation
invalid-resource
resource-not-found
resource-already-exists
resource-version-conflict
command-not-found
command-timeout
command-failed
job-cancel-failed
job-suspend-failed
job-resume-failed
slurm-unavailable
slurm-command-failed
bridge-unavailable
ipc-invalid-message
ipc-protocol-error
internal-failure
```

Avoid codes such as:

```
errno-13
exit-code-1
sacctmgr-error-1045
```

because these expose implementation details and make the public contract
unstable.

# 8. Error Envelope

Errors are transported through the IPC protocol.

A conceptual error response is:

```json
{
  "protocol": "cockpit-slurm",
  "version": "1.0",
  "messageId": "01KERROR001",
  "type": "error",
  "payload": {
    "error": {
      "category": "authorization-error",
      "code": "permission-denied",
      "message": "User is not authorized to cancel this job",
      "retryable": false
    }
  }
}
```

The exact IPC envelope is defined by:

```
ipc-protocol.md
```

This document defines the semantics of the `error` payload.

---

# 9. Error Payload

Recommended structure:

```json
{
  "error": {
    "category": "authorization-error",
    "code": "permission-denied",
    "message": "User is not authorized to cancel this job",
    "retryable": false,
    "details": {}
  }
}
```

Optional correlation fields may be included:

```json
{
  "error": {
    "category": "authorization-error",
    "code": "permission-denied",
    "message": "User is not authorized to cancel this job",
    "retryable": false,
    "messageId": "MSG001",
    "commandId": "CMD001",
    "resource": {
      "kind": "Job",
      "name": "12345"
    }
  }
}
```

---

# 10. Error Correlation

Errors must be traceable to the operation that produced them.

The architecture has several identifiers:

```
connectionId
messageId
commandId
subscriptionId
eventId
```

An error response should contain the identifier that is relevant to its
operation.

For a command:

```
messageId
commandId
```

For a query:

```
messageId
```

For a subscription:

```
messageId
subscriptionId
```

Example:

```json
{
  "error": {
    "category": "slurm-error",
    "code": "job-cancel-failed",
    "message": "Slurm rejected the cancellation request",
    "commandId": "CMD001",
    "messageId": "MSG001"
  }
}
```

---

# 11. Command Errors

The Command Model defines command lifecycle and command-specific behavior.

The Error Model defines how command failures are represented.

Relationship:

```
Command
   ↓
Command Service
   ↓
success ─────────────→ command-response
   │
   └── failure ──────→ error
```

A failed command should normally be represented by a command response
containing an error.

Example:

```json
{
  "protocol": "cockpit-slurm",
  "version": "1.0",
  "messageId": "MSG002",
  "type": "command-response",
  "payload": {
    "commandId": "CMD001",
    "status": "failed",
    "error": {
      "category": "slurm-error",
      "code": "job-cancel-failed",
      "message": "Slurm rejected the job cancellation request",
      "retryable": false
    }
  }
}
```

The exact command-response structure remains defined by
`command-model.md` and `ipc-protocol.md`.

---

# 12. Query Errors

Queries can also fail.

Example:

```json
{
  "protocol": "cockpit-slurm",
  "version": "1.0",
  "messageId": "MSG010",
  "type": "error",
  "payload": {
    "error": {
      "category": "not-found",
      "code": "resource-not-found",
      "message": "Node 'node001' was not found",
      "retryable": false
    }
  }
}
```

A query failure does not create a resource event.

---

# 13. Subscription Errors

Subscription failures should be distinguishable from resource events.

Examples:

```
invalid subscription
unauthorized subscription
invalid resource
unsupported filter
```

Example:

```json
{
  "error": {
    "category": "validation-error",
    "code": "invalid-subscription",
    "message": "The requested resource subscription is invalid",
    "retryable": false
  }
}
```

If an existing subscription is terminated because of a transport failure,
the Channel should report the transport condition separately.

---

# 14. Error vs Event

An error is not an event.

Do not use:

```text
event = command-failed
```

to represent command failure.

Instead:

```text
command-response
    status = failed
    error = ...
```

Resource events represent changes to resource state.

For example:

```
Job/12345
    RUNNING
      ↓
    CANCELLED
```

produces a resource event.

A failed command:

```
cancel Job/12345
      ↓
Slurm rejects request
```

produces a command error.

These are different concepts.

---

# 15. Error vs Audit

An error is also not an audit record.

An error answers:

```
What happened to this request?
```

An audit record answers:

```
Who requested what, and what was the result?
```

For example:

```
Error:
    permission-denied

Audit:
    user=alice
    operation=cancel
    resource=Job/12345
    result=denied
```

The same command may therefore produce:

```
command-response
    ↓
error
```

and:

```
audit record
```

---

# 16. Retryable

Each externally visible error should indicate whether retrying may be
appropriate.

Example:

```json
{
  "category": "transport-error",
  "code": "bridge-unavailable",
  "message": "Unable to connect to the Slurm bridge",
  "retryable": true
}
```

versus:

```json
{
  "category": "authorization-error",
  "code": "permission-denied",
  "message": "Permission denied",
  "retryable": false
}
```

`retryable` is guidance, not a guarantee.

---

# 17. Recommended Retry Semantics

| Category             | Usually Retryable |
| -------------------- | ----------------- |
| authentication-error | No                |
| authorization-error  | No                |
| validation-error     | No                |
| not-found            | No                |
| conflict             | No                |
| slurm-error          | Depends           |
| timeout              | Depends           |
| internal-error       | Usually no        |
| transport-error      | Usually yes       |

The actual value should be determined by the specific error code.

For example:

```
slurm-unavailable
    retryable = true
```

while:

```
invalid-job-state
    retryable = false
```

---

# 18. Idempotency and Retry

Command retry must follow the Command Model.

A retry of the same logical command MUST reuse:

```
commandId
```

Example:

```
CMD001
   ↓
timeout
   ↓
retry CMD001
```

The Bridge must first check the command record.

It must not blindly execute:

```
CMD002
```

because that could execute the operation twice.

This is especially important for:

```
cancel
delete
create
update
```

---

# 19. Timeout Semantics

A timeout is a special case.

Example:

```
CMD001
   ↓
Slurm
   ↓
timeout
   ↓
Bridge returns timeout
```

The Bridge does not necessarily know whether Slurm completed the operation.

Therefore:

```
timeout != operation failed
```

The Bridge should attempt reconciliation:

```
timeout
   ↓
refresh resource
   ↓
observe current state
   ↓
cache
   ↓
event if changed
```

The final resource state is therefore determined by the Resource Model and
Cache rather than inferred solely from the timeout.

---

# 20. Conflict Errors

Conflict is particularly important for the canonical resource model.

Example:

```
UI loads Account/research
    resourceVersion = 42

another administrator modifies account

    resourceVersion = 43

UI sends:

    expectedResourceVersion = 42
```

The Bridge returns:

```json
{
  "error": {
    "category": "conflict",
    "code": "resource-version-conflict",
    "message": "The account has changed since it was loaded",
    "retryable": false,
    "details": {
      "expectedResourceVersion": "42",
      "currentResourceVersion": "43"
    }
  }
}
```

The UI should then:

```
refresh resource
   ↓
display current state
   ↓
allow user to retry intentionally
```

---

# 21. Not Found vs Conflict

These must remain distinct.

### Not Found

The resource does not exist.

```
Account/research
      ↓
not found
```

### Conflict

The resource exists, but its current state differs from the state expected by
the command.

```
Account/research
    expected version = 42
    current version  = 43
          ↓
      conflict
```

---

# 22. Authorization Details

Authorization errors may optionally contain safe details.

Example:

```json
{
  "error": {
    "category": "authorization-error",
    "code": "capability-required",
    "message": "The operation requires jobs.cancel",
    "retryable": false,
    "details": {
      "requiredCapability": "jobs.cancel"
    }
  }
}
```

However, the Bridge should avoid exposing unnecessary authorization
internals.

For example, do not expose:

```
complete ACL implementation
internal policy rules
sensitive account mappings
security configuration
```

---

# 23. Coordinator Scope Errors

Coordinator authorization is resource-scoped.

Example:

```
User:
    alice

Coordinator:
    research

Command:
    update Account/finance
```

The result may be:

```json
{
  "error": {
    "category": "authorization-error",
    "code": "resource-scope-denied",
    "message": "User is not authorized to modify this account",
    "retryable": false
  }
}
```

The UI does not need to know the internal Coordinator implementation.

---

# 24. Slurm Errors

Slurm-specific errors should be normalized by the Slurm Adapter.

For example, the adapter may receive:

```
exit status = 1
```

and output:

```
Access/permission denied
```

The Adapter should translate this into:

```text
category = slurm-error
code     = command-failed
```

rather than exposing raw subprocess output as the canonical error.

---

# 25. Preserving Slurm Details

Useful Slurm information may be preserved under `details`.

Example:

```json
{
  "error": {
    "category": "slurm-error",
    "code": "job-cancel-failed",
    "message": "Unable to cancel job",
    "retryable": false,
    "details": {
      "slurmErrorCode": 123,
      "slurmMessage": "Job already completed"
    }
  }
}
```

The public message should remain stable.

Slurm-specific detail fields are implementation-dependent and should not be
required by the UI.

---

# 26. Security Rule for Error Messages

Errors MUST NOT expose sensitive implementation information.

Do not expose:

```
passwords
authentication tokens
Unix credentials
environment variables
SQL statements
filesystem internals
complete command-line arguments containing secrets
stack traces
internal network configuration
```

For example, do not return:

```text
dial unix /run/cockpit-slurm/bridge.sock: permission denied
at internal/ipc/server.go:183
```

to the normal UI.

Instead:

```json
{
  "category": "transport-error",
  "code": "bridge-unavailable",
  "message": "Unable to connect to the Slurm bridge"
}
```

Detailed diagnostics belong in server-side logs.

---

# 27. Internal Error vs Public Error

The Bridge may internally have:

```go
fmt.Errorf(
    "failed to refresh node cache: %w",
    err,
)
```

This is not the public API error.

It should be classified as:

```text
category = internal-error
code     = resource-refresh-failed
```

The original Go error may be logged with correlation information.

---

# 28. Error Cause

Internal errors may preserve a cause chain.

Conceptually:

```go
type ErrorCause struct {
    Type    string
    Message string
}
```

The cause should normally NOT be sent to the browser.

It is primarily for:

```
logging
debugging
diagnostics
tracing
```

Example internal chain:

```
command failed
   ↓
adapter failed
   ↓
subprocess failed
   ↓
exit status 1
```

Public result:

```
slurm-error
command-failed
```

---

# 29. Logging

Every significant error should be logged with correlation information.

Recommended fields:

```
timestamp
level
connectionId
messageId
commandId
username
resource
operation
error.category
error.code
```

Example:

```text
ERROR
commandId=CMD001
user=alice
operation=cancel
resource=Job/12345
category=slurm-error
code=job-cancel-failed
```

Do not log sensitive command parameters without explicit justification.

---

# 30. Error Severity

Error category and log severity are different concepts.

For example:

```
authorization-error
    → INFO/WARN

validation-error
    → INFO/WARN

slurm-error
    → WARN

transport-error
    → WARN/ERROR

internal-error
    → ERROR
```

An authorization failure should not necessarily generate an ERROR-level
application log.

---

# 31. Transport Error Handling

The Channel has a special responsibility.

The Channel should translate failures between:

```
Cockpit protocol
   ↕
Unix socket
```

into transport-level behavior.

The Channel MUST NOT reinterpret Slurm business errors.

For example:

```
Bridge returns:
    authorization-error
```

The Channel forwards it unchanged.

But:

```
Unix socket cannot connect
```

is a:

```
transport-error
```

---

# 32. Channel Error Boundary

The architecture is:

```
React
   ↓
cockpit.channel()
   ↓
cockpit-slurm-channel
   ↓
Unix socket
   ↓
cockpit-slurm-bridge
```

The Channel should therefore perform only transport-related error handling:

```
connection failure
framing failure
process failure
socket closure
```

It should not convert:

```
authorization-error
```

into:

```
transport-error
```

---

# 33. Bridge Error Boundary

The Bridge converts internal failures into canonical errors.

Examples:

```
invalid JSON
    → validation-error

unknown command
    → validation-error

permission denied
    → authorization-error

missing resource
    → not-found

version mismatch
    → conflict

Slurm failure
    → slurm-error

execution timeout
    → timeout

unexpected application failure
    → internal-error
```

---

# 34. UI Error Boundary

React should consume the canonical error.

Example:

```typescript
interface SlurmError {
    category: string;
    code: string;
    message: string;
    retryable?: boolean;
    details?: Record<string, unknown>;
}
```

The UI can then implement common behavior.

Example:

```text
authorization-error
    → permission notification

validation-error
    → form validation

not-found
    → resource no longer exists

conflict
    → refresh resource

timeout
    → show uncertain-operation warning

transport-error
    → reconnect

slurm-error
    → display Slurm operation failure

internal-error
    → generic error + diagnostic ID
```

---

# 35. UI Must Not Parse Slurm Messages

Do not implement:

```typescript
if (error.message.includes("Access/permission denied")) {
    ...
}
```

This is fragile.

Instead:

```typescript
if (error.category === "authorization-error") {
    ...
}
```

or:

```typescript
if (error.code === "permission-denied") {
    ...
}
```

The code/category is the machine contract.

The message is for human consumption.

---

# 36. User-Facing Messages

Messages should be understandable and safe.

Bad:

```text
exec.Command("scancel", "12345"): exit status 1
```

Good:

```text
Unable to cancel job 12345.
```

Better when useful:

```text
Job 12345 could not be cancelled because Slurm rejected the request.
```

---

# 37. Localization

The canonical error `message` may initially be generated by the Bridge.

However, for the React application, a future implementation may prefer:

```
code
   ↓
localized UI message
```

For example:

```text
code = permission-denied
```

React maps this to a localized message.

Therefore the stable machine contract is:

```
category
code
```

while:

```
message
```

is primarily a human-readable fallback.

---

```json
{

  "retryable": false

```

Optional:

```json
{
  "category": "authorization-error",

  "message": "User is not authorized to perform this operation",

  "details": {},
  "messageId": "MSG001",
  "commandId": "CMD001",
  "resource": {
    "kind": "Job",

```

# 40. Error Registry

The implementation should centralize error definitions.

Conceptual Go code:

```go
type ErrorCategory string
```

```text
   ↓
```

Similarly:

```text
   ↓

   ↓
```

```text
   ↓

   ↓
```

# 44. Error Propagation Rules

Errors should normally move upward without losing their semantic category.

Example:

```text
Slurm Adapter
      ↓
slurm-error
      ↓
Command Service
      ↓
command-response
      ↓
IPC
      ↓
React
```

The Command Service may enrich the error with:

```
commandId
resource
operation
```

but should not arbitrarily change:

```
slurm-error
```

into:

```
internal-error
```

unless the failure truly prevents classification.

# 45. Error Translation Rules

Each layer has a defined responsibility.

| Layer            | Responsibility                       |
| ---------------- | ------------------------------------ |
| Slurm Adapter    | classify Slurm failures              |
| Command Service  | add command context                  |
| Authorization    | classify permission failures         |
| Resource Service | classify resource/query failures     |
| Cache            | classify cache failures              |
| Event Service    | classify event failures              |
| IPC              | classify protocol/transport failures |
| Channel          | classify transport failures          |
| React            | present errors to user               |

# 46. Do Not Leak Implementation Layers

The UI should not need to know whether:

```

```


or:

```

```

or:

```
another future Slurm API.
```

All three should produce the same canonical error model.

For example:

```text
category = slurm-error
code     = account-operation-failed
```

# 47. Versioning

The error model is part of the IPC contract.

The protocol version identifies the version of the error schema.

Example:

```json
{

  "version": "1.0"
```

Backward-compatible additions may include:

```

new error codes
```

Breaking changes require a protocol/schema version change.

# 48. Unknown Error Codes

The UI must gracefully handle unknown error codes.

Example:

```text
category = slurm-error
code     = new-future-error
```

The UI should fall back to:

```
category-specific behavior
```

and:

```
message
```

rather than failing to render the error.

# 49. Error Recovery

Error recovery should be category-aware.

Example:

```text
authentication-error
    reconnect/authenticate

authorization-error
    disable operation

validation-error
    correct request

not-found
    refresh/remove stale resource

conflict
    refresh resource

slurm-error
    inspect Slurm state

timeout
    reconcile resource

internal-error
    report diagnostic ID

transport-error
    reconnect
```

---

# 50. Error Recovery and Resource State

The UI should not infer resource state from an error alone.

For example:

```text
cancel Job/12345
       ↓
timeout
```

The UI should not display:

```text
Job cancelled
```

nor necessarily:

```text
Job cancellation failed
```

until the actual resource state is known.

Instead:

```text
Command timed out.
Checking current job state...
```

Then:

```text
Resource refresh
       ↓
Job state
```

determines the actual state.

---

# 51. Error and Cache Consistency

An error must never cause the cache to be updated optimistically.

Incorrect:

```text
Command failed
    ↓
Cache marks resource FAILED
```

Correct:

```text
Command failed
    ↓
No command-induced cache change
```

If resource state changes independently, the normal resource synchronization
pipeline updates the cache.

---

# 52. Error and Event Consistency

A command error does not automatically produce a resource event.

Example:

```text
cancel Job/12345
       ↓
authorization-error
```

No Job Modified event should be generated by that failed command.

However, an independent Slurm state change may still generate an event.

---

# 53. Error and Command Lifecycle

Command state and error are related.

For example:

```text
accepted
   ↓
running
   ↓
failed
```

with:

```text
error.category = slurm-error
```

Or:

```text
accepted
   ↓
rejected
```

with:

```text
error.category = authorization-error
```

Recommended mapping:

| Command state | Error           |
| ------------- | --------------- |
| accepted      | none            |
| running       | none            |
| completed     | none            |
| rejected      | usually present |
| failed        | usually present |
| timeout       | present         |
| cancelled     | optional        |

# 60. Error Handling in React

A common React helper may be introduced:

```typescript
function handleSlurmError(error: SlurmError) {
    switch (error.category) {
        case "authorization-error":
            // permission notification
            break;

        case "validation-error":
            // form validation
            break;

        case "not-found":
            // refresh resource
            break;

        case "conflict":
            // reload current resource
            break;

        case "timeout":
            // reconcile state
            break;

        case "transport-error":
            // reconnect
            break;

        default:
            // generic error
            break;
    }
}
```

Individual components should not implement their own incompatible error
classification.

# 64. Error Handling for Subscriptions

```text

authorization-error
transport-error
internal-error
```

A temporary transport failure should not necessarily destroy local resource
state.

The UI may retain:

```text

```

```text

```

until the subscription is re-established.

# 65. Reconnection

For:

```text
transport-error
```

the Channel/UI may reconnect.

After reconnection, the subscription should normally perform:

```text
subscribe
   ↓
snapshot
   ↓
events
```

rather than assuming that events missed during the disconnected period can
be reconstructed locally.

The Event Model defines the exact recovery mechanism.

# 68. Error Contract Invariants

The following rules are architectural invariants.

## Invariant 1

Every externally visible error has a stable category.

## Invariant 2

Every externally visible error has a stable machine-readable code.

## Invariant 3

The human-readable message is not the machine contract.

## Invariant 4

The Channel does not reinterpret Bridge business errors.

## Invariant 5

The Bridge normalizes implementation-specific errors.

## Invariant 6

The UI does not parse Slurm CLI output.

## Invariant 7

Internal stack traces are never exposed through normal IPC errors.

## Invariant 8

A command error does not automatically become a resource event.

## Invariant 9

A timeout does not imply that the Slurm operation failed.

## Invariant 10

Errors do not cause optimistic cache updates.

## Invariant 11

Retries of state-changing commands use the same `commandId`.

## Invariant 12

Authorization is always enforced by the Bridge.

# 76. Initial Go Error Type

A practical initial implementation is:

```go
type Error struct {
    Category  ErrorCategory `json:"category"`
    Code      ErrorCode     `json:"code"`
    Message   string        `json:"message"`
    Retryable bool          `json:"retryable,omitempty"`

    Details map[string]any `json:"details,omitempty"`

    MessageID string `json:"messageId,omitempty"`
    CommandID string `json:"commandId,omitempty"`

    Resource *ResourceReference `json:"resource,omitempty"`

    Cause error `json:"-"`
}
```

The `Cause` field must not be serialized.

---

# 77. Go Error Interface

The canonical error should implement Go's `error` interface:

```go
func (e *Error) Error() string {
    return e.Message
}
```

It should also support:

```go
func (e *Error) Unwrap() error {
    return e.Cause
}
```

This allows normal Go error handling internally while preserving the
canonical public representation.

# 82. Final Architectural Rule

The fundamental rule is:

```
Every layer may have its own internal error mechanism,
but every layer crossing an architecture boundary must use
the canonical cockpit-slurm Error Model.
```

Therefore:

```

   ↓
Canonical Error
   ↓
IPC Error
   ↓
React SlurmError
```

```
   ↓

   ↓
```

# 83. Summary

The six v3.5 architecture contracts now have clear responsibilities:

    ipc-protocol.md
        HOW messages travel

    user-context.md
        WHO is making the request

    command-model.md
        WHAT operation is requested

    resource-model.md
        WHAT resource is involved

    event-model.md
        WHAT resource state changed

    error-model.md
        WHAT went wrong and how it is represented

Together they form the foundation of the Bridge-centered architecture:

```text
                         ┌──────────────────┐
                         │   UserContext    │
                         │      WHO         │
                         └────────┬─────────┘
                                  │
                                  ▼
┌───────────────┐          ┌───────────────┐
│ IPC Protocol  │─────────▶│ Command Model │
│ HOW           │          │ WHAT          │
└───────────────┘          └───────┬───────┘
                                   │
                                   ▼
                           ┌───────────────┐
                           │ Resource Model│
                           │ TARGET        │
                           └───────┬───────┘
                                   │
                                   ▼
                                Slurm
                                   │
                                   ▼
                           ┌───────────────┐
                           │ Event Model   │
                           │ WHAT CHANGED  │
                           └───────────────┘

                    ┌───────────────────────┐
                    │      Error Model      │
                    │       WHAT FAILED     │
                    │                       │
                    │  cross-cutting        │
                    │  all architecture     │
                    │  boundaries           │
                    └───────────────────────┘
```

This is consistent with the v3.5 implementation plan, which calls for these six contracts to be frozen in Phase 0 before substantial coding, followed by the Bridge IPC foundation, Channel integration, and the first Node vertical slice. ([GitHub][1])

**One refinement I recommend:** keep `error-model.md` relatively stable and deliberately small after this. In particular, don't turn it into a catalog of every possible Slurm error. The **category + stable code + safe message + retryable + correlation information** should be the durable contract; the growing list of Slurm-specific failures belongs in the adapter's error-code registry. This will prevent the architecture contract from becoming tightly coupled to individual Slurm versions.
