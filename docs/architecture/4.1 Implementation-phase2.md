# cockpit-slurm Implementation Phase 2

# 1. Purpose

Phase 2 implements the Version 3.6 frontend/backend transport integration.

The purpose of this phase is to establish and verify the complete transport path:

```text
React
  │
  │ cockpit.channel()
  ▼
Cockpit transport
  │
  │ Unix socket / byte stream
  ▼
cockpit-slurm
  │
  ├── IPC Server
  └── Protocol Dispatcher
```

The phase must prove that the existing `cockpit-slurm` backend can communicate directly with the React frontend through `cockpit.channel()`.

Phase 2 does **not** implement a real Slurm resource or production UI.

The first successful application-level exchange should remain:

```text
React
  │
  │ ping
  ▼
cockpit.channel()
  │
  ▼
Unix socket
  │
  ▼
cockpit-slurm
  │
  ▼
Dispatcher
  │
  │ pong
  ▼
React
```

This follows the Version 3.6 implementation plan, which defines Phase 2 as the first frontend/backend integration milestone and explicitly removes `cockpit-slurm-channel`.

The authoritative architectural references are:

* `docs/architecture/0.1 development-cockpit-slurm-_v3.6.md`
* `docs/architecture/1.0 implementation-plan-v3.6.md`

This document defines the incremental implementation sequence for Phase 2.

---

# 2. Phase 2 implementation principle

Phase 2 should itself be implemented incrementally.

Do not attempt to implement the complete frontend/backend integration in one task.

Use the following sequence:

```text
Phase 2A
  Verify existing backend transport boundary
        ↓
Phase 2B
  Create frontend IPC transport layer
        ↓
Phase 2C
  Implement application frame encoder/decoder
        ↓
Phase 2D
  Establish cockpit.channel() connection
        ↓
Phase 2E
  Implement frontend IPC client
        ↓
Phase 2F
  Implement ping/pong end-to-end path
        ↓
Phase 2G
  Test stream fragmentation and aggregation
        ↓
Phase 2H
  Test connection lifecycle and concurrency
        ↓
Phase 2I
  End-to-end integration test page
        ↓
Phase 2 complete
```

The key principle is:

> Each Phase 2 step must establish one transport boundary before the next boundary is implemented.

Do not combine:

* Cockpit channel creation;
* application framing;
* request correlation;
* React state;
* Slurm resources;
* resource cache;
* subscriptions;
* commands;

into one implementation task.

# 4. Existing architecture to preserve

Version 3.6 has already established the following architectural decisions.

## 4.1 Application name

The application is:

```text
cockpit-slurm
```

The backend is a persistent systemd service.

`cockpit-slurm-channel` is removed from the Version 3.6 architecture.

The term `Cockpit bridge` refers to Cockpit's own infrastructure and must not be used as the name of the `cockpit-slurm` application.

---

## 4.2 Transport architecture

The required transport path is:

```text
React
  │
  │ cockpit.channel()
  ▼
Cockpit transport
  │
  │ Unix socket
  ▼
cockpit-slurm
  │
  ▼
IPC Server
  │
  ▼
Dispatcher
```

---

## 4.3 Application protocol

The `cockpit-slurm` application protocol remains independent of Cockpit.

The application protocol uses:

```text
4-byte unsigned big-endian payload length
+
UTF-8 JSON payload
```

Conceptually:

```text
+----------------------+----------------------+
| Payload length       | JSON payload         |
| uint32, big-endian   | UTF-8 bytes          |
+----------------------+----------------------+
        4 bytes                N bytes
```

The framing contract belongs to `cockpit-slurm`, not to Cockpit.

The frontend must therefore reconstruct complete application frames from arbitrary Cockpit stream chunks.

# 6. Phase 2B — Create the frontend IPC transport layer

## 6.1 Objective

Create a small frontend transport package that isolates Cockpit transport details from React components.

A proposed structure is:

```text
src/
└── ipc/
    ├── channel.ts
    ├── framing.ts
    ├── client.ts
    └── types.ts
```

This structure follows the Version 3.6 implementation plan.

---

## 6.2 `channel.ts`

`channel.ts` owns:

* `cockpit.channel()` creation;
* channel lifecycle;
* sending bytes;
* receiving bytes;
* close handling;
* error handling.

It must not own:

* Slurm resources;
* React components;
* authorization;
* application resource state;
* request-specific business logic.

Conceptually:

```text
React / IPC client
        │
        ▼
    channel.ts
        │
        ▼
cockpit.channel()
```

---

## 6.3 `framing.ts`

`framing.ts` owns:

* application frame encoding;
* application frame decoding;
* incomplete-frame buffering;
* multiple-frame extraction;
* frame-size validation.

It must not depend on:

```text
channel.onmessage
```

containing exactly one application message.

---

## 6.4 `client.ts`

`client.ts` owns:

* request/response correlation;
* message IDs;
* request lifecycle;
* application-level errors.

React components must not implement application framing directly.

---

## 6.5 `types.ts`

`types.ts` should contain only frontend representations required to communicate with the application protocol.

Do not duplicate backend business models unnecessarily.

---

## 6.6 Acceptance criteria

```text
[ ] src/ipc/ exists
[ ] channel.ts exists
[ ] framing.ts exists
[ ] client.ts exists
[ ] types.ts exists
[ ] React components do not parse application frames
[ ] React components do not directly manage stream buffering
[ ] no Slurm logic exists in src/ipc/
[ ] TypeScript compiles
```

# 7. Phase 2C — Implement application frame encoding and decoding

## 7.1 Objective

Implement the Version 3.6 application framing contract in TypeScript.

The frontend must use exactly the same framing semantics as the backend.

---

## 7.2 Encoder

The encoder must produce:

```text
4-byte big-endian payload length
+
UTF-8 JSON payload
```

For example:

```text
Application message
        ↓
JSON.stringify()
        ↓
UTF-8 bytes
        ↓
calculate byte length
        ↓
4-byte big-endian length
        ↓
concatenate
```

The length must represent the UTF-8 payload byte count, not the JavaScript string length.

---

## 7.3 Decoder

The decoder must maintain a persistent receive buffer.

Conceptually:

```text
incoming chunk
      ↓
append to buffer
      ↓
while complete frame exists
      ↓
extract frame
      ↓
validate frame
      ↓
decode JSON
      ↓
emit application message
      ↓
retain incomplete bytes
```

The decoder must support:

### Case A — complete frame

```text
[frame]
```

### Case B — frame split across chunks

```text
chunk 1: [length + partial payload]
chunk 2: [remaining payload]
```

### Case C — multiple frames in one chunk

```text
chunk:
[frame 1][frame 2][frame 3]
```

### Case D — arbitrary fragmentation

```text
chunk 1
chunk 2
chunk 3
chunk 4
...
```

---

## 7.4 Frame validation

The decoder must reject:

* invalid length;
* zero/invalid frame length where prohibited by the protocol;
* frame larger than the configured maximum;
* invalid UTF-8;
* invalid JSON;
* invalid application envelope.

The frontend must not silently discard malformed application frames.

---

## 7.5 Unit tests

Tests must explicitly cover:

```text
[ ] encode one frame
[ ] decode one complete frame
[ ] decode a frame split across two chunks
[ ] decode a frame split across multiple chunks
[ ] decode multiple frames in one chunk
[ ] decode multiple frames across arbitrary chunks
[ ] preserve remaining incomplete bytes
[ ] reject oversized frame
[ ] reject malformed JSON
[ ] reject invalid application envelope
[ ] preserve messageId
```

---

## 7.6 Acceptance criteria

The frontend framing implementation is complete when:

```text
[ ] framing.ts implements the v3.6 length-prefix contract
[ ] UTF-8 byte length is used
[ ] big-endian length is used
[ ] incomplete frames are buffered
[ ] multiple frames are extracted
[ ] frame-size limits are enforced
[ ] malformed frames are rejected
[ ] unit tests cover fragmentation
[ ] unit tests cover aggregation
[ ] all frontend tests pass
```

# 8. Phase 2D — Establish the Cockpit channel

## 8.1 Objective

Create the first real `cockpit.channel()` connection from the frontend.

The intended configuration is conceptually:

```typescript
const channel = cockpit.channel({
    payload: "stream",
    unix: "/run/cockpit-slurm/cockpit-slurm.sock",
    binary: true,
});
```

The exact supported API must be verified against the Cockpit version supported by the project before implementation is frozen.

The Version 3.6 architecture specifically requires `stream` to be treated as an arbitrary byte stream.

---

## 8.2 Important rule

Do not assume:

```text
one onmessage event
=
one application frame
```

Instead:

```text
Cockpit stream
       ↓
arbitrary byte chunks
       ↓
application framing decoder
       ↓
complete application frames
```

---

## 8.3 Connection lifecycle

The channel layer must handle:

```text
open
message
error
close
```

The exact Cockpit API behavior should be verified against the supported Cockpit release.

---

## 8.4 Acceptance criteria

```text
[ ] cockpit.channel() is created successfully

[ ] binary transport is used when supported
[ ] configured Unix socket is used
[ ] channel open is detectable
[ ] channel error is detectable

```

# 9. Phase 2E — Implement the frontend IPC client

## 9.1 Objective

Create a small application-level client above the transport and framing layers.

Conceptually:

```text
React
  ↓
IPC client
  ↓
framing
  ↓
channel
  ↓
Cockpit
```

The client should expose application-level operations without exposing Cockpit stream details to React components.

---

## 9.2 Request lifecycle

The client should support:

```text
create messageId
      ↓
encode request
      ↓
send frame
      ↓
wait for response
      ↓
match response.messageId
      ↓
resolve request
```

For example:

```text
request(message)
        ↓
pending[messageId]
        ↓
send()
        ↓
receive()
        ↓
messageId lookup
        ↓
resolve()
```

---

## 9.3 Message ID preservation

The frontend must never replace the application message ID returned by the backend.

For a request:

```json
{
  "messageId": "abc123"
}
```

the corresponding response must contain:

```json
{
  "messageId": "abc123"
}
```

The frontend client uses this value for correlation.

---

## 9.4 Connection errors

The client must distinguish:

```text
transport error
connection closed
application error
request timeout
```

Only implement request timeout behavior here if it is already defined by the existing contract.

Do not invent a new error model.

---

## 9.5 Acceptance criteria

```text
[ ] client can send an application message
[ ] client generates/preserves message IDs according to contract
[ ] client correlates responses
[ ] unrelated responses do not resolve another request
[ ] application errors are surfaced
[ ] connection errors are surfaced
[ ] channel close rejects pending requests appropriately
[ ] React does not need to understand stream framing
```

# 11. Phase 2G — Verify arbitrary stream framing

## 11.1 Objective

Prove that application framing is independent of Cockpit stream message boundaries.

This is one of the most important Phase 2 tests.

The implementation must not work only because the development environment happens to deliver one frame per event.

---

## 11.2 Fragmentation test

Simulate:

```text
Frame:
[length][JSON payload]

Delivery:
[length]
[part of JSON]
[remaining JSON]
```

The decoder must produce exactly one application message.

---

## 11.3 Aggregation test

Simulate:

```text
[frame1][frame2][frame3]
```

delivered in one chunk.

The decoder must produce:

```text
message1
message2
message3
```

---

## 11.4 Mixed fragmentation test

Simulate:

```text
chunk 1:
[frame1][partial frame2]

chunk 2:
[remaining frame2][frame3][partial frame4]

chunk 3:
[remaining frame4]
```

The decoder must produce:

```text
frame1
frame2
frame3
frame4
```

in the correct order.

---

## 11.5 Acceptance criteria

```text
[ ] partial frame works
[ ] multiple frames in one chunk works
[ ] mixed partial/multiple frames works
[ ] frame order is preserved
[ ] no bytes are lost
[ ] no bytes are duplicated
[ ] malformed trailing data is detected
[ ] maximum frame size is enforced
```

# 12. Phase 2H — Connection lifecycle and concurrency

---

```text
  ↓

  ↓

  ↓

```

---

Verify that:

```text

```

is handled correctly.

---

## 12.4 Repeated connection

```text

close

pong
```

```text
      │
```
