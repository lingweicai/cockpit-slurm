# cockpit-slurm Implementation Phase 1

## 1. My main recommendation: Phase 1 should be deliberately small

Your plan says:

> Phase 1 — Build the Bridge foundation first

with:

```text
cmd/
└── cockpit-slurm-bridge/

internal/
├── ipc/
├── protocol/
├── identity/
├── service/
├── resource/
├── cache/
├── event/
├── subscription/
├── command/
└── adapter/
```

and the first steps are IPC server → protocol dispatcher → UserContext → service interfaces. ([GitHub][1])

I **would not implement all those packages yet**.

Instead, I recommend making Phase 1 itself an incremental sequence:

```text
Phase 1A  Go skeleton
    ↓
Phase 1B  Unix socket IPC server
    ↓
Phase 1C  Protocol encode/decode
    ↓
Phase 1D  Request dispatcher
    ↓
Phase 1E  Connection/UserContext
    ↓
Phase 1F  Service interfaces
    ↓
Phase 1G  Integration tests
    ↓
Phase 1 complete
```

The key principle is:

> **Don't build empty architecture. Build the smallest executable architecture that proves each boundary.**

That will make Copilot much more effective too.

# 4. Phase 1C: Treat `protocol` as a particularly important package

Because you already completed `ipc-protocol.md`, I would make the Go implementation follow that document very closely.

For example:

```text
internal/protocol/
    envelope.go
    message.go
    types.go
    errors.go
    codec.go
```

Conceptually:

```go
type Envelope struct {
    Protocol  string          `json:"protocol"`
    Version   string          `json:"version"`
    MessageID string          `json:"messageId"`
    Type      MessageType     `json:"type"`
    Resource  string          `json:"resource,omitempty"`
    Payload   json.RawMessage `json:"payload,omitempty"`
}
```

But I would **not ask Copilot to invent these structures**.

Give Copilot your `ipc-protocol.md` and tell it:

> Implement the Go protocol types according to this contract. Do not introduce fields, message types, semantics, or error codes that are not defined by the contract.

That distinction is very important for your project.

# 5. Protocol dispatcher should initially be intentionally boring

Your plan has:

```go
switch message.Type {
case "query":
case "subscribe":
case "command":
case "unsubscribe":
case "ping":
}
```

([GitHub][1])

I would initially implement:

```text
ping
query
subscribe
unsubscribe
command
```

but only give `ping` real behavior.

For example:

```text
ping       → pong
query      → "not implemented"
subscribe  → "not implemented"
command    → "not implemented"
unsubscribe → "not implemented"
```

This is better than prematurely implementing fake query/command behavior.

It gives you a clean distinction between:

**protocol understood**

and

**feature implemented**.

# 6. UserContext should come after the transport works

Your plan says to establish the authenticated Cockpit user at the beginning of a connection. ([GitHub][1])

I agree, but I would make the first version very simple:

```text
IPC connection
      ↓
identify peer
      ↓
create UserContext
      ↓
dispatcher
```

For example:

```go
type UserContext struct {
    Username     string
    UID          uint32
    GID          uint32
    AdminLevel   AdminLevel
    Coordinator  []string
    Accounts     []string
    Capabilities CapabilitySet
}
```

Your `user-context.md` should remain the authoritative definition.

Do **not** let Copilot independently redesign the authorization model.

This is especially important because your project has the somewhat unusual combination of:

```text
Linux identity
     +
Slurm AdminLevel
     +
Coordinator
     +
account associations
     +
capabilities
```

That is one of the architectural areas where human design decisions are much more important than generated code.

# 7. Don't implement Cache yet

This is probably my most important recommendation.

Although your architecture contains:

```text
Adapter
Canonical Resource
Cache
Service
Event
Subscription
```

I would **not implement a sophisticated cache during Phase 1**.

Your own plan eventually establishes the important invariant:

```text
Command
   ↓
Slurm
   ↓
Refresh
   ↓
Canonical Resource
   ↓
Cache
   ↓
Event
```

rather than:

```text
Command
   ↓
Cache.Update()
   ↓
Slurm
```

because the cache should represent actual Slurm state rather than optimistic desired state. ([GitHub][1])

That is an excellent architectural rule.

But it belongs to the later resource/vertical-slice work.

        ↓

# 9. Yes — GitHub Copilot is a very good fit for this project

In fact, your project is unusually suitable for Copilot because you now have something that many AI-assisted projects lack:

**written architectural contracts.**

You have:

```text
architecture.md
ipc-protocol.md
resource-model.md
user-context.md
event-model.md
command-model.md
error-model.md
```

This gives Copilot a specification to implement against rather than asking it to invent the architecture.

GitHub's current guidance also recommends giving Copilot **well-scoped tasks with clear acceptance criteria and specific files**, rather than handing it a large ambiguous task. ([GitHub Docs][2])

So I would use Copilot like a **junior Go developer working under your architecture**, not like an architect.

# 10. A very good Copilot workflow for your project

I recommend this cycle:

```text
You + ChatGPT
      ↓
Architecture/design decision
      ↓
Small implementation task
      ↓
GitHub Copilot
      ↓
Code
      ↓
Go tests
      ↓
Your review
      ↓
ChatGPT architectural review
      ↓
Commit
```

For each task:

### Step 1 — You define the architectural boundary

For example:

> Implement Unix socket listener for the cockpit-slurm bridge according to `ipc-protocol.md`.

### Step 2 — Copilot explores

Ask it to **inspect first, don't modify**.

### Step 3 — Copilot produces a plan

For example:

```text
Files to create:
internal/ipc/server.go
internal/ipc/server_test.go

Files to modify:
cmd/cockpit-slurm-bridge/main.go
```

### Step 4 — You approve the plan

### Step 5 — Copilot implements

### Step 6 — Copilot writes tests

### Step 7 — Run:

```bash
go test ./...
go vet ./...
go fmt ./...
```

and your build.

### Step 8 — Review the diff yourself.

This "explore → plan → implement → review" workflow is also recommended in current GitHub/Microsoft Copilot guidance. ([GitHub][3])

## My recommended development strategy

So, in short:

| Area                               | My recommendation               |
| ---------------------------------- | ------------------------------- |
| Phase 0                            | **Done — freeze it**            |
| Phase 1                            | **Bridge foundation only**      |
| Phase 2                            | **Bring Channel in very early** |
| First real resource                | **Node**                        |
| AI assistance                      | **Definitely use Copilot**      |
| Architecture decisions             | **You + me**                    |
| Routine Go implementation          | **Copilot**                     |
| Tests                              | **Copilot + you verify**        |
| Architecture review                | **Me / human review**           |
| Large autonomous Copilot task      | **Avoid**                       |
| Small acceptance-test-driven tasks | **Strongly recommended**        |
| Cache                              | **Don't implement prematurely** |
| Slurm adapter                      | **Don't implement in Phase 1**  |
| React UI                           | **Don't implement in Phase 1**  |

**I think the next useful step is not to start coding immediately.** I would first turn your current Phase 1 section into a **concrete Phase 1 implementation task breakdown (1A, 1B, 1C, ...), including exact Go files, interfaces, tests, acceptance criteria, and recommended Copilot prompts**. That would give you a very good "implementation contract" that you can execute task-by-task with Copilot while keeping the v3.5 architecture under control.

And importantly, your existing architecture is already at the right maturity for this approach: the contracts are written first, and the implementation can now be generated incrementally against them. ([GitHub][1])
