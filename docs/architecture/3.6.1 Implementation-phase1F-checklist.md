# 3.6.1 Implementation Phase 1F Checklist

This checklist is the concrete coding checklist for Phase 1F: the first authenticated application service layer.

It is intended to be a buildable implementation contract for the next coding step.

---

## 1. Goal

Implement the first authenticated application service path above the connection/session layer from Phase 1E.

The implementation must:

- keep the service layer separate from the IPC/protocol layer;
- use the server-owned `connection.UserContext` established for the connection;
- enrich identity only where needed for the first authenticated query;
- evaluate the first authorization checks in the service layer;
- return protocol-compliant responses;
- remain within Phase 1F scope and not introduce cache or event logic.

---

## 2. In-Scope Work

### 2.1 Service package creation

- [ ] Create `internal/service/` if it does not already exist.
- [ ] Add the initial service files required by the implementation:
  - [ ] `service.go`
  - [ ] `identity.go`
  - [ ] `auth.go`
  - [ ] `query.go`
  - [ ] `service_test.go`
- [ ] Keep the service package small and focused on application logic.
- [ ] Ensure the service package depends on `internal/connection` and `internal/protocol` only as needed.

### 2.2 Connection-context integration

- [ ] Confirm the service receives the connection-scoped `UserContext`.
- [ ] Confirm the service never trusts client-supplied identity values.
- [ ] Confirm the service only works with server-owned identity information.
- [ ] Confirm the service rejects a missing or invalid `UserContext`.

### 2.3 Identity enrichment

- [ ] Implement a minimal identity enrichment step for the first authenticated query.
- [ ] Resolve only the required Slurm identity metadata for Phase 1F.
- [ ] Keep the enrichment step explicit and server-owned.
- [ ] Fail closed if enrichment cannot complete.
- [ ] Do not implement broad enterprise identity logic in this phase.

### 2.4 Authorization

- [ ] Implement a minimal authorization evaluator for the first authenticated action.
- [ ] Check whether the connection's `UserContext` is valid before proceeding.
- [ ] Check whether the user has the required capability or role for the requested action.
- [ ] Deny requests with explicit authorization errors.
- [ ] Do not infer authorization from raw client input.

### 2.5 First authenticated query path

- [ ] Select one narrow authenticated query resource or action for Phase 1F.
- [ ] Implement a minimal query path that requires a valid `UserContext`.
- [ ] Return a valid protocol envelope for both success and failure.
- [ ] Ensure the response uses a non-empty `messageId`.
- [ ] Ensure payload is valid JSON and passes protocol validation.

### 2.6 Dispatcher integration

- [ ] Ensure the dispatcher can invoke the service layer for the selected Phase 1F request.
- [ ] Preserve existing `hello` and `ping` behavior unchanged.
- [ ] Preserve existing Phase 1B–1E protocol behavior.
- [ ] Return `NOT_IMPLEMENTED` when the message type is known but intentionally not implemented in this phase.
- [ ] Return a protocol-safe error for invalid or unknown message types.

### 2.7 Error mapping

- [ ] Map identity/authorization failures to the project error model.
- [ ] Return explicit service-layer errors instead of generic internal errors where possible.
- [ ] Ensure errors are represented as valid protocol envelopes.
- [ ] Keep error semantics aligned with `error-model.md` and the dispatcher contract.

---

## 3. Out-of-Scope Work

The following must not be implemented in Phase 1F:

- [ ] No canonical resource model work.
- [ ] No resource cache implementation.
- [ ] No event bus or subscription manager.
- [ ] No command adapter logic.
- [ ] No Slurm write operations.
- [ ] No full authorization matrix across all future resources.
- [ ] No session-sharing or multi-connection session infrastructure.
- [ ] No UI logic or Cockpit channel behavior.

---

## 4. Required Go Types and Interfaces

### 4.1 Service interfaces

- [ ] Define a minimal `IdentityService` interface.
- [ ] Define a minimal `AuthorizationService` interface.
- [ ] Define a minimal `QueryService` interface.
- [ ] Keep interfaces intentionally small.
- [ ] Avoid introducing unnecessary abstraction layers.

### 4.2 Concrete service types

- [ ] Define a concrete `ApplicationService` or equivalent minimal implementation.
- [ ] Register the identity, authorization, and query behavior in initialization.
- [ ] Ensure the service is initialized with server-owned connection data and not client data.

### 4.3 Required context usage

- [ ] Use `connection.UserContext` as the canonical context model.
- [ ] Ensure `UserContext` origin is the server-side connection layer.
- [ ] Explicitly differentiate between raw peer identity and enriched service identity.

---

## 5. Unit Test Checklist

### 5.1 Identity tests

- [ ] Test that a valid connection-owned `UserContext` remains valid.
- [ ] Test that missing peer identity fails closed.
- [ ] Test that empty identity values are rejected.
- [ ] Test that identity enrichment adds only the expected metadata.
- [ ] Test that identity resolution failure is reported cleanly.

### 5.2 Authorization tests

- [ ] Test authorized user access succeeds.
- [ ] Test unauthorized user access fails.
- [ ] Test missing `UserContext` fails authorization.
- [ ] Test capability mismatch fails authorization.
- [ ] Test an explicit authorization error is returned as a protocol-safe response.

### 5.3 Query tests

- [ ] Test the chosen authenticated query returns a valid protocol envelope.
- [ ] Test payload structure is valid JSON.
- [ ] Test a success response has a non-empty `messageId`.
- [ ] Test service errors map to protocol error semantics.
- [ ] Test the query does not mutate cache state.

### 5.4 Isolation tests

- [ ] Test the service does not depend on a Unix socket for unit testing.
- [ ] Test the service does not access the cache.
- [ ] Test the service does not trigger Slurm write operations.
- [ ] Test the service does not depend on event or subscription logic.

---

## 6. Integration Checklist

- [ ] Confirm a valid IPC request reaches the dispatcher.
- [ ] Confirm the dispatcher routes to the service layer.
- [ ] Confirm the service sees the server-owned `UserContext`.
- [ ] Confirm the service executes the first authenticated query path.
- [ ] Confirm the response is encoded with the same protocol envelope used earlier.
- [ ] Confirm existing hello / ping behavior still works.
- [ ] Confirm requests for not-yet-implemented message types still produce `NOT_IMPLEMENTED` when appropriate.

---

## 7. Verification Commands

Run the following before marking Phase 1F complete:

- [ ] `go test ./...`
- [ ] `go vet ./...`
- [ ] ensure no new Slurm write path is introduced
- [ ] ensure no cache dependency is introduced
- [ ] ensure no event/subscription logic is introduced

---

## 8. Completion Gate

Phase 1F is complete only when all of the following are true:

- [ ] service package exists and is small and focused
- [ ] server-owned `UserContext` is used consistently
- [ ] identity enrichment is implemented only for the first authenticated flow
- [ ] authorization is enforced in the service layer
- [ ] unauthorized access is denied explicitly
- [ ] authenticated query response is valid and protocol-safe
- [ ] hello/ping and earlier protocol behavior still pass
- [ ] unit tests cover identity, authorization, and service response handling
- [ ] `go test ./...` passes
- [ ] `go vet ./...` passes
- [ ] the implementation remains within the Phase 1F boundary

---

## 9. Implementation Order

Use this order when coding:

1. [ ] create minimal service package and interfaces
2. [ ] wire server-owned `UserContext` into service methods
3. [ ] add identity enrichment helper
4. [ ] add minimum authorization check
5. [ ] add first authenticated query path
6. [ ] integrate with dispatcher
7. [ ] add unit tests
8. [ ] run Go verification commands
9. [ ] check scope against Phase 1F boundary

---

## 10. Final review rule

Before considering the implementation complete, confirm that:

- [ ] this phase did not become a full resource/cache implementation;
- [ ] this phase did not pull event or subscription logic forward;
- [ ] this phase did not broaden the scope into command execution;
- [ ] the service layer remains a narrow application boundary, not a full application framework.
