# Implementation Plan for `cockpit-slurm` Project — Version 3.6

## 1. Purpose

This document defines the implementation plan for `cockpit-slurm` Version 3.6.

Version 3.6 continues the backend and frontend work established in Version 3.5, but changes the transport architecture:

* `cockpit-slurm` is the application and persistent backend service.
* `cockpit-slurm-channel` is removed.
* The React frontend communicates with the backend through `cockpit.channel()`.
* Cockpit provides the transport path between the frontend and the backend Unix socket.
* The `cockpit-slurm` application protocol remains independent of the Cockpit protocol.
* The backend owns resource state, cache, synchronization, commands, subscriptions, authorization, and IPC.
* The frontend owns presentation, UI state, and frontend-facing protocol handling.
* The backend must remain usable and testable without Cockpit.

The implementation plan is subordinate to:

`docs/architecture/0.1 development-cockpit-slurm-_v3.6.md`

The v3.6 development architecture document is the normative architectural reference.

---

# 2. Version 3.5 → Version 3.6 Changes

## 2.1 Transport architecture change

Version 3.5 contained three conceptual implementation areas:

```text
React
  │
  │ cockpit.channel()
  ▼
cockpit-slurm-channel
  │
  │ Unix socket
  ▼
cockpit-slurm-bridge
  │
  ▼
Backend services
```

Version 3.6 removes the intermediate application channel process:

```text
React
  │
  │ cockpit.channel()
  ▼
Cockpit transport
  │
  │ Unix socket
  ▼
cockpit-slurm
  │
  ├── IPC Server
  ├── Dispatcher
  ├── Query Service
  ├── Command Service
  ├── Resource Service
  ├── Cache
  ├── Event Bus
  └── Subscription Manager
```

The backend application name is:

```text
cockpit-slurm
```

The terms `cockpit-slurm-bridge` and `cockpit-slurm-channel` must not be used as primary Version 3.6 application component names.

---

## 2.2 Removed Version 3.5 component

The following Version 3.5 component is removed:

```text
cockpit-slurm-channel
```

The following are therefore no longer part of the v3.6 target architecture:

* `cockpit-slurm-channel` executable
* channel-specific Go package
* channel executable manifest entry
* channel-specific Unix socket forwarding process
* channel-specific application transport layer

The existing v3.5 channel implementation may remain temporarily in Git history or be removed from the working tree, but it must not be required for the v3.6 runtime architecture.

---

## 2.3 Persistent backend

The backend remains a persistent system service:

```text
cockpit-slurm.service
        │
        ▼
cockpit-slurm
```

The backend is not started once per `cockpit.channel()` request.

It remains alive independently of frontend connections and maintains the authoritative Slurm state cache.

The service owns:

* Slurm synchronization
* canonical resources
* resource cache
* event bus
* subscriptions
* IPC server
* query processing
* command processing
* authorization
* audit information where required

---

# 3. Version 3.6 Implementation Strategy

Version 3.6 should be implemented as a sequence of vertical milestones rather than as independent frontend and backend projects.

The recommended sequence is:

| Phase | Area                         | Primary result                                 |
| ----- | ---------------------------- | ---------------------------------------------- |
| 0     | Architecture/contracts       | v3.6 contracts and decisions frozen            |
| 1     | Backend foundation           | Persistent backend and application IPC ready   |
| 2     | Frontend/backend integration | `cockpit.channel()` communicates with backend  |
| 3     | First vertical slice         | Real resource query reaches React              |
| 4     | Resource system              | Canonical resources, cache, synchronization    |
| 5     | Events/subscriptions         | Real-time resource updates                     |
| 6     | Commands/authorization       | Slurm mutations with server-side authorization |
| 7     | UI integration               | Providers, navigation, role-based UI           |
| 8     | Production hardening         | Resilience, security, audit, recovery          |

The most important v3.6 milestone is **Phase 2**, because it proves that the new transport architecture works without `cockpit-slurm-channel`.

# 4. Phase 0 — Freeze Version 3.6 Contracts

## 4.1 Objective

Confirm that the contracts produced during Version 3.5 remain valid under the Version 3.6 transport architecture.

The following contracts must remain application-owned:

```text
IPC protocol
Resource model
UserContext
Event model
Command model
Error model
```

They must not depend on:

* Cockpit channel message boundaries
* React components
* PatternFly
* Cockpit bridge framing
* `cockpit-slurm-channel`

---

## 4.2 Application IPC framing

The application protocol remains length-prefixed.

Conceptually:

```text
┌──────────────┬──────────────────────┐
│ frame length │ application payload  │
└──────────────┴──────────────────────┘
```

The application frame may contain:

```json
{
  "protocol": "cockpit-slurm",
  "version": "1.0",
  "messageId": "01...",
  "type": "query",
  "resource": "nodes",
  "payload": {}
}
```

The backend must parse application frames independently of Cockpit.

The frontend integration layer must also reconstruct complete application frames from the arbitrary byte chunks delivered by `cockpit.channel()`.

---

## 4.3 UserContext

The server remains authoritative for user identity and authorization.

The backend derives identity from the server-side connection rather than trusting frontend-supplied identity.

The conceptual model remains:

```text
Cockpit authenticated user
        │
        ▼
Unix socket peer identity
        │
        ▼
UserContext
        │
        ├── Username
        ├── UID
        ├── GID
        ├── AdminLevel
        ├── Coordinator
        ├── Accounts
        └── Capabilities
```

The frontend may receive a safe representation of `UserContext`, but it must not establish the authoritative identity itself.

## 5.3 IPC server

The IPC server must:

* create/listen on the configured Unix socket;
* accept concurrent connections;
* read application frames;
* enforce frame-size limits;
* reject malformed frames;
* derive peer identity;
* construct the connection context;
* forward valid messages to the dispatcher;
* write application frames;
* close connections cleanly.

The IPC server must not contain Slurm-specific business logic.

The dispatcher must:

* decode the application envelope;
* validate protocol version;
* validate message type;
* validate required fields;
* route requests;
* return protocol errors;
* preserve message IDs.

The dispatcher must remain independent of Cockpit.

```text
Cockpit
  │
```

```text

```

    `docs/architecture/4.1 Implementation-phase2.md`

This document defines the implementation sequence and acceptance
criteria for Phase 2. It is subordinate to the v3.6 development
architecture and implementation plan.

---

## 6.2 Important transport rule

Cockpit `stream` is a byte stream.

Application message boundaries must therefore not depend on:

```text
channel.onmessage
```

being one application message.

A single application frame may arrive as:

```text
chunk A
chunk B
chunk C
```

or multiple application frames may arrive in:

```text
one chunk
```

Therefore:

```text
Cockpit stream framing
        ≠
cockpit-slurm application framing
```

The application length-prefix decoder must remain in the frontend integration layer and backend IPC layer.

---

## 6.3 Frontend Cockpit channel

The intended frontend transport is conceptually:

```typescript
const channel = cockpit.channel({
    payload: "stream",
    unix: "/run/cockpit-slurm/cockpit-slurm.sock",
    binary: true,
});
```

The exact API behavior must be verified against the Cockpit version supported by the project before freezing the implementation.

The current Cockpit protocol specifies `unix` for the `stream` payload and describes `stream` as raw data whose boundaries are arbitrary.

---

## 6.4 Frontend integration layer

Create a small frontend transport layer, for example:

```text
src/ipc/
    channel.ts
    framing.ts
    client.ts
    types.ts
```

Responsibilities:

### `channel.ts`

Own:

* creation of `cockpit.channel()`;
* channel lifecycle;
* close/error handling;
* sending bytes;
* receiving bytes.

### `framing.ts`

Own:

* application frame encoding;
* application frame decoding;
* buffering incomplete frames;
* handling multiple frames in one chunk;
* frame-size validation.

### `client.ts`

Own:

* request/response correlation;
* message IDs;
* request lifecycle;
* application-level errors.

React components must not directly implement frame parsing.

---

The first end-to-end test should be deliberately simple.

For example:

```text

  ↓

  ↓

  ↓

  ↓

  ↓

  ↓

  ↓
Unix socket
  ↓

  ↓

```

The UI should display the returned message.

This is preferable to immediately implementing Slurm resources.

## 6.6 Integration test

The first integration page should demonstrate:

```text
Connection status
Message sent
Message received
Message ID
Round-trip latency
Connection error
Connection closed
```

The page is a development/test page and does not need to be the final Slurm UI.

---

## 6.7 Socket installation modes

The v3.6 architecture should define one authoritative production socket:

```text
/run/cockpit-slurm/cockpit-slurm.sock
```

A user-local socket may be supported for development, but it should be treated as a development installation mode rather than an alternative runtime identity architecture.

Do not select the production socket based on whether the current user belongs to `wheel`.

The backend should instead use:

* socket ownership;
* socket group;
* socket permissions;
* system security policy;
* server-side peer credentials.

The backend derives the user identity from the accepted Unix socket connection.

---

## 6.8 Phase 2 acceptance criteria

Phase 2 is complete when:

1. React can create a Cockpit channel.
2. Cockpit can connect the channel to the configured Unix socket.
3. The backend accepts the connection.
4. The backend identifies the peer.
5. React can send an application frame.
6. The backend can decode it.
7. The backend can return an application frame.
8. React can reconstruct the frame.
9. Message IDs are preserved.
10. Partial frame delivery works.
11. Multiple frames in one stream chunk work.
12. Channel close is handled correctly.
13. Backend disconnect is reported to React.
14. Multiple concurrent frontend connections work.
15. `cockpit-slurm-channel` is not required.

```text
├── UserContextProvider
├── SlurmConnectionProvider
├── NodeProvider
├── JobProvider
├── AccountProvider
```


# 19. Version 3.6 Architectural Rule

The central rule for Version 3.6 is:

> **Cockpit transports application bytes; `cockpit-slurm` owns application semantics.**

Therefore:

```text
Cockpit
    = transport

cockpit.channel()
    = frontend transport API

Unix socket
    = transport endpoint

cockpit-slurm IPC protocol
    = application protocol

cockpit-slurm
    = application/backend

React
    = presentation and frontend state
```

No component should blur these boundaries.
