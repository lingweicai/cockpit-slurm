# cockpit-slurm Development Plan Version 3.6

# 1. Purpose

This document defines the software architecture and development direction for
`cockpit-slurm` Version 3.6.

Version 3.6 changes the transport architecture introduced in Version 3.5:

- `cockpit-slurm` is the application and persistent backend service.
- The separate `cockpit-slurm-channel` executable is removed.
- The React frontend communicates with `cockpit-slurm` through
  `cockpit.channel()`.
- The persistent backend owns the Slurm state cache, resource synchronization,
  commands, subscriptions, and IPC server.
- The IPC protocol remains independent of Cockpit.
- Cockpit is treated as the frontend transport provider, not as the owner of
  Slurm application state.

This document is normative for the Version 3.6 implementation.

---

# 2. Version 3.6 Architectural Decisions

### 2.1 Application name

The application is named:

`cockpit-slurm`

The name is used for:

* the Go module;

* the persistent backend service;

* the application architecture;

* the systemd service;

* the application-level IPC server;

* the frontend project;

* documentation and source-code packages.

The term `Cockpit bridge` refers only to Cockpit's own bridge process and protocol infrastructure.

The project must not use `cockpit-slurm-bridge` as the primary application name in Version 3.6 documentation.

### 2.2 Persistent backend

`cockpit-slurm` runs as a persistent systemd service.

The service:

* initializes the Slurm adapters;

* maintains the canonical resource cache;

* synchronizes Slurm state;

* publishes resource events;

* accepts IPC connections;

* manages subscriptions;

* processes queries and commands;

* performs authorization;

* records audit information where required.

The service is started by systemd, not created or destroyed for every frontend request.

```text
systemd
  │
  ▼
cockpit-slurm.service
  │
  ├── Resource Synchronizer
  ├── Resource Cache
  ├── Event Bus
  ├── Subscription Manager
  ├── IPC Server
  ├── Dispatcher
  ├── Query Service
  ├── Command Service
  └── Unix socket
```

### The cockpit-slurm service owns the Unix socket.

* The socket is created under /run/cockpit-slurm.
* Socket ownership and permissions must allow authorized Cockpit users to connect.
* The socket must not be world-writable.
* The backend must validate the peer identity and derive UserContext from the server-side identity. 

Recommended unit: 

```INI
[Unit]
Description=Cockpit Slurm Persistent Service
After=slurmctld.service
Wants=slurmctld.service

[Service]
Type=simple
ExecStart=/usr/local/bin/cockpit-slurm
Restart=on-failure
RestartSec=5

User=cockpit-slurm
Group=cockpit-slurm

RuntimeDirectory=cockpit-slurm
RuntimeDirectoryMode=0750

[Install]
WantedBy=multi-user.target
```

### 2.3 Removal of `cockpit-slurm-channel`

The separate executable named:

`cockpit-slurm-channel`

is removed from the Version 3.6 target architecture.

It must not be required for normal communication between the React frontend and the persistent `cockpit-slurm` service.

The following concepts are therefore removed:

* a separate channel executable;

* a channel-specific Go package;

* a channel executable manifest entry;

* a channel process responsible for forwarding application messages;

* a second application-level transport layer between Cockpit and `cockpit-slurm`.

### 2.4 Cockpit transport

The React frontend uses:

```
cockpit.channel()
```

as its Cockpit-facing transport API.

The exact Cockpit channel configuration must be verified against the Cockpit version supported by the project.

For the direct Unix-socket architecture, the intended configuration is not in a manifest file, instead in the frontend JavaScript:
```TS
const channel = cockpit.channel({
    payload: "stream",
    unix: "/run/cockpit-slurm/cockpit-slurm.sock",
    binary: "raw",
});
```
The stream payload explicitly supports a unix option for opening a Unix socket. 

So the architecture would be:
```text
React
  │
  │ cockpit.channel({ payload: "stream", unix: ... })
  ▼
Cockpit
  │
  │ Unix socket connection
  ▼
cockpit-slurm
  │
  │ Application IPC protocol
  ▼
Resource Cache / Dispatcher / Services
```
No package-bridge manifest entry is needed for that direct socket connection at cockpit version [cockpit doc protocol](https://github.com/cockpit-project/cockpit/blob/main/doc/protocol.md#payload-stream).

cockpit-slurm communication architecture diagram:
```text
                         Cockpit / React
                               │
                               │ cockpit.channel()
                               │ payload: "stream"
                               │ unix: /run/cockpit-slurm/...
                               ▼
                    Cockpit Unix socket transport
                               │
                               ▼
                    cockpit-slurm IPC Server
                               │
                               ▼
                         Dispatcher
                               │
              ┌────────────────┴────────────────┐
              ▼                                 ▼
        Query Controller                 Command Controller
              │                                 │
              ▼                                 ▼
        Resource Cache                    UserContext
              │                                 │
              │                                 ▼
              │                           Authorization
              │                                 │
              │                                 ▼
              │                           Command Service
              │                                 │
              │                                 ▼
              │                           Slurm Adapter
              │                                 │
              └────────────────┬────────────────┘
                               ▼
                         Slurm Cluster
```
The application must not assume that one Cockpit `message` event represents one application message. A Cockpit stream is a byte stream and may split or combine application frames.

### 2.5 Application IPC protocol

The application IPC protocol remains owned by `cockpit-slurm`.

The protocol is independent of:

* React;

* TypeScript;

* Cockpit UI components;

* Cockpit channel event boundaries;

* Cockpit bridge internal framing;

* any particular frontend implementation.

The same IPC protocol should be usable over:

* Unix domain sockets;

* Go `net.Pipe` in tests;

* other stream transports in future implementations.

# 3. Design Goals

Version 3.6 has the following goals:

1. Maintain one authoritative in-memory state cache.

2. Separate read operations from write operations.

3. Keep Slurm-specific details inside adapters.

4. Provide a stable canonical resource model.

5. Support multiple concurrent Cockpit sessions.

6. Support multiple IPC connections per logical session.

7. Perform authorization on the server.

8. Avoid trusting client-supplied identity information.

9. Support snapshot and event-based synchronization.

10. Keep the IPC protocol transport-independent.

11. Remove unnecessary forwarding processes.

12. Make the backend testable without Cockpit or React.

13. Support future non-Cockpit clients.

14. Keep the architecture compatible with Slurm REST/OpenAPI models.

# 4. Non-Goals

Version 3.6 does not attempt to:

* implement a complete Slurm replacement;

* expose every Slurm command immediately;

* make React responsible for authorization;

* make the frontend maintain the authoritative cluster state;

* make Cockpit understand the application protocol;

* implement a general-purpose message broker;

* introduce a distributed cache;

* introduce persistent database storage for all Slurm resources;

* support arbitrary remote clients over TCP;

* guarantee that every frontend request is completed synchronously;

* preserve the removed `cockpit-slurm-channel` executable.

                               │
                               ▼
                       cockpit-slurm
                    Persistent systemd service
                               │
       ┌───────────────────────┴────────────────────────┐
       │                                                │
       ▼                                                ▼
 Application IPC Server                         Resource Synchronizer
       │                                                │
       ▼                                                ▼

       │                                                │
       ├───────────────────────┐                        ▼
       ▼                       ▼                 Canonical Resources

* application protocol semantics.

# 6. Main Architectural Layers

### 6.1 Cockpit Integration Layer

Responsibilities:

* create and configure the Cockpit channel;

* send and receive application bytes;

* convert received binary data into application frames;

* encode outgoing application frames;

* translate channel closure into frontend connection state;

* expose a frontend-friendly API to React providers.

This layer must not:

* execute Slurm commands directly;

* implement authorization;

* maintain the authoritative resource cache;

* interpret Slurm-specific command semantics.

Suggested frontend location:

```
src/ipc/
src/services/
```

### 6.2 Application IPC Server Layer

Responsibilities:

* listen on the Unix domain socket;

* accept concurrent connections;

* maintain connection lifecycle;

* read application frames;

* write application frames;

* enforce frame-size limits;

* reject malformed frames;

* associate each connection with server-derived identity;

* pass validated messages to the dispatcher.

This layer knows nothing about individual Slurm resources.

It must not contain:

* Slurm command execution;

* resource-specific business rules;

* React-specific logic;

* UI state.

### 6.3 Protocol Dispatcher

Responsibilities:

* decode the application envelope;

* validate required envelope fields;

* validate message type;

* validate payload structure;

* route requests to the appropriate controller;

* encode responses and events;

* return protocol errors for invalid messages.

The dispatcher does not directly execute Slurm commands.

### 6.4 Query Controller

Responsibilities:

* handle read-only requests;

* validate query parameters;

* read canonical resources from the cache;

* return snapshots;

* return resource metadata;

* return current generation information.

The Query Controller must never communicate directly with Slurm.

```
Query
  ↓
Query Controller
  ↓
Query Service
  ↓
Resource Cache
  ↓
Snapshot
```

### 6.5 Command Controller

Responsibilities:

* validate commands;

* resolve the current server-side user context;

* check capabilities;

* apply command-level authorization;

* enforce idempotency where required;

* create command-tracking records;

* invoke the Command Service;

* return command results or command status.

The Command Controller must not update the resource cache directly.

```
Command
  ↓
Command Controller
  ↓
UserContext
  ↓
Capability Check
  ↓
Command Service
  ↓
Command Adapter
  ↓
Slurm
```

### 6.6 Command Service

Responsibilities:

* coordinate command execution;

* manage command lifecycle;

* invoke command adapters;

* handle command errors;

* create audit records;

* trigger resource refresh after successful mutations.

The Command Service must not modify canonical resources directly.

### 6.7 Resource Service

Responsibilities:

* coordinate resource synchronization;

* invoke resource adapters;

* normalize Slurm data;

* update the canonical resource layer;

* update the resource cache;

* publish resource events.

Only the Resource Service or its controlled cache-update path may modify canonical resource state.

### 6.8 Command Adapter Layer

Purpose:

Translate canonical application commands into Slurm operations.

Examples:

```
CreateAccount
  ↓
sacctmgr add account

CancelJob
  ↓
scancel

DrainNode
  ↓
scontrol update

UpdateQOS
  ↓
sacctmgr modify qos
```

The Command Adapter Layer performs writes only.

It must not:

* update the cache directly;

* publish frontend events directly;

* make authorization decisions;

* contain React-specific logic.

### 6.9 Resource Adapter Layer

Purpose:

Translate Slurm state into canonical resources.

Possible sources:

```
slurmrestd
squeue
scontrol
sacct
sacctmgr
Slurm event or trigger mechanisms
polling fallback
```

Example:

```
squeue
  ↓
Job Resource Adapter
  ↓
Canonical Job
  ↓
Resource Cache
```

The Resource Adapter Layer performs reads and synchronization.

### 6.10 Canonical Resource Layer

Purpose:

Provide stable domain models independent of Slurm CLI commands.

Each canonical resource contains:

```
Metadata
Spec
Status
```

Typical metadata:

```
Resource ID
Kind
Generation
UpdatedAt
Source
```

The `Spec` and `Status` structures may use generated Slurm OpenAPI models where appropriate, but the frontend must not depend directly on raw CLI output.

### 6.11 Resource Cache

The resource cache is the authoritative application state within the `cockpit-slurm` service.

Responsibilities:

* store canonical resources;

* maintain indexes;

* perform resource lookup;

* generate snapshots;

* maintain generation values;

* compare resource changes;

* provide consistent read access;

* support event generation after updates.

The cache must not store:

* UI state;

* form state;

* unsent commands;

* frontend component state;

* arbitrary client identity claims.

### 6.12 Event Bus

The Event Bus publishes changes after the cache has been updated.

Typical event types:

```
Created
Updated
Deleted
```

Examples:

```
AccountCreated
JobUpdated
NodeUpdated
PartitionDeleted
```

Events must describe changes to authoritative canonical resources.

The Event Bus must not publish an event before the corresponding cache update has succeeded.

### 6.13 Subscription Manager

Responsibilities:

* maintain active subscriptions;

* associate subscriptions with a defined scope;

* send an initial snapshot;

* send subsequent resource events;

* remove subscriptions when their owner disconnects;

* apply resource-kind and filter constraints.

Each subscription contains:

```
Subscription ID
Scope
Connection or Session Reference
Resource Kind
Filter
Last Delivered Generation
```

The initial implementation may use connection-scoped subscriptions.

The architectural model must keep subscription scope explicit so that session-scoped subscriptions can be introduced later.

A subscription scope must not be inferred solely from the connection ID.

# 7. Session and Connection Model

The architecture distinguishes a logical session from an IPC connection.

```
Cockpit Login
      │
      ▼
Logical Session
      │
      ├── IPC Connection A
      ├── IPC Connection B
      └── IPC Connection C
```

A logical session represents the user's authenticated Cockpit session.

An IPC connection represents one active transport connection between Cockpit and `cockpit-slurm`.

Each connection has:

```
Connection ID
Session ID, when available
Server-derived UserContext
Connection lifecycle
Subscription references
```

The Connection ID identifies one transport connection.

The Session ID identifies the logical session to which the connection belongs.

The server owns the identity associated with the connection.

The client must not be allowed to select or override:

```
Username
UID
GID
AdminLevel
Capabilities
Accounts
DefaultAccount
```

# 8. Identity and Authorization Model

### 8.1 Identity flow

```
Cockpit Authentication
        │
        ▼
Server-derived Linux Identity
        │
        ▼
Slurm User Lookup
        │
        ▼
Slurm AdminLevel
        │
        ▼
Capability Resolver
        │
        ▼
UserContext
        │
        ▼
Authorization
```

### 8.2 UserContext

The server-owned context may contain:

```Go
type UserContext struct {
    Username         string
    UID              uint32
    GID              uint32

    AdminLevel       AdminLevel
    CoordinatorAccounts []string
    Capabilities     CapabilitySet

    Accounts         []string
    DefaultAccount   string
}
```
**Important**: CoordinatorAccounts should represent the accounts for which the user is a Slurm coordinator. It should not be interpreted as “all accounts the user can access.”

The exact Go structure is defined by the identity and connection implementation documents.

Every active connection must have a server-owned user context before it can execute an authorized application operation.

### 8.3 Capability-based authorization

Authorization must be based on capabilities rather than direct UI checks against Slurm's internal enum values.

Examples:

```
ManageAccounts
ManageUsers
ManageNodes
ManagePartitions
ManageQOS
SubmitJobs
CancelJobs
ViewAccounting
ViewClusterState
```

Application services must check capabilities such as:

```
Capabilities.ManageAccounts
Capabilities.CancelJobs
```
Application needs coordinator-specific operations:
```
ManageCoordinatorAccounts
```
The capability resolver should decide what a coordinator may do. Do not make every coordinator automatically equivalent to an operator.


The frontend may use capabilities to build navigation, but the backend must repeat all authorization checks.



### 8.4 Role mapping

|Cockpit-Slurm AdminLevel|Application role|Home page|
| --- | --- | --- |
|Not Set|Visitor|Welcome / Not Configured|
|None|User|User Dashboard|
|Coord| Coordinator | Coordinators Dashboard|
|Operator|Operator|Operations Dashboard|
|Admin|Administrator|Administration Dashboard|

Users should see application roles and capabilities rather than raw internal Slurm authorization values.

## 9. IPC Transport Architecture

### 9.1 Transport path

```
React
  ↓
cockpit.channel()
  ↓
Cockpit transport
  ↓
Unix socket
  ↓
cockpit-slurm IPC Server
  ↓
Protocol Dispatcher
  ↓
Application Services
```

There is no intermediate `cockpit-slurm-channel` executable.

### 9.2 Unix socket

The persistent service listens on a Unix domain socket.

Recommended production path:

```
/run/cockpit-slurm/socket
```

A development-specific per-user path may be used when required.

The socket must have controlled ownership and permissions.

The service must not expose an unauthenticated world-writable socket.

### 9.3 Connection concurrency

The IPC server must support multiple concurrent connections.

Each connection must have:

* independent receive buffering;

* independent send handling;

* independent connection lifecycle;

* independent subscription references;

* independent request correlation;

* access to shared application services and cache.

A slow client must not block unrelated clients.

### 9.4 Application framing

The IPC transport is a byte stream.

The application protocol uses explicit length-prefixed frames.

Each frame consists of:

```
4-byte unsigned big-endian payload length
UTF-8 JSON payload
```

The length excludes the four-byte prefix.

```
+----------------------+----------------------+
| Payload length       | JSON payload         |
| uint32, big-endian   | UTF-8 bytes          |
+----------------------+----------------------+
        4 bytes              N bytes
```

The receiver must support:

* partial frames;

* multiple frames in one read;

* one frame split across multiple reads;

* arbitrary Cockpit message boundaries.

The receiver must reject:

* invalid lengths;

* frames larger than the configured maximum;

* invalid UTF-8;

* invalid JSON;

* invalid application envelopes.

The initial maximum frame size should be explicitly configured, for example:

```
1 MiB
```

The final value must be defined by the implementation configuration.

### 9.5 Binary mode

The frontend should use binary mode for the Cockpit stream when the selected Cockpit API and version support the required configuration:

TypeScript

```
cockpit.channel({
    payload: "stream",
    binary: true,
});
```

The exact Unix-socket option must be verified against the supported Cockpit version before implementation is finalized.

The application framing code must not depend on Cockpit event boundaries.

### 9.6 Text mode

Newline-delimited JSON is not the Version 3.6 target protocol.

Text mode may be used for temporary diagnostics or a standalone test client, but production IPC must use the length-prefixed framing contract.

## 10. Application Message Envelope

Every application message must contain a common envelope.

A conceptual envelope is:

JSON

```
{
  "version": 1,
  "type": "request",
  "request_id": "req-123",
  "operation": "list_nodes",
  "payload": {}
}
```

The final envelope schema is defined by the IPC protocol document.

The envelope should support at least:

```
hello
hello-response
ping
pong
request
response
event
error
```

### 10.1 Request correlation

Requests that expect a response must contain a unique request ID.

The response must contain the same request ID.

The frontend must not assume that responses arrive in the same order as requests.

### 10.2 Events

Events are asynchronous messages generated by the backend.

Events must not require a request ID unless the protocol explicitly defines such a relationship.

### 10.3 Errors

Protocol errors, validation errors, authorization errors, Slurm errors, and internal errors must be distinguishable.

The frontend must not depend on parsing human-readable error text to determine the error category.

## 11. Read Path

```
React
  ↓
cockpit.channel()
  ↓
IPC Server
  ↓
Protocol Dispatcher
  ↓
Query Controller
  ↓
Query Service
  ↓
Resource Cache
  ↓
Snapshot
  ↓
React
```

The read path must not access Slurm directly.

The cache is the source of truth for normal frontend queries.

If the cache is unavailable or not initialized, the service must return a defined application error rather than silently executing an uncontrolled fallback query.

## 12. Write Path

```
React
  ↓
cockpit.channel()
  ↓
IPC Server
  ↓
Protocol Dispatcher
  ↓
Command Controller
  ↓
UserContext
  ↓
Capability Check
  ↓
Command Service
  ↓
Command Adapter
  ↓
Slurm
  ↓
Resource Service
  ↓
Resource Adapter
  ↓
Canonical Resource
  ↓
Resource Cache
  ↓
Event Bus
  ↓
Subscription Manager
  ↓
React
```

The Command Adapter must not update the cache directly.

After a successful mutation:

1. the command result is returned or tracked;

2. the affected resource is refreshed;

3. the Resource Service normalizes the new Slurm state;

4. the cache is updated;

5. the Event Bus publishes the resulting change;

6. subscribed clients receive the event.

# 13. Synchronization Model

### 13.1 Initial subscription

```
Subscribe
  ↓
Validate subscription
  ↓
Read current cache generation
  ↓
Send snapshot
  ↓
Register subscription
  ↓
Send subsequent events
```

The implementation must define the ordering needed to avoid losing an event between snapshot generation and subscription registration.

### 13.2 Normal operation

```
Slurm state changes
  ↓
Resource Adapter
  ↓
Resource Service
  ↓
Cache update
  ↓
Event Bus
  ↓
Subscription Manager
  ↓
IPC connection
  ↓
React
```

The frontend should not poll Slurm directly.

If polling is used internally, it belongs to the Resource Synchronizer and must not be implemented separately by every React component.

### 13.3 Generation tracking

The cache should maintain a monotonically increasing generation value.

Generation values are used for:

* snapshot identification;

* event ordering;

* detecting missed events;

* reconnect recovery;

* debugging;

* consistency checks.

The exact generation semantics must be defined in the IPC and cache documents.

# 14. Command Tracking

The backend should maintain a lightweight command cache.

Responsibilities:

* idempotency;

* duplicate detection;

* progress tracking;

* command status lookup;

* correlation between frontend requests and Slurm operations.

Suggested states:

```
Pending
Running
Succeeded
Failed
Cancelled
```

The initial retention period may be:

```
5–30 minutes
```

The retention period must be configurable.

Long-running operations must not require the IPC connection to remain blocked until Slurm finishes.

# 15. Audit Logging

Commands that change cluster state should produce audit records.

An audit record may contain:

```
User
UID
Timestamp
Command
Parameters
Resource
Result
Error
Duration
Request ID
```

Audit logging must not record every UI interaction.

Sensitive values must be excluded or appropriately protected.

The exact audit policy is defined separately from the transport protocol.

# 16. React Architecture

The React frontend should contain a single reusable IPC client layer.

Suggested structure:

```
src/
  ipc/
    client.ts
    framing.ts
    protocol.ts
    errors.ts

  services/
    resource-service.ts
    command-service.ts
    subscription-service.ts

  contexts/
    UserProvider.tsx
    AccountProvider.tsx
    NodeProvider.tsx
    JobProvider.tsx
```

### 16.1 IPC client responsibilities

The IPC client owns:

* channel creation;

* frame encoding;

* frame decoding;

* receive buffering;

* request correlation;

* connection state;

* protocol error handling;

* reconnect behavior, if implemented.

React components must not implement framing directly.

### 16.2 Resource providers

Each provider may own one or more logical subscriptions.

Examples:

```
AccountProvider
  ↓
Subscribe(Account)

NodeProvider
  ↓
Subscribe(Node)

JobProvider
  ↓
Subscribe(Job)
```

Each provider receives:

```
Snapshot
  ↓
Events
  ↓
Context state update
```

The frontend cache is a presentation cache only.

It must not replace the authoritative backend cache.

### 16.3 Dynamic navigation

Navigation should be derived from the server-provided user context and capabilities.

```
UserContext
  ↓
Capability Resolver
  ↓
Navigation Builder
  ↓
React Sidebar
  ↓
Pages
```

Every page must still rely on backend authorization.

* adapters must not depend on frontend code;

# 18. Lifecycle and Shutdown

The persistent service must:

1. initialize configuration;

2. initialize logging;

3. initialize identity and authorization dependencies;

4. initialize adapters;

5. initialize the canonical resource cache;

6. initialize synchronization;

7. create the Unix socket;

8. start the IPC server;

9. accept connections;

10. handle termination signals;

11. stop accepting new connections;

12. close or drain active connections;

13. stop synchronization;

14. flush required audit information;

15. remove the socket if appropriate;

16. exit cleanly.

The service must not leave a stale socket that prevents a later startup.

# 19. Security Requirements

The implementation must:

* restrict Unix socket permissions;

* validate peer identity where supported;

* derive identity on the server;

* reject client-supplied identity overrides;

* enforce authorization for every command;

* validate all message envelopes;

* enforce maximum frame size;

* avoid shell command construction from untrusted strings;

* use safe argument handling for Slurm commands;

* avoid logging secrets;

* prevent one client from reading another client's private state;

* prevent unauthorized subscription access;

* close connections on unrecoverable protocol violations.

The frontend is not a security boundary.

# 22. Migration from Version 3.5

The following Version 3.5 elements are removed or renamed.

|Version 3.5|Version 3.6|
| --- | --- |
|`cockpit-slurm-bridge` application name|`cockpit-slurm`|
|`cockpit-slurm-channel` executable|Removed|
|Channel forwarding package|Removed|
|Channel-specific manifest entry|Removed|
|React → channel executable → socket|React → Cockpit channel → socket|
|Bridge-owned application terminology|`cockpit-slurm` service terminology|
|NDJSON framing|Length-prefixed binary framing|
|Transport-specific message assumptions|Explicit stream buffering and framing|

Existing internal packages may be retained when they implement reusable functionality, but their names and responsibilities must be reviewed against the Version 3.6 boundaries.

# 23. Acceptance Criteria

Version 3.6 architecture is considered implemented when:

* the persistent service is named `cockpit-slurm`;

* the separate `cockpit-slurm-channel` executable is removed;

* the frontend uses `cockpit.channel()`;

* the frontend can communicate with the Unix socket without the removed forwarding executable;

* the application protocol uses explicit length-prefixed framing;

* the frontend handles fragmented and coalesced stream data;

* the IPC server supports multiple concurrent connections;

* identity is server-derived;

* authorization is performed by the backend;

* queries read from the cache;

* commands do not update the cache directly;

* resource refresh updates the cache;

* cache updates produce events;

* subscriptions receive snapshots and subsequent events;

* protocol errors are structured;

* frame-size limits are enforced;

* unit and integration tests pass;

* `go test ./...` passes;

* `go vet ./...` passes;

* the supported Cockpit version and Unix-socket channel configuration are documented and verified.
