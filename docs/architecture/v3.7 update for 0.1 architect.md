## 1. Main objective

Create a complete and internally consistent v3.7 architecture document by carrying forward the accepted v3.6 architecture and incorporating the new daemon identity and privilege model.

This is an architecture-version update, not a redesign of the entire application.

The principal v3.7 change is:

**The persistent `cockpit-slurm` daemon runs as the dedicated Linux user `cockpit-slurm`, while the corresponding SlurmDB user `cockpit-slurm` is configured with `AdminLevel=Administrator`.**

This provides the daemon with the required Slurm administrative authorization through SlurmDB without requiring membership in the Linux `SlurmUser` group or running the daemon as root.

The objective is to reduce unnecessary OS-level privileged helpers, including D-Bus helper services, for Slurm operations that have been verified to work under the daemon's SlurmDB identity.

Do not describe the daemon as running with Linux root privileges or as the configured SlurmUser.

Terminology must be accurate:
- Use `AdminLevel=Administrator` when describing the SlurmDB setting.
- Distinguish the SlurmDB AdminLevel value `Administrator` from the CLI representation `Admin` where applicable.
- `SlurmUser` refers to the configured Slurm Linux user, not a Unix group.
- Do not use the term `SlurmLevel`.

## 3. Define the three independent identities

Add a clear normative section describing the three identities used by the system.

### 3.1 Daemon operating-system identity

The persistent daemon runs as:

- Linux username: `cockpit-slurm`
- Dedicated Linux UID.
- Dedicated primary group: `cockpit-slurm`.
- No Linux root execution.
- No membership in the configured SlurmUser's Unix group solely to obtain Slurm administrative authorization.

The daemon must retain only the OS permissions required for its own runtime, configuration, logs, socket, and other explicitly approved resources.

Its systemd service should continue to use a dedicated service account:

```ini
User=cockpit-slurm
Group=cockpit-slurm
```

Do not add `SupplementaryGroups=slurm` as a substitute for SlurmDB authorization.

### 3.2 Daemon Slurm identity

The corresponding SlurmDB user is also named:

`cockpit-slurm`

Its SlurmDB account configuration is:

`AdminLevel=Administrator`

This identity is used by the daemon when invoking supported Slurm commands and APIs.

The architecture must explicitly state:

- SlurmDB Administrator privileges are Slurm-level privileges, not Linux root privileges.
- They do not grant access to arbitrary OS files or privileged operating-system operations.
- They do not make the daemon the configured SlurmUser.
- They do not imply that the daemon should execute arbitrary shell commands.
- Slurm still performs its own authorization and validation.
- The daemon must use fixed, validated command adapters and arguments.

The SlurmDB user and its accounting associations are different concepts.

An accounting association is not the source of the user's AdminLevel. Do not require associations with every Slurm account merely to obtain SlurmDB Administrator authorization.

The existing test environment has an association for `cockpit-slurm` with account `devel`. This must not be interpreted as restricting its SlurmDB Administrator privileges to that account.

However, associations and account context remain relevant to accounting and job-submission operations. Their requirements must be considered separately for each operation.

### 3.3 Requesting-user identity

The requesting user is the authenticated Cockpit user connecting to the daemon.

The backend must continue to:

1. Obtain the peer credentials from the IPC connection using the trusted server-side mechanism.
2. Validate the Linux identity.
3. Resolve the corresponding SlurmDB user and its current AdminLevel.
4. Resolve coordinator-account membership and other trusted scope data.
5. Construct the requesting user's `UserContext`.
6. Evaluate the operation against `operations.yaml`.
7. Apply the relevant resource visibility policy.

The requesting user's identity must never be replaced by the daemon's SlurmDB Administrator identity.

The daemon's SlurmDB Administrator privilege must never be inherited by a frontend user.

## 4. Define the new identity and command-execution flow

Update the architecture diagrams and relevant explanations to show the separation between requester authorization and daemon execution.

The intended flow is:

```text

      |

      |

      |
      v

```

The application authorization check must occur before invoking the Slurm command.

A successful SlurmDB authorization does not replace the application's requester authorization.

The backend must never allow a frontend client to select:
- A different Linux execution user.
- A different SlurmDB execution identity.
- An arbitrary executable.
- Arbitrary command-line arguments outside the operation specification.
- A shell command.
- A privilege escalation mechanism.

## 5. Revise the privileged-helper architecture

The v3.6 architecture must be updated to reflect the new SlurmDB service identity.

The default execution model for supported Slurm operations should be direct execution by the daemon under its own Linux account and SlurmDB identity.

A privileged D-Bus helper or sudo-based helper must not be a mandatory architectural dependency for Slurm operations that have been validated under this identity.

However, do not state that all privileged helpers are permanently prohibited or unnecessary.

Retain a narrowly scoped helper mechanism as a possible future exception when an operation genuinely requires OS-level privileges that SlurmDB Administrator authorization does not provide.

Examples include:
- Operating-system configuration changes.
- Access to protected OS resources.
- Operations requiring a Linux identity different from the daemon.
- Operations whose semantics require preserving the original requesting user's execution identity.

Any such helper must:
- Expose only explicitly approved operations.
- Avoid arbitrary command execution.
- Validate all inputs.
- Be invoked only after requester authorization.
- Preserve the original requester identity in audit records.
- Have a separately documented security boundary and acceptance tests.

Do not introduce a D-Bus helper simply to duplicate Slurm authorization already provided by SlurmDB.

## 6. Preserve application authorization and Phase 5 decisions

This is a critical requirement.

The new daemon SlurmDB Administrator identity must not change the accepted Phase 5 application authorization policy.

In particular, preserve the accepted Node operations:

- `node.drain`
- `node.resume`

These operations must continue to require the requesting user's currently resolved Slurm `AdminLevel=Administrator`, using the existing `slurm_admin_level_admin` predicate.

Do not replace that predicate with:
- The daemon's SlurmDB AdminLevel.
- The application role `Administrator` alone.
- A broader predicate that implicitly treats root or SlurmUser as equivalent.

Preserve the distinction between:
- Application role.
- Requesting user's Slurm AdminLevel.
- Daemon's SlurmDB execution identity.
- Linux OS identity.

The operation policy remains the authoritative application-level authorization source.

The frontend's capabilities and role presentation are not authorization mechanisms.

## 7. Define identity-sensitive operations and exceptions

Do not assume that every Slurm operation can safely execute under the daemon's SlurmDB Administrator identity.

Some operations may depend on the identity of the original user, particularly operations involving:
- Job submission.
- Job ownership.
- User-specific accounting associations.
- User-specific limits or defaults.
- Operations requiring direct-owner authorization.
- Slurm commands with special authorization rules.

For each such operation, its execution semantics must be explicitly reviewed.

The architecture must distinguish:

1. Operations that can execute safely under the daemon's SlurmDB identity after application authorization.
2. Operations that require the original user's identity to be preserved.
3. Operations requiring OS-level privileges beyond the daemon's permissions.
4. Operations that must be rejected until a supported execution mechanism exists.

Do not silently execute identity-sensitive operations as `cockpit-slurm` and assume their behavior is equivalent to execution by the requester.

Do not assume that SlurmDB Administrator privileges automatically satisfy every special Slurm command authorization rule.

## 8. Revise resource acquisition and PrivateData

The daemon's SlurmDB identity is also the normal Slurm identity used for backend resource acquisition.

The resource architecture remains:

- One shared canonical resource cache.
- Backend resource acquisition.
- Per-connection visibility evaluation.
- Per-connection snapshots and events.

Slurm's `PrivateData` configuration and application-level visibility remain separate security layers.

The document must explicitly state:

- `PrivateData` controls what Slurm permits the backend execution identity to retrieve.
- `visibility.yaml` controls which retrieved canonical records are returned to each authenticated IPC connection.
- Application visibility must not bypass Slurm's own restrictions.
- SlurmDB Administrator privileges must not be assumed to bypass every `PrivateData` restriction.
- If a configured `PrivateData` setting prevents the backend from acquiring required resources, the data-acquisition design must be reviewed and tested.
- The application must not silently present incomplete data as a complete resource collection.

The existing test environment has:

```text
SlurmUser=slurm
PrivateData=none
AccountingStorageType=accounting_storage/slurmdbd
AuthType=auth/munge
```

The daemon runs as Linux user `cockpit-slurm`, and its corresponding SlurmDB user has `AdminLevel=Administrator`.

Tests under `PrivateData=none` demonstrate behavior under that configuration only. They do not establish behavior under more restrictive `PrivateData` configurations.

Do not claim that all restrictive `PrivateData` configurations have already been validated.

## 9. Audit and command execution identity

Update the audit architecture to record the two identities separately.

For every command execution, the audit and command ledger should retain sufficient information to identify:

- Authenticated requesting username and UID.
- Requesting user's resolved Slurm AdminLevel and application role, where relevant.
- IPC connection or request correlation information.
- OperationID.
- Target resource and scope.
- Authorization decision and policy result.
- Linux execution identity.
- SlurmDB execution identity.
- Command outcome.
- Relevant timestamps and error information.

The audit must make it possible to distinguish:

```text
Requested by: dev
Executed by: cockpit-slurm
```

The daemon must not record `cockpit-slurm` as the original requester merely because it executed the command.

Do not expose sensitive internal command details to unauthorized frontend users.

## 10. Deployment and configuration requirements

Add or update deployment requirements to cover the SlurmDB service identity.

The architecture should document the following administrative setup conceptually:

1. Create a dedicated Linux user and group named `cockpit-slurm`.
2. Create or configure the corresponding SlurmDB user named `cockpit-slurm`.
3. Configure that SlurmDB user with `AdminLevel=Administrator`.
4. Keep the daemon outside the Linux `slurm` group unless a separately justified OS permission requires it.
5. Run the daemon as Linux user `cockpit-slurm`.
6. Verify that the daemon can execute the required Slurm read and command operations.
7. Verify that application authorization still rejects unauthorized requesting users.

## 11. Security and acceptance requirements

Add a v3.7 acceptance section covering at least the following.

### A. Daemon operating-system identity

- Verify the daemon runs as Linux user `cockpit-slurm`.
- Verify it does not run as root.
- Verify it is not dependent on Linux `SlurmUser` group membership for Slurm administrative authorization.
- Verify it has only the OS permissions required by its documented responsibilities.

### B. SlurmDB identity

- Verify the SlurmDB user `cockpit-slurm` exists.
- Verify its `AdminLevel` is `Administrator`.
- Verify supported Slurm administrative read operations work under this identity.
- Verify supported administrative mutations, including Node drain and resume, work under this identity.
- Verify command-specific exceptions separately rather than assuming every Slurm operation works.

### C. Requester authorization

- Verify an authorized requesting user can perform only the operations permitted by `operations.yaml`.
- Verify an ordinary User cannot obtain administrative access through the daemon.
- Verify an Operator cannot obtain Administrator privileges through the daemon.
- Verify frontend-supplied identity or role values cannot change the authorization decision.
- Verify Node drain/resume retain the accepted Phase 5 requester authorization predicate.
- Verify an unauthorized request is rejected before Slurm command execution.

### D. Identity separation and audit

- Verify the requesting user remains distinct from the daemon execution identity.
- Verify command ledger and audit records preserve both identities.
- Verify the daemon identity is never substituted for the requester in authorization decisions.

### E. Resource acquisition and visibility

- Verify global resource acquisition under the tested Slurm configuration.
- Verify the canonical cache remains shared.
- Verify visibility is applied independently to each IPC connection.
- Verify snapshots, queries, and events use the same visibility evaluator.
- Verify the behavior under the intended `PrivateData` configuration.
- Record separately any `PrivateData` configurations that remain untested.

### F. Helper reduction

- Verify supported Slurm operations no longer depend on unnecessary privileged D-Bus or sudo helpers.
- Verify any remaining helper has a documented OS-level or identity-preservation requirement.
- Verify helper invocation cannot bypass application authorization.
