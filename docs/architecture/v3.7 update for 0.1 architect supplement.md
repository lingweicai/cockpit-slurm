### Resource Synchronizer Execution Identity

The Resource Synchronizer runs within the persistent `cockpit-slurm` daemon and uses the daemon's dedicated SlurmDB identity, `cockpit-slurm`, configured with `AdminLevel=Administrator`, when acquiring global Slurm resource state.

The Resource Synchronizer must:

1. Execute Slurm resource queries under the daemon's Linux service account, `cockpit-slurm`.
2. Use the corresponding SlurmDB identity `cockpit-slurm` with `AdminLevel=Administrator` for Slurm-level authorization.
3. Acquire the canonical resource state independently of the requesting Cockpit user's identity.
4. Populate the shared canonical resource cache with the resource data successfully retrieved from Slurm.
5. Apply the appropriate per-connection visibility policy before exposing resource snapshots, query results, or events to an IPC client.

The Resource Synchronizer's administrative SlurmDB identity is strictly a backend data-acquisition identity. It must not be used as the identity or authorization context of an IPC client.

The Resource Synchronizer must not assume that `AdminLevel=Administrator` bypasses all Slurm `PrivateData` restrictions. Resource acquisition must respect the data actually made available by Slurm under the configured security policy. Any incomplete or restricted acquisition must be handled explicitly rather than represented as complete global state. 


### One important architectural distinction
I suggest documenting these two paths separately:
```
1. Resource acquisition path
Resource Synchronizer

Daemon identity: cockpit-slurm

SlurmDB AdminLevel=Administrator


Slurm queries

Acquire global canonical resource state


Shared canonical cache


Per-connection visibility filtering


2. User command path
Cockpit user request

Identity from SO_PEERCRED


operations.yaml authorization

Authorize the actual requesting user


Command execution

Execute supported operation as cockpit-slurm
```

The distinction is important: global backend data acquisition and user-requested command authorization are different responsibilities.

**Two additional points I would include**
**1. Global cache does not mean unrestricted frontend visibility.** The Resource Synchronizer can acquire shared data, but every IPC connection must still receive only the resources and fields permitted by its visibility policy. This includes snapshots, incremental events, and query responses.

**2. Define what happens when acquisition is incomplete.** For example, if Slurm restricts access to some jobs or partitions, the backend must not silently treat the returned partial collection as the complete global state. This matters for cache generations and event delivery too.

I would put this text in the v3.7 resource synchronization/data-acquisition section, and ask Copilot to update the architecture diagrams and the security section consistently. This makes the new daemon identity model explicit throughout the architecture.
