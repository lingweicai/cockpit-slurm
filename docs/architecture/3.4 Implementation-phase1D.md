# 3.4 Implementation Phase 1D — IPC Dispatcher

## 1. Purpose

Phase 1D implements the **IPC message dispatcher** for cockpit-slurm.

The dispatcher receives a validated protocol `Envelope` from the IPC/protocol layer, determines the message type, invokes the appropriate handler, and produces a protocol response.

Phase 1D establishes the first complete request/response path without implementing Slurm operations.

---

## 2. Scope

Phase 1D SHALL implement:

1. Message dispatcher.
2. Message handler registration/routing.
3. `hello` → `hello-response`.
4. `ping` → `pong`.
5. Handling of known-but-unimplemented message types.
6. Handling of unknown/invalid messages passed to the dispatcher.
7. Protocol response generation.
8. Dispatcher unit tests.
9. Basic IPC-to-dispatcher integration testing where practical.

The dispatcher SHALL operate on the `protocol.Envelope` defined in Phase 1C.

---

## 3. Non-goals

Phase 1D SHALL NOT implement:

* Slurm command execution;
* `sacctmgr`;
* `scontrol`;
* `squeue`;
* `sinfo`;
* `slurmrestd`;
* canonical resource models;
* resource cache;
* event manager;
* subscription manager;
* authorization;
* `UserContext`;
* Linux user/group permission evaluation;
* session management;
* Cockpit `channel()` integration.

These concerns belong to later phases.

---

## 4. Architecture Boundary

The architecture SHALL remain:

```text id="4v4j4k"
                Unix socket
                    │
                    ▼
             ┌─────────────┐
             │  internal/  │
             │     ipc     │
             └──────┬──────┘
                    │
                 net.Conn
                    │
                    ▼
             ┌─────────────┐
             │  protocol   │
             │             │
             │ Decode      │
             │ Validate    │
             └──────┬──────┘
                    │
                Envelope
                    │
                    ▼
             ┌─────────────┐
             │  dispatcher │
             │             │
             │ route type  │
             │ invoke      │
             │ handler     │
             └──────┬──────┘
                    │
             Response Envelope
                    │
                    ▼
             protocol.Encode
                    │
                    ▼
                Unix socket
```

### `internal/ipc`

Owns:

* Unix socket;
* connection lifecycle;
* reading/writing the connection.

### `internal/protocol`

Owns:

* framing;
* encoding;
* decoding;
* envelope;
* protocol validation;
* protocol message types.

### Dispatcher

Owns:

* message routing;
* handler invocation;
* response selection.

The dispatcher MUST NOT implement Unix socket framing or JSON framing.

The dispatcher MUST NOT execute Slurm operations.

---

## 5. Dispatcher Interface

The dispatcher SHOULD expose a small interface.

Recommended form:

```go id="cx7x0q"
type Dispatcher interface {
    Dispatch(ctx context.Context, msg protocol.Envelope) protocol.Envelope
}
```

The exact implementation may use a concrete type such as:

```go id="s4z9ar"
type MessageDispatcher struct {
    handlers map[protocol.MessageType]Handler
}
```

The implementation MAY use a different internal structure, but the responsibilities SHALL remain the same.

---

## 6. Handler Interface

A handler SHOULD be responsible for one logical message type.

Recommended form:

```go id="xk7v1m"
type Handler interface {
    Handle(ctx context.Context, msg protocol.Envelope) protocol.Envelope
}
```

For Phase 1D:

```text id="4o1s7y"
hello-handler
ping-handler
```

are required.

Handlers for later functionality MAY be registered later.

The handler MUST receive an already decoded and validated envelope.

---

## 7. Message Routing

The dispatcher SHALL route messages by `Envelope.Type`.

Required Phase 1D behavior:

```text id="q5o3ch"
hello
   ↓
hello handler
   ↓
hello-response

ping
   ↓
ping handler
   ↓
pong
```

For known but unimplemented message types:

```text id="2kvx5w"
query
subscribe
unsubscribe
command
event
...
   ↓
not implemented response
```

The dispatcher MUST NOT silently discard a known message.

---

## 8. `hello` Handling

The `hello` handler SHALL return a `hello-response`.

Example request:

```json id="l1i7kw"
{
  "protocol": "cockpit-slurm",
  "version": "1.0",
  "messageId": "MSG001",
  "type": "hello",
  "payload": {
    "client": "cockpit-slurm-channel",
    "clientVersion": "0.1.0"
  }
}
```

Example response:

```json id="t2c4xk"
{
  "protocol": "cockpit-slurm",
  "version": "1.0",
  "messageId": "MSG002",
  "type": "hello-response",
  "payload": {
    "server": "cockpit-slurm-bridge",
    "serverVersion": "0.1.0"
  }
}
```

The response SHALL contain a new response `messageId`.

Phase 1D does not define message-ID generation. The implementation MAY use a simple local generator until the connection/session layer defines the final mechanism.

The `hello` handler SHALL NOT authenticate or authorize the client.

---

## 9. `ping` Handling

The `ping` handler SHALL return `pong`.

Example:

```text id="4k9d9x"
ping
  ↓
pong
```

The response SHALL use:

```text id="pr8s8k"
type = pong
```

and SHALL contain a valid protocol envelope.

No Slurm operation SHALL be performed.

---

## 10. Known-but-Unimplemented Messages

The dispatcher SHALL recognize protocol message types defined by Phase 1C but not implemented in Phase 1D.

Examples:

```text id="h01g9b"
query
query-response
subscribe
unsubscribe
command
command-response
command-status
event
```

These messages SHALL receive an explicit error response.

Example:

```json id="9f6d4g"
{
  "protocol": "cockpit-slurm",
  "version": "1.0",
  "messageId": "MSG003",
  "type": "error",
  "payload": {
    "code": "NOT_IMPLEMENTED",
    "message": "Message type 'query' is not implemented"
  }
}
```

The dispatcher SHALL NOT attempt to execute or emulate the operation.

---

## 11. Unknown Message Types

Messages that fail Phase 1C protocol validation because their type is unknown SHOULD normally be rejected by the protocol layer before reaching the dispatcher.

If an unknown type reaches the dispatcher, the dispatcher SHALL return:

```text id="h90x9d"
UNKNOWN_MESSAGE_TYPE
```

and SHALL NOT invoke a handler.

This provides defense in depth without moving protocol validation into the dispatcher.

---

## 12. Response Rules

Responses SHALL use the same `protocol.Envelope` structure defined in Phase 1C.

The response SHALL:

* use the negotiated/supported protocol version;
* contain a valid message type;
* contain a non-empty `messageId`;
* contain a JSON payload;
* pass protocol validation.

For request/response messages, the implementation SHOULD preserve a way to correlate the response with the request.

At this phase, correlation MAY be represented by the response payload or a future correlation field. The final correlation design SHALL be defined before implementing asynchronous commands/events.

---

## 13. Error Handling

The dispatcher SHALL distinguish between:

### Protocol errors

Examples:

```text id="0x2ocf"
INVALID_PROTOCOL
UNSUPPORTED_VERSION
INVALID_MESSAGE
UNKNOWN_MESSAGE_TYPE
INVALID_JSON
MESSAGE_TOO_LARGE
```

These belong to Phase 1C.

### Dispatcher errors

Examples:

```text id="s4y0qq"
NOT_IMPLEMENTED
HANDLER_ERROR
```

These belong to Phase 1D.

### Application/Slurm errors

These SHALL NOT be implemented in Phase 1D.

They belong to the later service/application layers and SHALL use the error model defined in `error-model.md`.

---

## 15. Implementation Requirements

The dispatcher implementation SHALL:

1. Accept a validated `protocol.Envelope`.
2. Determine the message type.
3. Locate the registered handler.
4. Invoke the handler.
5. Return a valid response envelope.
6. Return `NOT_IMPLEMENTED` for known-but-unimplemented types.
7. Return an appropriate error for unexpected/unknown types.
8. Never panic because of an invalid external message.
9. Never execute Slurm commands.
10. Never access the canonical resource cache.

Handler registration SHOULD occur during dispatcher initialization.

For example:

```text id="1jtpku"
NewDispatcher()
     │
     ├── register hello handler
     ├── register ping handler
     └── register future handlers
```

## 16. Test Requirements

### Dispatcher routing

```text id="z0h7qh"
[ ] hello routes to hello handler
[ ] ping routes to ping handler
[ ] known unimplemented type returns NOT_IMPLEMENTED
[ ] unknown type returns UNKNOWN_MESSAGE_TYPE
```

### `hello`

```text id="s8kqg1"
[ ] hello produces hello-response
[ ] response has valid envelope
[ ] response has non-empty messageId
[ ] response payload is valid JSON
```

### `ping`

```text id="31x2p7"
[ ] ping produces pong
[ ] pong has valid envelope
[ ] pong payload is valid JSON
```

### Error handling

```text id="n9rj0c"
[ ] unimplemented query returns NOT_IMPLEMENTED
[ ] unimplemented subscribe returns NOT_IMPLEMENTED
[ ] unimplemented command returns NOT_IMPLEMENTED
[ ] handler error produces protocol error response
```

### Isolation

```text id="yk6w3s"
[ ] dispatcher does not access Slurm
[ ] dispatcher does not access cache
[ ] dispatcher does not require UserContext
[ ] dispatcher does not require a Unix socket
```

The dispatcher unit tests SHOULD use `protocol.Envelope` values directly rather than requiring a live Unix socket.

Phase 1D is complete when:

* [ ] Dispatcher package exists.
* [ ] Handler registration/routing works.
* [ ] `hello` → `hello-response` works.
* [ ] `ping` → `pong` works.
* [ ] Known-but-unimplemented messages return `NOT_IMPLEMENTED`.
* [ ] Unknown message types are handled safely.
* [ ] Dispatcher responses pass protocol validation.
* [ ] Dispatcher unit tests pass.
* [ ] Existing Phase 1B and Phase 1C tests continue to pass.
* [ ] `go test ./...` passes.
* [ ] `go vet ./...` passes.
* [ ] Dispatcher has no Slurm dependency.
* [ ] Dispatcher has no cache dependency.
* [ ] Dispatcher has no authorization dependency.
* [ ] Dispatcher has no UserContext dependency.
* [ ] No session-management logic has been introduced.

## 18. Phase 1E Boundary

Phase 1E SHALL introduce the **connection/session and identity layer**.

The expected architecture becomes:

```text id="tqj9vf"
Unix socket
    │
    ▼
   IPC
    │
    ▼
 Protocol
    │
    ▼
 Dispatcher
    │
    ▼
 Connection / Session
    │
    ├── connection identity
    ├── UserContext
    ├── Linux UID/GID
    ├── groups
    └── Slurm AdminLevel
```

Phase 1E SHALL address:

* connection/session state;
* client identity;
* Linux peer credentials;
* `UserContext`;
* Slurm identity;
* authorization context;
* connection lifecycle.

Phase 1E SHALL NOT yet implement the full Slurm resource/service layer unless explicitly specified by its implementation plan.

The architectural sequence is:

```text id="9u4h0d"
Phase 1B
Unix socket transport
       ↓
Phase 1C
Protocol
       ↓
Phase 1D
Dispatcher
       ↓
Phase 1E
Connection / Session / UserContext
       ↓
Later phases
Slurm services / cache / commands / events
```
