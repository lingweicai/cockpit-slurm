# Integration of Frontend and Backend for Development v3.6

# 1. Purpose

This document defines the implementation of the **frontend/backend integration milestone** for `cockpit-slurm` Version 3.6.

This document is an implementation document under:

* `0.1 development-cockpit-slurm-_v3.6.md`
* `1.0 implementation-plan-v3.6.md`

The Version 3.6 architecture document is normative for architectural decisions.

The Version 3.6 implementation plan defines the overall implementation sequence.

This document defines the implementation details for **Phase 2 / Milestone M2 — Frontend/Backend Integration**.

The objective is to prove that the React frontend can communicate directly with the persistent `cockpit-slurm` backend through Cockpit's `cockpit.channel()` API, without the `cockpit-slurm-channel` executable.

---

# 2. Integration Objective

The target communication path is:

```text
┌──────────────────────────────┐
│ React Frontend               │
│                              │
│ cockpit.channel()            │
└──────────────┬───────────────┘
               │
               │ Cockpit stream
               ▼
┌──────────────────────────────┐
│ Cockpit                      │
│                              │
│ cockpit-bridge / transport   │
└──────────────┬───────────────┘
               │
               │ Unix socket
               ▼
┌──────────────────────────────┐
│ cockpit-slurm                │
│                              │
│ Persistent Backend            │
│ IPC Server                   │
└──────────────────────────────┘
```

The following component is **not** part of the Version 3.6 integration path:

```text
cockpit-slurm-channel
```

The backend application itself owns the application-level IPC protocol.

---

# 3. Relationship to Version 3.5

Version 3.5 used an intermediate channel process:

```text
React
  │
  │ cockpit.channel()
  ▼
cockpit-slurm-channel
  │
  │ Unix socket
  ▼
cockpit-slurm backend
```

Version 3.6 removes that process:

```text
React
  │
  │ cockpit.channel()
  ▼
Cockpit
  │
  │ Unix socket
  ▼
cockpit-slurm
```

Therefore, the purpose of this integration milestone is not to create another channel process.

The purpose is to verify that Cockpit itself can provide the required transport between the frontend and the persistent backend.

## 4.1 Included

```text

```

and:

```text

```

or an equivalent protocol message defined by the application protocol.

# 5. Architectural Boundaries

The integration must preserve the following boundaries.

## 5.1 Cockpit is the transport

Cockpit provides the channel transport:

```text
cockpit.channel()
```

Cockpit does not own Slurm application state.

---

## 5.2 cockpit-slurm owns application semantics

The backend owns:

* application protocol;
* message validation;
* message IDs;
* request/response handling;
* UserContext;
* authorization;
* resource state;
* commands;
* subscriptions.

---

## 5.3 React owns presentation

React owns:

* UI state;
* rendering;
* frontend providers;
* user interaction;
* presentation of backend responses.

React must not implement Slurm authorization rules.

---

# 6. Application Protocol Versus Cockpit Protocol

The Version 3.6 application protocol remains independent of the Cockpit protocol.

There are therefore two layers:

```text
┌──────────────────────────────────────┐
│ Cockpit channel transport            │
│                                      │
│ cockpit.channel({ payload: "stream" })│
└───────────────────┬──────────────────┘
                    │
                    │ byte stream
                    ▼
┌──────────────────────────────────────┐
│ cockpit-slurm application protocol   │
│                                      │
│ length-prefixed application frames   │
└──────────────────────────────────────┘
```

Cockpit must not be treated as the application message boundary.

---

# 7. Stream Framing Requirement

A Cockpit stream is a byte stream.

Therefore, one call to:

```typescript
channel.onmessage
```

must not be assumed to represent exactly one `cockpit-slurm` application message.

For example, one application frame may arrive as:

```text
chunk 1
chunk 2
chunk 3
```

Alternatively, several application frames may arrive in one received chunk:

```text
frame 1 + frame 2 + frame 3
```

The frontend therefore requires an application-frame decoder.

The backend already uses the application protocol framing defined by the Version 3.5 protocol work.

The Version 3.6 integration must preserve that protocol.

---

# 8. Application Frame

The Version 3.6 application frame remains length-prefixed.

Conceptually:

```text
┌──────────────────┬─────────────────────────┐
│ frame length     │ JSON application frame  │
└──────────────────┴─────────────────────────┘
```

The JSON envelope may contain:

```json
{
  "protocol": "cockpit-slurm",
  "version": "1.0",
  "messageId": "01...",
  "type": "request",
  "payload": {}
}
```

The exact fields must follow the existing Version 3.6 protocol contract.

The integration implementation must not introduce a second application framing scheme.

---

# 9. Unix Socket

## 9.1 Production socket

The Version 3.6 system installation uses:

```text
/run/cockpit-slurm/cockpit-slurm.sock
```

This is the authoritative production socket.

The socket belongs to the persistent `cockpit-slurm` backend service.

---

## 9.2 Development socket

A user-local socket may be supported for development and testing.

A recommended path is:

```text
/run/user/<uid>/cockpit-slurm/cockpit-slurm.sock
```

or another explicitly configured development path.

The development socket must be selected by the **installation/configuration mode**, not by checking whether the current user belongs to `wheel`.

---

## 9.3 No wheel-based socket selection

The backend must not contain logic such as:

```text
if user belongs to wheel:
    use system socket
else:
    use user socket
```

Membership in `wheel` is not the architectural criterion for selecting the transport endpoint.

The socket path is determined by:

```text
installation mode
       │
       ├── system installation
       │
       └── development/user installation
```

User identity is handled separately through the authenticated Cockpit session and server-side peer credentials.

---

# 10. Socket Permissions

For the system installation, the socket must permit the intended Cockpit users to connect.

The recommended model is:

```text
Owner:  cockpit-slurm
Group:  cockpit-slurm
Mode:   0660
```

or an equivalent group/security policy appropriate for the deployment.

The exact group policy should be finalized during system installation.

The backend must not rely on frontend claims of identity.

The backend obtains the peer identity from the Unix connection and constructs the appropriate `UserContext`.

---

# 11. Systemd Service

The persistent backend remains a systemd service.

A development version of the service should be conceptually equivalent to:

```ini
[Unit]
Description=Cockpit Slurm Persistent Service
After=slurmctld.service
Wants=slurmctld.service

[Service]
Type=simple
ExecStart=/usr/local/bin/cockpit-slurm
Restart=on-failure
RestartSec=5

User=cockpit-slurm
Group=cockpit-slurm

RuntimeDirectory=cockpit-slurm
RuntimeDirectoryMode=0750

[Install]
WantedBy=multi-user.target
```

The exact service dependencies and installation paths must follow the Version 3.6 architecture and deployment requirements.

The systemd service is responsible for keeping the backend alive independently of Cockpit frontend sessions.

---

# 12. Backend IPC Server

## 12.1 Responsibility

The backend IPC server is responsible for:

* creating/listening on the Unix socket;
* accepting connections;
* reading application frames;
* validating frame lengths;
* decoding application messages;
* creating a connection context;
* passing messages to the dispatcher;
* sending application responses;
* handling connection closure;
* cleaning up the connection.

It must not contain React-specific logic.

---

## 12.2 Connection lifecycle

The expected lifecycle is:

```text
Accept
  │
  ▼
Create Connection
  │
  ▼
Establish Peer Identity
  │
  ▼
Create UserContext
  │
  ▼
Read Application Frames
  │
  ▼
Dispatch Messages
  │
  ▼
Write Application Frames
  │
  ▼
Connection Closed
```

# 15. Frontend Cockpit Channel

The frontend should create a Cockpit stream channel.

Conceptually:

```typescript
const channel = cockpit.channel({
    payload: "stream",
    unix: "/run/cockpit-slurm/cockpit-slurm.sock",
    binary: true,
});
```

Cockpit documents `binary: true` as the mechanism for transferring binary payloads, with channel send/receive data represented as byte arrays such as `Uint8Array`.

The implementation must use the Cockpit API version available on the supported development platform.

The integration should not use:

```typescript
binary: "raw"
```

as the Version 3.6 contract.

---

# 16. Frontend Transport Layer

The frontend should isolate Cockpit channel handling from React components.

A recommended structure is:

```text
src/
└── ipc/
    ├── channel.ts
    ├── framing.ts
    ├── client.ts
    └── types.ts
```

---

## 16.1 `channel.ts`

Responsibilities:

* create `cockpit.channel()`;
* configure the Unix socket;
* configure binary mode;
* send bytes;
* receive bytes;
* handle channel close;
* expose connection state.

It must not know Slurm resource semantics.

---

## 16.2 `framing.ts`

Responsibilities:

* encode application frames;
* decode application frames;
* buffer incomplete frames;
* process multiple frames in one received chunk;
* validate frame lengths;
* reject malformed frames.

This is the frontend counterpart of the backend protocol framing implementation.

---

## 16.3 `client.ts`

Responsibilities:

* create message IDs;
* send requests;
* correlate responses;
* handle application errors;
* expose request promises or equivalent APIs;
* manage connection-level state.

React components should use this client rather than calling `cockpit.channel()` directly.

---

The frontend must handle at least:

# 20. No Automatic User-Socket Fallback

The Version 3.6 integration must not automatically perform:

```text
system socket
      │
      │ failed
      ▼
user socket
```

based on the current user's UID.

This creates two different runtime architectures and makes deployment behavior difficult to reason about.

Instead:

### System installation

Use:

```text
/run/cockpit-slurm/cockpit-slurm.sock
```

### Development installation

Explicitly configure the development socket.

The frontend should receive the socket path from the build/development configuration rather than determining it from `wheel` membership.

---

# 21. Socket Configuration

The socket path should be represented as configuration.

For example:

```typescript
const SLURM_SOCKET_PATH =
    process.env.COCKPIT_SLURM_SOCKET ??
    "/run/cockpit-slurm/cockpit-slurm.sock";
```

The exact implementation depends on the project's build system.

The important rule is:

```text
socket path = installation/development configuration
```

not:

```text
socket path = user privilege inference
```

---

# 22. Makefile Changes

The Makefile must support both:

### System installation

```text
/usr/local/bin/cockpit-slurm
/run/cockpit-slurm/cockpit-slurm.sock
```

### Development installation

```text
user-local executable
user-local runtime socket
```

The exact paths should be configurable rather than duplicated throughout the Makefile and source code.

Suggested variables:

```make
PREFIX ?= /usr/local
SYSCONFDIR ?= /etc
RUNDIR ?= /run/cockpit-slurm
```

Development overrides may provide:

```make
PREFIX=$(HOME)/.local
RUNDIR=/run/user/$(UID)/cockpit-slurm
```

The frontend must not be trusted for:

* username;
* GID;
* AdminLevel;
* Coordinator;

# 37. Architectural Rule

The central rule for this integration is:

> **Cockpit transports application bytes; `cockpit-slurm` owns application semantics.**

Therefore:

```text
Cockpit
    = transport

cockpit.channel()
    = frontend transport API

Unix socket
    = transport endpoint

cockpit-slurm protocol
    = application protocol

cockpit-slurm
    = application/backend

React
    = presentation and frontend state
```

No component should blur these boundaries.
