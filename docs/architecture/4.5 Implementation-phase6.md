# cockpit-slurm Implementation Phase 6 — Resource System Generalization

## 1. Purpose

Phase 6 generalizes the proven Node implementation from Phases 3–5 into reusable resource infrastructure without replacing working behavior or designing a universal Slurm resource model in advance.

Phase 3 established Node queries and the authoritative backend cache. Phase 4 added Node synchronization, events, and the automatic per-connection stream. Phase 5 added Node commands, server-derived identity, capability-based authorization, command lifecycle handling, and post-command synchronization.

Phase 6 extracts the reusable mechanisms from that working vertical slice and validates them with **Node plus Job**.

The governing principle is:

> Generalize the infrastructure around resources; keep canonical resource models, adapters, and domain rules resource-specific.

The target is not to implement every Slurm resource. It is to demonstrate that a second resource can use the same backend resource infrastructure while existing Node reads, live updates, commands, and authorization continue to work.

The v3.6 architecture and accepted Phase 4/5 specifications govern over conflicting older proposed or v3.5 documentation. Phase 4 defines an automatic per-connection Cockpit stream: there are no application-level `subscribe` or `unsubscribe` messages and no `subscriptionId`. Keep the backend stream registry/fan-out needed to deliver events to connected clients; do not implement a second application subscription protocol.

If an implementation conflicts with those governing contracts, preserve the accepted protocol and security invariants. Do not silently introduce a contract change; document and review any necessary change before implementation.

Before changing code, inspect the current repository and these documents. Reuse the existing implementation and names where they already satisfy the requirements. Do not create duplicate services, caches, registries, or protocol definitions just to match illustrative names in this document.

## 3. Phase 6 objective

Extract and validate the reusable resource mechanisms:

- resource identity and resource-kind registration;
- canonical resource storage and lookup;
- generation and update metadata;
- indexes and snapshots;
- semantic change detection;
- resource synchronization and refresh;
- event publication after successful cache updates;
- per-connection event stream registration, fan-out, and initial snapshot delivery;
- query request/response handling;
- preservation of Phase 5 command handling and capability-based authorization;
- frontend IPC/client abstractions needed by resource-specific providers.

Phase 6 may generalize shared request-dispatch and operation-lookup mechanisms only where the existing Node query/command implementation demonstrates a concrete common need. Query execution and command execution MUST remain separate paths, and all accepted Phase 5 command guarantees MUST be preserved.

The backend Resource Cache remains the authoritative in-memory application state. Frontend providers maintain client-side state for presentation and must not become a second authoritative cache.

## 4. Scope

### 4.1 In scope

1. Review the accepted Node implementation and identify the reusable mechanisms actually demonstrated by Phases 3–5.
2. Extract generic backend infrastructure incrementally from the working Node path.
3. Keep the Node adapter, canonical Node model, Node-specific query behavior, and Node command definitions resource-specific.
4. Add a Job resource vertical slice using the generalized infrastructure.
5. Support Job snapshot/query and change delivery through the shared cache/event/per-connection stream mechanisms.
6. Keep command authorization and execution backend-authoritative.
7. Preserve the existing application IPC envelope, framing, correlation, event semantics, and error model unless a separately reviewed contract change is required.
8. Add unit, integration, regression, and end-to-end tests for the generalized infrastructure and Job vertical slice.
9. Update architecture/implementation documentation where actual implementation findings require it.

### 4.2 Explicitly out of scope

Phase 6 MUST NOT expand into:

- full Job command support, including submit, cancel, suspend, or resume;
- User, Account, Association, Partition, Reservation, QOS, or Cluster resource implementation beyond any minimal shared types needed by existing code;
- a complete administrative UI or role-driven navigation;
- a new generic frontend resource framework;
- a second authoritative frontend cache;
- frontend execution of Slurm CLI commands or business rules;
- frontend authorization as a security boundary;
- replacing the current IPC transport or adding another socket/channel;
- replacing the accepted Phase 5 command protocol, authorization model, or ledger without an explicit design review;
- broad production-hardening work unrelated to correctness of the generalized resource path.

These items belong to later milestones where appropriate.

Phase 6 MUST NOT introduce a universal CRUD command model for all resources. Commands MUST use explicit resource-scoped operation IDs (for example, `node.drain` and `node.resume`). An operation category such as create, update, delete, lifecycle, or query may be classification metadata only; it MUST NOT replace the explicit operation ID. Read operations such as `show` belong to the query path.

## 5. Required architecture

The backend should retain the following conceptual flow:

```text
Slurm
  │
  ├── Node Adapter ──> Canonical Node ──┐
  │                                     │
  └── Job Adapter ───> Canonical Job ───┤
                                        ▼
                               Resource Infrastructure
                              ├── Resource Registry
                              ├── Resource Cache
                              ├── Indexes and Snapshots
                              ├── Change Detection
                              ├── Event Bus
                              ├── Per-connection Stream Registry
                              ├── Query Service
                              └── Phase 5 Node Command Path (preserved)
                                        │
                                        ▼
                                Dispatcher / IPC
                                        │
                                        ▼
                                  React clients
                              ├── NodeProvider
                              └── JobProvider
```

The diagram is conceptual. Preserve the current repository's package layout where practical. Do not create a single large service that absorbs adapter logic, authorization, protocol handling, and UI behavior.

### 5.1 Ownership boundaries

**Resource-specific code owns:**

- canonical domain model;
- Slurm-specific data acquisition and parsing;
- resource-specific identity and keys;
- resource-specific indexes where needed;
- semantic comparison rules where generic comparison is insufficient;
- supported operations and their parameter validation;
- resource-specific authorization requirements;
- frontend columns, formatting, and presentation.

**Shared backend infrastructure owns:**

- resource-kind registration and lookup;
- common resource metadata conventions;
- safe cache operations and consistent snapshots;
- generation/update bookkeeping;
- event publication ordering;
- per-connection stream lifecycle and delivery;
- common query dispatch;
- common protocol validation, error handling, and request correlation;
- a consistent operation-registration/lookup pattern where justified by existing query and command use cases;
- preservation of the accepted Phase 5 Node command and authorization lifecycle.

Query and command dispatch MUST remain separate. Query handlers own resource-specific read behavior; command handlers own resource-specific mutation and lifecycle behavior. Shared infrastructure MUST NOT bypass or weaken command-specific authorization, ledger/deduplication, lifecycle, audit, or execution controls.

**Frontend services remain transport/client abstractions.** They may send requests, receive responses/events, correlate messages, and expose typed APIs. They MUST NOT own Slurm business rules, execute Slurm commands, make authoritative authorization decisions, or duplicate backend synchronization logic.

## 6. Resource contract and canonical models

### 6.1 Resource identity

Define or consolidate a shared resource identity contract only to the extent supported by the existing implementation. It should make the resource kind and stable resource key explicit.

Requirements:

- Node and Job identities MUST be unambiguous.
- Resource keys MUST be stable for the lifetime of the represented entity according to Slurm semantics.
- The implementation MUST NOT assume every resource is keyed by a single string if a resource requires a compound identity.
- Cache lookup and event routing MUST use the same identity rules.
- Resource identity MUST NOT be inferred from frontend display labels.

Examples of domain identity (illustrative, not a mandate to change existing key formats):

- Node: node name.
- Job: the composite tuple defined below.

#### Initial Job identity and population

The `cluster` identity component comes from backend cluster configuration, never from client input. If the Slurm response includes a cluster name, it MUST match that configured value; a mismatch invalidates the complete snapshot.

Phase 6 initially represents active queue entries only. The Job adapter MUST invoke an unfiltered `squeue --json` query against the configured Slurm cluster using the approved backend service identity and normalize its response through the generated Slurm OpenAPI Job representation; it MUST NOT use `sacct` or another accounting/history source as a fallback. The complete cluster-wide active Job set returned to that backend query defines the population for this phase; if the service identity or response cannot establish a complete cluster-wide snapshot, reject the refresh rather than treating a partial result as complete. Completed-job history is out of scope.

The canonical Job identity MUST be the typed tuple `(cluster, job_id, array_job_id, array_task_id)`. `cluster` and `job_id` are required. Array identifiers retain Slurm's value/set semantics; an unset/no-value field is represented as absent and MUST NOT be coerced to zero or to a sentinel integer. A normal Job has both array fields absent; an array element has both present; an array parent/placeholder may have `array_job_id` present and `array_task_id` absent. `array_task_id` present without `array_job_id` is invalid. The cache key and serialized Job identity MUST encode the tuple unambiguously. Reject records with missing required identity fields, invalid array identity combinations, or duplicate tuple keys in one snapshot.

The adapter MUST reject a response as incomplete if the command fails, JSON/schema decoding fails, Slurm reports response errors, the `jobs` collection is missing or malformed, or any record fails identity/model validation. Such a response MUST NOT mutate the cache or cause deletions. A complete valid snapshot may be empty; after that snapshot is committed, any previously cached Job not present in it is a confirmed deletion. No partial or incremental Job synchronization is supported in Phase 6. The complete serialized snapshot MUST fit the existing IPC message-size limit; if it does not, reject it without truncation, cache commit, or deletion events. Snapshot chunking is out of scope.

### 6.2 Shared metadata

Where appropriate, canonical resources should expose consistent metadata such as:

- resource kind;
- stable resource identity;
- generation or version;
- update timestamp;
- source/provenance when useful for diagnostics.

Reuse existing fields and wire representations when they already meet the accepted contract. Do not introduce redundant generation counters or competing timestamps.

### 6.3 Resource-specific canonical models

Node and Job MUST remain distinct canonical models.

A Job model may contain job ID, owner, state, partition, allocated resources, submit/start/end times, and other fields supported by the current Slurm version and chosen adapter. This list is illustrative; use the repository's existing generated Slurm API types and domain decisions where appropriate.

The frontend MUST NOT depend on raw CLI output. Slurm-specific parsing and normalization belong in adapters.

Do not force Node and Job into one union of fields or make resource-specific fields optional merely to make all models appear identical.

## 7. Resource registration and adapter boundaries

Introduce or consolidate a registry for resource-kind-specific behavior if the current code does not already provide an equivalent mechanism.

The registry should make it possible for the shared infrastructure to identify the adapter/model behavior for a resource kind without embedding Node-specific or Job-specific branching throughout generic services.

Requirements:

- Register Node and Job explicitly.
- Reject unknown resource kinds with a defined protocol/application error.
- Detect duplicate or invalid registrations during initialization or tests.
- Keep adapter initialization and resource registration deterministic.
- Do not use reflection or untyped `any` as a shortcut for avoiding resource-specific types.
- Do not turn the registry into a container for unrelated application services.

The resource adapter is responsible for obtaining Slurm data and translating it into canonical resources. The cache and event infrastructure must not invoke Slurm CLI commands directly.

## 8. Resource cache, snapshots, and change detection

The backend cache remains the sole authoritative in-memory application state.

The generalized cache MUST support the operations required by both Node and Job:

- insert or update a canonical resource;
- remove a resource when authoritative synchronization confirms deletion;
- retrieve an individual resource by its identity;
- enumerate/query resources using supported indexes and filters;
- produce a consistent snapshot for a query or per-connection stream baseline;
- maintain resource generation/update metadata;
- determine whether a newly synchronized resource is semantically changed.

Requirements:

1. A generation MUST advance according to the established contract when the represented resource state changes.
2. A semantically unchanged refresh MUST NOT generate a false update event.
3. Snapshot contents and their generation/baseline MUST be mutually consistent.
4. A failed refresh or parse MUST NOT partially corrupt the authoritative cache.
5. Events MUST NOT be published before the corresponding cache mutation succeeds.
6. Resource deletion MUST be based on a completed, authoritative synchronization result—not a partial or failed read.
7. Concurrent reads and refreshes MUST be race-safe.
8. Indexes MUST remain consistent with inserts, updates, and deletes.
9. Resource-specific equality must account for semantic fields, not incidental output ordering or formatting.
10. The cache MUST NOT store UI state, form state, pending commands, or client-supplied identity claims.

Use the existing Node generation and snapshot/event contract as the reference. Node and Job maintain independent collection generations, each advancing once per changed complete snapshot. Do not silently redefine generation or event-sequence semantics during extraction.

## 9. Synchronization and event delivery

### 9.1 Synchronization

Keep resource acquisition separate from generic cache/event infrastructure.

Node synchronization MUST continue to behave as it did at the end of Phase 5. Add a Job synchronization path using `squeue --json` that normalizes active Job records and updates the same generalized infrastructure.

The implementation MUST define how each adapter reports:

- a successful complete snapshot;
- a successful partial/incremental update, if supported (Job partial updates are not supported in this phase);
- a transient acquisition failure;
- malformed or unparseable data;
- a confirmed deletion.

Do not interpret an acquisition failure as an empty resource collection.

### 9.2 Event ordering

For both Node and Job:

```text
authoritative Slurm observation
        ↓
canonicalization
        ↓
successful cache mutation
        ↓
resource change event
        ↓
each connected stream's bounded queue
        ↓
serialized IPC delivery
        ↓
frontend provider update
```

Events describe committed cache state, not guesses about what a command probably changed.

Preserve the Phase 4 guarantees for atomic stream baseline registration, event sequencing, bounded/serialized writes, disconnect cleanup, and recovery. Reuse those guarantees for Job rather than creating a separate event mechanism. Each connected IPC connection receives the initial Node and Job snapshots, followed by committed Node and Job change batches on the same `type: "event"` envelope. Resource-specific providers ignore event payloads for other resource kinds.

### 9.3 Per-connection stream behavior

The generalized stream infrastructure MUST preserve the Phase 4 contract:

- one automatically registered resource stream per IPC connection;
- an initial snapshot for each supported resource kind;
- subsequent committed changes using the existing event envelope and resource discriminator;
- atomic snapshot baseline and event publication ordering;
- bounded, serialized writes and cleanup on disconnect;
- generation-gap detection and the established reconnect/snapshot recovery behavior.

Phase 6 MUST NOT add application-level `subscribe` or `unsubscribe` messages, `subscriptionId`, client-selected resource filters, or a second stream format. The stream lifetime is the IPC connection lifetime; do not assume an IPC connection ID and a logical Cockpit session ID are interchangeable. Backend authorization remains server-side and connection-scoped.

Preserve the Phase 4 `type: "event"` format and add Job payloads through its established resource discriminator. Do not introduce a second Job-only wire format.

## 10. Query infrastructure

Generalize common query processing without making resource-specific query semantics identical.

The shared query path should validate the envelope and common request metadata, resolve the resource kind, invoke the correct resource query/cache behavior, and return the established response/error structure with message correlation preserved.

Requirements:

- Node query requests and responses remain compatible with the accepted contract.
- Job queries return canonical Job data, not raw CLI output.
- Unknown resource kinds, malformed filters, unsupported query options, and invalid identifiers fail explicitly.
- Pagination, filtering, and sorting MUST be implemented only where their semantics are defined and tested; do not imply support that an adapter does not provide.
- Query behavior MUST not bypass the backend cache with ad hoc Slurm calls unless the architecture explicitly defines a separate operation requiring live acquisition.
- Existing protocol framing, size limits, message IDs, and error object shape remain unchanged.

## 11. Command infrastructure and authorization

Phase 6 MUST preserve the Phase 5 Node command and authorization path, but MUST NOT refactor or generalize command infrastructure speculatively. Job mutations are out of scope, so Phase 6 has no second command resource that could validate such an abstraction. Keep Node operations, validation, authorization, ledger behavior, execution boundary, and lifecycle unchanged except for fixes required by a failing regression test and separately reviewed.

Security requirements:

1. The backend remains the authorization authority.
2. Identity is derived from the initialized server-side connection, never from command payload fields.
3. Unknown or unresolved identity fails closed.
4. Every operation declares its required capability or equivalent accepted authorization metadata.
5. Authorization is enforced before privileged execution.
6. A frontend capability response is advisory UI data, not an authorization grant.
7. The accepted Phase 5 command lifecycle, error contract, and durable deduplication guarantees MUST remain intact.
8. Do not broaden daemon privileges or change the privileged-execution mechanism as a side effect of resource generalization.

Job commands such as submit, cancel, suspend, and resume are explicitly out of scope for this phase. They can be designed after the shared infrastructure and Job read path are accepted.

## 12. IPC and protocol compatibility

The current `cockpit.channel()` stream to the existing `cockpit-slurm` Unix socket remains the transport path. The application protocol remains independent of Cockpit message boundaries.

Phase 6 MUST NOT introduce:

- `cockpit-slurm-channel`;
- a second Unix socket or transport;
- a resource-specific framing format;
- frontend `cockpit.spawn()` for Slurm commands;
- a second application protocol for Job.

Preserve the accepted envelope, length-prefixed framing, maximum frame size, request correlation, command lifecycle messages, error object structure, and event contracts.

Cockpit stream chunks may split or combine application frames. Existing framing/reassembly tests remain mandatory.

## 13. Frontend integration boundary

Phase 6 should add only the frontend client/provider integration needed to prove the Job read/live-update vertical slice and preserve Node behavior.

- Reuse the existing IPC client and frontend resource/query/stream handling.
- Keep frontend services as transport/client abstractions, not business-logic services.
- Keep NodeProvider and JobProvider responsible for their respective client-side resource state.
- Use strict TypeScript types; do not use `any` to bypass model differences.
- Do not add a generic frontend resource framework or broad navigation/page redesign in Phase 6.
- Do not let the frontend infer successful resource state from a command response; authoritative state comes from the backend cache and event stream.
- Preserve existing PatternFly conventions and the current application structure.

## 14. Suggested implementation order

Complete these steps in order, making small reviewable changes.

### Stage A — Audit and baseline

1. Read the normative architecture, implementation plan, and Phase 1–5 implementation documents.
2. Inspect the actual Node adapter, canonical model, cache, synchronizer, stream registry, query path, command service, authorization path, IPC protocol, and frontend provider.
3. Record which mechanisms are already generic and which contain Node-specific assumptions.
4. Run the existing Go, TypeScript, lint, and relevant integration tests before refactoring.
5. Establish regression tests for accepted Phase 5 Node behavior.

**Exit condition:** the proposed extraction plan maps to real code and does not duplicate existing abstractions.

### Stage B — Extract shared backend resource infrastructure

1. Introduce or consolidate resource-kind registration and common identity/metadata handling.
2. Generalize cache operations, indexing, snapshots, generation bookkeeping, and semantic change detection.
3. Generalize synchronization-to-cache update and event publication ordering.
4. Reuse and generalize the existing per-connection stream registry/fan-out; do not add application subscription messages or IDs.
5. Generalize query dispatch while preserving the Node wire contract.
6. Keep adapters and canonical models resource-specific.
7. Identify shared request-dispatch or operation-lookup logic between query and command paths; extract only common mechanisms justified by existing code.
8. Do not generalize command definitions for Jobs or other resources, and do not redesign the Phase 5 command framework solely for anticipated future operations.
9. Do not introduce Go generics or a merged query/command dispatcher solely because both request payloads contain a resource field; require a concrete shared behavior and preserve their distinct contracts.

**Exit condition:** Node uses the generalized path and all Phase 3/4/5 regression tests still pass.

### Stage C — Phase 5 command and authorization regression gate

The accepted Node command path remains the behavioral baseline. A limited infrastructure extraction is allowed only if Stage B identifies concrete duplication and all Phase 5 invariants remain unchanged.

1. Add or retain focused regression tests for the accepted Phase 5 Node command and authorization behavior.
2. Verify server-derived identity, fresh capability checks, audit context, command IDs, ledger/deduplication, and failure semantics remain unchanged.
3. Verify unknown operations and unauthorized requests cannot reach the executor.
4. Do not change resource-specific command definitions, semantics, or execution behavior.

**Exit condition:** all accepted Phase 5 Node command and authorization regression tests pass with no privilege expansion or semantic redesign. Any shared mechanism is limited to dispatch/lookup/validation conventions justified by existing Node code.

### Stage D — Add Job query and live-update vertical slice

1. Implement the Job adapter and canonical Job model using `squeue --json` for active Jobs only.
2. Register Job with the shared resource infrastructure.
3. Populate and refresh Job data without treating acquisition failure as an empty collection.
4. Add Job snapshot/query behavior.
5. Deliver Job changes through the shared cache/event/per-connection stream path.
6. Add the minimal typed frontend client/provider integration required to display and update Job state.
7. Keep Job mutation commands out of scope.

**Exit condition:** a real Job snapshot and subsequent Job changes reach the frontend through the same IPC, cache, and per-connection stream architecture used by Node.

### Stage E — Verification and documentation

1. Run all relevant unit, integration, regression, and end-to-end tests.
2. Review protocol compatibility and security invariants.
3. Update documentation to describe the actual generalized implementation, not planned abstractions that were not implemented.
4. Record known limitations and defer unrelated work to the correct later phase.

**Exit condition:** the acceptance checklist below is satisfied and the Phase 6 implementation is ready for review.

## 15. Testing requirements

### 15.1 Resource registry and model tests

- Node and Job register successfully.
- Duplicate/invalid registrations fail deterministically.
- Unknown resource kinds produce a defined error.
- Node and Job identity rules remain distinct and stable.
- Job identity tests cover normal Jobs, array elements, array parent/placeholders, missing required fields, and duplicate composite keys.
- Canonicalization rejects malformed source data without corrupting the cache.

### 15.2 Cache and generation tests

- Insert, update, lookup, list/query, and delete work for Node and Job.
- Indexes remain consistent after each mutation.
- Semantically unchanged refreshes do not emit false update events.
- Real semantic changes update generation according to the existing contract.
- Failed/partial refreshes do not erase valid cached resources.
- Failed commands, Slurm response errors, missing/malformed `jobs` collections, invalid Job records, duplicate keys, and oversized snapshots leave the Job cache unchanged and emit no deletion events.
- A complete valid empty Job snapshot removes previously cached active Jobs and emits the corresponding committed deletion changes.
- Snapshots are internally consistent under concurrent reads and refreshes.
- Race tests cover cache and synchronization paths.

### 15.3 Event and stream tests

- Cache mutation succeeds before the event is published.
- Node and Job events use the same per-connection stream and established resource discriminator.
- Initial snapshots and subsequent events do not lose or reorder changes under the established contract.
- Disconnect removes the connection's stream and associated resources.
- Event sequence gaps trigger the existing recovery behavior.
- Slow clients and write failures follow the existing bounded-queue and cleanup behavior.

### 15.4 Query and protocol tests

- Node protocol fixtures remain unchanged unless a reviewed contract change is approved.
- Job query returns canonical models and correct correlation IDs.
- Unknown resources, invalid filters, malformed frames, and unsupported operations return explicit errors.
- Arbitrary stream chunk boundaries do not corrupt frame decoding.
- Maximum frame-size and malformed-envelope protections remain effective.

### 15.5 Command and authorization regression tests

- Existing Node commands still succeed or fail according to their declared capabilities.
- Unresolved identity and unknown capabilities fail closed.
- Payload fields cannot override caller identity or capabilities.
- Unauthorized requests never reach the command executor.
- Duplicate command IDs retain the Phase 5 behavior, including denial and persistence-failure semantics.
- Command responses/statuses and resource events coexist without interleaved IPC frames.
- Command success does not directly mutate frontend resource state; authoritative state arrives through synchronization and cache events.

### 15.6 End-to-end tests

At minimum, verify:

1. Node snapshot → NodeProvider.
2. Node change → cache → event/connection stream → NodeProvider.
3. Authorized Node command → Slurm mutation → synchronization → cache → Node event → NodeProvider.
4. Job snapshot → JobProvider.
5. Job change → cache → event/connection stream → JobProvider.
6. Unauthorized Node command is denied by the backend.
7. Node and Job traffic can coexist on the same transport without corrupting messages; each provider applies only its own resource events.

Use deterministic fixtures for unit tests and real Slurm/Cockpit integration tests where the target environment is required. Clearly label tests that require a configured Slurm cluster.

## 17. Definition of done

Phase 6 demonstrates that the system is no longer a Node-only implementation with generic names: **Node and Job use genuinely shared resource infrastructure while retaining distinct canonical models and adapters.**

The completed system preserves the Phase 5 Node command/authorization vertical slice and supports this end-to-end flow for both resources:

```text
Slurm
  ↓
Resource-specific adapter
  ↓
Canonical resource
  ↓
Shared authoritative cache
  ↓
Shared query / event / per-connection stream infrastructure
  ↓
Existing IPC protocol and transport
  ↓
Resource-specific frontend provider
  ↓
React presentation
```

Node mutation remains backend-authorized and its resulting state remains derived from authoritative synchronization and cache events.

Phase 6 does not claim that all Slurm resources are implemented, that Job mutations are supported, or that the full administrative UI is complete. Those are separate milestones.

## 18. Handoff to Phase 7

After Phase 6 is accepted, Phase 7 may focus on frontend architecture and UI integration using the proven resource infrastructure. It may evaluate shared presentation patterns and capability-driven navigation, but must preserve the boundary that frontend services are transport/client abstractions and backend services own authoritative resource state, business rules, and authorization.

Phase 7 should not be used to compensate for missing backend correctness or to introduce a second authoritative resource cache.
