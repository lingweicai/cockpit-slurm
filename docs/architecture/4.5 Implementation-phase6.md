# cockpit-slurm Implementation Phase 6 — Resource System Generalization

## 1. Purpose

Phase 6 generalizes the proven Node implementation from Phases 3–5 into reusable resource infrastructure without replacing working behavior or designing a universal Slurm resource model in advance.

Phase 3 established Node queries and the authoritative backend cache. Phase 4 added Node synchronization, events, and the automatic per-connection stream. Phase 5 added Node commands, server-derived identity, capability-based authorization, command lifecycle handling, and post-command synchronization.

Phase 6 extracts the reusable mechanisms from that working vertical slice and validates them with **Node plus Job**.

The governing principle is:

> Generalize the infrastructure around resources; keep canonical resource models, adapters, and domain rules resource-specific.

The target is not to implement every Slurm resource. It is to demonstrate that a second resource can use the same backend resource infrastructure while existing Node reads, live updates, commands, and authorization continue to work.

## 3. Phase 6 objective

Extract and validate the reusable resource mechanisms:

- resource identity and resource-kind registration;
- canonical resource storage and lookup;
- adapter-based normalization from Slurm source/API models into stable canonical resource models;
- generation and update metadata;
- indexes and snapshots;
- semantic change detection;
- resource synchronization and refresh;
- event publication after successful cache updates;
- per-connection event stream registration, fan-out, and initial snapshot delivery;
- query request/response handling;
- preservation of Phase 5 command handling and capability-based authorization;
- frontend IPC/client abstractions needed by resource-specific providers.

Phase 6 may generalize shared request parsing, resource resolution, operation registration/lookup, and validation conventions only where existing code demonstrates a concrete common need. Query execution and command execution MUST remain separate paths. Do not create a universal CRUD executor or speculative abstractions for future resources. All accepted Phase 5 command guarantees MUST be preserved.

The backend Resource Cache remains the authoritative in-memory application state. Frontend providers maintain client-side state for presentation and must not become a second authoritative cache.

## 4. Scope

### 4.1 In scope

1. Review the accepted Node implementation and identify the reusable mechanisms actually demonstrated by Phases 3–5.
2. Extract generic backend infrastructure incrementally from the working Node path.
3. Keep the Node adapter, canonical Node model, Node-specific query behavior, and Node command definitions resource-specific.
4. Add a Job read/live-update vertical slice using the generalized infrastructure; Job mutation commands remain out of scope.
5. Support Job snapshot/query and change delivery through the shared cache/event/per-connection stream mechanisms.
6. Keep command authorization and execution backend-authoritative.
7. Preserve the existing application IPC envelope, framing, correlation, event semantics, and error model unless a separately reviewed contract change is required.
8. Add unit, integration, regression, and end-to-end tests for the generalized infrastructure and Job vertical slice.
9. Update architecture/implementation documentation where actual implementation findings require it.

### 4.2 Explicitly out of scope

Phase 6 MUST NOT expand into:

- full Job command support, including submit, cancel, suspend, or resume;
- User, Account, Association, Partition, Reservation, QOS, or Cluster resource implementation beyond any minimal shared types needed by existing code;
- a complete administrative UI or role-driven navigation;
- a new generic frontend resource framework;
- a second authoritative frontend cache;
- frontend execution of Slurm CLI commands or business rules;
- frontend authorization as a security boundary;
- replacing the current IPC transport or adding another socket/channel;
- replacing the accepted Phase 5 command protocol, authorization model, or ledger without an explicit design review;
- broad production-hardening work unrelated to correctness of the generalized resource path.

These items belong to later milestones where appropriate.

Phase 6 MUST NOT introduce a universal CRUD command model for all resources. Commands MUST use explicit resource-scoped operation IDs (for example, `node.drain` and `node.resume`). An operation category such as create, update, delete, lifecycle, or query may be classification metadata only; it MUST NOT replace the explicit operation ID. Read operations such as `show` belong to the query path.

The shared command infrastructure may resolve a resource kind and explicit operation ID and apply common request validation, correlation, and error conventions. Resource-specific handlers MUST retain operation semantics, parameter constraints, Slurm execution behavior, and authorization requirements. Do not assume all operations are CRUD operations or that every Slurm command is a short synchronous subprocess.

### 4.3 Scope decision
| Work item | Phase 6 decision |
| --- | --- |
| Central operation policy and Go loader  | Implement
| Separate resource visibility policy and Go evaluator for Node and Job  | Implement
| Central registry for Node drain/resume | Implement |
| Preserve Phase 5 Node authorization | Mandatory |
| Job query visibility filtering | Implement |
| Job event visibility filtering | Implement |
| `job.submit`, `job.cancel`, `job.suspend` | Planned only |
| Full `sacctmgr` administration | Future phase |
| Generic CRUD command framework | Do not implement |

This keeps Phase 6 focused on resource generalization, while ensuring the authorization design is not merely documentation for some future phase.

One further architectural consideration: neither policy file should become the only place where resource-specific ownership logic lives. The operation policy controls invocation permission; the visibility policy selects a reusable resource scope rule. The visibility evaluator uses trusted UserContext and canonical resource information, while the resource adapter supplies normalized facts needed to evaluate ownership and scope. This preserves the distinction between shared policy infrastructure and resource-specific semantics.

## 5. Required architecture

The backend should retain the following conceptual flow:

```text
Slurm
  │
  ├── Node Adapter ──> Canonical Node ──┐
  │                                     │
  └── Job Adapter ───> Canonical Job ───┤
                                        ▼
                               Resource Infrastructure
                              ├── Resource Registry
                              ├── Resource Cache
                              ├── Indexes and Snapshots
                              ├── Change Detection
                              ├── Event Bus
                              ├── Per-connection Stream Registry
                              ├── Query Service
                                └── Command Dispatcher / Operation Registry
                                  (Phase 5 Node behavior preserved; resource handlers remain specific)
                                        │
                                        ▼
                                Dispatcher / IPC
                                        │
                                        ▼
                                  React clients
                              ├── NodeProvider
                              └── JobProvider
```

The diagram is conceptual. Preserve the current repository's package layout where practical. Do not create a single large service that absorbs adapter logic, authorization, protocol handling, and UI behavior.

### 5.1 Ownership boundaries

**Resource-specific code owns:**

- canonical domain model;
- Slurm-specific data acquisition and parsing;
- resource-specific identity and keys;
- resource-specific indexes where needed;
- semantic comparison rules where generic comparison is insufficient;
- supported operations and their parameter validation;
- resource-specific authorization requirements;
- frontend columns, formatting, and presentation.

**Shared backend infrastructure owns:**

- resource-kind registration and lookup;
- common resource metadata conventions;
- safe cache operations and consistent snapshots;
- generation/update bookkeeping;
- event publication ordering;
- per-connection stream lifecycle and delivery;
- common query dispatch;
- common protocol validation, error handling, and request correlation;
- a consistent operation-registration/lookup pattern where justified by concrete command use cases;
- shared command-dispatch mechanics only where they can be extracted without merging query and command execution;
- preservation of the accepted Phase 5 Node command and authorization lifecycle.

Query and command dispatch MUST remain separate. Query handlers own resource-specific read behavior; command handlers own resource-specific mutation and lifecycle behavior. Shared infrastructure MUST NOT bypass or weaken command-specific authorization, ledger/deduplication, lifecycle, audit, or execution controls.

**Frontend services remain transport/client abstractions.** They may send requests, receive responses/events, correlate messages, and expose typed APIs. They MUST NOT own Slurm business rules, execute Slurm commands, make authoritative authorization decisions, or duplicate backend synchronization logic.

## 6. Resource contract and canonical models

### 6.1 Resource identity

Define or consolidate a shared resource identity contract only to the extent supported by the existing implementation. It should make the resource kind and stable resource key explicit.

Requirements:

- Node and Job identities MUST be unambiguous.
- Resource keys MUST be stable for the lifetime of the represented entity according to Slurm semantics.
- The implementation MUST NOT assume every resource is keyed by a single string if a resource requires a compound identity.
- Cache lookup and event routing MUST use the same identity rules.
- Resource identity MUST NOT be inferred from frontend display labels.

Examples of domain identity (illustrative, not a mandate to change existing key formats):

- Node: node name.
- Job: the composite tuple defined below.

#### Initial Job identity and population

The `cluster` identity component comes from backend cluster configuration, never from client input. If the Slurm response includes a cluster name, it MUST match that configured value; a mismatch invalidates the complete snapshot.

Phase 6 initially represents active Jobs only; completed-job/accounting history is out of scope. Stage A MUST evaluate `scontrol show job` as the preferred candidate source and verify its behavior on the target Slurm version before Stage D implementation. The selected source MUST be documented and approved at the Stage A exit gate.

For the tested installation, the selected candidate source is `scontrol --all --local show job --json` executed under the `cockpit-slurm` data-acquisition identity with `SLURM_BITSTR_LEN=0`. The owner approved this selection for the tested Slurm 25.05.7 configuration and observed `data_parser/v0.0.43`; this is not a claim of universal completeness or compatibility with other versions or configurations. Hidden-partition behavior remains unverified and requires separate evidence before such a deployment is supported. Stage A remains unaccepted until the remaining evidence limitations and documentation are reviewed and explicitly accepted.

The source selection does not waive complete-snapshot validation. The adapter MUST preserve the cache and emit no removal events on acquisition failure, invalid or incomplete data, or an oversized snapshot. In the tested parser, the default array-expression limit produced syntactically valid but abbreviated JSON; explicitly set `SLURM_BITSTR_LEN=0`, validate the complete response, and reject abbreviated or otherwise incomplete expressions. A successful command or JSON parse alone does not establish completeness.

The selected source MUST provide a complete cluster-wide active Job snapshot using the approved backend execution identity. Verify enumeration behavior, output format/parser, required fields, array identity, and whether the configured service identity can observe the required population. If `scontrol show job` cannot satisfy these requirements, stop and review the source decision before implementation; do not silently switch to another source. Do not assume CLI output can be unmarshaled directly into an OpenAPI-generated REST model, or that `scontrol show job` output is JSON.

The canonical Job identity MUST be the typed tuple `(cluster, job_id, array_job_id, array_task_id)`. `cluster` and `job_id` are required. In the canonical model, a normal Job has both array identifiers absent; an array element has both present; an array parent/placeholder may have `array_job_id` present and `array_task_id` absent. `array_task_id` present without `array_job_id` is invalid. Array task ID zero is a valid value when the approved source identifies it as set and MUST be preserved.

The adapter MUST normalize the approved Slurm source representation into these canonical set/absent semantics using verified source-specific rules. It MUST NOT infer absence from a numeric zero alone, because zero may be a valid array task ID. A source sentinel or set/value combination may be normalized to absence only when representative output and the source's documented semantics establish that interpretation; retain enough raw source information during parsing to distinguish an unset field from a set zero. Stage A MUST verify normal Jobs and array Jobs, including an array task with ID zero where available, using representative output from the approved source and record the evidence and normalization rule. The cache key and serialized Job identity MUST encode the canonical tuple unambiguously. Reject records with missing required identity fields, invalid array identity combinations, or duplicate tuple keys in one snapshot.

For the observed Slurm 25.05.7 `data_parser/v0.0.43` source representations, the owner approved these source-specific normalization rules:

- Retain the configured cluster identity and source `job_id`.
- A normal Job with `array_job_id` set to zero, `array_task_id` unset, and empty `array_task_string` has both canonical array identifiers absent.
- An individual array element retains both array identifiers, including a set `array_task_id` of zero.
- An aggregated array placeholder retains the array Job ID and nonempty task expression, with the canonical task ID absent.
- Unknown, inconsistent, or ambiguous source combinations reject the entire refresh without cache mutation or removal events. These rules apply to the observed representations and do not approve arbitrary behavior for other parser versions.

#### Active Job state classification proposal

This proposal targets the selected Slurm 25.05.7 `data_parser/v0.0.43`
representation. Slurm defines base states separately from transition flags.
The source's exact encoding of a base state and its flags must be verified;
documentation or a generated schema alone does not establish that the CLI
returns a particular combination.

| Source classification | Proposed active-collection behavior | Evidence and support status |
| --- | --- | --- |
| Base `PENDING`, no transition flag | Include. | `PENDING` appears in the supplied daemon-context held-array sample; Slurm state documentation classifies it as nonterminal. |
| Base `RUNNING`, no transition flag | Include. | `RUNNING` appears in supplied daemon-context normal-Job and array-element samples; Slurm state documentation classifies it as nonterminal. |
| Base `SUSPENDED`, no transition flag | Include. | Slurm state documentation classifies it as nonterminal; no supplied CLI sample establishes this representation. It remains source-unverified. |
| Active base plus `CONFIGURING` | Include only if the parser exposes an unambiguous active base and recognized `CONFIGURING` flag together. | The manual describes the allocation transition; no supplied CLI output establishes this combination. Until verified, reject it as unsupported. |
| Active or terminal base plus `COMPLETING` | Include during cleanup only if the parser exposes an unambiguous base and recognized `COMPLETING` flag together. | The manual describes the cleanup flag; no supplied CLI output establishes its encoding or terminal-base combinations. Until verified, reject it as unsupported. |
| Terminal base `COMPLETED`, `CANCELLED`, or `FAILED`, with no recognized active transition | Exclude only after a complete, valid snapshot. | `COMPLETED` and `CANCELLED` appear in supplied daemon-context output; `FAILED` appears only in a supplied `dev` query, not the daemon-context sample. Slurm state documentation classifies these as terminal. |
| Active base plus `REQUEUED`, `REQUEUE_HOLD`, or `REQUEUE_FED` | Proposed include only when the base is explicitly active and the flag combination is recognized and unambiguous. | Slurm documentation and `squeue --helpstate` identify these state/flag names; no supplied CLI output establishes a combination. Until verified, reject it as unsupported. |
| `SPECIAL_EXIT`, a requeue-related flag without an active base, or any flag combined with a terminal/cleanup base not explicitly classified above | Reject the entire refresh. | No supplied CLI output establishes these combinations or their source encoding. |
| Unknown base state, unknown flag, unsupported combination, missing base when needed to classify a flag, or ambiguous representation | Reject the entire refresh; preserve the cache and emit no removals. | Required fail-closed behavior; no source sample is needed to classify unknown input as invalid. |

`CONFIGURING`, `COMPLETING`, `REQUEUED`, `REQUEUE_HOLD`, `REQUEUE_FED`,
`SPECIAL_EXIT`, and other flags have not been observed in the supplied CLI
output. Their inclusion rows are policy proposals, not source-supported
classifications. Other flags requiring explicit evidence and classification
include `STOPPED`, `RESIZING`, `SIGNALING`, `STAGE_OUT`, `POWER_UP_NODE`,
`RESV_DEL_HOLD`, `REVOKED`, `LAUNCH_FAILED`, and `RECONFIG_FAIL`; do not infer
their behavior from a name alone. No unsupported or ambiguous combination may
be treated as terminal by default.

The adapter MUST reject a refresh as incomplete if the command fails, parsing/schema validation fails, the response is truncated or malformed, or any record fails identity/model validation. Incomplete data MUST NOT mutate the cache or cause removals. A complete valid snapshot may be empty; only after that snapshot is committed may previously cached active Jobs absent from it be removed from the active collection. No partial or incremental Job synchronization is supported in Phase 6. The complete serialized snapshot MUST fit the existing IPC message-size limit; if it does not, reject it without truncation, cache commit, or removal events. Snapshot chunking is out of scope.

### 6.2 Shared metadata

Where appropriate, canonical resources should expose consistent metadata such as:

- resource kind;
- stable resource identity;
- generation or version;
- update timestamp;
- source/provenance when useful for diagnostics.

Reuse existing fields and wire representations when they already meet the accepted contract. Do not introduce redundant generation counters or competing timestamps.

### 6.3 Resource-specific canonical models

Node and Job MUST remain distinct canonical models.

A Job model may contain job ID, owner, state, partition, allocated resources, submit/start/end times, and other fields supported by the current Slurm version and chosen adapter. This list is illustrative; use the repository's existing generated Slurm API types and domain decisions where appropriate.

The frontend MUST NOT depend on raw CLI output. Slurm-specific parsing and normalization belong in adapters.

The canonical Job model MUST be able to represent missing or unresolved owner
and account attributes without inventing trusted values. Their absence alone
MUST NOT invalidate an otherwise valid identity or authorize visibility; the
visibility evaluator applies the independent branch rules in §11.3.4. This
does not relax rejection of malformed identities, ambiguous source records,
or incomplete snapshots.

The generated `hack/openapi/slurm_openapi.gen.go` types MAY be reused as Slurm API/source models when the actual source schema matches them. They MUST NOT automatically become canonical application models or define generic cache interfaces. Keep canonical Node and Job types stable and resource-specific; adapters MUST normalize source data into those types. A CLI output format such as `scontrol show job` MUST be parsed according to its actual verified format and MUST NOT be assumed to match a generated REST model. Do not edit generated files manually; update the source specification and regenerate them when needed.

Do not force Node and Job into one union of fields or make resource-specific fields optional merely to make all models appear identical.

## 7. Resource registration and adapter boundaries

Introduce or consolidate a registry for resource-kind-specific behavior if the current code does not already provide an equivalent mechanism.

The registry should make it possible for the shared infrastructure to identify the adapter/model behavior for a resource kind without embedding Node-specific or Job-specific branching throughout generic services.

Requirements:

- Register Node and Job explicitly.
- Reject unknown resource kinds with a defined protocol/application error.
- Detect duplicate or invalid registrations during initialization or tests.
- Keep adapter initialization and resource registration deterministic.
- Do not use reflection or untyped `any` as a shortcut for avoiding resource-specific types.
- Do not turn the registry into a container for unrelated application services.

The resource adapter is responsible for obtaining Slurm data and translating it into canonical resources. The cache and event infrastructure must not invoke Slurm CLI commands directly.

Adapters MAY use generated OpenAPI types as intermediate source models when appropriate, but the cache, generic resource registry, and event infrastructure MUST depend on canonical resource identity/model contracts rather than Slurm API-version-specific generated structs.

## 8. Resource cache, snapshots, and change detection

The backend cache remains the sole authoritative in-memory application state.

The generalized cache MUST support the operations required by both Node and Job:

- insert or update a canonical resource;
- remove a resource when authoritative synchronization confirms deletion or removal from its represented collection;
- retrieve an individual resource by its identity;
- enumerate/query resources using supported indexes and filters;
- produce a consistent snapshot for a query or per-connection stream baseline;
- maintain resource generation/update metadata;
- determine whether a newly synchronized resource is semantically changed.

Requirements:

1. A generation MUST advance according to the established contract when the represented resource state changes.
2. A semantically unchanged refresh MUST NOT generate a false update event.
3. Snapshot contents and their generation/baseline MUST be mutually consistent.
4. A failed refresh or parse MUST NOT partially corrupt the authoritative cache.
5. Events MUST NOT be published before the corresponding cache mutation succeeds.
6. Resource removal MUST be based on a completed, authoritative synchronization result—not a partial or failed read. A Job removed from the active collection is not necessarily deleted from Slurm.
7. Concurrent reads and refreshes MUST be race-safe.
8. Indexes MUST remain consistent with inserts, updates, and deletes.
9. Resource-specific equality must account for semantic fields, not incidental output ordering or formatting.
10. The cache MUST NOT store UI state, form state, pending commands, or client-supplied identity claims.

Use the existing Node cache-generation and snapshot/event contract as the reference for authoritative state. Node and Job maintain independent collection generations, each advancing once per changed complete snapshot. A collection generation describes backend cache state; it is not the event-loss counter for a filtered connection. Stream delivery and recovery use the per-connection event `sequence` defined in §9, and the two values MUST NOT be conflated.

## 9. Synchronization and event delivery

### 9.1 Synchronization

Keep resource acquisition separate from generic cache/event infrastructure.

Node synchronization MUST continue to behave as it did at the end of Phase 5. Add a Job synchronization path using the source selected and approved at the Stage A exit gate. The preferred candidate is `scontrol show job`, subject to verified complete-snapshot, parsing, identity, and visibility requirements in §6.1.

The implementation MUST define how each adapter reports:

- a successful complete snapshot;
- a successful partial/incremental update, if supported (Job partial updates are not supported in this phase);
- a transient acquisition failure;
- malformed or unparseable data;
- a confirmed deletion or removal from the represented collection.

Do not interpret an acquisition failure as an empty resource collection.

### 9.2 Event ordering

For both Node and Job:

```text
authoritative Slurm observation
        ↓
canonicalization
        ↓
successful cache mutation
        ↓
resource change event
        ↓
each connected stream's bounded queue
        ↓
serialized IPC delivery
        ↓
frontend provider update
```

Events describe committed cache state, not guesses about what a command probably changed.

Preserve the Phase 4 guarantees for atomic stream baseline registration, bounded/serialized writes, disconnect cleanup, and recovery. Reuse those guarantees for Job rather than creating a separate event mechanism. Each connected IPC connection receives the initial Node and Job snapshots, followed by projected Node and Job changes on the same `type: "event"` envelope. Resource-specific providers ignore event payloads for other resource kinds only after the shared connection-level stream consumer has validated sequence continuity.

### 9.3 Per-connection stream behavior

The generalized stream infrastructure MUST preserve the Phase 4 transport,
lifecycle, and per-connection event-sequence contract. Phase 4 already defines
the shared connection sequence, independent authoritative collection
generations, visibility projection before sequence allocation, no sequence
consumption for hidden changes, identity-only visibility removals, and
reconnect/fresh-snapshot recovery. Phase 6 brings the existing Node
implementation into conformance with that accepted contract and applies the
same mechanism to Job events:

- one automatically registered resource stream per IPC connection;
- one complete, per-connection visibility-filtered initial snapshot for each supported resource kind; all initial snapshots establish the same sequence baseline;
- subsequent visibility-projected changes using the existing event envelope and resource discriminator;
- atomic snapshot baseline and event publication ordering;
- bounded, serialized writes and cleanup on disconnect;
- one monotonically increasing `sequence` across all resource event envelopes on the connection; allocate it only for an event actually enqueued for that connection;
- no sequence increment or event for a change that does not alter that connection's visible projection;
- explicit identity-only removal when a previously visible record becomes invisible, including after trusted authorization context changes;
- identity-only removals carry the full canonical resource identity (`nodeName` for Node; `(cluster, job_id, array_job_id, array_task_id)` for Job) and no other resource fields;
- connection-level sequence-gap detection and recovery by closing/reopening the stream to receive fresh snapshots. The global collection `generation` may skip and MUST NOT drive gap detection.

Phase 6 MUST NOT add application-level `subscribe` or `unsubscribe` messages, `subscriptionId`, client-selected resource filters, or a second stream format. The stream lifetime is the IPC connection lifetime; do not assume an IPC connection ID and a logical Cockpit session ID are interchangeable. Backend authorization remains server-side and connection-scoped.

Preserve the Phase 4 `type: "event"` format and add Job payloads through its established resource discriminator. Event payloads MUST carry both the authoritative resource `generation` and connection `sequence`; clients use only `sequence` for stream continuity. The shared frontend stream consumer validates every event across resource kinds before provider dispatch. Reopening the connection is the snapshot request under the automatic-stream contract; do not add a separate snapshot-request message.

## 10. Query infrastructure

Generalize common query processing without making resource-specific query semantics identical.

The shared query path should validate the envelope and common request metadata, resolve the resource kind, invoke the correct resource query/cache behavior, and return the established response/error structure with message correlation preserved.

Requirements:

- Node query requests and responses remain compatible with the accepted contract.
- Job queries return canonical Job data, not raw CLI output.
- Unknown resource kinds, malformed filters, unsupported query options, and invalid identifiers fail explicitly.
- Pagination, filtering, and sorting MUST be implemented only where their semantics are defined and tested; do not imply support that an adapter does not provide.
- Query behavior MUST not bypass the backend cache with ad hoc Slurm calls unless the architecture explicitly defines a separate operation requiring live acquisition.
- Existing protocol framing, size limits, message IDs, and error object shape remain unchanged.

## 11. Command infrastructure and authorization

Phase 6 MUST preserve the Phase 5 Node command and authorization path. Job mutations are out of scope, so Phase 6 MUST NOT implement Job command handlers or refactor command infrastructure speculatively. Keep Node operations, validation, authorization, ledger behavior, execution boundary, and lifecycle unchanged except for fixes required by a failing regression test and separately reviewed. Limited extraction of common dispatch/registration mechanics is permitted only when Stage A/B identifies concrete duplication and all Phase 5 invariants remain unchanged.


### 11.1 Central authorization policy integration

Phase 6 MUST integrate the central policy in `config/authorization/operations.yaml`
as defined by architecture §8.5 and implementation plan §10.1.

Requirements:
1. Load and fully validate the policy during backend initialization. The file
   MUST be administrator-managed and MUST NOT be writable by `cockpit-slurm`.
2. Every entry MUST declare `operation_type: query` or `operation_type: command`,
   independently of `status: enabled|planned`.
3. Use one policy source and evaluator, but separate immutable registries:
   enabled query entries go only to the query-policy registry; enabled command
   entries go only to the command registry. Planned entries are validated but
   registered in neither registry and cannot be invoked.
4. Resolve handler names only through the compiled Go handler allowlist. YAML
   MUST NOT define arbitrary executables, shell fragments, or command templates.
5. Integrate the existing Phase 5 Node operations with the command registry.
   Preserve operation IDs, validation, authorization decisions, command ledger,
   audit context, execution boundary, lifecycle, and error behavior.
6. Evaluate permission cells against server-derived identity and canonical
   target resources. Client-supplied role, ownership, or account claims MUST NOT
   establish authorization.
7. Keep application permissions, Slurm-native authorization, resource scope,
   and command execution identity as separate checks.
8. Use the operation-authorization evaluator for query/command invocation permission and the separate resource-visibility evaluator for record filtering. Collection-level query permission MUST NOT imply unrestricted visibility. The two evaluators MUST NOT be collapsed into one policy decision.
9. Frontend capabilities are advisory. Every backend query and command MUST
   be independently authorized.

If the policy is missing, unreadable, malformed, incomplete, or semantically
invalid, daemon initialization MUST fail. Neither query nor command services
may become ready with a partial registry, permissive defaults, or fallback
policy. Publish both registries only after complete validation.

The accepted Phase 5 Node authorization semantics MUST remain unchanged:
`node.drain` and `node.resume` require a currently resolved Slurm
`AdminLevel=Administrator`. Use `slurm_admin_level_admin`, not `slurm_admin`,
which also includes root and SlurmUser. The application role `Administrator`
alone does not satisfy this predicate.

Phase 6 enabled policy entries are:
- Query-policy registry: `node.list` and `job.list`.
- Command registry: `node.drain` and `node.resume`.
- All other entries remain `planned`, validated only, and absent from both
  registries.

Job snapshot/query and Node/Job event delivery MUST apply trusted per-resource
visibility filtering. When access is revoked, resources no longer visible MUST
be removed from the affected connection's frontend projection through the
established event/snapshot recovery contract.

Security requirements:

1. The backend remains the authorization authority.
2. Identity is derived from the initialized server-side connection, never from command payload fields.
3. Unknown or unresolved identity fails closed.
4. Every operation declares its required capability or equivalent accepted authorization metadata.
5. Authorization is enforced before privileged execution.
6. A frontend capability response is advisory UI data, not an authorization grant.
7. The accepted Phase 5 command lifecycle, error contract, and durable deduplication guarantees MUST remain intact.
8. Do not broaden daemon privileges or change the privileged-execution mechanism as a side effect of resource generalization.

Job commands such as submit, cancel, suspend, and resume are explicitly out of scope for this phase. They can be designed after the shared infrastructure and Job read path are accepted.

The shared command path is a reusable dispatch/registration mechanism, not a universal CRUD executor. Phase 6 MAY extract common resource resolution, operation lookup, request validation, correlation, or error handling where concrete duplication is identified. Query and command execution MUST remain separate; operation-specific validation, authorization, ledger/deduplication, execution, audit, and lifecycle behavior remain command-specific.

Authorization and execution identity MUST be treated as separate concerns. The backend MUST authorize the IPC caller using the accepted Phase 5 server-derived identity/capability model before privileged execution. A Slurm CLI process ordinarily acts under the operating-system identity that executes it; do not assume the browser user's permissions are automatically propagated to a daemon running as `cockpit-slurm`. Before adding future command handlers, document and verify the execution identity and Slurm authorization behavior for the specific command and target. Any helper/delegation mechanism MUST expose only narrowly defined approved operations and MUST NOT allow clients to select arbitrary users, executables, or command lines. Slurm authorization policies must be operation- and target-specific and checked against the documentation for the deployed Slurm version/configuration.

### 11.2 Central authorization matrix integration

Phase 6 MUST integrate the central operation authorization policy defined in:

- Architecture §8.5 — Operation Registry and Authorization Policy.
- Implementation Plan §10.1 — Central Operation Authorization Matrix.
- `config/authorization/operations.yaml`.

The purpose of this work is to make the accepted Phase 5 Node authorization behavior use the central policy source without changing its externally observable behavior or weakening any security guarantees.

Requirements:

1. Load and validate the authorization configuration during backend initialization. The configuration MUST be treated as trusted, administrator-managed input and MUST NOT be writable by the `cockpit-slurm` service account.
2. Construct an immutable backend operation registry from valid, enabled entries. Planned entries MUST NOT be registered or executable.
3. Resolve handler names only through the compiled Go handler allowlist. The configuration MUST NOT define arbitrary executables, shell commands, or command templates.
4. Integrate the existing Phase 5 Node operations with the central registry. Preserve their operation IDs, validation, effective authorization decisions, command ledger, audit context, execution boundary, lifecycle, and error behavior.
5. Evaluate permission cells against the server-derived requesting identity and canonical target resource. Role labels or client-supplied ownership/account information MUST NOT establish authorization.
6. Keep application role permissions, Slurm-native authorization requirements, resource scope, and execution identity as separate concerns.
7. Use the operation-authorization evaluator for invocation permission and the separate resource-visibility evaluator for record filtering. Collection-level query permission MUST NOT imply unrestricted visibility of every resource.
8. Frontend capabilities MUST be derived presentation data. Every backend query and command request MUST be independently authorized.

Phase 6 scope:

- The existing Node drain and resume operations are the initial enabled command operations.
- Job snapshot and query authorization MUST enforce the applicable per-user resource visibility rules.
- Node and Job snapshots and events MUST use the same trusted resource-scope evaluation where applicable.
- Future command entries may be documented as `planned`, but Phase 6 MUST NOT implement Job mutation handlers or unrelated Slurm command families.
- Slurm-native policy entries MUST be verified against the supported Slurm version and cluster configuration before being enabled.

The central matrix MUST NOT become a reason to redesign the accepted Phase 5 command framework. Any necessary migration MUST be incremental and covered by Phase 5 regression tests.

### 11.3 Resource visibility policy

Phase 6 MUST implement resource visibility as a policy system separate from
the operation authorization policy in `operations.yaml`.

#### 11.3.1 Policy source and relationship to operations

Repository policy source:

```text
config/authorization/visibility.yaml
```

Installed runtime configuration:

```text
/etc/cockpit-slurm/visibility.yaml
```

`operations.yaml` answers whether the requesting application role may invoke
an operation. `visibility.yaml` answers which canonical records of a resource
may be returned to that authenticated connection. An `allow` permission in
`operations.yaml` MUST NOT grant unrestricted record visibility.

Every enabled query operation that returns canonical resource records MUST
declare a `visibility_policy` identifier. The identifier MUST resolve to the
policy for that resource in `visibility.yaml`; an unknown or mismatched
identifier MUST fail validation. The operation entry references the policy
but MUST NOT duplicate or override its role scopes or record-level rules.
Automatic resource-change events MUST select the visibility policy by
canonical resource kind and apply it independently to each IPC connection.
Command operations remain governed by operation authorization and their
resource-specific command checks; a query visibility reference MUST NOT
replace command authorization.

For Phase 6, `operations.yaml` MUST contain these exact references for its
enabled resource-returning queries:

| `operation_id` | `resource` | `visibility_policy` in `operations.yaml` | Policy in `visibility.yaml` |
| --- | --- | --- | --- |
| `node.list` | `node` | `node.cluster` | `node.cluster` |
| `job.list` | `job` | `job.active` | `job.active` |

`visibility.yaml` MUST define `node.cluster` for canonical Nodes, granting all
four authenticated application roles visibility of Nodes in the configured
cluster, and `job.active` for active canonical Jobs, with the role scopes in
§11.3.3. Any later resource-returning query MUST add an explicit reference and
a matching policy before it can be enabled; no implicit unrestricted policy
is permitted.

The policy is resource-oriented, not a list of Slurm commands. The same
resource policy SHOULD be reusable for collection queries, individual
lookups, initial snapshots, and resource-change events.

#### 11.3.2 Policy model and validation

Each resource policy MUST identify:

* the canonical resource kind;
* an explicit visibility policy/scope rule;
* the supported application roles and the scopes granted to each role;
* the trusted canonical attributes required by the evaluator.

The policy MUST use default-deny behavior. Unknown resources, policy
identifiers, roles, or scope rules MUST NOT grant visibility. Missing or
invalid required attributes MUST fail closed for the affected record.
Frontend-supplied identity, role, owner, account, association, or
coordinator-scope values MUST NOT influence the decision.

Both `operations.yaml` and `visibility.yaml` MUST be administrator-managed,
read-only to the `cockpit-slurm` service account, and fully validated during
backend initialization. Missing, unreadable, malformed, incomplete, or
semantically invalid configuration MUST prevent service readiness. The
backend MUST NOT start with a partial policy, permissive fallback, or
implicit unrestricted visibility. Publish immutable policy registries only
after successful validation. Runtime reload is out of scope unless a
separate atomic-reload design is approved.

#### 11.3.3 Phase 6 visibility rules

Phase 6 implements visibility only for Nodes and active Jobs:

| Resource | Administrator | Operator | Coordinator | User |
| --- | --- | --- | --- | --- |
| Node | All Nodes | All Nodes | All Nodes | All Nodes |
| Active Job | All active Jobs | All active Jobs | Directly owned Jobs OR Jobs in coordinated accounts | Directly owned Jobs |

Node visibility is cluster-wide for all authenticated application roles.
It does not grant permission to modify Node state; Node command
authorization remains governed by `operations.yaml`, the accepted Phase 5
authorization contract, and Slurm-native checks.

For active Jobs:

* Administrator and Operator may see all active Jobs in the configured
  cluster.
* Coordinator may see a Job if the user directly owns it OR the Job's
  canonical Slurm account is in the user's server-derived
  `CoordinatorAccounts`.
* User may see a Job only if the user directly owns it.

Direct ownership and account coordination are independent conditions. A
Coordinator MUST be able to see a directly owned Job even when its account
is not in `CoordinatorAccounts`.

#### 11.3.4 Trusted canonical attributes

Visibility decisions MUST use server-derived `UserContext` and normalized
canonical resource fields:

| Context/resource | Attribute | Purpose |
| --- | --- | --- |
| `UserContext` | `UID` | Authenticated Linux UID for direct ownership |
| `UserContext` | resolved application role / `AdminLevel` | Determine privileged role scope |
| `UserContext` | `CoordinatorAccounts` | Server-derived accounts coordinated by the user |
| Canonical Job | `UserID` | Numeric UID of the Job owner |
| Canonical Job | `Account` | Slurm account associated with the Job |
| Canonical Job | `JobID` and cluster identity | Identify and scope the canonical Job |
| Canonical Node | `NodeName` and cluster identity | Identify and scope the canonical Node |

Direct ownership MUST compare `UserContext.UID` with canonical Job `UserID`.
The Job adapter MUST normalize the Slurm owner identity into a numeric UID.
It MUST NOT infer ownership from a frontend display name or an unverified
username. If the UID mapping cannot be established reliably, direct
ownership MUST NOT be granted.

Coordinator scope MUST compare canonical Job `Account` with the
server-derived `UserContext.CoordinatorAccounts`. The general
`UserContext.Accounts` membership list MUST NOT be treated as the coordinator
account set. Direct ownership and coordinator-account scope are independent
branches. A missing or invalid Job account denies the coordinator-account
branch but MUST NOT invalidate an established direct-owner match. Missing or
invalid Job owner information denies the direct-owner branch but MUST NOT
invalidate an established coordinator-account match. Each branch requires its
own valid trusted context and resource attributes; missing or invalid data
MUST NOT grant access. If neither applicable branch establishes access, deny
visibility. Cluster identity and authenticated connection context remain
mandatory. Administrator and Operator visibility remains governed by their
existing privileged-role policy.

Node visibility does not depend on a frontend-selected account or user
filter. Such filters may narrow a query for presentation/performance only;
they MUST NOT broaden the records authorized by the visibility policy.

#### 11.3.5 Cache, query, snapshot, and event filtering

The authoritative backend cache MAY retain the complete canonical Node and
Job collections. It MUST NOT be sent directly to a frontend connection and
MUST NOT be replaced by separate per-user authoritative caches.

The same visibility evaluator MUST be applied per IPC connection to:

1. initial Node and Job snapshots;
2. explicit Node and Job collection query responses;
3. individual resource lookups, if exposed;
4. subsequent Node and Job change events; and
5. reconnect and snapshot-recovery responses.

When a Job becomes invisible because its owner/account scope or the
connection's trusted authorization context changes, the backend MUST remove
that Job from the affected connection's frontend projection. This is a
visibility removal, not deletion of the Slurm Job or removal from the global
cache. A resource-change event MUST NOT disclose fields of a record that is
not visible to that connection.

The same rule applies to Nodes if a future policy change makes a Node
invisible. Frontend filtering is presentation-only and MUST NOT be relied on
as a security boundary.

#### 11.3.6 Relationship with Slurm PrivateData

Slurm `PrivateData` remains a Slurm-native setting configured only in
`slurm.conf`. It MUST NOT be configured through `operations.yaml` or
`visibility.yaml`.

Slurm `PrivateData` controls what the backend's Slurm execution identity may
retrieve. Cockpit-slurm visibility controls which acquired canonical records
are returned to each authenticated IPC connection. Cockpit-slurm MUST
enforce its per-connection policy even when Slurm's default information
visibility is broad, and MUST respect Slurm-native authorization.

Phase 6's initial data-acquisition design assumes `PrivateData=jobs` and
`PrivateData=nodes` are not enabled. Stage A MUST verify complete snapshot
acquisition under the actual backend execution identity. If a deployment
enables a `PrivateData` restriction that prevents complete acquisition, the
data-acquisition identity and authorization design MUST be separately
reviewed and tested before that configuration is supported. The backend
MUST NOT bypass Slurm authorization or treat an incomplete collection as a
complete snapshot.

#### 11.3.7 Event categories

The following event categories are distinct and MUST NOT inherit one
another's visibility policy:

1. **Resource-change events:** IPC notifications about canonical Node or Job
   changes. They use the visibility policy of the related resource.
2. **Slurm accounting events:** Slurm-maintained event/history records. They
   are a future resource type and require their own explicit policy.
3. **Cockpit-slurm audit events:** Records of application actions and
   outcomes. They require a separately defined audit-access policy.

Permission to receive a Node or Job resource-change event MUST NOT imply
permission to query Slurm accounting event history or Cockpit-slurm audit
records.

#### 11.3.8 Future resource policies and Phase 6 boundary

The framework is intended to support future resources, including Accounts,
Users, Associations, Partitions, Reservations, Slurm accounting Events, and
Usage/accounting records. Their visibility scopes are NOT defined or
implemented by Phase 6. Each future resource MUST receive an explicit
resource policy, trusted canonical attributes, and acceptance tests before
it is exposed through queries, snapshots, or events.

#### 11.3.9 Visibility acceptance tests

Phase 6 MUST verify:

* all four authenticated application roles can see all configured-cluster
  Nodes;
* Administrator and Operator can see all active Jobs;
* Coordinator can see directly owned Jobs and Jobs belonging to coordinated
  accounts, but not unrelated Jobs;
* User can see directly owned Jobs only;
* direct ownership uses numeric UID comparison and coordinator scope uses
  `CoordinatorAccounts`, not the general account-membership list;
* a User or Coordinator with a valid direct-owner match can see a Job with an
  empty or missing account; a non-owner cannot obtain direct-owner access;
* a Coordinator with a valid coordinated-account match can see a Job whose
  owner is missing or invalid; an unrelated account cannot grant access;
* missing or invalid owner, account, coordinator scope, or both denies each
  dependent branch; access is denied when neither branch establishes it;
* invalid or unresolved authenticated identity, role, or cluster scope does
  not grant access, and privileged-role visibility remains policy-controlled;
* frontend-supplied identity, role, owner, account, or scope values cannot
  alter visibility decisions;
* missing or invalid required attributes fail closed;
* snapshots, queries, individual lookups, and events produce consistent
  per-connection visibility;
* visibility revocation removes records from the affected frontend
  projection without deleting them from the global cache;
* reconnect and snapshot recovery apply the same rules; and
* invalid or incomplete visibility configuration prevents service
  readiness without a permissive fallback.

The existing Phase 5 Node command authorization regression tests remain
mandatory and are separate from these record-visibility tests.

## 12. IPC and protocol compatibility

The current `cockpit.channel()` stream to the existing `cockpit-slurm` Unix socket remains the transport path. The application protocol remains independent of Cockpit message boundaries.

Phase 6 MUST NOT introduce:

- `cockpit-slurm-channel`;
- a second Unix socket or transport;
- a resource-specific framing format;
- frontend `cockpit.spawn()` for Slurm commands;
- a second application protocol for Job.

Preserve the accepted envelope, length-prefixed framing, maximum frame size, request correlation, command lifecycle messages, error object structure, and event contracts.

Cockpit stream chunks may split or combine application frames. Existing framing/reassembly tests remain mandatory.

## 13. Frontend integration boundary

Phase 6 should add only the frontend client/provider integration needed to prove the Job read/live-update vertical slice and preserve Node behavior.

- Reuse the existing IPC client and frontend resource/query/stream handling.
- Keep frontend services as transport/client abstractions, not business-logic services.
- Keep NodeProvider and JobProvider responsible for their respective client-side resource state.
- Use strict TypeScript types; do not use `any` to bypass model differences.
- Do not add a generic frontend resource framework or broad navigation/page redesign in Phase 6.
- Do not let the frontend infer successful resource state from a command response; authoritative state comes from the backend cache and event stream.
- Preserve existing PatternFly conventions and the current application structure.

## 15. Testing requirements

### 15.1 Resource registry and model tests

- Node and Job register successfully.
- Duplicate/invalid registrations fail deterministically.
- Unknown resource kinds produce a defined error.
- Node and Job identity rules remain distinct and stable.
- Job identity tests cover normal Jobs, array elements, array parent/placeholders, missing required fields, and duplicate composite keys.
- Adapter tests use representative output from the approved backend source for normal Jobs and array Jobs, including array task ID zero where available; they verify source-specific normalization, preserve valid zero values, and produce absent canonical array identifiers for normal Jobs.
- Source-specific identity tests cover the approved normal-Job zero/set combination, individual array elements, aggregated placeholders with their task expression, and rejection of unknown, inconsistent, or ambiguous combinations without partial cache updates.
- Active-state tests cover `PENDING`, `RUNNING`, `SUSPENDED`, recognized `CONFIGURING` and `COMPLETING` transitions, terminal states without active transitions, and rejection of unknown or ambiguous states or flags. Transition combinations require reviewed source evidence before implementation.
- Canonicalization rejects malformed source data without corrupting the cache.

### 15.2 Cache and generation tests

- Insert, update, lookup, list/query, and delete work for Node and Job.
- Indexes remain consistent after each mutation.
- Semantically unchanged refreshes do not emit false update events.
- Real semantic changes update generation according to the existing contract.
- Failed/partial refreshes do not erase valid cached resources.
- Failed commands, parser/schema errors, truncated/incomplete output, invalid Job records, duplicate keys, and oversized snapshots leave the Job cache unchanged and emit no removal events.
- Acquisition tests verify `SLURM_BITSTR_LEN=0` is supplied to the selected source and that valid JSON with an abbreviated array expression, unsupported state/flag combinations, and incomplete snapshots do not mutate cache state or emit removal events.
- A complete valid empty Job snapshot removes previously cached active Jobs and emits the corresponding committed removal changes; this does not assert that the Jobs were deleted from Slurm.
- Snapshots are internally consistent under concurrent reads and refreshes.
- Race tests cover cache and synchronization paths.

### 15.3 Event and stream tests

- Cache mutation succeeds before the event is published.
- Node and Job events use the same per-connection stream and established resource discriminator.
- Initial snapshots and subsequent events do not lose or reorder changes under the established contract.
- Initial Node and Job snapshots share a per-connection sequence baseline; the connection-level consumer validates every resource event before provider dispatch.
- Changes invisible to a connection do not emit events or consume sequence numbers; global collection generations may therefore skip without triggering recovery.
- A visible-to-invisible transition emits an identity-only removal from that connection's projection, and a hidden-to-visible transition emits an addition.
- Changes to trusted connection authorization context reconcile the visible projection and emit required removals.
- Duplicate, stale, malformed, or skipped connection sequences trigger recovery through a new connection and fresh automatic snapshots without partial state mutation.
- Disconnect removes the connection's stream and associated resources.
- Event sequence gaps trigger the existing recovery behavior.
- Slow clients and write failures follow the existing bounded-queue and cleanup behavior.

### 15.4 Query and protocol tests

- Node protocol fixtures remain unchanged unless a reviewed contract change is approved.
- Job query returns canonical models and correct correlation IDs.
- Every resource-returning query has a `visibility_policy` reference that resolves to a policy for the same canonical resource kind.
- Phase 6 policy references are `node.list` → `node.cluster` and `job.list` → `job.active`; both policies are defined in `visibility.yaml`.
- Policy validation tests reject missing references, unknown policy identifiers, resource-kind mismatches, and any enabled record-returning query without a policy reference.
- Unknown resources, invalid filters, malformed frames, and unsupported operations return explicit errors.
- Arbitrary stream chunk boundaries do not corrupt frame decoding.
- Maximum frame-size and malformed-envelope protections remain effective.

### 15.5 Command and authorization regression tests

- Existing Node commands still succeed or fail according to their declared capabilities.
- Unresolved identity and unknown capabilities fail closed.
- Tests or documented integration evidence establish which OS/Slurm identity executes the existing command path; future command handlers must define their operation-specific authorization and execution-identity assumptions.
- Payload fields cannot override caller identity or capabilities.
- Unauthorized requests never reach the command executor.
- Duplicate command IDs retain the Phase 5 behavior, including denial and persistence-failure semantics.
- Command responses/statuses and resource events coexist without interleaved IPC frames.
- Command success does not directly mutate frontend resource state; authoritative state arrives through synchronization and cache events.
- The central policy configuration loads successfully and produces the expected enabled Node registry entries.
- Missing, unreadable, malformed, incomplete, or semantically invalid policy configuration prevents daemon startup/readiness; neither query nor command services become available.
- Planned operations cannot be invoked.
- Node authorization decisions remain equivalent to the accepted Phase 5 behavior.
- Node drain/resume allow only a currently resolved Slurm `AdminLevel=Administrator`; root and SlurmUser are not implicitly included.
- `node.list` and `job.list` are registered only in the query-policy registry; Node drain/resume are registered only in the command registry.
- Planned entries are validated but appear in neither registry.
- Job snapshots and events do not disclose resources outside the requesting user's effective visibility scope.
- Node snapshots, query responses, and events apply the same trusted resource-scope filtering.
- Access revocation removes previously visible resources from the user's projection.

### 15.6 End-to-end tests

At minimum, verify:

1. Node snapshot → NodeProvider.
2. Node change → cache → event/connection stream → NodeProvider.
3. Authorized Node command → Slurm mutation → synchronization → cache → Node event → NodeProvider.
4. Job snapshot → JobProvider.
5. Job change → cache → event/connection stream → JobProvider.
6. Unauthorized Node command is denied by the backend.
7. Node and Job traffic can coexist on the same transport without corrupting messages; each provider applies only its own resource events.

Use deterministic fixtures for unit tests and real Slurm/Cockpit integration tests where the target environment is required. Clearly label tests that require a configured Slurm cluster.

## 17. Definition of done

Phase 6 demonstrates that the system is no longer a Node-only implementation with generic names: **Node and Job use genuinely shared resource infrastructure while retaining distinct canonical models and adapters.**

The completed system preserves the Phase 5 Node command/authorization vertical slice and supports this end-to-end flow for both resources:

```text
Slurm
  ↓
Resource-specific adapter
  ↓
Canonical resource
  ↓
Shared authoritative cache
  ↓
Shared query / event / per-connection stream infrastructure
  ↓
Existing IPC protocol and transport
  ↓
Resource-specific frontend provider
  ↓
React presentation
```

Node mutation remains backend-authorized and its resulting state remains derived from authoritative synchronization and cache events.

Phase 6 does not claim that all Slurm resources are implemented, that Job mutations are supported, or that the full administrative UI is complete. Those are separate milestones.

## 18. Handoff to Phase 7

After Phase 6 is accepted, Phase 7 may focus on frontend architecture and UI integration using the proven resource infrastructure. It may evaluate shared presentation patterns and capability-driven navigation, but must preserve the boundary that frontend services are transport/client abstractions and backend services own authoritative resource state, business rules, and authorization.

Phase 7 should not be used to compensate for missing backend correctness or to introduce a second authoritative resource cache.
