# cockpit-slurm Implementation Phase 3 — First Vertical Slice: Nodes

# 1. Purpose

Phase 3 implements the first real `cockpit-slurm` resource as a complete end-to-end vertical slice.

The selected resource is:

```text
Node
```

The purpose of this phase is to prove that a real Slurm resource can travel through the Version 3.6 architecture:

```text
Slurm
  ↓
Node Resource Adapter
  ↓
Canonical Node
  ↓
Resource Cache
  ↓
Query Service
  ↓
IPC
  ↓
Cockpit channel
  ↓
Frontend IPC client
  ↓
Node Provider
  ↓
Node Table
```

This phase therefore moves the project from the Phase 2 transport proof:

```text
ping → pong
```

to the first application-level resource operation:

```text
query nodes → snapshot nodes
```

The Version 3.6 implementation plan defines M3 as the first vertical slice and specifically recommends Node as the first resource. The first vertical slice is complete when a real Slurm resource is read, normalized, stored in cache, requested by React, and displayed without React executing Slurm commands.

The authoritative architecture documents are:

```text
docs/architecture/0.1 development-cockpit-slurm-_v3.6.md
docs/architecture/1.0 implementation-plan-v3.6.md
docs/architecture/4.1 Implementation-phase2.md
```

This document defines the incremental implementation sequence for Phase 3.

---

# 2. Phase 3 implementation principle

Phase 3 must be implemented incrementally.

Do not attempt to implement the complete Node vertical slice in one coding task.

Use the following sequence:

```text
Phase 3A
  Verify Phase 2 transport baseline
        ↓
Phase 3B
  Establish Node resource contract
        ↓
Phase 3C
  Identify OpenAPI-generated Node types
        ↓
Phase 3D
  Implement Node canonical model
        ↓
Phase 3E
  Implement Slurm Node query adapter
        ↓
Phase 3F
  Implement Node cache
        ↓
Phase 3G
  Implement Node Query Service
        ↓
Phase 3H
  Connect Node query through Dispatcher / IPC
        ↓
Phase 3I
  Implement frontend Node data layer
        ↓
Phase 3J
  Implement Node Provider
        ↓
Phase 3K
  Implement Node Table
        ↓
Phase 3L
  End-to-end Node vertical slice
        ↓
Phase 3 complete
```

The key principle is:

> Each Phase 3 step must establish one resource boundary before the next boundary is implemented.

Do not combine:

* Slurm CLI execution;
* OpenAPI decoding;
* canonical resource normalization;
* cache management;
* query routing;
* IPC;
* frontend state;
* React rendering;

into one implementation task.

# 4. Architecture to preserve

Phase 3 must preserve all Version 3.6 decisions established by Phases 0–2.

## 4.1 Application name

The application remains:

```text
cockpit-slurm
```

The backend remains a persistent systemd service.

`cockpit-slurm-channel` is not part of the Version 3.6 architecture.

The backend communicates with the frontend through the existing Version 3.6 Cockpit channel transport.

---

## 4.2 Transport architecture

The transport path remains:

```text
React
  ↓
cockpit.channel()
  ↓
Cockpit transport
  ↓
Unix socket
  ↓
cockpit-slurm
  ↓
IPC Server
  ↓
Dispatcher
```

Phase 3 must build the Node resource path above this already-established transport boundary.

---

## 4.3 Application protocol

The existing application protocol remains authoritative.

The query request is:

```json
{
  "protocol": "cockpit-slurm",
  "version": "1.0",
  "messageId": "01...",
  "type": "query",
  "resource": "nodes",
  "payload": {}
}
```

The corresponding snapshot response is:

```json
{
  "protocol": "cockpit-slurm",
  "version": "1.0",
  "messageId": "01...",
  "type": "snapshot",
  "resource": "nodes",
  "generation": 1,
  "payload": {}
}
```

These message shapes follow the Version 3.6 implementation plan.

Phase 3 must not introduce another application protocol.

# 6. Phase 3B — Establish the Node resource contract

## 6.1 Objective

Define the application-level Node resource before implementing the adapter or cache.

The canonical Node model must represent a `cockpit-slurm` resource, not a raw Slurm CLI result.

The conceptual model is:

```text
Slurm/OpenAPI Node representation
              ↓
        Node Adapter
              ↓
       Canonical Node
              ↓
        Node Cache
```

---

## 6.2 Resource identity

The canonical Node identity must be stable.

The primary identity is:

```text
NodeName
```

The implementation must use the exact Node identity exposed by the Slurm/OpenAPI representation.

Do not use:

* array position;
* hostname as a replacement for NodeName;
* frontend row number;
* React key generated from array position.

A Node's identity must remain stable when the order of Slurm output changes.

---

## 6.3 Canonical Node responsibilities

The canonical Node model should contain only information required by the application resource contract.

At minimum, the first slice should support:

```text
NodeName
NodeAddr
NodeHostname
State
Reason
CPULoad
RealMemory
AllocMem
FreeMem
```

Additional Node fields may be added when required by the actual generated model and UI.

The exact generated Slurm/OpenAPI field names and Go types must be verified during Phase 3C.

Do not invent field names when a generated model already defines the corresponding field.

# 7. Phase 3C — Identify the generated OpenAPI Node types

## 7.1 Objective

The repository already contains generated Slurm OpenAPI Go types under:

```text
hack/openapi/slurm_openapi.gen.go
```

The generated types must be inspected before implementing the Node adapter.

The generated file is a generated artifact and must not be manually modified to implement Phase 3.

---

## 7.2 Required procedure

Copilot must first inspect:

```text
hack/openapi/slurm_openapi.gen.go
```

and identify:

1. the top-level type representing the `scontrol show nodes --json` response, if available;
2. the type representing an individual Node;
3. nested Node-related types;
4. enum types relevant to Node state;
5. pointer/value semantics;
6. JSON tags;
7. generated field names.

Do not assume that the type name can be inferred solely from a line number.

The generated source contains many Slurm API types and enums, so the exact Node type must be found by inspecting the generated definitions and their references.

---

## 7.3 Generated model ownership

Generated OpenAPI models belong to the external API/schema boundary.

They must not automatically become the application's canonical domain model.

The required architecture is:

```text
scontrol show nodes --json
             ↓
      generated API type
             ↓
       Node Adapter
             ↓
      canonical Node
             ↓
         Node Cache
```

The Node adapter owns the mapping between the generated model and the canonical model.

---

## 7.4 Generated source rule

Do not manually edit:

```text
hack/openapi/slurm_openapi.gen.go
```

If generated source must be regenerated, use the existing repository generation mechanism.

Phase 3 implementation code must adapt to the generated model rather than modifying generated code to accommodate the implementation.

# 8. Phase 3D — Implement the canonical Node model

## 8.1 Objective

Implement the first application-owned canonical resource model.

The model must not depend on:

* React;
* PatternFly;
* Cockpit;
* `cockpit.channel()`;
* frontend JSON structures;
* generated OpenAPI implementation details.

The model belongs to the backend resource layer.

---

## 8.2 Conceptual structure

The canonical resource should conceptually contain:

```text
Node
├── Identity
│   └── Name
├── Address
│   ├── Addr
│   └── Hostname
├── State
├── Reason
├── CPU
│   └── Load
├── Memory
│   ├── Real
│   ├── Allocated
│   └── Free
└── Resource metadata
    ├── Generation
    └── observed timestamp
```

The exact Go representation must follow the existing project resource conventions.

Do not duplicate fields unnecessarily.

---

## 8.3 State normalization

Slurm exposes a Node `State` together with state flags.

The Slurm documentation defines base states such as:

```text
ALLOCATED
DOWN
ERROR
FUTURE
IDLE
MIXED
UNKNOWN
```

and flags such as:

```text
CLOUD
COMPLETING
DRAIN
DYNAMIC
INVALID_REG
MAINTENANCE
NOT_RESPONDING
POWER_DOWN
POWERED_DOWN
POWERING_DOWN
POWERING_UP
PLANNED
REBOOT_ISSUED
REBOOT_REQUESTED
RESERVED
```

The Slurm documentation states that the `State` field identifies node states and that flags are represented as state flags.

The adapter must preserve sufficient information to avoid losing meaningful Slurm state information.

Do not prematurely reduce every Slurm state to a small UI-only enumeration.

If the canonical model requires both:

```text
base state
+
flags
```

then preserve them separately.

---

## 8.4 Generation

The cache must associate the Node snapshot with a generation.

Generation belongs to backend resource state.

The frontend must treat generation as opaque.

The frontend must not generate or calculate the backend generation.

# 9. Phase 3E — Implement the Slurm Node query adapter

## 9.1 Objective

Implement the first real Slurm Resource Adapter.

The adapter is responsible for obtaining Node information from Slurm.

The required query command is:

```bash
scontrol show nodes --json
```

The adapter is the only Phase 3 component that should execute this Slurm query command.

---

## 9.2 Adapter ownership

The Node adapter owns:

* command invocation;
* command arguments;
* stdout capture;
* stderr capture;
* exit status;
* JSON decoding;
* generated OpenAPI model conversion;
* canonical Node normalization;
* adapter-specific error conversion.

The adapter must not own:

* IPC;
* Cockpit channel;
* React;
* Node table rendering;
* request message IDs;
* frontend state;
* subscriptions.

---

## 9.3 Query command

The initial command must be exactly:

```text
scontrol show nodes --json
```

Do not replace it with:

```text
sinfo
sinfo --json
scontrol show node
scontrol show node <name>
```

unless a later architecture decision explicitly changes the Phase 3 contract.

The purpose of this phase is to establish the first Node snapshot using the selected command.

---

## 9.4 Command execution

Use the project's existing backend command-execution conventions.

Do not invoke shell pipelines such as:

```text
sh -c "scontrol show nodes --json | ..."
```

unless the existing command adapter architecture explicitly requires this.

Prefer direct executable invocation with arguments:

```text
scontrol
show
nodes
--JSON
```

The adapter must capture stdout separately from stderr.

---

## 9.5 Exit status

The adapter must treat a non-zero `scontrol` exit status as a query failure.

The error should preserve enough information to diagnose:

* executable failure;
* exit status;
* stderr;
* JSON decode failure;
* mapping failure.

Do not convert all failures into an empty Node list.

An empty Node list and a failed Node query are different conditions.

---

## 9.6 JSON decoding

The adapter must decode the JSON response using the generated OpenAPI model where the generated model matches the response contract.

Do not first convert the JSON to arbitrary:

```go
map[string]any
```

and then build the canonical model from untyped maps unless the generated OpenAPI model genuinely cannot represent the required response.

The preferred path is:

```text
stdout
  ↓
generated response type
  ↓
Node item type
  ↓
canonical Node
```

---

## 9.7 Node mapping

The mapping must explicitly handle the fields required by the canonical Node model.

At minimum verify:

```text
NodeName
NodeAddr
NodeHostname
State
Reason
CPULoad
RealMemory
AllocMem
FreeMem
```

The adapter must inspect the actual generated field names before implementation.

Do not blindly assume that the JSON names and Go field names are identical.

---

## 9.8 Slurm field semantics

The implementation must follow the Slurm `scontrol` documentation for Node fields.

For example:

* `AllocMem` is currently allocated memory in MiB;
* `CPULoad` is the node CPU load reported by the OS;
* `FreeMem` is currently free memory in MiB;
* `RealMemory` is total node memory in MiB;
* `State` represents Node state and state flags;
* `Reason` identifies the reason for states such as DOWN, DRAINED, DRAINING, FAILING, or FAIL.

The adapter must not silently reinterpret these units or meanings.

---

## 9.9 Adapter interface

The exact interface should follow the project's existing adapter conventions.

Conceptually:

```go
type NodeAdapter interface {
    ListNodes(ctx context.Context) ([]Node, error)
}
```

This is illustrative rather than a requirement to use this exact method signature.

If Phase 1/Phase 2 already established an adapter interface, reuse that contract rather than creating a competing abstraction.

---

## 9.10 Adapter tests

The adapter must be testable without requiring a live Slurm controller for ordinary unit tests.

Tests should cover:

```text
[ ] valid Node JSON
[ ] multiple Nodes
[ ] empty Node result
[ ] malformed JSON
[ ] missing required identity
[ ] optional field absent
[ ] null field where applicable
[ ] unexpected state value
[ ] command failure
[ ] non-zero exit status
[ ] stderr capture
[ ] mapping to canonical Node
```

Use a fixture or injectable command runner consistent with existing project conventions.

Do not make the complete Go test suite depend on a live Slurm installation.

# 10. Phase 3F — Implement the Node cache

## 10.1 Objective

Implement the first real resource cache for Node snapshots.

The cache becomes the source from which the Query Service obtains the Node snapshot.

The required query path is:

```text
IPC
  ↓
Dispatcher
  ↓
Query Service
  ↓
Node Cache
  ↓
Node Snapshot
```

The Version 3.6 architecture defines the cache as backend-owned state and places the cache behind the Query Service.

---

## 10.2 Cache ownership

The Node cache owns:

* current Node snapshot;
* Node identity index;
* generation;
* snapshot timestamp;
* concurrency protection.

It must not own:

* Slurm command invocation;
* IPC;
* Cockpit;
* React;
* UI state;
* subscription delivery.

---

## 10.3 Cache operations

The Phase 3 Node cache should support at least:

```text
ReplaceSnapshot
GetSnapshot
GetNode
Generation
```

The exact API should follow existing project conventions.

---

## 10.4 Snapshot replacement

When a successful adapter query produces a new complete Node collection:

```text
adapter result
      ↓
cache ReplaceSnapshot
      ↓
new generation
      ↓
new Node snapshot
```

A failed adapter query must not replace a previously valid snapshot with an empty or partially decoded snapshot.

This means:

```text
successful query
    → replace cache

failed query
    → preserve previous valid cache
    → return/report error
```

The exact stale-cache policy can be generalized in a later hardening phase.

---

## 10.5 Generation

The Node cache must maintain a monotonically increasing generation for successful snapshot replacement.

For example:

```text
initial snapshot → generation 1
next snapshot    → generation 2
next snapshot    → generation 3
```

The exact initial value is not important as long as it is deterministic and consistent with the protocol.

The generation must not be incremented merely because a query was requested.

It changes when the cached snapshot is replaced.

---

## 10.6 Concurrency

The cache must be safe for concurrent readers and writers.

At minimum test:

```text
concurrent snapshot reads
concurrent replacement
read while replacement
multiple frontend requests
```

Use the project's existing synchronization conventions.

Do not expose mutable internal cache state directly to callers.

---

## 10.7 Cache tests

Tests must cover:

```text
[ ] initial empty state
[ ] replace first snapshot
[ ] generation assigned
[ ] get snapshot
[ ] get individual Node
[ ] replace second snapshot
[ ] generation increases
[ ] previous snapshot is no longer returned
[ ] failed adapter result does not corrupt cache
[ ] concurrent access is safe
```

---

# 17. Node resource data contract

## 17.1 External source

The authoritative Slurm query source is:

```bash
scontrol show nodes --json
```

The `scontrol` manual defines the Node `show` fields and their semantics. Relevant fields include `AllocMem`, `CPULoad`, `FreeMem`, `RealMemory`, `State`, and related Node information.

---

## 17.2 Initial canonical field set

The first vertical slice should support at least:

| Canonical field | Source               |
| --------------- | -------------------- |
| `name`          | Slurm `NodeName`     |
| `addr`          | Slurm `NodeAddr`     |
| `hostname`      | Slurm `NodeHostname` |
| `state`         | Slurm `State`        |
| `reason`        | Slurm `Reason`       |
| `cpuLoad`       | Slurm `CPULoad`      |
| `realMemory`    | Slurm `RealMemory`   |
| `allocMemory`   | Slurm `AllocMem`     |
| `freeMemory`    | Slurm `FreeMem`      |

The exact Go type of every field must be determined from the generated OpenAPI model and the existing canonical resource conventions.

Do not force all numeric fields into strings merely because some Slurm CLI output formats are textual.

---

## 17.3 Units

Memory fields derived from:

```text
AllocMem
FreeMem
RealMemory
```

must retain their Slurm-defined MiB semantics.

The UI may format them for display, but the canonical model must not silently change their unit.

Slurm documents these Node memory fields as MiB.

# 19. Query versus refresh

Phase 3 intentionally separates:

```text
query
```

from:

```text
refresh
```

The initial Node query path reads the current backend cache.

Conceptually:

```text
React
  ↓
query nodes
  ↓
Node Cache
  ↓
snapshot
```

The mechanism that periodically refreshes Slurm data and detects resource changes belongs to the later Resource System/Event architecture.

Do not implement a full background Node synchronization system merely to complete the Phase 3 snapshot query.

If an initial cache population mechanism is required for the first vertical slice, it must be explicit and isolated so it can later be replaced or generalized.

---

# 20. Cache initialization

Before the first frontend Node query can succeed, the backend must have a Node snapshot.

The implementation must choose one explicit initialization mechanism consistent with the v3.6 architecture.

The preferred Phase 3 behavior is:

```text
backend startup
      ↓
Node initial load
      ↓
scontrol show nodes --json
      ↓
Node normalization
      ↓
Node cache
      ↓
IPC becomes able to serve node snapshot
```

If the existing backend lifecycle makes another initialization point more appropriate, document it explicitly.

Do not silently execute `scontrol` inside the Query Service as a substitute for cache initialization.

```text

      ↓

      ↓

      ↓

      ↓

      ↓

```

The backend must obtain the Node information from:

```bash
scontrol show nodes --json
```

The Node information must be normalized into the canonical `cockpit-slurm` Node model before entering the cache.

React must not execute `scontrol`.

The backend Query Service must not execute `scontrol`.

The generated OpenAPI model must remain an external/API representation and must not replace the canonical application resource model.

The Phase 3 implementation must not require the Event Bus or Subscription Manager.

The result is a complete first vertical slice:

```text
real Slurm data
      ↓
adapter
      ↓
canonical resource
      ↓
cache
      ↓
query
      ↓
IPC
      ↓
React
      ↓
Node Table
```

This satisfies M3 — First Vertical Slice.

The next architectural milestone is the generalized Resource System and then Resource Events/Subscriptions; those must not be pulled forward into Phase 3 merely to satisfy the Node snapshot path.
