## Transport framing

The important point is that your latest `ipc-protocol.md` defines the transport framing as:

```text
┌──────────────┬───────────────────────┐
│ uint32 length│ UTF-8 JSON payload    │
│ big endian   │                       │
└──────────────┴───────────────────────┘
```
rather than newline-delimited JSON. ([GitHub][2])

That should be the foundation of Phase 1C.

## JSON requires UTF-8

JSON transmitted over the protocol is required to be UTF-8.

The decoder should reject invalid UTF-8 in the JSON payload.

However, Go's encoding/json has some behavior around invalid UTF-8 that you should be careful not to accidentally interpret as a protocol guarantee.

So specification:

>The payload MUST be valid UTF-8 JSON. Implementations MUST reject malformed JSON input. Invalid UTF-8 MUST NOT be accepted as valid protocol text.

**Make JSON UTF-8 an explicit test**.

### Phase 1C clarifications

1. `messageId` generation stays outside the protocol package.
   
   Phase 1C accepts any non-empty `messageId` as protocol-valid, but it does not own generation logic. The message identity producer belongs to the request/response layer and may be introduced later in Phase 1D or the connection/session layer.

2. The error-model boundary is explicit.
   
   Phase 1C defines only the protocol-level error envelope and validation failures. The richer canonical error model in `error-model.md` remains the later architecture contract for application and service errors.

3. Validation scope is intentionally narrow.
   
   Phase 1C validates the shared envelope structure and transport framing only. Message-specific payload validation belongs to the dispatcher or later message handlers; the protocol package should not become a giant validation layer for every future request type.

4. Known-but-unimplemented messages are not the same as unknown messages.
   
   A type such as `query` is protocol-valid in Phase 1C even when it is not yet implemented. The dispatcher may reject it later with a protocol-compliant "not implemented" response. An unknown type such as `bogus-type` must be rejected immediately as invalid protocol input.

# 4. `internal/protocol/envelope.go`

The current protocol specification requires:

* `protocol`
* `version`
* `messageId`
* `type`
* `timestamp` recommended
* `payload`

and `payload` is required. ([GitHub][2])

Please use:

```go
package protocol

import (
	"encoding/json"
	"time"
)

const (
	ProtocolName    = "cockpit-slurm"
	ProtocolVersion = "1.0"
)

// Envelope is the common envelope for every cockpit-slurm IPC message.
type Envelope struct {
	Protocol  string          `json:"protocol"`
	Version   string          `json:"version"`
	MessageID string          `json:"messageId"`
	Type      MessageType     `json:"type"`
	Timestamp string          `json:"timestamp,omitempty"`
	Payload   json.RawMessage `json:"payload"`
}

// NewEnvelope creates a protocol envelope.
func NewEnvelope(messageID string, messageType MessageType, payload json.RawMessage) Envelope {
	return Envelope{
		Protocol:  ProtocolName,
		Version:   ProtocolVersion,
		MessageID: messageID,
		Type:      messageType,
		Timestamp: time.Now().UTC().Format(time.RFC3339),
		Payload:   payload,
	}
}
```

I deliberately use `json.RawMessage` here.

That is important because the envelope should **not know the concrete payload type**. This is one of the strongest architectural decisions in the document.

It means:
```text
Envelope
    │
    └── Payload
          │
          ├── HelloPayload
          ├── PingPayload
          ├── QueryPayload
          ├── SubscribePayload
          └── CommandPayload
```
The envelope doesn't become coupled to all Slurm resource models.

That will be extremely useful later when you introduce:
```text
canonical resource models
command model
error model
query model
event model
```
So explicitly tell Copilot:

>Do not replace json.RawMessage with interface{} or a large union structure.

The envelope remains stable.

# 7. The most important Phase 1C file: `codec.go`

This is where the protocol becomes real.

Your specification says:

```text
uint32 length
big endian
UTF-8 JSON
```

and explicitly says the protocol must **not** depend on newline delimiters. ([GitHub][2])

Please use:

```go
package protocol

import (
	"encoding/binary"
	"encoding/json"
	"errors"
	"fmt"
	"io"
)

const (
	HeaderSize     = 4
	MaxMessageSize = 4 * 1024 * 1024
)

// Encoder writes length-prefixed JSON messages.
type Encoder struct {
	w io.Writer
}

// NewEncoder creates a protocol encoder.
func NewEncoder(w io.Writer) *Encoder {
	return &Encoder{w: w}
}

// Encode writes one complete envelope.
func (e *Encoder) Encode(message Envelope) error {
	payload, err := json.Marshal(message)
	if err != nil {
		return fmt.Errorf("encode JSON: %w", err)
	}

	if len(payload) > MaxMessageSize {
		return fmt.Errorf(
			"message size %d exceeds maximum %d",
			len(payload),
			MaxMessageSize,
		)
	}

	var header [HeaderSize]byte

	binary.BigEndian.PutUint32(header[:], uint32(len(payload)))

	if _, err := e.w.Write(header[:]); err != nil {
		return fmt.Errorf("write message length: %w", err)
	}

	if _, err := e.w.Write(payload); err != nil {
		return fmt.Errorf("write message payload: %w", err)
	}

	return nil
}
```

But there is an important improvement:

**Don't use `Write()` directly and assume it writes everything.**

Use `io.Copy`/`io.WriteString` or, better, `writeFull`.

For a robust implementation:

```go
func writeFull(w io.Writer, data []byte) error {
	for len(data) > 0 {
		n, err := w.Write(data)

		if err != nil {
			return err
		}

		if n == 0 {
			return io.ErrShortWrite
		}

		data = data[n:]
	}

	return nil
}
```

Then:

```go
if err := writeFull(e.w, header[:]); err != nil {
	return fmt.Errorf("write message length: %w", err)
}

if err := writeFull(e.w, payload); err != nil {
	return fmt.Errorf("write message payload: %w", err)
}
```

Make writeFull() a private helper:
```go
func writeFull(w io.Writer, p []byte) error
```
and test it with a writer that deliberately performs partial writes.

That's an excellent Phase 1C unit test. 

For example:
```
input:
    100 bytes

writer:
    accepts 17
    accepts 23
    accepts 11
    ...
```

The encoder must still produce the exact complete frame.

This is the sort of test that gives you confidence that the IPC layer is actually robust.


## MaxMessageSize
```
MaxMessageSize = 4 * 1024 * 1024
```
That's perfectly reasonable as a starting point. The architecture document explicitly say:

>The maximum applies to the JSON payload length, excluding the 4-byte length prefix.

Otherwise a future implementation might interpret it differently.

Defining the constant as:
```go
const (
    FrameHeaderSize = 4
    MaxPayloadSize  = 4 * 1024 * 1024
)
```
rather than:
```
HeaderSize
MaxMessageSize
```
because we're actually talking about:
```text
frame
├── 4-byte header
└── payload
```
This terminology will become useful later.

## "Too-short length prefix" needs clarification

The terminology should be precise.

A valid frame is:
```text
4 bytes length
+
N bytes payload
```
If only:
```text
01 00
```
arrives and then EOF occurs, the decoder should return an error.

That's why:
```Go
io.ReadFull(reader, header[:])
```
is important.

Similarly:
```
length = 100
payload = only 50 bytes
EOF
```
must fail.

So I would define:

>A frame header is invalid if fewer than 4 bytes can be read before EOF.

And:

>A frame is incomplete if the declared payload length cannot be completely read before EOF.

This is an important distinction for stream handling.

## Zero-length payload: distinguish payload from frame

Specification:

>zero-length payload rejection

I'd change the terminology slightly.

Your frame is:
```
[length][JSON payload]
```
The **payload length** may not be zero because every message must contain JSON.

So:
```
length = 0
```
→ reject.

But:
```JSON
"payload": {}
```
is perfectly valid.

Therefore:
```
frame payload length == 0
        ↓
      reject

JSON payload == {}
        ↓
      valid
```
This distinction should be in the document.

# 8. Decoder

The decoder needs to be particularly careful because the network/socket is a **stream**, not a message-oriented transport.

```go
package protocol

import (
	"encoding/binary"
	"encoding/json"
	"fmt"
	"io"
)

type Decoder struct {
	r io.Reader
}

// NewDecoder creates a protocol decoder.
func NewDecoder(r io.Reader) *Decoder {
	return &Decoder{r: r}
}

// Decode reads exactly one length-prefixed message.
func (d *Decoder) Decode() (Envelope, error) {
	var envelope Envelope

	var header [HeaderSize]byte

	if _, err := io.ReadFull(d.r, header[:]); err != nil {
		return envelope, fmt.Errorf(
			"read message length: %w",
			err,
		)
	}

	length := binary.BigEndian.Uint32(header[:])

	if length == 0 {
		return envelope, fmt.Errorf("invalid message length: zero")
	}

	if length > MaxMessageSize {
		return envelope, fmt.Errorf(
			"message length %d exceeds maximum %d",
			length,
			MaxMessageSize,
		)
	}

	payload := make([]byte, length)

	if _, err := io.ReadFull(d.r, payload); err != nil {
		return envelope, fmt.Errorf(
			"read message payload: %w",
			err,
		)
	}

	if err := json.Unmarshal(payload, &envelope); err != nil {
		return envelope, fmt.Errorf(
			"decode JSON: %w",
			err,
		)
	}

	if err := ValidateEnvelope(envelope); err != nil {
		return envelope, err
	}

	return envelope, nil
}
```

### Decoder requirements:

```text
✓ read 4-byte header
✓ big-endian uint32
✓ reject zero length
✓ reject > MaxPayloadSize
✓ allocate payload
✓ io.ReadFull()
✓ JSON unmarshal
✓ envelope validation
```

The document correctly calls out the stream nature of Unix sockets.

This is one of the areas where I would not simplify the implementation merely to make it shorter.

### Adding one security requirement

Because this is a Unix socket, the protocol is not exposed directly to the network, but still  treat the peer as untrusted input.

Add:

Resource exhaustion protection
```text
[ ] Decoder must validate frame length before allocating payload
[ ] Decoder must never allocate based on an unbounded uint32 length
[ ] Decoder must reject payloads larger than MaxPayloadSize
```
The document already effectively specifies this behavior, but I would make it an explicit security requirement, not just a codec requirement.

The important sequence is:
```text
read 4 bytes
    ↓
decode uint32
    ↓
if > MaxPayloadSize
    ↓
REJECT
    ↓
only then allocate
```

Never:
```text
read length
    ↓
make([]byte, length)
    ↓
check length
```

This directly addresses the protocol's testing requirements for length framing, invalid lengths, oversized messages and invalid JSON. ([GitHub][2])

# 9. Another important boundary: unknown message type

Your current acceptance criteria say:

>unknown message rejection

That's slightly ambiguous.

There are two different cases:

**Unknown protocol message**
```JSON
"type": "something-completely-unknown"
```

This should be rejected by Phase 1C validation.

**Known but not yet implemented message**
```JSON
"type": "query"
```
Phase 1C knows that query is a valid protocol message, but the application does not implement query yet.

That should not be treated as an invalid protocol.

Instead:
```text
known message type
       │
       ▼
dispatcher
       │
       ▼
"not implemented"
```
So I recommend changing your acceptance criterion from:

> unknown message rejection

to:

> Unknown message type is rejected; known-but-unimplemented message types remain protocol-valid and are handled by a later dispatcher.

This is an important distinction.

## Validation rules are extremely explicit

```text
| Field / condition | Phase 1C rule                          |
| ----------------- | -------------------------------------- |
| `protocol`        | MUST exist and equal `cockpit-slurm`   |
| `version`         | MUST exist and equal supported version |
| `messageId`       | MUST exist and be non-empty            |
| `type`            | MUST exist and be a known message type |
| `timestamp`       | MAY be omitted                         |
| `payload`         | MUST exist                             |
| `payload` value   | MUST contain valid JSON                |
| JSON              | MUST be valid UTF-8 JSON               |
| frame length      | MUST be 1..`MaxPayloadSize`            |
| length prefix     | MUST be exactly 4 bytes                |
| byte order        | MUST be big-endian                     |
| unknown `type`    | MUST be rejected                       |
| unknown fields    | **SHOULD be ignored**                  |
```

### allowing unknown JSON fields

For example, suppose future version 1.0 adds:
```JSON
{
  "protocol": "cockpit-slurm",
  "version": "1.0",
  "messageId": "abc",
  "type": "ping",
  "timestamp": "...",
  "payload": {},
  "traceId": "xyz"
}
```
An older implementation should ideally not fail just because it sees traceId.

So I recommend explicitly saying:

>Phase 1C MUST ignore unknown JSON fields in the envelope and payload unless a later protocol version specifies otherwise.

This gives you forward compatibility.

Don't use:
```Go
decoder.DisallowUnknownFields()
```
for the generic envelope.

### Validation boundary, explicit

>Phase 1C validates only the common Envelope structure and transport framing. Message-specific payload semantics are not part of this package; they belong to later dispatcher/message-handler logic.

This is the cleanest boundary for the implementation and should remain in place through the end of Phase 1C.

## Errors
Keep protocol errors separate from the future application error model. 

For Phase 1C:

Validation and errors example code (to be updated): 

```go
package protocol

import "fmt"

var (
	ErrInvalidProtocol = fmt.Errorf("invalid protocol")
	ErrInvalidVersion  = fmt.Errorf("unsupported protocol version")
	ErrInvalidMessage  = fmt.Errorf("invalid message")
	ErrUnknownMessage  = fmt.Errorf("unsupported message type")
)

func ValidateEnvelope(e Envelope) error {
	if e.Protocol == "" {
		return fmt.Errorf("%w: missing protocol", ErrInvalidProtocol)
	}

	if e.Protocol != ProtocolName {
		return fmt.Errorf(
			"%w: %q",
			ErrInvalidProtocol,
			e.Protocol,
		)
	}

	if e.Version == "" {
		return fmt.Errorf("%w: missing version", ErrInvalidVersion)
	}

	if e.Version != ProtocolVersion {
		return fmt.Errorf(
			"%w: %q",
			ErrInvalidVersion,
			e.Version,
		)
	}

	if e.MessageID == "" {
		return fmt.Errorf("%w: missing messageId", ErrInvalidMessage)
	}

	if e.Type == "" {
		return fmt.Errorf("%w: missing type", ErrInvalidMessage)
	}

	if !e.Type.IsKnown() {
		return fmt.Errorf(
			"%w: %q",
			ErrUnknownMessage,
			e.Type,
		)
	}

	if len(e.Payload) == 0 {
		return fmt.Errorf("%w: missing payload", ErrInvalidMessage)
	}

	return nil
}
```

The eventual error semantics should follow your `error-model.md`; don't let this Phase 1C implementation invent a completely different application error structure.

# 13. But Phase 1C should eventually replace this handler in `server.go`

Your current `server.go` handler is:

```go
<-serveCtx.Done()
```

which is only a Phase 1B placeholder. ([GitHub][3])

At the end of Phase 1C, it should become conceptually:

```go
func (s *Server) handleConnection(ctx context.Context, conn net.Conn) {
	defer conn.Close()

	decoder := protocol.NewDecoder(conn)
	encoder := protocol.NewEncoder(conn)

	for {
		message, err := decoder.Decode()
		if err != nil {
			return
		}

		response := handleProtocolMessage(message)

		if err := encoder.Encode(response); err != nil {
			return
		}
	}
}
```

But **I would not put `handleProtocolMessage()` into `ipc.Server`**.

That's the next phase.

Instead, Phase 1C can introduce a tiny protocol-level handler:

```text
internal/protocol/
    handler.go
```

with only:

```text
hello → hello-response (define message types)
ping  → pong
everything else → protocol "not implemented"
```

That gets us to a useful end-to-end test without prematurely creating the service layer.

# 15. One important correction: `ping` vs `hello`

There is a small evolution in your documents worth making explicit.

The Phase 1 implementation plan initially describes the minimal proof as:

```text
ping → pong
```

while the more complete IPC specification defines a **connection handshake**:

```text
hello
  ↓
hello-response
  ↓
query/subscribe/command...
```

and also defines message types `ping/pong` and `hello/hello-response`. ([GitHub][5])

Therefore I recommend:

### Phase 1C

Implement:

```text
ping  → pong
```

but don't yet enforce a complicated connection state machine.

### Phase 1D

Add the dispatcher and enforce:

```text
new connection
      ↓
hello required
      ↓
hello-response
      ↓
normal messages
```

This keeps Phase 1C manageable.
