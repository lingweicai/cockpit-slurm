# 4. `internal/protocol/envelope.go`

The current protocol specification requires:

* `protocol`
* `version`
* `messageId`
* `type`
* `timestamp` recommended
* `payload`

and says `payload` is required. ([GitHub][2])

Please use:

```go
package protocol

import (
	"encoding/json"
	"time"
)

const (
	ProtocolName    = "cockpit-slurm"
	ProtocolVersion = "1.0"
)

// Envelope is the common envelope for every cockpit-slurm IPC message.
type Envelope struct {
	Protocol  string          `json:"protocol"`
	Version   string          `json:"version"`
	MessageID string          `json:"messageId"`
	Type      MessageType     `json:"type"`
	Timestamp string          `json:"timestamp,omitempty"`
	Payload   json.RawMessage `json:"payload"`
}

// NewEnvelope creates a protocol envelope.
func NewEnvelope(messageID string, messageType MessageType, payload json.RawMessage) Envelope {
	return Envelope{
		Protocol:  ProtocolName,
		Version:   ProtocolVersion,
		MessageID: messageID,
		Type:      messageType,
		Timestamp: time.Now().UTC().Format(time.RFC3339),
		Payload:   payload,
	}
}
```

I deliberately use `json.RawMessage` here.

That is important because the envelope should **not know the concrete payload type**. This is one of the strongest architectural decisions in the document.

It means:
```text
Envelope
    │
    └── Payload
          │
          ├── HelloPayload
          ├── PingPayload
          ├── QueryPayload
          ├── SubscribePayload
          └── CommandPayload
```
The envelope doesn't become coupled to all Slurm resource models.

That will be extremely useful later when you introduce:
```text
canonical resource models
command model
error model
query model
event model
```
So explicitly tell Copilot:

>Do not replace json.RawMessage with interface{} or a large union structure.

The envelope remains stable.

# 7. The most important Phase 1C file: `codec.go`

This is where the protocol becomes real.

Your specification says:

```text
uint32 length
big endian
UTF-8 JSON
```

and explicitly says the protocol must **not** depend on newline delimiters. ([GitHub][2])

Please use:

```go
package protocol

import (
	"encoding/binary"
	"encoding/json"
	"errors"
	"fmt"
	"io"
)

const (
	HeaderSize     = 4
	MaxMessageSize = 4 * 1024 * 1024
)

// Encoder writes length-prefixed JSON messages.
type Encoder struct {
	w io.Writer
}

// NewEncoder creates a protocol encoder.
func NewEncoder(w io.Writer) *Encoder {
	return &Encoder{w: w}
}

// Encode writes one complete envelope.
func (e *Encoder) Encode(message Envelope) error {
	payload, err := json.Marshal(message)
	if err != nil {
		return fmt.Errorf("encode JSON: %w", err)
	}

	if len(payload) > MaxMessageSize {
		return fmt.Errorf(
			"message size %d exceeds maximum %d",
			len(payload),
			MaxMessageSize,
		)
	}

	var header [HeaderSize]byte

	binary.BigEndian.PutUint32(header[:], uint32(len(payload)))

	if _, err := e.w.Write(header[:]); err != nil {
		return fmt.Errorf("write message length: %w", err)
	}

	if _, err := e.w.Write(payload); err != nil {
		return fmt.Errorf("write message payload: %w", err)
	}

	return nil
}
```

But there is an important improvement:

**Don't use `Write()` directly and assume it writes everything.**

Use `io.Copy`/`io.WriteString` or, better, `writeFull`.

For a robust implementation:

```go
func writeFull(w io.Writer, data []byte) error {
	for len(data) > 0 {
		n, err := w.Write(data)

		if err != nil {
			return err
		}

		if n == 0 {
			return io.ErrShortWrite
		}

		data = data[n:]
	}

	return nil
}
```

Then:

```go
if err := writeFull(e.w, header[:]); err != nil {
	return fmt.Errorf("write message length: %w", err)
}

if err := writeFull(e.w, payload); err != nil {
	return fmt.Errorf("write message payload: %w", err)
}
```

Make writeFull() a private helper:
```go
func writeFull(w io.Writer, p []byte) error
```
and test it with a writer that deliberately performs partial writes.

That's an excellent Phase 1C unit test. 

For example:
```
input:
    100 bytes

writer:
    accepts 17
    accepts 23
    accepts 11
    ...
```

The encoder must still produce the exact complete frame.

This is the sort of test that gives you confidence that the IPC layer is actually robust.


## MaxMessageSize
```
MaxMessageSize = 4 * 1024 * 1024
```
That's perfectly reasonable as a starting point. The architecture document explicitly say:

>The maximum applies to the JSON payload length, excluding the 4-byte length prefix.

Otherwise a future implementation might interpret it differently.

Defining the constant as:
```go
const (
    FrameHeaderSize = 4
    MaxPayloadSize  = 4 * 1024 * 1024
)
```
rather than:
```
HeaderSize
MaxMessageSize
```
because we're actually talking about:
```text
frame
├── 4-byte header
└── payload
```
This terminology will become useful later.

# 8. Decoder

The decoder needs to be particularly careful because the network/socket is a **stream**, not a message-oriented transport.

```go
package protocol

import (
	"encoding/binary"
	"encoding/json"
	"fmt"
	"io"
)

type Decoder struct {
	r io.Reader
}

// NewDecoder creates a protocol decoder.
func NewDecoder(r io.Reader) *Decoder {
	return &Decoder{r: r}
}

// Decode reads exactly one length-prefixed message.
func (d *Decoder) Decode() (Envelope, error) {
	var envelope Envelope

	var header [HeaderSize]byte

	if _, err := io.ReadFull(d.r, header[:]); err != nil {
		return envelope, fmt.Errorf(
			"read message length: %w",
			err,
		)
	}

	length := binary.BigEndian.Uint32(header[:])

	if length == 0 {
		return envelope, fmt.Errorf("invalid message length: zero")
	}

	if length > MaxMessageSize {
		return envelope, fmt.Errorf(
			"message length %d exceeds maximum %d",
			length,
			MaxMessageSize,
		)
	}

	payload := make([]byte, length)

	if _, err := io.ReadFull(d.r, payload); err != nil {
		return envelope, fmt.Errorf(
			"read message payload: %w",
			err,
		)
	}

	if err := json.Unmarshal(payload, &envelope); err != nil {
		return envelope, fmt.Errorf(
			"decode JSON: %w",
			err,
		)
	}

	if err := ValidateEnvelope(envelope); err != nil {
		return envelope, err
	}

	return envelope, nil
}
```

### Decoder requirements:

```text
✓ read 4-byte header
✓ big-endian uint32
✓ reject zero length
✓ reject > MaxPayloadSize
✓ allocate payload
✓ io.ReadFull()
✓ JSON unmarshal
✓ envelope validation
```

The document correctly calls out the stream nature of Unix sockets.

This is one of the areas where I would not simplify the implementation merely to make it shorter.

### Adding one security requirement

Because this is a Unix socket, the protocol is not exposed directly to the network, but still  treat the peer as untrusted input.

Add:

Resource exhaustion protection
```text
[ ] Decoder must validate frame length before allocating payload
[ ] Decoder must never allocate based on an unbounded uint32 length
[ ] Decoder must reject payloads larger than MaxPayloadSize
```
The document already effectively specifies this behavior, but I would make it an explicit security requirement, not just a codec requirement.

The important sequence is:
```text
read 4 bytes
    ↓
decode uint32
    ↓
if > MaxPayloadSize
    ↓
REJECT
    ↓
only then allocate
```

Never:
```text
read length
    ↓
make([]byte, length)
    ↓
check length
```

This directly addresses the protocol's testing requirements for length framing, invalid lengths, oversized messages and invalid JSON. ([GitHub][2])

# 9. Another important boundary: unknown message type

Your current acceptance criteria say:

>unknown message rejection

That's slightly ambiguous.

There are two different cases:

**Unknown protocol message**
```JSON
"type": "something-completely-unknown"
```

This should be rejected by Phase 1C validation.

**Known but not yet implemented message**
```JSON
"type": "query"
```
Phase 1C knows that query is a valid protocol message, but the application does not implement query yet.

That should not be treated as an invalid protocol.

Instead:
```text
known message type
       │
       ▼
dispatcher
       │
       ▼
"not implemented"
```
So I recommend changing your acceptance criterion from:

> unknown message rejection

to:

> Unknown message type is rejected; known-but-unimplemented message types remain protocol-valid and are handled by a later dispatcher.

This is an important distinction.

Validation and errors example code (to be updated): 

```go
package protocol

import "fmt"

var (
	ErrInvalidProtocol = fmt.Errorf("invalid protocol")
	ErrInvalidVersion  = fmt.Errorf("unsupported protocol version")
	ErrInvalidMessage  = fmt.Errorf("invalid message")
	ErrUnknownMessage  = fmt.Errorf("unsupported message type")
)

func ValidateEnvelope(e Envelope) error {
	if e.Protocol == "" {
		return fmt.Errorf("%w: missing protocol", ErrInvalidProtocol)
	}

	if e.Protocol != ProtocolName {
		return fmt.Errorf(
			"%w: %q",
			ErrInvalidProtocol,
			e.Protocol,
		)
	}

	if e.Version == "" {
		return fmt.Errorf("%w: missing version", ErrInvalidVersion)
	}

	if e.Version != ProtocolVersion {
		return fmt.Errorf(
			"%w: %q",
			ErrInvalidVersion,
			e.Version,
		)
	}

	if e.MessageID == "" {
		return fmt.Errorf("%w: missing messageId", ErrInvalidMessage)
	}

	if e.Type == "" {
		return fmt.Errorf("%w: missing type", ErrInvalidMessage)
	}

	if !e.Type.IsKnown() {
		return fmt.Errorf(
			"%w: %q",
			ErrUnknownMessage,
			e.Type,
		)
	}

	if len(e.Payload) == 0 {
		return fmt.Errorf("%w: missing payload", ErrInvalidMessage)
	}

	return nil
}
```

The eventual error semantics should follow your `error-model.md`; don't let this Phase 1C implementation invent a completely different application error structure.

# 15. One important correction: `ping` vs `hello`

There is a small evolution in your documents worth making explicit.

The Phase 1 implementation plan initially describes the minimal proof as:

```text
ping → pong
```

while the more complete IPC specification defines a **connection handshake**:

```text
hello
  ↓
hello-response
  ↓
query/subscribe/command...
```

and also defines `ping/pong` and `hello/hello-response`. ([GitHub][5])

Therefore I recommend:

### Phase 1C

Implement:

```text
ping  → pong
```

but don't yet enforce a complicated connection state machine.

### Phase 1D

Add the dispatcher and enforce:

```text
new connection
      ↓
hello required
      ↓
hello-response
      ↓
normal messages
```

This keeps Phase 1C manageable.
